# part05-13-pssr の期待値(手計算・未検証、2026-09-27設計)

## この接続が存在する理由

`verify/part05-13-tickets`の`RUNCOMBO`は、クリーンな`JUCHUD`/`JUCHUM`
データしか読まないため、`za0500-ticket3.rpg`自身の`*PSSR`
(`QCMDEXC`/`CHGDTAARA(*LDA)`)は一度も発火しない。チケット3の採点表
(`docs/part05/05-13-checkpoint-tickets.md`)にある「再現確認」(意図的に
エラーを再現させ、ハングせずに安全に終了し、原因がわかる証拠が残ることを
確認する)を満たすのは、この`part05-13-pssr`接続である。

## 手順の要約

1. `RUNTXRESET`でJUCHUD/JUCHUM/ZAIKOMをクリーンな状態に戻す。
2. `C0511RUN`/`C0511S`(05-11の技法)・`JU0900C`(チケット1修正版)・
   `ZA0500`(チケット3の`*PSSR`付き)・`VLDA3`をそれぞれコンパイルする。
3. `RUNC0511S`が`JUNO='C05119'`の行を`JUCHUD`(不正な`JUSU`)・`JUCHUM`
   (一致するヘッダー)へ植え付ける。
4. `RUNCOMBO3`が`JU0900C`(チケット1修正済み)を呼び、`ZA0500`
   (チケット3)へ渡す。`OPNQRYF KEYFLD((JUNO)(JULINE))`の順で
   `C05119`が(EBCDIC上`J`より前なので)最初に読まれる。**`JUSU`が最初に
   問題を起こす段階は、実は未確定である**(下の「`*LDA`が空白のまま」の
   節を参照)——`SUB JUSU AVAIL`(計算仕様書)で発火する可能性も、
   レコードの入力段階(`OPNQRYF`経由の読み取り自体)で発火する可能性も
   どちらもあり得る。どちらであっても`*PSSR`が発火することを期待する
   設計だが、後者の場合は`*PSSR`の対象範囲外になる可能性がある(下記)。
5. `RUNVLDA3`が同一ジョブ内で`*LDA(21,20)`を読み戻し、`SNDPGMMSG`で報告する。

## 期待する`VLDA3`の出力(ジョブ・ログ、VFYLOG経由)

`za0500-ticket3.rpg`自身の`*PSSR`は`CHGDTAARA DTAARA(*LDA (21 20))
VALUE('ZA0500 SHORT ERR')`を実行する(`'ZA0500 SHORT ERR'`は16文字)。
`*LDA`の21-40桁目=20バイトなので、残り4バイトは空白でパディングされる
はず(`CHGDTAARA`のVALUEが宣言長より短い場合の一般的な既定動作という
前提、`part05-qcmdexc-runtime`の`ZA0510 ERROR`パディングで実証済みの
挙動と同じ)。

```
VLDA3: *LDA(21,20)=[ZA0500 SHORT ERR    ]
```

(`ZA0500 SHORT ERR` 16文字 + 空白4文字 = 20バイト)

**これが本命の証拠であり、これだけで判定する。** 下の「参考: 副次的な
シグナル」は補強材料に過ぎず、これだけで代用しないこと。

## 参考: 副次的なシグナル(これだけでは判定しない)

- `RUNCOMBO3`のジョブ・ログに`JU0900C: ZA0500 ended abnormally.`が
  出ていれば、`ENDSR '*CANCL'`が`JU0900C`に伝わった弱い状況証拠になる
  (`part05-qcmdexc-runtime`の実際の結果——`work/verify/results/`配下、
  gitignore対象——で`Error RPG0000 caused program ZA0510V to stop.`と
  いう形で呼び出し元に伝わることは確認済みだが、これは**別のプログラム
  (ZA0510V)・別の発火条件(LOKUP失敗)**での観測であり、
  `za0500-ticket3.rpg`自身の`*PSSR`が同じように振る舞うと決めつけては
  いけない、あくまで類推)。
- 逆に、このメッセージが出ていない・`RPG0907`等の生の例外メッセージが
  そのまま`RUNCOMBO3`のジョブ・ログに出ている、という場合は、`*PSSR`が
  そもそも発火していない(または例外がスコープ外だった)可能性が高い。

## `collect`の期待値

- `JUCHUD`の`JUNO='C05119'`行: `JUSHO='P00001'`・`HEX(JUSU)`が
  `C0511S`の植え付けどおりの生バイト('ABCDE'のEBCDICバイト列、
  05-11自身の仮説どおりなら`C1C2C3C4C5`——これも実機未確認)である
  はず。
- `ZAIKOM`の`P00001`行: `RUNMODE='*TEST'`のため、接続前後で在庫数
  (`ZASU`)が変化していないはず(`part05-ju0900c-baseline`の元の値を
  基準に確認すること)。

## 実際の結果をどう読むか

1. **予想どおり(`VLDA3: *LDA(21,20)=[ZA0500 SHORT ERR    ]`)** →
   チケット3の`*PSSR`が実際にこのシナリオで発火し、`CHGDTAARA`で証拠を
   残したことが実機で確認できたことになる。チケット3の「再現確認」
   採点項目はこれで満たされる。
2. **`*LDA`が空白のまま(`[                    ]`)** → `*PSSR`が
   発火しなかった可能性が高い。まず疑うこと:
   (a) `C05119`行が本当に最初に読まれたか(`collect`で`JUCHUD`の
   `C05119`行自体が存在するか、`HEX(JUSU)`が本当に不正な値か)。
   (b) `RUNC0511S`自体が失敗していないか(`C0511RUN: C0511S ended
   abnormally.`が出ていないか)。
   (c) 想定と違う経路(`CHAIN`失敗等、`N90`が立って`SUB`まで到達しない
   経路)を通っていないか。
   (d) **(2026-09-27追記、advisor指摘)`*PSSR`の対象範囲外だった
   可能性**: `za0500-ticket3.rpg`の実際のコンパイル結果
   (`work/verify/results/part05-qcmdexc-runtime-2026-09-26T23-43-17-905Z.json`
   の`ZA0500T3`クロス・リファレンス)によれば、`JUSU`は`P(5,0)`
   (パック10進)としてコンパイルされている——`JUCHUD`のディスク上の
   ゾーン10進表現から、レコード入力時に内部のパック表現へ変換される
   ことを意味する。つまり不正な`JUSU`バイト列は、`SUB JUSU AVAIL`
   (計算仕様書)より**前**、`OPNQRYF`経由でレコードを読み取る入力段階
   そのもので既に問題を起こす可能性がある。`za0500-ticket3.rpg`には
   `JUCHUD`用の個別`INFSR`が無い(ヘッダー・コメント自身が「計算仕様書中の
   例外」だけを対象範囲としていると明記しており、オープン/クローズ時の
   失敗は対象外だが、**オープン済みファイルの1レコード読み取り時の
   例外が`*PSSR`の対象に入るかどうかは、このセッションでは未確定**)。
   もし`VFYLOG`のジョブ・ログに`SUB`起因の10進データ・エラーではなく、
   照会/ファイル系の例外(`CPF50xx`系等、レコードの読み取り自体に関する
   メッセージ)がそのまま(`*PSSR`に捕まらず)出ている場合、これは
   「エラーが`*PSSR`の対象範囲外の段階で起きた」という、チケット3の
   採点表の`段階の特定`・`対象範囲の判断`項目そのものに対応する、
   **それ自体有意義な発見**であり、この接続の設計ミスではない
   (`*LDA`が空白なのは正しい結果ということになる)。この場合は
   `verify/part05-mch1202-corrupt`(同じ`C0511S`技法をas-shipped・
   `*PSSR`無しの`ZA0500`に対して実行する、本稿執筆時点でまだ未接続)を
   先に接続し、`*PSSR`が無い状態でどのメッセージIDが出るかを先に確定
   させる方が、切り分けとしては安上がりである。
3. **`*LDA`に何か別の値が入っている** → `CHGDTAARA`のバイト数・命令
   自体を疑うこと(`za0500-ticket3.rpg`のヘッダー・コメントに書かれた
   命令文と実際のC仕様書を再度突き合わせる)。
4. **ハングした・照会メッセージで止まった** → `CHGJOB
   INQMSGRPY(*DFT)`が効いていない、または想定していない種類の照会
   メッセージが出た可能性がある。次回接続では歯止め(接続回数制限)を
   踏まえ、原因を静的に調査してから再接続すること。
