# part05-mch1202-corrupt の期待値(手計算、実機未確認)

**この設計は2名の批評担当の指摘(2026-09-27)を受けて全面的に書き直した版。**
書き直しの理由・根拠は manifest.json の description 本文に詳しいので、ここでは
「実機に接続したあと、VFYLOG をどう読むか」だけを整理する。

## 前提: このマニフェストが解消した2つの懸念

1. **JUCHUM のレコード様式問題(reviewer 2)**: `za0500.rpg` の F 仕様書
   `FJUCHUM IS F 26 DISK` は31桁目(レコード・アドレス・タイプ)が空白。
   `work/design/refs/rpg400ref.txt`("Position 31 (Record Address Type)")の
   規定どおり、これは「到着順(arrival sequence)で読む」ことを意味する
   ——`db/v1/juchum.pf` 自身の DDS が `A K JUNO` を持っていても、ZA0500 は
   それをキー順読み込みには使わない。このため、新しい `CLRJUCHUM` ステップ
   (`RUNSQL DELETE FROM &LIB/JUCHUM`、TXRESET の直後・C0511S の直前)で
   JUCHUM を一旦空にし、C0511S が挿入する `C05119` の1行だけにしてある。
   これにより、M1/MR 突合せサイクルが `C05119` を「01+MR」の一致行と
   して処理し、破損した `JUSU` を実際に読み込み・使うコード(下の表の
   統計文6400/8000/9300のいずれか)へ到達する**設計**になっている
   (ただし「到達するはず」という設計上の根拠であり、`JUCHUD` 自体の
   `OPNQRYF` 昇順読み取りが実際にどう振る舞うかにも依存する——下の
   manifest.json 本文・remainingRisks 参照)。
2. **チケット1の交絡(reviewer 2)**: `JU0900C` の as-shipped 版
   (`&MINQTY LEN(3 0)`)は ZA0500 の `*ENTRY PLIST`(`MINQTY 5,0`)と
   食い違う(05-13チケット1のバグ)。このマニフェストは
   `solutions/05-13/ju0900c-ticket1.clp`(`&MINQTY LEN(5 0)`)を別名
   `JU0900T` でコンパイルして CALL するため、このバグは構造的に排除されて
   いる——観測されるどんな10進数データ・エラーも、チケット1由来ではなく
   `C05119` の破損 `JUSU` に由来すると解釈してよい。

## 統計文番号の対応表(za0500.rpg、統合ソースの行番号 x 100、実機確認済みの規則)

`docs/probes.md` の `part05-ju0900c-baseline`(確認日2026-09-27)が、この
未変更ファイルに対して統計文8100=行81(`N90 AVAIL COMP MINQTY`)を実機の
クロス・リファレンス・リストで確認済み。同じ規則を他の行にも当てはめる
(I/O仕様書の行にも同じ規則が及ぶかどうかは未確認だが、確認済みの1点
[行81→8100]から機械的に外挿しただけの他の行より外挿の距離が近いとは
言えない——**すべて「未確認」のまま並列に扱うこと**):

| 行番号 | ソース | 想定統計文番号 | 意味 |
|---|---|---|---|
| 64 | `I 16 200 JUSU`(JUCHUD入力仕様書) | 6400 | レコード選択時、破損した `JUSU` をゾーン10進数として読み込む(**ここで落ちれば`SUB`より前**) |
| 78 | `N90 JUSHO CHAINZAIKOM 90` | 7800 | ZAIKOM を JUSHO='P00001' でCHAIN(90=not found) |
| 79 | `N90 Z-ADDZASU AVAIL` | 7900 | AVAIL = ZASU (在庫数) |
| 80 | `N90 SUB JUSU AVAIL` | 8000 | AVAIL -= JUSU (破損した `JUSU` を算術に使う) |
| 81 | `N90 AVAIL COMP MINQTY` | 8100 | AVAIL と MINQTY を比較(SHORT/OK判定、チケット1のバグの現場——`JU0900T`使用によりこの接続では原理上排除ずみ) |
| 93 | `O JUSU 21`(QSYSPRT出力仕様書) | 9300 | 破損した `JUSU` を印字用に編集する(**`SUB`が例外を起こさなかった場合、ここで初めて落ちる可能性がある**) |

**統計文6400・8000・9300のいずれかを指すエラーは、すべて「破損した
`JUSU` が原因」という同じ結論を裏付ける**(どの段階で検出されたかが
違うだけ)。統計文8100を指すエラーだけが「予想外」(下記2番)。

## 期待される結果と読み方

1. **統計文6400・8000・9300のいずれかを指す10進数データ・エラー
   (メッセージIDは `RPG0907` の可能性が高いが、`MCH1202` も既存の
   一次資料からは排除できない)** → 本命どおり。破損した `JUSU`
   (`'ABCDE'` の生バイト)が原因で落ちたことになる。`docs/probes.md`
   の記述(OPM RPG/400 は自分自身の `RPG0907` で報告し、`MCH1202` は
   MI/ILEレベルの等価物)を踏まえると `RPG0907` が最有力だが、**this
   session ではまだ実機で確認できていない仮説であり、実際に出た
   メッセージIDをそのまま記録すること**(決めつけない)。
2. **統計文8100を指すエラーが出た場合** → 予想外。`JU0900T` で
   チケット1を修正済み(`&MINQTY LEN(5 0)`、ZA0500の`*ENTRY PLIST`と
   一致)なので、このマニフェストの設計では起こらないはずのエラー。
   起きた場合はまず `CPJU0900T` が本当に `LEN(5 0)` 版をコンパイル
   できたか(コンパイル・リストや`solutions/05-13/ju0900c-ticket1.clp`
   との突き合わせ)を疑うこと。
3. **エラーが一切出ない場合(job logに10進数データ・エラーが無い)** →
   これは**「JUSU破損は例外を起こさない」という確定結果ではなく、
   まだ判定できない状態**として扱うこと。理由:
   - MI(CPYNV相当)がゾーン10進数の変換時に「符号ニブル以外のバイトの
     ゾーン・ニブルは無視し、数字ニブルだけを見る」という実装であれば、
     `'ABCDE'`(数字ニブル1-5・符号ニブルC、いずれも単体では有効)は
     **例外にならず、`JUSU=12345`として読める**——05-11本文の「正直な
     注記」がまさにこの未確定点を指摘している。
   - この場合、期待される印字は `C05119`/`P00001` の `SHORT` 行
     (`AVAIL = 45 - 12345 = -12300 < MINQTY(5)`)で、印字欄の
     `JUSU` には `12345` が出るはず——これが「JUSU破損はエラーには
     ならなかったが、実際に(異常な値のまま)算術に使われた」ことを
     示す積極的な証拠になる。
   - **ただしZA0500自身のQSYSPRT出力が、この接続のrunセクションの
     標準出力に実際に乗るかどうかは未確認**(`part05-13-tickets/
     expected/notes.md`の「実際の結果をどう読むか」3番(b)が既に
     指摘している未確定点——ZA0500での確認例はまだ一度も無い)。
   - **`collect`の1本目・2本目(`JUNO/JULINE/HEX(JUSU)`)が1行返ることは、
     `C05119`が`JUCHUD`に植え付けられたことの証拠であって、`ZA0500`が
     その行を実際に処理した(`PROCLN`に到達した)ことの証拠ではない。**
     `CLRJUCHUM`によるJUCHUM単独行化の設計は「到達するはず」という
     設計上の根拠であって、到達した観測ではない——混同しないこと。
   - 結論: 「エラー無し」かつ「run セクションにSHORT/JUSU=12345の
     印字が見えない」場合は、**「JUSU破損は無害」と「C05119がそもそも
     処理されていない」のどちらとも判定できない曖昧な結果**として
     正直に記録し、次の接続で(例えば`DSPJOB OPTION(*PGMSTK)`相当の
     追加証拠、またはQSYSPRT出力の回収経路そのものを別途確認してから)
     切り分けること。
4. **`CLRJUCHUM`/`RUNC0511S`/`RUNJU0900T` のいずれかで想定外の
   `MONMSG` 発火・コンパイル失敗** → まず `VFYLOG` の `S* FAILED` 系
   メッセージでどのステップが失敗したかを特定する。特に `CLRJUCHUM` は
   新規ステップ(このマニフェストで初めて実行される)なので、`RUNSQL`
   の構文そのものが通るかどうかも含めて未検証。
   **注意: `RUNC0511S`が`FAILED`と出ないことは、`C0511S`が成功した
   ことの証拠には全くならない。** `C0511S`自身の`FAILSAFE`ラベルは
   `SNDPGMMSG ... MSGTYPE(*COMP)`のあと`RETURN`する(`*ESCAPE`を投げ
   直さない)ため、`C0511RUN`からは正常終了に見え、`C0511RUN`は
   「C0511S: C0511S returned normally.」とだけ送る——`RUNC0511S`ステップ
   自身は`FAILED`にならない。**本当の成否は、VFYLOGに
   `C0511S: planted a decimal data error in JUCHUD (JUNO=C05119, ...)`
   という行があるかどうかで判定すること。** この行が無ければ、
   `CLRJUCHUM`だけが実行されて`C0511S`は何も挿入できなかった可能性が
   高く、その場合`JUCHUM`は空のままで`JU0900T`は
   「JU0900C: JUCHUM is empty.」を送るはず(`JU0900T`は
   `solutions/05-13/ju0900c-ticket1.clp`のコピーで、メッセージ文言は
   すべて`JU0900C:`のまま——`JU0900T`という名前はこのマニフェストが
   付けたオブジェクト名であって、メッセージ本文の`JU0900C:`は誤記では
   ない)。また、`RUNJU0900T`が`CPF9999`のような未処理エスケープを
   `JU0900T`自身の統計文番号で報告する場合、`part05-ju0900c-baseline`が
   観測した「statement 7400」(as-shippedの`ju0900c.clp`でのCALL行)
   ではなく、**`ju0900c-ticket1.clp`のCALL行(88行目)に対応する
   statement 8800**になるはず——これはCLプログラム側の統計文番号で
   あり、上の表(ZA0500側のRPG統計文番号)とは別物なので混同しない
   こと。

## collect ステップの読み方

- 1本目(`HEX(JUSU)` のみ、`JUSU` 生列なし)が **この接続で最優先に守る
  べき証拠**。万一2本目(生の `JUSU` を含む、05-11本文が「表示が乱れる
  可能性がある」と警告している版)がエラーで落ちても、1本目が生きていれば
  `'ABCDE'` → `C1C2C3C4C5` という仮説は検証できる。
- 3本目(`JUNO <> 'C05119'` の比較用、通常行の `HEX(JUSU)`)は、
  `JUCHUD` 自体は `CLRJUCHUM` の対象外(削除されるのは `JUCHUM` だけ)
  なので、TXRESET が入れた通常行が引き続き存在し、この比較は成立する
  はず。
- 4本目(`ZAIKOM.P00001`)は、`RUNMODE='*TEST'` により `UPDAT` が一度も
  実行されていないことの確認。`part05-ju0900c-baseline` 確認済みの値
  (`ZASU=45`)と一致するはず。

## このマニフェスト後に &LIB へ残る状態(次に接続するマニフェストへの注意)

`JUCHUM` は **`C05119` の1行だけ**(`C0511S`が失敗していれば0行)になる
(TXRESET前の`J00001`〜`J00008`の8件のヘッダー行は `CLRJUCHUM` で全削除
される)。`JUCHUD` は通常の**12件**(`part05-13-tickets/expected/
notes.md`の12行表参照——`JUCHUM`のヘッダー8件とは行数が異なる)+
`C05119` の13件のまま(`JUCHUD`自体は`CLRJUCHUM`の対象外)。

**この後に接続する他の part05-* マニフェストは、自分自身の冒頭で
`TXRESET` を必ず実行すること**(`part05-13-tickets` の
`expected/notes.md` 前提(2)が既にこの防御をしている——ただし元の設計
[`C05119`を追加するだけ]より削除範囲が広がった点に注意。`TXRESET`は
無条件にデータを再投入するので、この防御は元の設計・この設計のどちらに
対しても有効)。

この設計時点(2026-09-27)で同じセッション中に存在する他の未コミット
マニフェスト(`verify/part05-promote-rollback`・`verify/part05-txmigr-to2`)
を確認した: どちらも本マニフェストとは無関係([promote-rollback]は
`&LIB`/`&LIB2`間で`TK0100D`/`TK0100`のみを扱い、`JU0900C`/`ZA0500`を
一度もCALLせず、`JUCHUM`/`JUCHUD`のデータ内容も読まない。
[txmigr-to2]は`TXSETUP LIB(&LIB2)`で`&LIB2`(別ライブラリー)に独立した
DBを新規構築し、そちらに対してのみ`JU0900C`をCALLする——`&LIB`の
`JUCHUM`/`JUCHUD`データには一切触れない)ので、本マニフェストが
`&LIB/JUCHUM`を1行に減らしても、この2本には影響しない。ただし、
これは2026-09-27時点の内容を読んだ結果であり、これらのマニフェストが
その後変更されればこの結論も再確認が必要。
