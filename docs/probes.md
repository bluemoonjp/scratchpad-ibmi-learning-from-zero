## P01: 自分のライブラリー構成(読み取り専用、確認日 2026-09-24)

```sql
SELECT OBJNAME, OBJTYPE, OBJOWNER
  FROM TABLE(QSYS2.OBJECT_STATISTICS('<USER>1','*ALL')) X
 ORDER BY OBJNAME FETCH FIRST 10 ROWS ONLY;

SELECT OBJNAME, OBJTYPE, OBJOWNER
  FROM TABLE(QSYS2.OBJECT_STATISTICS('<USER>2','*ALL')) X
 ORDER BY OBJNAME FETCH FIRST 10 ROWS ONLY;

SELECT OBJNAME, OBJTYPE, OBJOWNER
```

## P08: SSH・PASE・OSS ツールの有無(確認日 2026-09-24)

SSH の remote command として `/usr/bin/qsh` を直接起動し(ログイン・シェルの bsh は経由しない)、標準入力からシェル・コマンドを渡して確認した。

```text
echo PATH=$PATH
command -v git; git --version
command -v bash
command -v makei; makei --version
command -v python3
command -v gmake
command -v make
```

結果:

- `PATH=/usr/bin:.:/QOpenSys/usr/bin` — **既定の PATH に `/QOpenSys/pkgs/bin` は含まれない。**
- `bash`: `/usr/bin/bash` にあり、既定 PATH で見つかる。
- `make`: `/QOpenSys/usr/bin/make`(PASE 標準の make。GNU make と非互換なオプション体系)。
- `git`: 既定 PATH では **見つからない**(`qsh: 001-0019 Error found searching for command git.`)。
- `makei`: 既定 PATH では **見つからない**。

追加確認(`/QOpenSys/pkgs/bin/` を直接指定):

- `/QOpenSys/pkgs/bin/git` は実在する(`git version 2.47.0`)。
- `/QOpenSys/pkgs/bin/gmake`、`/QOpenSys/pkgs/bin/makei`、`/QOpenSys/pkgs/bin/python3` はいずれも実在する。
- `/QOpenSys/pkgs/bin/tobi` という名前のコマンドは **無い**(TOBi への改称後も、コマンド名は `makei` のまま)。
- `/QOpenSys/pkgs/bin/` には約 1.5GB 相当のパッケージ群がインストール済み(git・Python・GNU make・Ansible 等、多数)。

**結論**: git・GNU make・makei・python3 はすべて使えるが、**既定の PATH には入っていない。** SSH 経由の自動化(02-04 の `git clone`、08-01/08-02 の `makei` ビルド)では、フルパスを使うか、`~/.profile` に `export PATH=/QOpenSys/pkgs/bin:$PATH` を追記する必要がある。

**影響**: 02-04, 03-10, 08-01, 08-02。批評で確定した「中重大度」の修正(PATH の既定に関する項目)を、この実測で裏付けた。

## 接続数に関する注意(確認日 2026-09-25)

TOKUIM の転送・コンパイル検証に成功した直後、5 本のソースをまとめて `scp` しようとしたところ `Connection closed by <IP> port 2222` で即座に切断された(認証エラーではなく、TCP 接続確立の直後に切断)。短時間に 7 回程度の接続を行った後だったため、**同一 IP からの接続数制限に触れた可能性がある**(PUB400 のコミュニティ規約に明記されている `hard restriction on number of connections from a single IP` に該当すると推測)。このときは 15〜20 分ほど間隔を空けたところ、接続できる状態に戻った。

**その後、同じセッション内でさらに接続を重ねた結果、`ssh`(2222番)だけが `Connection timed out` で一切繋がらなくなった。** `Test-NetConnection` で確認したところ、**2222番(SSH)だけが不通**で、**992番(5250 TLS)と443番(HTTPS)は疎通していた。** 認証の失敗を1回も起こしていないにもかかわらず、短時間に多数(合計15回程度)の SSH 接続を行ったことが原因とみられる。

**対応(確定)**:

- 1回の接続で行う作業を、これまで以上にまとめる。
- 同じセッション内で SSH 接続を繰り返す場合、**目安として10回を超えたら、大きく間隔を空けるか、その日はそれ以上接続しない。**
- SSH だけが不通で 5250(992番)は生きている場合がある。**5250 は影響を受けないため、SSH が使えない間は 5250 で進められるレッスンに切り替える**(全体方針 §2 の「SSH が使えない場合のルート」に反映する)。
- この種のブロックが解除されるまでの時間は今回は未計測(私的な学習記録にある「鍵の連続認証失敗による約1日のブロック」とは別の現象とみられる。認証失敗を伴わない、純粋な接続数によるものである可能性が高い)。

**影響**: P37(接続数の確認)。全体方針 §10(接続数と容量の予算)、および §2(SSH が使えない場合のルート)に、この実測を反映する。TXSETUP の実機検証(コンパイル・エラーは残り1件まで絞り込み済み)は、次回 SSH が復旧してから再開する。

## TXSETUP の実機デバッグで分かった CL の落とし穴(確認日 2026-09-25)

`<USER>2` でサンプル DB の DDS 一式(TOKUIM 等6物理ファイル+2論理ファイル)を実際にコンパイルし、CL ツール(TXSETUP)を実装・コンパイルする過程で、次の CL の仕様を実機のコンパイル・リストから確認した。教材(第3部・第4部)にも反映する。

- **`PARM()` で受け取る変数の `DCL` に `VALUE()` を書くとエラーになる**(`CPD0702`)。既定値が要る場合は、`PGM` の直後で `IF COND(&VAR *EQ ' ') THEN(CHGVAR ...)` のように後から代入する。
- **`ADDLIBLE` は SSH 経由の `system` コマンドを跨いで持続しない。** `system "CL コマンド"` は呼ぶたびに別ジョブになるため(01-08 の実機メモと同じ現象)、`ADDLIBLE` の効果を次の `system` 呼び出しで使うことはできない。ライブラリー・リストを変更してから使う処理は、**同じ CL プログラムの中で完結させる**必要がある。
- **論理ファイルの `PFILE()` キーワードにライブラリー名を書かない場合、`*LIBL` で探す。** 配布用の DDS ソースにライブラリー名を焼き込みたくない場合、`CRTLF` の前に `ADDLIBLE` で対象ライブラリーをライブラリー・リストに入れておく必要がある(上記の「別ジョブ」問題と合わせて、1つの CL プログラム内で行うこと)。
- **`RTVJOBA` でジョブのユーザーを取得するキーワードは `USRPRF` ではなく `USER`。**(`CPD0043`)
- **`%LOWER(%TRIM(&VAR))` のように組み込み関数を直接ネストすると `CPD0181` になる。** いったん `CHGVAR` で中間変数に代入してから、もう一段階 `CHGVAR` で関数を適用する。
- **`ADDPFM` の `SRCTYPE` は `*PF`/`*LF` のような CL 特殊値ではなく、`PF`/`LF` という単なる文字列。** アスタリスクを付けると `CPD0133` になる。

**影響**: 03-01(コンパイル・リストの読み方)、tools/qclsrc/txsetup.clp。

## TXSETUP・TXRESET の続報(確認日 2026-09-25)

SSH が復旧してから、上記の4件を修正した版を実機で再コンパイルしたところ、さらに1件見つかった。

- **`SNDPGMMSG` に `MSGTYPE(*ESCAPE)` を指定すると、`MSG()` の自由形式テキストではなく `MSGID` が必要になる**(`CPD2489`)。`*ESCAPE`・`*NOTIFY`・`*STATUS` のような正式なメッセージ種別は、メッセージ・ファイルに登録された定型メッセージを前提にしている。自前のメッセージ・ファイルを用意しない簡易なエラー処理では、`MONMSG` を付けずに**元のコマンドの失敗メッセージをそのまま未処理のまま伝播させる**(プログラムが異常終了し、その失敗の本来のメッセージが呼び出し元に伝わる)のが簡単で確実。

この修正により、**`TXSETUP` と `TXRESET` は 0 エラーでコンパイルできることを確認した。**

- **`CALL` はライブラリー修飾が要る場合がある。** `system` 経由の `CALL PGM(TXSETUP)`(無修飾)は、コンパイル先のライブラリーがそのジョブの `*LIBL` に入っていないため `CPD0170`(見つからない)になった。`CALL PGM(<LIB>/TXSETUP)` と修飾したところ解決した。
- **`CALL` にパラメーターを一切付けずに実行すると `CPD0172`(渡されたパラメーターが必要なものと一致しない)になった。** 3つの `*CHAR` パラメーターを宣言しているプログラムに対し、`CALL PGM(...)`(パラメーターなし)で呼んだ場合の挙動で、CL プログラムなら本来「渡されなかった分は既定値」で済むはずだが、コマンド行(または `system` 経由の呼び出し)からは同様に振る舞わない場合があるとみられる。**`CALL PGM(...) PARM(値1 値2 値3)` のように、宣言した数だけ明示的に値を渡すことで解決した。** 原因の詳細は未特定。03-08(パラメーターと CALL の罠)で扱う。

**影響**: 03-01, 03-08, tools/qclsrc/txsetup.clp, tools/qclsrc/txreset.clp。

**実行そのものの検証は未完了。** `CALL PGM(<USER>2/TXSETUP) PARM(...)` を2回投入し、いずれも長時間(数十分)応答を返さなかった。**別の新しい接続で `<USER>2` の中身を確認したところ、2回とも `TOKUIM` を含め1つも物理ファイルが作られていなかった**(`QCLSRC`/`QDDSSRC`/`TXSETUP` 等のプログラムのみ)。つまり、`TXSETUP` はごく初期(1つ目のオブジェクトを作る前後)で止まっている。

**原因の有力な仮説(未確定)**: このテストでは `CLONEDIR('/home/<USER>/ibmi-kyozai')` を渡したが、実際に DDS ソース一式を置いたのは `/home/<USER>/db/v1/`(`ibmi-kyozai` というサブディレクトリーを経由していない、著者の手動テスト用の配置)である。そのため `CPYFRMSTMF` が存在しないパスを参照した可能性が高い。ただし、`CPYFRMSTMF` の失敗はプログラム・レベルの `MONMSG` なしで即座にエラー終了するはずであり、**なぜ「エラーで終わる」ではなく「応答なし」になるのかは未解明。**接続やツール側の何らかの事情の可能性も残る。

**追加の切り分け(確認日 2026-09-25)**:

- `CPYFRMSTMF` 単体を、存在しないパスに対して実行したところ、**即座に**(ハングせず)`CPFA0A9`/`CPFA095` で失敗した。パスの誤り自体はハングの原因ではないと判明した。
- `CLONEDIR('/home/<USER>')`(実際にファイルを置いた場所と一致させたパス)を渡して3回目を実行したが、**PowerShell 側で90秒のタイムアウトを明示的に付けても、バナー(`-> Enter your password for Logon below:`)より後の出力が一切返らなかった。** これは「ゆっくり実行されている」のではなく、**バナーの直後、最初のコマンドが実行される前後の、ごく早い段階で本当に停止している**ことを示す。

**最も有力な仮説**: `system "CALL PGM(...) PARM('A' 'B' 'C')"` のように、**CL の文字列リテラル(単一引用符)を、qsh の `system` に渡す二重引用符の中に埋め込む**という、この検証だけで使った呼び出し方それ自体に問題がある可能性が高い。何らかの理由で CL のコマンド行プロセッサーが「まだ入力が続く」と解釈し、**非対話のジョブでは誰も応答できない継続入力待ちの状態になっている**のではないかと推測する(未確定)。

**引用符ネスト仮説は反証された。** 上記の対策案3(パラメーターをソース内に埋め込んだラッパー・プログラム `TXTEST`)を実際に作り、`system "CALL PGM(<USER>2/TXTEST)"`(引用符のネストなし、パラメーターなし)で呼んだところ、**それでも90秒のタイムアウトまで応答がなかった。** `TXTEST` 自体は正常にコンパイルできている(0〜10重大度、実質エラーなし)。これにより、SSH/qsh の呼び出し方(引用符のネスト)が原因という仮説は否定された。**`TXSETUP` の実行そのものに、原因不明のハングを起こす何かがある。**

**現時点で分かっていること**:

- `TXSETUP` のコンパイルは0エラー。
- `TXSETUP` が実際に作るはずの6物理ファイル・2論理ファイルは、3回試行してもすべて**1つも作られていない**(=ごく早い段階、おそらく最初の `CALLSUBR SUBR(LOADPF)`(`TOKUIM` 分)の中で止まっている)。
- `LOADPF` サブルーチンの中身(`ADDPFM`・`CPYFRMSTMF`・`CRTPF`)は、このセッションの前半で個別に(サブルーチンを介さず直接)実行したときは正常に動作した。
- `CPYFRMSTMF` を存在しないパスに対して単体実行したときは、即座にエラーで失敗した(ハングしない)。

**次回試すべきこと(優先度順)**:

1. `LOADPF` サブルーチンの中身を、`CALLSUBR` を使わずに `TXTEST` へ直接(1つのオブジェクト分だけ)埋め込み、`CALLSUBR`/`SUBR`/`ENDSUBR` の組み合わせ自体に原因がないか切り分ける。
2. `RTVJOBA CURLIB(&LIB) USER(&USRPRF)` や、`IF COND(&LIB *EQ '*CURLIB')` のような、`TXTEST` 経由では実行されない(`TXTEST` は `TXSETUP` を CALL するだけで、`TXSETUP` 内部の初期化コードは通常どおり実行されるはずだが)前段の初期化コードを疑い、同様に段階的に切り分ける。
3. `WRKACTJOB` に相当する情報を(自分のジョブに限定して)確認できないか検討し、応答なしの `CALL` が実際にどのジョブとして・どの状態で残っているかを確認する(ただし全ユーザーを対象にした走査は絶対に行わない)。
4. それでも原因不明なら、`TXSETUP` を新規に、より小さい単位(まず1ファイルだけ作る版)から段階的に再構築し、どの行を追加した時点でハングが再発するかを二分探索的に切り分ける。

**このセッションでは、SSH 接続をこれ以上重ねるリスクを避けるため、ここで実機検証を打ち切る。** `TXSETUP` 自体のロジック上の疑わしい箇所(コンパイルは0エラーだが、実行時の未知の問題)を、次回セッションの最優先課題とする。

## 解決: ハングの真因が判明した(確認日 2026-09-25、遅延して届いたジョブ・ログから)

**接続を切った後も PUB400 側ではジョブが動き続けており、その結果が数十分後にようやく戻ってきた。** ジョブ・ログを読んだところ、真因が判明した。

```text
CPF9801:  Object TXSTATE in library <USER>2 not found.
       :  TXSETUP: building sample database in library <USER>2   ...
CPF5812:  Member TOKUIM already exists in file QDDSSRC in library <USER>2.
CPF7306:  Member TOKUIM not added to file QDDSSRC in <USER>2.
CPF9999:  Function check. CPF7306 unmonitored by TXSETUP at statement 12600, instruction X'017C'.
CPA0701:  CPF7306 received by TXSETUP at 12600. (C D I R)
       :  I
  (この後、多数の "CPC1129: Job ... changed by JOBMANAGER" が続く)
CPD018A:  Path name contains embedded nulls.
CPF0001:  Error found on CPYFRMSTMF command.
CPA0701:  CPF0001 received by TXSETUP at 13100. (C D I R)
```

**真因**: `ADDPFM` が「メンバーは既に存在する」で失敗したときのメッセージIDは、`CPF7302` ではなく **`CPF7306`** だった。`MONMSG MSGID(CPF7302)` はこれを捕まえられず、**未処理のまま `CPF9999`(機能検査)に格上げされ、`(C D I R)` の応答を求める照会メッセージになった。** SSH 経由の非対話ジョブには応答できる相手がいないため、**ここで無期限に停止していた。** これは、03-12 で教えている「バッチでは照会メッセージに誰も応答できず、永遠に待ち続ける」という注意そのものが、著者自身のツールで実際に起きた実例である。

**対応(修正済み)**:

1. `tools/qclsrc/txsetup.clp`・`txreset.clp`・`txstatus.clp` のすべてに、**宣言の直後にプログラム・レベルの `MONMSG MSGID(CPF0000) EXEC(GOTO CMDLBL(FAILSAFE))` を追加した。** これにより、今後同様に見落としがあっても、無期限のハングではなく、`FAILSAFE:` ラベルでの即時終了(ジョブ・ログにメッセージを残して正常に抜ける)になる。**この安全策自体が、02-05や03-07で教える価値のある実例になった。**
2. `MONMSG MSGID(CPF7302)` を `CPF7306` に修正した。
3. `%TRIM`/`%LOWER` を実行時に呼ぶ代わりに、各呼び出し箇所で小文字のファイル名を直接 `CHGVAR` するように変更した(`CPD018A: Path name contains embedded nulls` という2件目の未解明のエラーの発生源を断つため。根本原因は特定できていないが、実行時の文字列変換をなくすことでリスクを下げた)。

**まだ未確定なこと**: `CPD018A`(パス名にヌル文字が含まれる)がなぜ発生したかは、完全には解明していない。`%TRIM`/`%LOWER` を経由した文字列組み立てが疑わしいと考え、上記3で回避したが、次回、修正後の版で改めて実機確認する。

## *CMD ラッパーの追加(確認日 2026-09-25)

## 訂正: QUSER 問題は *CMD 経由でも再現し、真因は RTVJOBA USER の仕様だった(確認日 2026-09-25)

上記「実行確認」で「QUSER 問題も `*CMD` 経由では再現しなかった」と書いたのは、**検証が不十分だった。** そのときの `TXSETUP LIB(<USER>2)` 呼び出しは `TXSTATE` が既に存在していたため `CHKOBJ` の直後で「already initialized」となって早期終了しており、**`CLONEDIR` の既定値計算(`RTVJOBA USER`)が実際に使われる `BUILD:` 以降のコードには到達していなかった。** つまり QUSER 問題が起きるかどうかを検証できていない状態で「再現しなかった」と誤って記録してしまった。

**あらためて、`FORCE(*YES)` を指定して `BUILD:` を強制的に通す診断用ラッパー(`ADDLIBLE` してから `*CMD` 経由で `TXSETUP LIB(<USER>2) FORCE(*YES)` を呼ぶ CL プログラム)を作って実行したところ、`*CMD` 経由でも `CLONEDIR` はホーム・ディレクトリーが `QUSER` 配下(実在しないパス)として組み立てられ、`CPFA0A9: Object not found` になった。** つまり QUSER 問題は `CALL` か `*CMD` かに関係なく、**PASE の `system()` 経由でジョブを起動したときに共通して起きる**、ということが確定した。

**真因の切り分け**: `RTVJOBA USER(&VAR)` と `RTVJOBA CURUSER(&VAR)` の両方を1本の診断用 CL プログラムで実行して比較したところ、次の結果になった。

```text
USER=[QUSER     ] CURUSER=[<USER>    ]
```

**`RTVJOBA` の `USER` キーワードは、そのジョブの「ジョブ名のユーザー部分」を返す(PASE `system()` が起動するジョブは `QUSER` という名前になるため、常に `QUSER` が返る)。`CURUSER` キーワードは、実際にサインオン(または `system()` の場合は SSH 認証)した「現在のユーザー・プロファイル」を返し、こちらは正しく `<USER>` になる。** `USER` と `CURUSER` は別物であり、この教材のように「実際にログインした人の名前」が欲しい場合は **`CURUSER` を使わなければならない。**

**対応(修正・完全に検証済み)**: `tools/qclsrc/txsetup.clp`・`txreset.clp` の `RTVJOBA USER(&USRPRF)` を、両方とも **`RTVJOBA CURUSER(&USRPRF)`** に修正した。**この修正後、完全な通し実行を実機で確認した**: `<USER>2` を完全にクリーンな状態に戻し、02-04 のレッスンどおりに実際に `git clone --filter=blob:none --sparse` + `git sparse-checkout set src db tools` で `~/ibmi-kyozai` を作り、`CLONEDIR` を省略・`FORCE(*YES)` で `TXSETUP` を実行したところ、**`TXSETUP: done. DBVER=1.` まで完走した。** `TXSTATUS` で `DBVER=0000000001`、`TOKUIM`=6件・`JUCHUD`=12件、6物理ファイル+2論理ファイルすべての存在も SQL で確認した。**これで、学習者が実際に体験する経路(`~/ibmi-kyozai` への実クローン→ `CLONEDIR` 省略 → `TXSETUP` 実行)に最も近い形での通し検証が完了した。**

**教訓**: 「`*CMD` でラップしたから、`CALL` 由来の問題はすべて解決した」と早合点したのが今回の誤りの原因。`*CMD` が解決するのは**パラメーターの受け渡し**(32バイトの罠、`CPD0172`)の問題であり、**ジョブそのものがどのユーザーで動いているか**(`RTVJOBA USER` の挙動)は、呼び出し方法(`CALL`/`*CMD`)に関係ない、別のレイヤーの問題だった。検証は、実際に問題のコード経路(`BUILD:` 以降、`FORCE(*YES)` が必要)を通るところまで行わないと意味がない、という教訓も含めて記録しておく。

**影響**: tools/qclsrc/txsetup.clp・txreset.clp(`CURUSER` に修正、完全な通し実行を実機で確認済み)。02-05 の実機メモを更新した。

## 解決: DISK ファイルへの READ が実行時にハングしていた真因(確認日 2026-09-25)

`TOKUIM`(6件のデータが入っている、キー定義済みの物理ファイル)を `F`(全手続き方式)・外部記述で宣言し、`READ` 一発と `SETON LR` だけの最小プログラムを実行したところ、**コンパイルは Highest Severity 00 で成功するにもかかわらず、`CALL` での実行が応答なしになった**(90秒のタイムアウトでも応答なし)。

**切り分け済みのこと**:

- `EXCPT`・O仕様書(印字)を完全に除いた、`READ` + `SETON LR` だけの最小構成でも同じくハングする。**印字処理ではなく、`READ`(またはファイルのオープン)自体が原因。**
- `WRKOBJLCK OBJ(<USER>2/TOKUIM) OBJTYPE(*FILE)` で確認したところ、**ロックは一切なかった。** レコード・ロックが原因ではない。
- このセッションで RPG III から実際に DISK ファイルを開いて読んだのは、この検証が初めて(第4部のこれまでのプログラムは印刷装置ファイル `QSYSPRT` しか使っていない)。**PASE の `system()` 経由で起動したジョブから、RPG が DISK ファイルを開く際に、これまで気づいていなかった別の問題がある可能性がある**(TXSETUP のハングと同様、非対話ジョブが応答できない照会メッセージが絡んでいる可能性が高いが、まだ特定できていない)。

**追加の切り分け(同日)**:

- **280秒(約4分半)待っても応答がなかった。** TXSETUP のときのように「SSH 側は切れてもサーバー側で完走し、後から結果が取れる」パターンではなく、真に長時間ハングしている可能性が高い。
- `WRKOBJLCK`・`DSPFD TYPE(*ATR)` でファイル属性を確認したが、ロック・異常な属性は見当たらなかった(`WAITFILE 30`・`WAITRCD 60` という既定値のみ)。
- **`*PSSR`(RPG の標準エラー処理サブルーチン)を追加しても、同じくハングした。** `*PSSR` は通常、実行時エラー(レコード・ロック待ちのタイムアウト、10進データ・エラーなど)を捕まえて `CPF9999`(機能検査)への格上げを防ぐはずだが、それでも解消しなかった。**これは、ハングが RPG のエラー処理層に制御が戻る前、もっと低い層(ファイルのオープン処理そのもの)で起きていることを示唆する。**
- このセッションでこれ以上、原因を推測ベースで切り分け続けるのは非効率と判断し、いったん打ち切った。

**`P` 指定(プライマリー・ファイル)でも同じくハングすることを確認した**(`F`/`P` どちらの指定でも起きる、指定方法自体は原因ではない)。

**真因の特定**: ハングしたジョブを `WRKACTJOB` で特定できたため(自分のジョブのみ。他ユーザーのジョブは見ていない)、`DSPJOB OPTION(*PGMSTK)` でコール・スタックを、`DSPJOBLOG` でメッセージ履歴を直接確認したところ、次のことが分かった。

- コール・スタックの最下部が `R0406T`(の `.OPEN` 位置)→ `QRGXMSG` → `QMHRCVPM`(メッセージ受信 API)で止まっていた。**RPG のファイル・オープン処理が、応答を待つメッセージ受信 API で停止していた。**
- ジョブログに `CPF4101: File TOKUIM in library *LIBL not found or inline data file missing.` があった。**`TOKUIM` を `*LIBL` 上で見つけられず、暗黙のオープンが失敗していた。**
- 続いて `CPF9999`(機能検査。`CPF4101` が未処理だったため)、そして `RPG1216`(`Error message CPF4101 appeared during OPEN`。重大度99、`C`/`D`/`S`/`F` の応答を求める、RPG 独自の照会メッセージ)が記録されていた。

**つまり、原因はこのセッションで何度も踏んできたのと同じ `*LIBL` の問題だった。** `TXCRTW2`(`ADDLIBLE` してから `CRTRPGPGM` するラッパー)で `R0406T` を**コンパイル**したジョブでは `<USER>2` が `*LIBL` に入っていたが、その**後**、別の新しい SSH セッションから素の `CALL PGM(<USER>2/R0406T)` で**実行**したときは、その新しいジョブの `*LIBL` に `<USER>2` が入っておらず、F 仕様書で無修飾のまま書いた `TOKUIM` の暗黙オープンが `*LIBL` で見つからずに失敗していた。

**新しく分かったこと: RPG は、暗黙のファイル・オープンが失敗すると、`MONMSG`(CL)はもちろん `*PSSR`(RPG 自身のエラー処理サブルーチン)でも捕まえられない、専用の照会メッセージ(`RPG1216`)を送る。** `*PSSR` は計算仕様書の実行中に起きるエラーを捕まえるためのものだが、暗黙オープンはそれより前の、プログラムの初期化段階で起きるため、`*PSSR` の対象にならない。

**対応**: `ADDLIBLE LIB(<USER>2) POSITION(*FIRST)` してから同じジョブ内で `CALL PGM(<USER>2/R0406T)` する診断用ラッパー(`TXRUNR`)を作って実行したところ、**`TOKUIM` の6件すべてが正しく印刷され、完全に解決した。**

```text
 C00001  ACME TRADING CO
 C00002  NORTH STAR LTD
 C00003  BLUE OCEAN INC
 C00004  GREEN FIELD CO
 C00005  SUNRISE MARKET
 C00006  RIVER SIDE SHOP
```

`GOTO`/`TAG` の桁位置(`TAG` は Factor 1、`GOTO` は Factor 2。`BEGSR`/`EXSR` と同じ使い分け)も、この検証で実機確認できた。

**学習者への影響**: 02-05 と同様、**学習者が5250の対話的セッションで、コンパイルと同じセッション内で `CALL` する分には、通常 `*LIBL`/`*CURLIB` に自分のライブラリーが含まれているため、この問題は起きないと考えられる。** ただし、これも5250実機での確認はまだできていない。万一同じ現象(`CPF4101` や応答なし)に遭遇した場合の対処(`ADDLIBLE`)を 04-06 の「出力が違うとき」に明記した。

**影響**: 04-06(外部記述ファイルを順に読む)完成・実機検証済み(`R0406A`、`TOKUIM` 全6件の読み込み・印刷を確認)。`tools/gen/rpg3.mjs` に `GOTO`/`TAG` の桁位置を追記。

## CHAIN の桁位置(確認日 2026-09-25)

04-07(キーで読む)の検証で、`CHAIN` に関する2つの桁位置を実機コンパイルで確定した。TXWRAP2/TXRUNR と同じ「`ADDLIBLE` してから同じジョブ内で `CALL`」パターンを最初から使ったため、04-06 で踏んだ `*LIBL` ハングは再発しなかった。

- **F 仕様書31桁目(レコード・アドレス型)に `K` が必要。** 外部記述・キー付きファイル(`K TOKCD` のような DDS)を `CHAIN` でキー・アクセスする場合、これを指定しないと `CHAIN` の Factor 1(キー値)が「相対レコード番号として不正」(`QRG7055`)になる。29〜30桁目の `KEYLEN` は外部記述ファイルには不要(指定すると `QRG2008`)。
- **`CHAIN` の結果標識(「見つからない」を示す標識)は `HI`(54〜55桁目)。** `READ` の EOF 標識が `EQ` だったのとは異なる(`EQ` を指定すると `QRG5127`/`QRG5130`)。

実機で `CHAIN 'C00001'`(存在するキー)→ `C00001 ACME TRADING CO` が正しく印刷されること、`CHAIN 'C99999'`(存在しないキー)→ `HI` 標識が ON になり `TOKCD` は書き換わらず(空白のまま)`TOKNM` だけ `NOTFOUND` に上書きされることの両方を確認した。

**影響**: 04-07(キーで読む)完成・実機検証済み(`R0407A`)。`tools/gen/rpg3.mjs` に `CHAIN`・F仕様書31桁目の桁位置を追記。

## 解決: 「印刷が2重になる」謎はRPGのバグではなくTXSETUPのバグだった(確認日 2026-09-25)

04-08(JUCINQ3、`TOKUIM`+`JUCHUM` を組み合わせた帳票)の検証中、**`JUCHUM` を `READ` でループしながら条件付きで印刷するプログラムが、毎回すべての結果を正確に2回ずつ印刷する**という現象に遭遇した。`IFxx` を使わずに04-04方式の条件標識に変えても、`RETRN` を追加しても、無条件の印刷にしても再現し、**RPG のプログラム・ロジックの問題ではないと切り分けた段階で、直接 SQL で実データを見て真因が分かった。**

**真因: `<USER>2/JUCHUM` に実際に16件(本来8件の2倍)のデータが入っていた。** `JUNO` ごとに完全に重複した行が並んでいた。RPG は正しく16件を読んで正しく印刷していただけで、**バグはデータの方にあった。**

**さらに追跡したところ、原因は `tools/qclsrc/txsetup.clp` 自身の設計ミスだった。** `TXSETUP` の `BUILD:` 処理は、物理ファイルが「まだ無ければ」作成する(`CHKOBJ`+`MONMSG CPF9801`)が、**初期データの投入(`RUNSQLSTM load_v1.sql`)は無条件に毎回実行される。** このセッションでは `TXSETUP LIB(...) FORCE(*YES)` を(QUSER問題やCURUSER修正の検証のために)複数回実行しており、**そのたびに `load_v1.sql` の `INSERT` 文がすべて再実行され、データが積み上がっていた。** `JUCHUM` の DDS(`K JUNO`)には `UNIQUE` キーワードが無いため、重複キーの `INSERT` もエラーにならず黙って通ってしまう(`TOKUIM`・`SHOHIM`・`ZAIKOM`・`TANTOM`・`JUCHUD` も理論上は同じリスクがあるが、たまたまこのセッションでの実行タイミングにより `JUCHUM` だけがずれて重複していた)。

**対応(修正済み)**: `tools/qclsrc/txsetup.clp` の `BUILD:` 処理で、初期データを投入する直前に **`RUNSQLSTM SRCSTMF(... '/db/data/reset_v1.sql')`(削除)を追加**し、`load_v1.sql`(投入)の**前に必ず全件削除**するようにした。初回ビルド時はテーブルが空の状態で `DELETE` が実行されるだけなので害がなく、`FORCE(*YES)` の再実行でも重複が起きなくなる。**`<USER>2/TXRESET` で実データを正しい状態(`JUCHUM`=8件)に戻したうえで、修正版 `TXSETUP` を `FORCE(*YES)` で2回連続実行し、件数が8件のまま変わらないことを実機で確認した。**

**この調査の副産物として、04-08 の R0408A(`CHAIN`+条件付き `READ` ループ)のロジック自体は、最初の設計から一貫して正しかったことも実機で再確認できた**(正しいデータに対しては、`ACME TRADING CO J00001`/`J00003` の2行だけが正しく印刷された)。

**教訓**: 「プログラムの出力がおかしい」と思ったときは、**まずプログラムのロジックを疑う前に、実データが本当に想定どおりかを SQL で直接確認する**べきだった。今回は複数の代替ロジック(`IFxx` → 条件標識 → 無条件印刷)を試して初めてデータ側を疑ったため、遠回りになった。

**影響**: `tools/qclsrc/txsetup.clp` を修正(`FORCE(*YES)` の再実行でデータが重複しなくなった)。04-08(JUCINQ3)は当初の設計のまま完成・実機検証済み。

**細かい未了事項**: 04-06・04-07 の検証は、実際には使い捨てのメンバー名(`R0406T`)で行い、`src/qrpgsrc/r0406s.rpg`・`r0407s.rpg` に保存した内容と完全に同一のソースを、後から正式名(`R0406A`・`R0407A`)で再コンパイルして確認しようとしたところで SSH が接続数制限に触れた。**ソース内容は完全に同一なので動作は変わらないはずだが、`R0406A`・`R0407A` という名前そのものでのコンパイル確認はまだ行っていない。** 次回、余裕があれば確認する(優先度は低い)。

## 表示装置ファイル(画面)と WORKSTN の実機検証(確認日 2026-09-25)

04-11(表示装置ファイルを手書きして照会画面を作る)の検証。`tools/gen/dspf.mjs` を新規作成した。

**1. DDS(表示装置ファイル)の桁位置は、物理・論理ファイルと共通の基本桁(6=A 17=名前種別 19-28=名前 30-34=長さ 35=データ型 36-37=小数桁 45-=キーワード)に加えて、38桁目=使用法(`I`/`O`)、39-41桁目=行番号、42-44桁目=桁位置、を実機コンパイル(`CRTDSPF`、Highest Severity 00)で確認した。** レコード様式レベルのキーワード(`CF03(03)` などのファンクション・キー)は、`R` 行の直後に単独行として置く。

**2. WORKSTN の組み合わせ(C)ファイルで `EXFMT` を使うには、F仕様書16桁目(指定)を空欄ではなく `F`(完全手続き型)にする必要がある。** 空欄のままだと `QRG2096`(重大度20。生成基準の重大度9を超えるためコンパイル失敗)になる。RPG/400 Reference の `EXFMT` の説明に「WORKSTN file defined as a full procedural (F in position 16)」と明記されており、実機コンパイルでも裏付けられた。これは 04-06〜04-10 で「順に読むDISKファイル」に使ってきた `F` 指定と同じ文字だが、意味としては「EXFMTを使うWORKSTNファイルの必須指定」という別の理由による。

**3. DDS側の出力フィールドの長さは、外部記述ファイル側の同名フィールドの長さと完全に一致させる必要がある。** 一致しないと `QRG6033`(重大度30)になる。今回は `TOKUIM.TOKNM` が実際には30文字(`A(30)`)だったが、最初38文字で書いてしまい失敗した。RPG は DDS の出力フィールドと、プログラム内の同名フィールド(`CHAIN` で取得した `TOKUIM.TOKNM` など)を**フィールド名で自動的に対応付ける**ため、双方の長さが食い違うと検出される。

**4. 実機コンパイルで確認できなかったもの: DDS の条件標識(フィールド・定数行を標識の ON/OFF で出し分ける書き方)。** 7桁目に標識番号を置く形を試したが `CPD7410`/`CPD7606`/`CPD5238` で失敗し、正しい桁位置を特定できなかった(優先度低として保留)。**04-11 では代わりに、RPG 側で `CHAIN` の結果標識を使い、`MOVEL`(04-03 で確認済みの技法)で出力フィールドの内容そのものを書き換える方式**(`NOT FOUND` のときは `TOKNM` に `'NOTFOUND'` を上書きする)で「見つからない」を表現し、この問題を回避した。

**5. 重要な検証範囲の限界: `EXFMT` を含むプログラムの対話的な実行そのものは、このセッションの SSH(PASE `system()` 経由の非対話バッチ・ジョブ)では検証できない。** `WORKSTN` ファイルの `OPEN` は実際の5250デバイスを要求するため、`CALL` すると応答なくハングする("04-06のREADハング"と同種だが原因は別)。**今回は `CRTDSPF`・`CRTRPGPGM` のコンパイルが両方とも Highest Severity 00 であることまでを実機で確認し(V1)、画面の実際の表示・入力動作(V3)は一次資料の記述と、本レッスンの「実演」で学習者自身が5250で実行して確認する前提とした。**

## 実行時エラーの実機検証: RPG0102(ゼロ除算)は04-06のRPG1216と同種のハング(確認日 2026-09-25)

04-12(デバッグと実行時エラー)の検証。

**1. `DIV` でゼロ除算をすると、コンパイルは通るが実行時に `RPG0102`(重大度99、INQUIRY)が発生し、非対話ジョブがハングする。** 実際のメッセージ本文は次のとおり(`DSPLOG` の履歴ログで確認): `RPG0102 99 INQUIRY R0412T2 600 tried to divide by zero (factor 2) (C G S D F).` これは 04-06 で見つけた `RPG1216`(暗黙オープン失敗)と同じ種類の問題で、**`C`/`G`/`S`/`D`/`F` の応答を求める照会メッセージが、対話的な応答者のいないバッチ・ジョブで永遠に止まる。** `DIV` の結果標識(`+`/`-`/`Z`)は「結果の符号」を表すものであり、**ゼロ除算そのものを検出・防止する機能ではない**(結果標識を指定していても `RPG0102` は発生する)。最初の実機テストでは `CALL` した直後に応答が返らず(0ページの `QSYSPRT` スプールだけが作られる不可解な状態)、`DSPLOG PERIOD(...)` で当該時刻の履歴ログを調べて初めて `RPG0102` の発生と正体が分かった。ジョブ自体は SSH 接続の終了とともに自動的に片付いた(`WRKUSRJOB` で確認、手動での `ENDJOB` は不要だった)。

**2. 正しい防御パターンは「割る前に除数をチェックする」こと。** `COMP` で除数がゼロかどうかを先に確認し、ゼロなら `DIV` 自体を実行しない(条件標識で `DIV` 行をスキップする)。この方式で実機コンパイル(Highest Severity 00)・実行の両方を確認し、`DIV0ERR` が正しく印字され、ハングしないことを確認した。

**影響**: 04-12(デバッグと実行時エラー)完成。`R0412A`(ゼロ除算を安全に処理する例)を実機で作成・検証した。04-06 の `RPG1216` ハング調査(`WRKACTJOB`→`DSPJOB OPTION(*PGMSTK)`→`DSPJOBLOG`)を、実行時エラー調査の実例として再利用した。

## 検証ハーネス(`verify/`)自身の実機確認(確認日 2026-09-26、`harness-selftest`)

第5〜7部の実機検証を始める前段として、検証ハーネス自身が正しく動くかを3回の接続で確認した(結果ファイル: `work/verify/results/harness-selftest-2026-09-26T{11-57-52-819Z,12-13-00-709Z,12-30-08-434Z}.json`)。1・2回目で見つけたハーネス自身のバグはすべて `verify/lib/{batch,clgen}.mjs` を修正し、main へ commit・push・CI green 確認済み。3回目で全項目が成功した。

**1. `CHGJOB INQMSGRPY(*DFT)` は RPG0102(ゼロ除算の照会メッセージ)を自動応答し、ハングを防ぐ。** 3回目の接続の実際のジョブ・ログ: `RPG0102: T0ZERO 800 tried to divide by zero (factor 2) (C G S D F).` の直後に `:  C`(既定応答「取消」)が記録され、`RPG9001: Error RPG0102 caused program T0ZERO to stop.` という取消由来のエスケープになり、`CALL` ステップの `MONMSG MSGID(CPF0000 RPG0000 MCH0000)` がこれを正しく捕まえて「RUNIT FAILED」と報告し、そのまま次のステップ(`harness-selftest DONE`)へ正常に進んだ(ハングせず、`killedForTimeout: false`)。**これで、以後の検証マニフェストでゼロ除算や同種の照会メッセージを起こしうるステップ(第6部P24梯子の一部、旧システムの未検証コード等)を、`CHGJOB INQMSGRPY(*DFT)` の下で安心してバッチに含めてよいことが確定した。**

**2. heredoc で転送したファイルの CCSID タグは既定で 273(EBCDIC、PUB400 の QCCSID そのもの)になり、実バイト列も本物の EBCDIC である。** 1回目の接続では、ここへ明示的に `setccsid 1208`+`STMFCCSID(1208)` を指定していた(=実際は EBCDIC のバイト列を ASCII/UTF-8 だと偽って上書きタグ付けすることに相当)ため、`CPYFRMSTMF` が変換失敗(`CPFA0A2`/`CPFA095`)した。何もしなければ(タグとバイト列が一致したまま)、`CPYFRMSTMF` は正しく EBCDIC として読み取り、コンパイル可能な状態でメンバーへコピーできる(`CPCA081: Stream file copied to object.`)。ハーネスの既定を「CCSID を明示しない」に修正した(`verify/lib/batch.mjs`)。**教材内の git clone 経由の転送(`tools/qclsrc/txsetup.clp` 等の `STMFCCSID(1208)`)はこれとは別の実績(git 側で ASCII/UTF-8 として送られてくる)であり、混同しないこと。**

**3. heredoc の実装バグ: 転送されたファイルの末尾に、実在しない余分な空行が1行増えていた。** `content`(ファイルの中身、末尾に改行を1つ持つ)と終端マーカーの間の結合で改行が二重になっていたため。RPG III の固定形式コンパイラーはこの余分な空行を `QRG2001`(Form-Type entry invalid)として拒否した。`verify/lib/batch.mjs` を修正(`heredocWrite` が `content` 末尾の改行を1つ取り除いてから結合する)。**この修正前から存在した、教材ソース中の唯一の実例**(`solutions/05-13/za0500-ticket3.rpg` の末尾に本物の空行があった)も直接削除して修正済み。

**4. PUB400 の `QDECFMT`(SQL の小数点)はコンマである(ドイツ語圏ホスト)。** `SUBSTR(x,1,200)` のようにコンマの直後へ数字を続けて書く SQL は、コンマが小数点として解釈され `SQL0104`(不正なトークン)になる。一次資料 `cl_commands_75.txt` 4583-4600行目(`RUNSQL` の `Decimal point` パラメーターの注記)で確認済み。`docs/style-guide.md` に恒久的な注意を追記した(第6部の埋め込みSQL・第8部のDDL・第9部のSQLルーチンで必ず守ること)。

## 第6部の実機検証: `part06-0103-freeform`(確認日 2026-09-26)

## TXCHECK v1 の実機検証(確認日 2026-09-26、`part05-txcheck-probe`)

TXCHECK(`tools/qclsrc/txcheck.clp`、v1スコープ: オブジェクト存在・型のみ
`CHKOBJ`)を、`TXCKM`(マニフェスト表、`tools/qddssrc/txckm.pf`)への
自己参照1行(`TXCKM`自身が`*FILE`として存在するかを`CHKOBJ`で確認)で
初めて実機検証した。**3回の接続を要した(2件の実バグを発見・修正)**が、
3回目で完全にクリーンな成功を確認: `TXCKM`(DDS、メッセージ0件)・
`TXCHECK`(CL、Maximum error severity 00)ともにコンパイル成功、
実行結果は`TXCHECK PASS: TXCKM manifest exists (self-check)` /
`TXCHECK: lesson TEST01 - 1 passed, 0 failed`と期待どおり。

**発見1**: DDSの`UNIQUE`キーワードはファイル・レベルであり、`R`
レコード様式行より**前**に置く必要がある(`K`キー指定の後に置くと
`CPD7486`「キーワードの水準が不正」で失敗)。**さらに、桁位置は
キーワード欄(45桁目、`TEXT()`等のレコード・レベル/フィールド・
レベルのキーワードと同じ)であり、19桁目(名前欄)ではない**
(19桁目に置くと`CPD7420`/`CPD7401`/`CPD7914`で失敗する)。

**発見2**: `DCLF FILE(...)`で開いたデータベース・ファイルを閉じる
CLコマンドは`CLOSE`(`OPNID`パラメーター)であり、`CLOF`
(`FILE`パラメーター)という組み合わせは存在しない(`CPD0043`)。
`DCLF`で`OPNID`を省略すると既定値`*NONE`になり(IBM Docs確認済み)、
`CLOSE OPNID(*NONE)`で対応する。

**影響**: TXCHECKがIssue #6〜#10それぞれの完了条件C5(「TXCHECK
(相当)の実行を含めた」)の前提として使えることが確定した。
`work/design/part08-design-v1.md`の08-08節にあった
`blocked-pending-TXCHECK-verification`は解消してよい。
