## 1. 応答なしの照会メッセージが非対話ジョブを無期限に止める

**確認状況: 実機確認**(`docs/probes.md`。TXSETUP 自身が実際に数十分〜数時間ハングした)

**症状**: バッチ・ジョブや、SSH 経由の `system()` 呼び出しが、成功も失敗のメッセージも返さず、何分待っても(90秒どころか数分〜数十分待っても)応答が返ってこない。

**原因**: 未処理(`MONMSG` の対象外)のエスケープ・メッセージが `CPF9999`(機能検査)に格上げされ、さらに `C`/`D`/`I`/`R` などの応答を求める**照会メッセージ**(`CPA0701`)になる。あるいは、RPG が独自に出す照会メッセージ(`RPG1216`=暗黙オープン失敗、`RPG0102`=ゼロ除算)がそのまま出る。**対話的な画面を持たない非対話ジョブには、この問いに答えられる相手がいないため、ジョブはここで無期限に待ち続ける。**

このリポジトリー自身のツール `tools/qclsrc/txsetup.clp` が、まさにこれで実際にハングした。`ADDPFM` の失敗メッセージ ID を `CPF7302` だと思い込んで `MONMSG` していたが、実際には `CPF7306` だったため捕まえられず、`CPF9999` → `CPA0701`(`(C D I R)` の応答待ち)へと格上げされて止まった。

**確認**: `WRKACTJOB`(**自分のジョブに限定する**。他ユーザーのジョブは絶対に見ない)でハングしているジョブを見つけ、`DSPJOB OPTION(*PGMSTK)` でコール・スタックを、`DSPJOBLOG` でメッセージ履歴を確認する。SSH の接続自体が切れていても、ジョブが PUB400 側で動き続けていれば、後から `WRKSPLF`/`DSPLOG` でジョブ・ログを読める。

**対処**:

- `CPF` 系のエスケープ・メッセージには、プログラム冒頭の `DCL` 群の直後に **`MONMSG MSGID(CPF0000) EXEC(GOTO CMDLBL(FAILSAFE))`** を1行置く(実機確認済み。この安全網により、以後同種の見落としがあっても無期限ハングではなく即時終了になる)。
- ただし **`RPG1216`/`RPG0102` のような RPG 独自の照会メッセージは `CPF` で始まらないため、CL 側の `MONMSG MSGID(CPF0000)` では捕まえられない**(`src/legacy/qclsrc/mn0000c.clp` のヘッダー・コメントが明記)。RPG 自身の `*PSSR`(標準エラー処理サブルーチン)も、ファイル・オープンのような初期化段階のエラーには効かないことが実機で確認されている。これらは事後に捕まえるのではなく、**そもそも発生させない**しかない: `RPG1216` は同じジョブの中で `ADDLIBLE` するかライブラリー修飾する([04-06](../part04/04-06-sequential-read.md))、`RPG0102` は `DIV` の前に `COMP` で除数がゼロでないか確認する([04-12](../part04/04-12-debugging-runtime-errors.md))。
- `SBMJOB` には `INQMSGRPY(*DFT)`(照会メッセージに既定の応答を自動的に返す)を付けておくと、`MONMSG` で捕まえられない種類の照会メッセージが来ても、少なくとも無期限ハングだけは防げる。**`INQMSGRPY(*DFT)`自体の効果(既定の応答を自動的に返し、ハングを防ぐこと)は実機確認済みである**(harness-selftestで`RPG0102`への自動応答`C`を確認、`part05-lesson-decimal`でも`RPG0907`の照会メッセージに対して同じ`INQMSGRPY(*DFT)`込みの`CHGJOB`が実際に機能したことを確認)。**ただし`SBMJOB`コマンドそのものの書式(実際に`SBMJOB`から投入する形)は、本教材ではまだ実機確認できていない**([03-12](../part03/03-12-batch-jobs.md) 実機メモ、P15)。また既定の応答が必ずしも「処理を継続する」側とは限らない点にも注意([05-06](../part05/05-06-reading-opnqryf-sndrcvf.md))——今回の`RPG0907`照会も、既定の応答は`C`(取消)であり、プログラムはそのまま異常終了した。

**関連レッスン**: [03-06](../part03/03-06-monmsg-1.md), [03-07](../part03/03-07-monmsg-2.md), [03-12](../part03/03-12-batch-jobs.md), [04-06](../part04/04-06-sequential-read.md), [04-12](../part04/04-12-debugging-runtime-errors.md), [05-06](../part05/05-06-reading-opnqryf-sndrcvf.md), [docs/probes.md](../probes.md), `tools/qclsrc/txsetup.clp` のヘッダー・コメント。

## 2. *LIBL 無修飾参照の罠

**確認状況: 実機確認**([04-06](../part04/04-06-sequential-read.md) の実際のハング原因、`docs/probes.md`)

**症状**: 同じプログラムなのに、コンパイルした直後の同じセッションで `CALL` すると正常に動くが、後で別の SSH セッション・`system()` 呼び出し・新しいジョブから呼ぶと `CPF4101`(ファイルが見つからない)などで失敗する、またはハングする。

**原因**: DDS ソースのライブラリー名を焼き込みたくない設計上、F仕様書のファイル名や `PFILE()` キーワードなどは無修飾で書かれていることが多い。無修飾のオブジェクト参照は `*LIBL`(ライブラリー・リスト)で解決されるが、**`*LIBL` はジョブごとの状態**であり、コンパイルしたジョブと実行するジョブとで中身が違うことがある。特に PASE の `system()` は呼び出しのたびに別ジョブになるため、`ADDLIBLE` の効果は次の `system()` 呼び出しには持続しない。

**確認**: `WRKLIBL` で、実行時のジョブの `*LIBL` に対象ライブラリーが入っているかを確認する。

**対処**: ライブラリー修飾する(`CALL PGM(lib/prog)`)、または `ADDLIBLE LIB(lib) POSITION(*FIRST)` してから**同じジョブの中で** `CALL` する。ライブラリー・リストを変更してから使う処理は、必ず1つの CL プログラム(1つのジョブ)の中で完結させる。

**関連レッスン**: [04-06](../part04/04-06-sequential-read.md), [04-09](../part04/04-09-update-lock.md)(演習の注意書き), [05-09](../part05/05-09-add-field-level-check.md), [docs/probes.md](../probes.md)。

## 3. RTVJOBA USER() が QUSER を返す(SSH/system() 固有)

**確認状況: 条件付き確認**(SSH/`system()` 経由でのみ確認。`docs/probes.md`)

**症状**: SSH 経由で実行したときだけ、実際にログインしたユーザー名ではなく `QUSER` を前提にホーム・ディレクトリーやパスが組み立てられ、存在しないパスを探しに行って `CPFA0A9`(オブジェクトが見つからない)のようなエラーになる。5250 の対話的セッションで同じ現象が起きるかどうかは未確認。

**原因**: `RTVJOBA USER(&VAR)` は「ジョブ名のユーザー部分」を返す。PASE の `system()` が起動するジョブは名前が `QUSER` になるため、常に `QUSER` が返る。実際にサインオン(または SSH 認証)した「現在のユーザー・プロファイル」が欲しい場合は、**`RTVJOBA CURUSER(&VAR)` を使う必要がある。**

**確認**: 診断用の小さな CL プログラムで `RTVJOBA USER(&A) CURUSER(&B)` の両方を実行し、`&A`/`&B` をジョブ・ログに出して比較する(このリポジトリーでの実測: `USER=[QUSER]` / `CURUSER=[<USER>]`)。

**対処**: `CURUSER` を使う。`tools/qclsrc/txsetup.clp`/`txreset.clp` はこの修正を実機で確認済み(修正後、`~/ibmi-kyozai` への実クローンからの通し実行まで完走)。

**修正済み・実機確認済み(2026-09-26、ソース・本文とも)**: `src/qclsrc/setenv.clp`([03-11](../part03/03-11-custom-commands.md))と `src/qclsrc/juyakc.clp`([03-13](../part03/03-13-batch-practice-juyakc.md))も `RTVJOBA CURUSER(&USRPRF)` に直した(レッスン本文中のソース掲載箇所も同時に更新済み)。`verify/part03-rtvjoba-fix` で実機検証済み: `SETENV *DEV` を実際に CALL し、正しいカレント・ライブラリー値(`SETENV: now *DEV (curlib=...)`)が出力されることを確認した。5250 の対話的コマンド行からの違いは未確認のまま。

**関連レッスン**: [02-05](../part02/02-05-txsetup.md), `docs/probes.md`(この節の一次情報源)。

## 4. CRTPF/CRTLF/CRTSRCPF には REPLACE パラメーターが無い

**確認状況**: 設計レビューで発見(実機での予期しない失敗としては未観測)

**症状**: `CRTDSPF`/`CRTPRTF`/`CRTRPGPGM`/`CRTCLPGM` などと同じ感覚で `REPLACE(*YES)` を付けて `CRTPF`/`CRTLF`/`CRTSRCPF` を書くと、コンパイル時にパラメーター・エラーになる。

**原因**: `CRTPF`/`CRTLF`/`CRTSRCPF` は、`CRTDSPF`/`CRTPRTF`/`CRT*PGM` 系とは別のコマンド・ファミリーで、そもそも `REPLACE` パラメーター自体を持たない。この事実は、このセッションでのコード・レビュー(git 履歴 `326dabe`)で確認され、`tools/qclsrc/txmigr.clp` のコメントにも明記されている。

**対処**: `CHKOBJ` + `MONMSG MSGID(CPF9801) EXEC(CRTxxx ...)` による「無ければ作る」パターンを使う。既存オブジェクトがあれば何もしない(`tools/qclsrc/txsetup.clp`・`txlegacy.clp`・`src/qclsrc/c0511s.clp` の定番パターン)。

**「DLTF してから作り直す」は無条件には安全ではない**: `tools/qclsrc/txmigr.clp` は一度 `DLTF` してから `CRTLF` する方式を試みたが、直後のコミット(`67a92f3`)で取り消された。理由は、`DSPDBR OUTPUT(*OUTFILE)` が返す `WHFILE`/`WHLIB` 項目が「依存する論理ファイル」を指しているのか、それとも「参照元の物理ファイル自身(`JUCHUM`)」を指しているのかが、まだ実機で確認できていなかったため。もし後者だった場合、`DLTF` は移行したばかりの `JUCHUM` 物理ファイルとその実データを誤って消してしまう。**削除対象が何であるか確信が持てるまでは、`CHKOBJ` + 条件付き作成を優先し、`DLTF` を伴う方式は避ける。**

**関連レッスン**: `tools/qclsrc/txmigr.clp`・`txsetup.clp`・`src/qclsrc/c0511s.clp` のコメント、git 履歴(`326dabe`・`67a92f3`)。

## 5. CASxx と CABxx の取り違え

**確認状況**: 設計レビューで発見(実機コンパイルで実際に失敗させたわけではない)

**症状**: 分岐のつもりで書いた行が期待通りに動かない、または意図した「サブルーチンを呼ぶ」という動作にならない。

**原因**: `CABxx`(Compare And Branch)は結果フィールド(43〜48桁目)に **`TAG` ラベル名**を書く。`CASxx`(Conditionally invoke a SubRoutine)は結果フィールドに **`BEGSR`/`ENDSR` で定義したサブルーチン名**を書き、`CASxx` の並びは **`ENDCS` で閉じる**必要がある。両者は見た目がよく似ているため取り違えやすい。

このリポジトリー自身の `za0500.rpg` に実例がある。`DOLIVE` は(サブルーチンではなく)ただの `TAG` なのに、当初は `CASEQ` が使われていた。2026-09-26 のレビュー(RPG/400 Reference との突き合わせ)で発見され、`CABEQ` に修正された。**これは実機コンパイルで実際にエラーを起こして見つけたものではなく、コンパイルする前のコード・レビューで発見・修正されたものである**点に注意。

**対処**: 覚え方は「`CASxx` は S(SubRoutine)、`CABxx` は B(Branch = `TAG` へ分岐)」。分岐先が `TAG` か `BEGSR` かを見れば、どちらが正しいか分かる。

**関連レッスン**: [05-02](../part05/05-02-reading-old-opcodes.md), [05-03](../part05/05-03-reading-cycle-programs.md), git 履歴(`326dabe`)。

## 6. /COPY で共有フィールド定義を取り込んだときの名前衝突

**確認状況**: 設計レビューで発見・`part05-legacy-probe`/`part05-qcmdexc-runtime`で実機確認済み(`za0510.rpg`自身、Highest Severity 00でコンパイル)

**症状**: `/COPY` した共通フィールド定義メンバーと、外部記述ファイルの両方に同じ名前のフィールドがあるとき、型・長さ・小数桁数が**完全に一致していると、コンパイルは何のエラーも出さずに通ってしまう。**

**原因**: RPG/400 Reference のフィールド名規則は「同じ名前は、型・長さ・小数桁数がすべて同じである限り、複数の定義に使ってよい(すべて同じ記憶域を指す)」というものである。つまり一致している場合は**衝突として検出されない**。結果として、意味の異なる2つのフィールドが同じ記憶域を共有してしまい、片方への代入がもう片方の値を黙って上書きする。これは「コンパイルが失敗する」よりも危険な、静かなデータ事故になる。

このリポジトリーの `za0510.rpg` は、まさにこの状況(`ZAIKOM` の `ZASHO`/`ZASU` と、`/COPY` で取り込む `FLDREFR` の `CMNFLD.ZASHO`/`ZASU` が型・長さとも完全一致)を設計段階で見つけ、片方を I 仕様書のフィールド改名(21〜30桁目に外部名、53〜58桁目に新しい名前)で `ZKSHO`/`ZKSU` にリネームして衝突を回避している。

**対処**: `/COPY` で取り込む前に、外部記述ファイルのフィールド名と、型・長さ・小数桁数を突き合わせる。一致するものがあれば、片方を I 仕様書のフィールド改名でリネームする(6文字を超える外部名の改名と同じ仕組み。下記7も参照)。

**関連レッスン**: `src/legacy/qrpgsrc/za0510.rpg` のヘッダー・コメント、[05-04](../part05/05-04-reading-arrays-ds-error.md), [05-10](../part05/05-10-screen-field-and-crossfile.md)(改名の桁位置)。

## 7. RPG III の6文字シンボル制限と rpg3.mjs の桁書き込み

**確認状況**: 実機確認(UPDATE/UPDAT の実例)+ 設計レビューで発見(SKIPUPD/SKPUPD の実例)

**症状**: 命令コードやラベル名(`TAG`)を6文字(命令コード欄は5文字)を超えて書いても、コンパイラーが必ずエラーにしてくれるとは限らない。桁がずれた状態のまま、**たまたま動いてしまう**ことがある。

**原因**: RPG III のフィールド名・シンボル名は6文字までという制約がある。このリポジトリーの生成器 `tools/gen/rpg3.mjs` の `put()` ヘルパーは、与えられた文字列を指定した列から書き込むだけで、その項目の本来の幅を超えていないかのチェックを行わない。**幅を超えた分は、後続の桁(次の項目の列)にそのまま上書きされる。**

実例が2つある。

1. **実機で実際に踏んだケース**: 命令コード欄(28〜32桁目、5桁)に6文字の `UPDATE` を書いたところ、6文字目の `E` が Factor 2 の1文字目に重なった。ところが、その後の処理が同じ桁に Factor 2 の内容を書き込んだため、結果的に正しい `UPDAT` + Factor2 の形になり、**たまたま正しくコンパイル・実行できてしまった。** これに気づいたのは、生成コードを目視で再点検したときだった。正しくは、明示的に5文字の `UPDAT` と書く。
2. **実機で試す前にレビューで発見したケース**: 7文字の `TAG` 名 `SKIPUPD` を、コンパイルする前に6文字の `SKPUPD` に修正した。

**対処**: RPG III 向けの命令コード・シンボル名は、必ず6文字(命令コード欄は5文字)以内に収める。`rpg3.mjs` は幅超過を検出してくれないので、生成前に文字数を数える。

**関連レッスン**: [docs/probes.md](../probes.md)(`UPDATE`/`UPDAT` の実機記録), git 履歴(`326dabe`、`SKPUPD` への改名), `tools/gen/rpg3.mjs`, [02-01](../part02/02-01-db-design.md), [04-01](../part04/04-01-first-program.md)。

## 8. CPYF FMTOPT(*NOCHK) による10進データ破壊

**確認状況**: 実機確認(`part05-lesson-decimal`・`part05-decimal-screen`・`part05-mch1202-corrupt`)

**症状**: 型の違うファイル間の `CPYF` が `FMTOPT(*NOCHK)` によってエラーなく完了する。ずっと後になって、**別のプログラムがそのデータを読み込む・演算しようとしたときに初めて** 10進数データ・エラー(`RPG0907`)で異常終了する。呼び出し元が広い範囲の `MONMSG`(`CPF0000` 等)でエラーを飲み込んでいると、ジョブ・ログの**最後の行だけ**を見た場合「無事に終わった」ように見えてしまうことがある。

**原因**: `FMTOPT(*NOCHK)` はレコード様式間の型チェックを省略する。ゾーン10進数として無効なバイト列がそのままフィールドに入り込む。**ただし「見た目が壊れている」ことと「実際にエラーになる」ことは別物**: 実機で試した3パターンの範囲では、エラーになるかどうかを決めるのは**数字ニブル(各バイトの下位4ビット)が0〜9の範囲に収まっているかどうか**だった。`'ABCDE'`(EBCDIC、数字ニブル1〜5)や空白5個(数字ニブル0)は、どちらも数字ニブルが有効な範囲に収まっているため、`JUSU=12345`/`JUSU=0`として**エラーなく黙って読み込まれる**。一方、`'.....'`(ピリオド5個、数字ニブルB=無効)は、レコードを読み込む**入力段階**(I仕様書によるフィールド変換時、算術演算より前)で確実に `RPG0907` を起こす。

**確認**: `QPJOBLOG` で失敗したプログラム名・行番号を確認し、ソースの該当行と突き合わせる。`HEX(列名)` で実際のバイト値を確認する(壊れた行と正常な行を見比べる)。**ジョブ・ログは最後の行だけでなく、遡って読む**(「JU0900C: ZA0500 ended abnormally.」のような1行の完了通知の**前**に、本当の原因が埋もれていることがある)。**SQLの`SELECT`はRPGより緩い変換規則を持ち、数字ニブルが無効な値も一切エラーにせず`0`として黙って読んでしまう**——SQLでの動作確認だけでは、RPGが実際にどう振る舞うかの信頼できる予測にはならない。

**対処**: 原因データを直す(このリポジトリーでは `TXRESET`)。呼び出し元の `MONMSG` が広すぎて本当のエラーを握りつぶしていないかも合わせて確認する。

**関連レッスン**: [05-11](../part05/05-11-decimal-data-error.md), [05-12](../part05/05-12-promote-and-rollback.md)(復習問題)。

## 11. SQL0443 は本当の理由を覆っている

**確認状況: 実機確認**([08-06](../part08/08-06-dds-to-sql-ddl.md) の失敗の経緯。[09-05](../part09/09-05-external-api-adapter-mock.md) でも別の呼び出しで再発。09-05 側の原因は未確認)

**症状**: 外部ルーチン(`QSYS2.GENERATE_SQL` や `QSYS2.GET_CLOB_FROM_FILE` など)を呼ぶと、`SQL0443`(Trigger program or external routine detected an error)としか表示されず、具体的な理由が分からない。引数を直しても同じメッセージで止まる。

**原因**: `SQL0443` は「外部ルーチンの内部でエラーが起きた」を表す汎用メッセージで、それ自体は何も教えてくれません。08-06 では、同じ呼び出しを詳しい診断が出るインターフェースで試したところ、ネイティブ・エラー・コード `-443` とともに `DATABASE_OBJECT_TYPE NOT VALID` という具体的な理由が返ってきました(`docs/probes.md`「`part08-06-lvlid-and-gensql`」)。

**確認**: 汎用メッセージの1行だけで原因を推測せず、ジョブ・ログの他のメッセージ(09-05 では `CPF503E` が一緒に出た)や、詳細を返すインターフェースで同じ呼び出しを試す。引数のどれかを疑う前に、まず「値が有効か」を確かめる。

**対処**: 08-06 の場合は、`'*FILE'` を疑わずに使い続けたことが、2回の `SQL0443` の真因だった可能性が高いとされています。**同じ汎用エラーで2回続けて止まったら、直した箇所ではなく、直していない前提を疑う。**

**関連レッスン**: [08-06](../part08/08-06-dds-to-sql-ddl.md), [09-05](../part09/09-05-external-api-adapter-mock.md), [docs/probes.md](../probes.md)。

## 12. QTEMP はジョブ単位(qsh の system() 呼び出しごとに別ジョブ)

**確認状況: 条件付き確認**(`system()` が呼び出しごとに別ジョブになる点は [第9部 index](../part09/index.md) の実機確認、`QTEMP` がジョブ・スコープである点は [08-08](../part08/08-08-checkpoint-promote-rollback.md) の本文。5250 の対話ジョブでの違いは未確認)

**症状**: ある呼び出しで `QTEMP` に作ったオブジェクトが、次の呼び出しでは見つからない(オブジェクトが見つからないエラー)。`ADDLIBLE` した効果も次の呼び出しに残らない(上の「2. *LIBL 無修飾参照の罠」と同じ)。

**原因**: `QTEMP` は**ジョブ・スコープ**です。qsh(PASE)の `system()` は1回呼ぶごとに別ジョブになるため、1回ごとに `QTEMP` も `*LIBL` も新しくなります([2. *LIBL 無修飾参照の罠](#2-libl-無修飾参照の罠)と同じ仕組み)。サインオフすると `QTEMP` の中身は消えます(一般知識、要確認)。恒久的なライブラリー(`<USER>B` など)はジョブ・スコープではありません。

**確認**: 同じ CL プログラムの中(1つのジョブ)で作成と使用を完結させているかを見る。別々の `system()` 呼び出しに分かれていないかを確認する。

**対処**: `QTEMP` を使う一連の処理は、1つの CL プログラム(1つのジョブ)の中に入れる。呼び出しをまたいで残したいものは、`QTEMP` ではなく恒久的なライブラリーに置く(08-08 が控えを `<USER>B` に置いた理由)。`RMVLIBLE` で現行ライブラリーを外そうとすると `CPF2104` になる、という点も 05-12 で確認済みです([第9部 index](../part09/index.md)参照)。

**関連レッスン**: [08-08](../part08/08-08-checkpoint-promote-rollback.md), [05-12](../part05/05-12-promote-and-rollback.md), [第9部 index](../part09/index.md)。

## 16. RPG III の突合せで RPG1031(到着順の食い違い)

**確認状況: 実機確認**(`part05-13-pssr`、確認日 2026-09-27。`docs/probes.md`)

**症状**: マッチ・フィールド(M1/MR)を使う RPG III プログラムが、`RPG1031`(match field is out of sequence)で止まる。ジョブ・ログには `Function check. RPG9001` が続く。

**原因**: RPG III のマッチ処理は、両ファイルが**同じ昇順**であることを前提にします。F仕様書でキー順を指定していないプログラム記述ファイルは**到着順**で読まれます。そこへキー順に並んだヘッダー行(`C05119` のような値)を末尾に追加すると、片方のファイルでは先頭、もう片方では末尾になり、サイクル自身が順序の矛盾を検出して止まります。**計算仕様書に到達する前の、サイクルのレコード取得段階のエラーです。**

**確認**: ジョブ・ログの `RPG1031` の直前のメッセージ(どのファイルのマッチ・フィールドか)を読む。両ファイルのキー順(`OPNQRYF` の順序指定・F仕様書のキー指定の有無)を突き合わせる。

**対処**: 突合せに使う両ファイルの並び順を揃える(データの追加位置を到着順に合わせる、または対象を1行に絞る)。テスト用データでは、キー順に並んだ行を到着順のファイルの途中や末尾に足さない。

**関連レッスン**: [05-03](../part05/05-03-reading-cycle-programs.md)(`RPG1031` の説明), [05-13](../part05/05-13-checkpoint-tickets.md), [docs/probes.md](../probes.md)。

## おまけ: 本文の依頼にはなかったが、実際に確認済みのパターン

以下は、上記の各件ほど大きくは扱われていないものの、`docs/probes.md` に実機確認の記録がある、実際に役立つパターンです。

### おまけ: 32バイト未満の CALL PARM リテラルが化ける

**確認状況**: 実機確認

**症状**: `CALL PGM(...) PARM('短い文字列')` のように、宣言長より短い文字リテラルを渡すと、受け取り側の変数の後半に、意図しない別の値の断片が残る(例: `CPD018A` パス名にヌル文字、のような形で表面化する)。

**原因**: コマンド行(および `system()` 経由の呼び出し)から渡す文字リテラルは、**32バイトまでしか空白で埋められない。** 宣言長がそれを超えていると、33バイト目以降は埋められず、直前・直後に渡した別の値の断片がそのまま残る。

**対処**: 宣言長ぴったりに空白パディングして渡すか、値を省略して内部の既定値計算に任せるか、`*CMD` ラッパー経由で渡す。`*CMD` 経由のパラメーター構築は必ず宣言長ぴったりに行われるため、この罠が原理的に起きない(`tools/qcmdsrc/` の設計、実機確認済み)。

**関連レッスン**: [03-08](../part03/03-08-parameters-and-call.md), [docs/probes.md](../probes.md)。

### おまけ: 出力が2倍になる謎はデータの重複だった

**確認状況**: 実機確認

**症状**: プログラムのロジックを何度書き換えても(`IFxx` → 条件標識 → 無条件出力)、結果が正確に整数倍(この実例では2倍)になる。

**原因**: プログラムではなく、参照しているテーブルの**実データ自体に重複行**が入っていた。

**確認**: プログラムのロジックを疑う前に、まず SQL で実データの件数・内容を直接確認する。

**対処**: このリポジトリーでは、ツール(`TXSETUP`)が初期データ投入を毎回無条件に `INSERT` していたことが原因だった(`FORCE(*YES)` の複数回実行で積み上がった)。データ投入コマンドの前に必ず全件 `DELETE` するよう修正して解決した。

**教訓**: 「出力がおかしい」と思ったら、まずロジックではなくデータを疑う。

**関連レッスン**: [docs/probes.md](../probes.md)(04-08 JUCINQ3 の節)。

### おまけ: SSH だけが不通になる(5250 は生きている)

**確認状況**: 実機確認

**症状**: 認証には一度も失敗していないのに、あるタイミングから突然 SSH(2222番)にまったく接続できなくなる。

**原因**: 短時間に多数(目安10回超)の SSH 接続を行ったことによる、同一 IP からの接続数制限とみられる。

**確認**: `Test-NetConnection` 等で、5250(992番、TLS)や HTTPS(443番)には別途疎通できる場合がある。

**対処**: 1回の接続でまとめて作業する。目安として10回を超えたら、大きく間隔を空けるか、その日はそれ以上 SSH 接続をしない。SSH が使えない間は、5250 で進められるレッスンに切り替える。

**関連レッスン**: [docs/probes.md](../probes.md)。

### おまけ: WORKSTN/EXFMT の SSH ハングは照会メッセージとは別物

**確認状況**: 実機確認(コンパイルまで)。対話的実行そのものは検証範囲外

**症状**: `EXFMT` を使うプログラムを SSH 経由で `CALL` すると、応答なくハングする。

**原因**: 上記「1. 応答なしの照会メッセージ」とは**別の原因**である。`WORKSTN` ファイルの `OPEN` は実際の5250デバイスを要求するため、対話的デバイスがそもそも存在しない SSH/`system()` 経由の非対話バッチでは、応答を待ち続けることになる。

**確認**: このセッションの SSH(PASE `system()` 経由の非対話バッチ)では、`EXFMT` を含む対話的実行そのものを検証できない、という制約として理解する。`CRTDSPF`/`CRTRPGPGM` のコンパイルが Highest Severity 00 であることまでは実機確認できている。

**対処**: 対話的な画面を伴うプログラムは、必ず学習者自身の5250セッションで実行・確認する。
