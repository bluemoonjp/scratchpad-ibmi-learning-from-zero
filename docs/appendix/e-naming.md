# 付録E 命名規則

この教材の第0部〜第9部のレッスンで実際に使われている名前から集めています。第10部(総合演習)で加わる名前も、第10部の名前として区別して載せています(第10部の本文は書き終えています。各レッスンの実機メモの日付は2026-09-30です)。

この教材には、性格の異なるいくつかの命名規則が同時に存在します。「なぜこのオブジェクトはこう呼ばれているのか」「自分で新しいオブジェクトを作るとき、何にならえばよいか」で迷ったときに、この付録を参照してください。実際のソース(`tools/`・`src/`・`db/`)から拾った、この教材が現に使っている規則だけを載せています。

## 1. `<USER>`/`<USER>1`/`<USER>2`/`<USER>B` — ドキュメント上の匿名化表記

PUB400.com のアカウントには、標準で3つのライブラリーが割り当てられます([01-04](../part01/01-04-objects-and-libraries.md))。

| ライブラリー | 役割 |
|---|---|
| `<USER>1` | 現在の開発用。この教材では主にここを使う |
| `<USER>2` | 本番役(第5部以降で使う) |
| `<USER>B` | 保存ファイル(バックアップ)の置き場 |

このライブラリー名は、実際には**自分の PUB400 ユーザー名の末尾に `1`/`2`/`B` を付けたもの**です。この教材の文章中では、実在のユーザー名を一切書かず、`<USER>`(ユーザー名そのもの)・`<USER>1`・`<USER>2`・`<USER>B` というプレースホルダーで表します。**これはこの教材が採用しているドキュメント上の匿名化の約束事であり、IBM i や PUB400 自体の仕組みではありません。** 実際の画面には `<USER>1` ではなく、自分の本当のユーザー名+`1` が表示されます。

この規則は書く側にも適用されます。演習の解答例やスクリーンショットの説明などで実在のユーザー名を書かないこと、パスワードやアカウント名を質問や画面キャプチャに含めないことは、[付録G](g-getting-help.md) でも触れているとおりです。

## 2. サンプル・データベース(`db/`)のオブジェクト名

第2部で導入される一貫したサンプル・データベース([02-01](../part02/02-01-db-design.md))は、6つの物理ファイルと2つの論理ファイルからなります。

| ファイル | 種別 | 内容 | 様式名 |
|---|---|---|---|
| `TANTOM` | PF | 担当者マスタ | `TANTOR` |
| `TOKUIM` | PF | 得意先マスタ | `TOKUIR` |
| `SHOHIM` | PF | 商品マスタ | `SHOHIR` |
| `JUCHUM` | PF | 受注マスタ | `JUCHUR` |
| `JUCHUD` | PF | 受注明細 | `JUCHDR` |
| `ZAIKOM` | PF | 在庫マスタ | `ZAIKOR` |
| `TOKUIL1` | LF | 得意先マスタの論理ファイル1号 | `TOKUIR`(PF と共通) |
| `JUCHUL1` | LF | 受注マスタの論理ファイル1号 | `JUCHUR`(PF と共通) |

読み取れる規則は次のとおりです。

- **業務名(ローマ字)+ 用途を表す1文字。** `TANTO`(担当)・`TOKUI`(得意先)・`SHOHI`(商品)・`JUCHU`(受注)・`ZAIKO`(在庫)という業務略称に、マスタ・ファイルなら `M`、明細ファイルなら `D` を付けます。
- **フィールド名はすべて6文字以内。** 第4部で学ぶ RPG III の制約(シンボル名は6文字まで)に合わせてあります。唯一 `TANTOM` だけが「他システム由来」という設定で、わざと6文字を超えるフィールド名(`TANTOCODE`・`TANTONAME`)にしてあり、第5部の保守レッスン([05-02](../part05/05-02-reading-old-opcodes.md)、[05-10](../part05/05-10-screen-field-and-crossfile.md))で、この名前を RPG III の I 仕様書で改名して扱う練習をします。
- **様式(レコード・フォーマット)名はファイル名と別に付ける。** 慣習として、ファイル名の末尾の文字を `R`(Record)に変えたものにします(`TOKUIM`→`TOKUIR`、`ZAIKOM`→`ZAIKOR`)。同じ様式名になってしまう場合は綴りを詰めて回避します(`JUCHUD` は `JUCHUR` が `JUCHUM` に取られているため `JUCHDR` にしてあります)。論理ファイルは基になる物理ファイルと同じ様式名をそのまま使います(`JUCHUL1` も `JUCHUR`)。
- **論理ファイルは `L` + 番号。** `TOKUIL1`・`JUCHUL1` はどちらも `L1` で、[02-08](../part02/02-08-logical-files.md) では「その物理ファイルに対する論理ファイル」とだけ説明され、番号自体の意味は明文化されていません。この教材では各物理ファイルに論理ファイルが1つしかないため、恐らく「1番目の論理ファイル」という単純な通し番号だと考えられますが、断定はできません(将来 `L2` が増える可能性への備え、という程度の意味でしょう)。

### バージョン・ディレクトリー(`db/v1`・`db/v2`)とDBVER

このリポジトリー自身は、サンプル DB のスキーマ変更を `db/v1/`・`db/v2/` というディレクトリー名で管理しています。各ライブラリーには `TXSTATE`(`*DEC(3 0)` のデータ域)を持たせ、「そのライブラリーが今 DBVER いくつの状態か」を記録します。`TXSETUP` が `DBVER=1` で作成し、`TXSTATUS` が `RTVDTAARA` で読んで `TXSTATUS: DBVER=nnnnnnnnnn in library <lib>` の形式で報告し、`TXMIGR` がスキーマ変更を伴う移行(例: [05-09](../part05/05-09-add-field-level-check.md) の `JUCHUM` への `JUDLV` 追加)を行います。

> **既知の抜け:** [05-09](../part05/05-09-add-field-level-check.md) の手順の中で指摘されているとおり、`tools/qclsrc/txmigr.clp` は移行完了メッセージで `DBVER=2` と報告しますが、ソースを読むと実際に `TXSTATE` を書き換える `CHGDTAARA` の呼び出しがありません。**ツール自身の実装漏れであり、`TXMIGR` 実行後は手動で `TXSTATE` を確認・修正する必要があります。** バージョン管理の仕組みそのものを鵜呑みにせず、ソースで裏を取る良い例として覚えておいてください。

## 3. この教材で学習者が作るオブジェクト

### 3.1 部・レッスン番号ベースの名前

第1〜4部、および第5部の一部の演習(例: [05-11](../part05/05-11-decimal-data-error.md) の `C0511S`)でレッスンに沿って作成するプログラムやCLソースの多くは、`<部番号2桁><レッスン番号2桁><変化字1文字>` という形の名前になります。先頭の1文字は言語を表します(`C`=CL、`R`=RPG III)。

| 例 | 意味 |
|---|---|
| `C0301A` | 03-01(CL の基本形)で作る、そのレッスンの主となるCLプログラム |
| `C0107A`/`C0107B`/`C0107C` | 01-07 で作る3つの演習用CLプログラム(同じレッスン内で複数作る場合は `A`・`B`・`C`と続ける) |
| `R0401A` | 04-01(RPG III 最初のプログラム)で作るRPGプログラム |
| `R0408A` | 04-08 で作る `JUCINQ3`(受注照会・帳票版)の実体 |
| `V0421D` | 04-21(第4部V。RPG III を通らないルート)で作る、`R0408A` と同じ出力の固定形式 RPG IV プログラム。第4部V のオブジェクトは `V042x`(学習者用 `A`〜`R`、配布の見本 `S`〜`Z`)、表示装置ファイルは `D0426A` の形 |
| `R0408BA`/`R0408BB` | 04-08b(枝番レッスン)で作る、呼ばれる側(得意先名を返す)と呼ぶ側 |
| `C0511S` | 05-11 で作る、意図的に10進数データ・エラーを仕込むCLプログラム |

**末尾の1文字(変化字)の意味は、レッスンごとにそのつど本文で説明されます。** 全体で固定された意味を持つコードではありません。例えば [03-08](../part03/03-08-parameters-and-call.md) では `C0308T`(呼ばれる側。T=Target)と `C0308S`(安全に呼ぶ側。S=Safe)のように、同じレッスンの中で複数のオブジェクトを区別するために使われています。`JUCINQ3`・`ZAHIK3` のような業務名(この教材を通して繰り返し出てくる通し例の名前)は、あくまで**説明用の呼び名**であり、実際にコンパイルするオブジェクト名は `R0408A` のような部・レッスン番号ベースの名前です(コード中に `CALL PGM(JUCINQ3)` のような形で出てくることはありません)。

**枝番レッスン(`b` の付くもの)では、レッスン番号の後ろに `b` を付け、その後ろに変化字を続けます**(`04-08b` なら `R0408B` + `A`・`B`・`C`…。`Q0614BA` も同じ形です)。04-08b は呼ばれる側と呼ぶ側を組にして作るため、`R0408BA`(呼ばれる側)・`R0408BB`(呼ぶ側)のように、組ごとに隣り合う文字を使います。RPG III の `CALL` の Factor 2 に書くプログラム名(`R0408BA` など)は7文字ですが、Factor 2 の10桁に収まります。

この教材自身のリポジトリーでは、これらのモデル解答のソースを `src/qclsrc/`・`src/qrpgsrc/`・`src/qddssrc/` 配下に、小文字で `<部番号2桁><レッスン番号2桁><接尾字>.拡張子` として保存しています(例: `src/qclsrc/c0301s.clp`、`src/qrpgsrc/r0408s.rpg`)。**1つのレッスンで複数のオブジェクトを作る場合(`c0308s.clp`/`c0308t.clp`、04-08b の `r0408ba.rpg`〜`r0408be.rpg`)は、git 上のファイル名をオブジェクト名そのままの小文字にします。**

この git 上のファイル名の接尾字(多くは `s`)は「このレッスンのモデル解答」という、リポジトリー自身の管理用の印であり、実機で作成するオブジェクトの変化字(`A`・`B`・`T`…)と機械的に一致するとは限りません。** 一方で `C0308S`/`C0308T` のように、たまたま両者が一致することもあります。実機で何と名付けるかは、必ずレッスン本文と `作る・変えるオブジェクト` の記載を確認してください。

### 3.1.1 第6〜7部(RPG IV)での先頭文字

第6部以降、`3.1` の「部・レッスン番号+変化字」という骨格は変わりませんが、先頭の1文字(言語を表す文字)に新しい種類が加わります。

| 先頭文字 | 意味 | 例 |
|---|---|---|
| `D` | DDS(表示装置ファイル、DSPF) | `D0604A`(06-04)、`D0611A`(06-11) |
| `F` | RPG IV `**FREE`(完全自由形式) | `F0603A`(06-03)、`F0612A`(06-12) |
| `P` | DDS(印刷装置ファイル、PRTF) | `P0612A`(06-12) |
| `Q` | SQLRPGLE(埋め込みSQL付きRPG IV) | `Q0613A`(06-13)、`Q0614BA`(06-14b) |
| `V` | 固定形式 RPG IV(`CVTRPGSRC` の変換結果、または第4部V で手書きするもの) | `V0601A`(06-01)、`V0601B`(06-01b)、`V0421D`(04-21)、`V0423D`(04-23) |
| `M` | モジュール(mainを持つ主モジュール) | `M0701A`(07-01) |

これらは `C`(CL)・`R`(RPG III)と同じ、3.1の骨格の延長です。同じレッスンの中で複数のオブジェクトを作る場合の変化字の続け方(`A`・`B`・`C`…)も3.1と同じ規則に従います——例えば06-12は `F0612A`(帳票本体)・`F0612B`・`F0612C`(06-11のオプション5修正のために06-12が新設した、06-11自身のD0611A/F0611Aは変更しないオブジェクト)と続きます。

### 3.1.1b 第8〜9部での先頭文字(`W`・`Z`)と作業表

第8〜9部には、3.1.1の表にない先頭文字も出てきます。[スタイル・ガイド](../style-guide.md)の命名の節では `W`=作業用の PF・LF・表、`Z`=その他、と定めています。

| 先頭文字 | 例 | 使われ方 |
|---|---|---|
| `W` | `W0902A`([09-02](../part09/09-02-sql-json.md)の演習4で作る作業表)、`W0904A`([09-04](../part09/09-04-api-boundary-sql-routines.md)の作業表)、`W0906A`([09-06](../part09/09-06-data-queues-async.md)のログ表) | レッスンの片付けで削除する作業用の表 |
| `Z` | `Z0906A`(要求用データ待ち行列)・`Z0906B`(応答用データ待ち行列)・`Z0906C`(メッセージ・キュー)(09-06) | 種別が PF・プログラム・DSPF のどれでもないオブジェクト(スタイル・ガイドの「その他」) |
| `Q`・`C`・`F` | `Q0805B`(SQLRPGLE)・`C0805B`(CL)・`F0805A`(`**FREE`)([08-05](../part08/08-05-control-level-refactor.md)・[08-05b](../part08/08-05b-matching-records-sql-rewrite.md)) | 3.1.1と同じ規則。`C0906A`(09-06のワーカーCL)も同様 |

第9部の作業表・キューなどは、レッスンごとに片付けで消すオブジェクトです。なお、`APICFG`・`APIMOCK`・`APILOG`([09-05](../part09/09-05-external-api-adapter-mock.md))のように、部・レッスン番号を持たず機能名で付けた表もあります(3.3参照)。

| ルーチン名 | `SPECIFIC`名(=実体のオブジェクト名) | 実体 |
|---|---|---|
| `JUCHU_INQUIRY_JSON`(関数) | `JUCHUINQJS` | `*SRVPGM` |

`SPECIFIC`名が有効なシステム名で、同名のオブジェクトがまだ無い場合にだけ、それが実体の名前になる、と09-04は説明しています。`SPECIFIC`名を付けないと、システムが名前を生成します(その名前の付け方は、この教材では扱っていません)。

**IFS上のリポジトリー名**: [08-01](../part08/08-01-git-project-srcstmf-build.md)・[08-02](../part08/08-02-makei-tobi-build.md)で、`JUCSRV`のプロジェクトは PC 側の`myproject`と IBM i 側の`pub400-bare.git`・`pub400-clone`、`ZAISRV`のプロジェクトは PC 側の`zaiproject`と IBM i 側の`zaisrv-bare.git`・`zaisrv-clone`を使います。`<ユーザー名>`のホーム・ディレクトリー(`$HOME`)の直下に置く自由な名前で、決まった規則はありません(08-01の練習用には`rehearsal-*`もあります)。

### 3.4 第10部(総合演習)で導入される名前

次の名前は**第10部で初めて出てきます**(第0〜9部のレッスンには登場しません)。10-01〜10-04の本文と食い違いがないかを確認した一覧です(2026-09-30)。

## 4. 旧システム(第5部・`src/legacy/`)のオブジェクト名

第5部で保守の題材として使う「旧システム」([05-01](../part05/05-01-legacy-intro.md))は、実際の引き継ぎ現場に近づけるため、**部・レッスン番号を含まない、いかにも古い業務システムらしい名前**にしてあります。

| オブジェクト | 種別 | 業務領域 | 補足 |
|---|---|---|---|
| `TK0100` | RPG III | 得意先(トクイサキ→ TK) | 得意先照会 |
| `TK0100D` | DSPF | 得意先 | `TK0100` の画面 |
| `JU0300` | RPG III | 受注(ジュチュウ→ JU) | 受注一覧(制御レベル `L1`/`L2` を使うサイクル・プログラム) |
| `ZA0500` | RPG III | 在庫(ザイコ→ ZA) | 在庫引当(一致レコード処理) |
| `ZA0510` | RPG III | 在庫 | `ZA0500` の読解用バリエーション(配列・DS・エラー処理を追加したデバッグ演習版) |
| `JU0900C` | CL | 受注 | 在庫引当バッチ・ドライバー(`ZA0500` を呼ぶ) |
| `MN0000C` | CL | メニュー(MeNu → MN) | 旧システム全体の入口メニュー |
| `MN0000D` | DSPF | メニュー | `MN0000C` の画面 |
| `FLDREF` | PF | (共通) | 複数プログラムで使うフィールド定義の DDS 版 |
| `FLDREFR` | RPG III `/COPY` メンバー | (共通) | `FLDREF` と同じフィールド定義を持つ、I仕様書のデータ構造(`/COPY`専用。単体ではコンパイルされない) |
| `JUBADD` | PF | 受注 | 05-11 の演習で `C0511S` が作る、検証用の「型を間違えたステージング・ファイル」(`TXLEGACY` の初回ロードには含まれない) |

上の一覧はレッスンで扱う主なオブジェクトの抜粋であり、旧システムの全部ではありません。なお、一覧の「種別」列の `RPG III` は、`TXLEGACY` を `LANG(*RPG)`(既定の動き)で入れた場合のものです。RPG III を通らないルートでは、`TXLEGACY ... LANG(*RPGLE)` で、`JU0300`・`ZA0500`・`TK0100` が同じ名前の固定形式 RPG IV プログラムとして入ります(未検証(2026-10-01時点))。読み取れる規則は次のとおりです。

- **2文字の業務領域コード + 4桁の番号。** `TK`(得意先)+`0100`、`JU`(受注)+`0300`/`0900`、`ZA`(在庫)+`0500`/`0510`、`MN`(メニュー)+`0000`。番号の付け方自体の規則(なぜ `0100` や `0300` なのか)はレッスン本文では説明されておらず、「長年運用されてきた業務システムらしい、通し番号による命名」という雰囲気を出すための演出と考えられます。
- **末尾の1文字は、その番号に対応するオブジェクトの種別を表す。** 無印(末尾が数字)は RPG III プログラム、`D` は表示装置ファイル、`C` は CL プログラムです。同じ番号を共有することで、「`TK0100` と `TK0100D` は対になっている」ということが名前だけで分かるようになっています。
- **入口はメニュー(`MN0000C`)。** 実際の利用者はメニューから辿り着くため、保守調査もメニューを起点にトレースするのが基本です([05-01](../part05/05-01-legacy-intro.md) の「入口から追う」)。
- **`FLDREF`/`FLDREFR` は番号を持たない例外。** 複数プログラムが参照する共通フィールド定義という性質上、業務領域や号数ではなく役割で名付けられています(`FLDREF` = Field Reference、`FLDREFR` = その RPG 版)。`JUBADD` も、番号を持つ他の旧システム・オブジェクトとは違い、05-11 の演習のためにあとから追加される検証専用ファイルです。

**`TXCHECK` は、同じジョブでは1回だけ実行してください。** 同じジョブ(検証では1つのCLラッパー・ジョブ)で2回目を実行すると `CPF4174` になることが、[08-08](../part08/08-08-checkpoint-promote-rollback.md)・[09-07](../part09/09-07-checkpoint-order-summary-api.md)のバッチ・ジョブで確認されています。5250の対話式ジョブで同じことが起きるかは、未検証です。なお `TXCHKRUN` は、著者側の検証環境で、CLのラッパーの中から `TXCHECK` を `QCMDEXC` 経由で実行するための補助プログラムで(09-07が説明しています)、教材のレッスンとして学習者が作るものではありません。

## 6. RPG III の6文字シンボル名制限と、この教材の生成ツールの注意点

RPG III のフィールド名・変数名・DS名などのシンボル名には、**6文字以内**という制限があります([04-01](../part04/04-01-first-program.md))。この制限は、この教材のサンプル・データベースのフィールド名をすべて6文字以内に揃えた理由そのものであり([02-01](../part02/02-01-db-design.md))、`TANTOM` の `TANTOCODE`/`TANTONAME`(9文字)のように意図的に超えさせた名前は、I仕様書での改名(21〜30桁に外部名、53〜58桁に6文字以内のプログラム内の名前)を経由しないと RPG III の C 仕様書に書けません([05-02](../part05/05-02-reading-old-opcodes.md)、[05-10](../part05/05-10-screen-field-and-crossfile.md))。

**この教材自身のRPG III生成ツール(`tools/gen/rpg3.mjs`)は、この6文字制限を検証しません。** 内部で桁位置に文字を書き込む共通関数は次のように、文字列の長さをまったくチェックせずに書き込みます。

```js
function put(arr, col1, text) {
  for (let i = 0; i < text.length; i++) arr[col1 - 1 + i] = text[i];
}
```

7文字以上の名前を渡しても、コンパイル・エラーにはなりません。**この関数自体は長さをチェックしないので、はみ出した文字は後続の桁位置に静かに書き込まれます。** その桁を後から別の `put()` 呼び出しが上書きすれば結果的に値が切り詰められたように見え、何も上書きしなければ隣の項目がそのまま壊れます(行全体が80桁を超えたときだけ、`finish()` がエラーで止めます)。どちらになるかは、その行のどこに何を書き込む生成コードかに依存します。

この教材では、`FLDREF`(DDS)と `FLDREFR`(RPG III の I仕様書データ構造)というフィールド定義が2か所に手で複製されているため、`scripts/check-fldref-fldrefr-consistency.mjs` という専用の恒久チェック・スクリプトを別途用意し、両者のフィールド名・長さ・型・小数桁が一致していること(6文字制限を含む)を確認しています。このスクリプト自身のヘッダー・コメントによれば、元々は生成時の使い捨てスクリプトに手書きの「6文字以内」チェックがあったものの、生成後にそのスクリプトごと削除されてしまったため、代わりに何度でも再実行できる恒久的なチェックとして書き直されたものです。生成ツール自体には汎用のガードがないので、**新しいRPG IIIソースを `rpg3.mjs` で生成・編集するときは、6文字を超える名前を渡していないか自分で確認してください。**
