# 付録G 助けの求め方

詰まったときに、どこへ何を書けば答えが返ってきやすいかをまとめます。ここに書いてあるのは、[00-01](../part00/00-01-orientation.md)・[00-02](../part00/00-02-pub400-signup.md)、[`CONTRIBUTING.md`](../../CONTRIBUTING.md)、[`SECURITY.md`](../../SECURITY.md) にすでにある約束事です。PUB400 のフォーラムの運用ルールなど、この教材で確認していないことは書いていません(未確認)。

## 1. まず自分で確かめること

質問する前に、次を順に見てください。答えが見つかることが多く、見つからなくても、質問に添える材料になります。

1. そのレッスンの「出会うメッセージ ID」の表と「出力が違うとき」の節。
2. [付録B メッセージ ID](b-message-ids.md)と[付録C トラブル](c-troubleshooting.md)。
3. レッスン末尾の「実機メモ」。**その操作が実機で確認済みか、未検証か**が書いてあります。未検証(V3を含む)の部分で食い違ったときは、教材の誤りではなく、まだ誰も確かめていないだけかもしれません。
4. 画面のメッセージそのもの。5250なら、メッセージにカーソルを置いて `F1`(ヘルプ)を押すと、詳細が出ます(一般知識、要確認。この付録では実機で確かめていません)。

## 2. 相談先

| 相談内容 | 送り先 |
|---|---|
| 教材の記述が実機と食い違う、コードが動かない、typo・リンク切れ | このリポジトリーの [Issue](https://github.com/bluemoonjp/scratchpad-ibmi-learning-from-zero/issues)(テンプレートは「技術的な誤りの指摘」「表記の誤り・リンク切れ」など) |
| PUB400 そのものの利用(アカウント、接続、規約) | PUB400 のフォーラム等(00-01が挙げています。具体的な場所はこの教材では確認していません) |
| 個人情報(実在のユーザー名、メールアドレス、内部パス等)が教材に混じっている | **公開の Issue ではなく**、GitHub の [Private vulnerability reporting](https://github.com/bluemoonjp/scratchpad-ibmi-learning-from-zero/security/advisories/new)(`SECURITY.md` の指示) |
| 大きな構成変更(部やレッスンの並び替えなど) | 先に Issue で相談(`CONTRIBUTING.md`) |

PUB400 は共有の練習機です。他の利用者に迷惑をかけないでください(00-02が引用するコミュニティー規約の "DO NOT NAG OTHER USERS!")。

## 3. Issue・質問に書くこと

次の順に書くと、読む側が状況をつかみやすくなります。

1. **対象**: どのレッスン・どのファイルか(例 `docs/part04/04-06-sequential-read.md`)。
2. **やろうとしたこと**: 手順の何番までは進めたか。
3. **起きたこと**: 画面下部のメッセージ ID(例 `CPF1120`)と、メッセージの本文。
4. **ジョブ・ログの抜粋**: 該当するメッセージの前後数行。長い場合は、最初に出たエラーの周辺だけにします。
5. **試したこと**: 同じ操作を繰り返したか、何を変えたか、その結果。
6. **環境**: 5250 エミュレーター(ACS・tn5250j)、ホスト・コード・ページ(00-03のとおり 273 か)、SSH や VS Code を併用したか。
7. **期待していた結果**: 本文のどこにそう書いてあったか。

貼るのは、スクリーンショットではなく**テキストのコード・ブロック**にします(`CONTRIBUTING.md`)。画像だと、写り込んだ情報を後から消せません。

## 4. 絶対に貼らないもの

- **パスワード。** 初期パスワードのメールも、変更後のパスワードも貼りません(00-01)。
- **実在のユーザー名・ライブラリー名・メールアドレス。** 必ず `<USER>`・`<USER>1`・`<USER>2`・`<USER>B` に置き換えます(`CONTRIBUTING.md`、[スタイル・ガイド](../style-guide.md))。
- **出力の中に入り込んだユーザー名。** ジョブ・ログやスプールの出力、IFS のパス(`/home/<自分のユーザー名>/...`)などに、自分のユーザー名がそのまま入っていることがあります。貼る前に、テキストで検索して置き換えてください。
- **他の利用者の情報。** 他人のオブジェクト・ジョブを調べた結果は、そもそも取らない約束です(00-02)。

うっかりパスワードを貼ってしまったら、投稿を消すだけでなく、パスワード自体をすぐに変更してください(一般的な対処です。この教材では確認していません)。教材の側に個人情報が混じっているのを見つけた場合は、上の Private vulnerability reporting で知らせてください。

## 5. 書き方の実例: 障害報告書を質問にする

第10部の課題A([10-01 準備と課題A: 運用と障害対応](../part10/10-01-preparation-incident.md))では、ジョブログから失敗した文・フィールド・バイトを探し、**障害報告書**にまとめて安全に復旧する、という練習をします。報告書に書くことは、そのまま「助けを求める質問」の書き方の手本になります(報告書の正式な書式は10-01が正で、下の表はその要点を質問向けに並べ替えたものです)。

| 障害報告書で書くこと | 質問での対応する項目 |
|---|---|
| どのジョブ・どのプログラムで起きたか | 対象(3節の1・2) |
| ジョブログのどの行が失敗か(メッセージ ID・失敗した文・フィールド・バイト) | 起きたこと・ジョブ・ログの抜粋(3節の3・4) |
| 原因の仮説と、確かめた方法 | 試したこと(3節の5) |
| 安全な復旧(直したうえで再投入) | 期待していた結果と、次にやりたいこと |

「動きません」の一言ではなく、報告書の型で書かれた質問は、読む側が最初のメッセージ ID を探し直す手間がなく、答えが返りやすくなります。10-01の内容そのものは、そのレッスンを読んでください。この付録では、10-01の手順や確認結果を代わりに説明しません。

## まとめ

- 先にレッスンの「実機メモ」を読む。未検証の部分かもしれない。
- メッセージ ID・ジョブ・ログの抜粋・試したことを、テキストで添える。
- パスワードとユーザー名は貼らない。`<USER>` に置き換える。
- 個人情報の混入は、公開の Issue ではなく Private vulnerability reporting へ。
