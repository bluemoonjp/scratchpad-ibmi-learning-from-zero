# 付録J 日本語・DBCS

この付録は、日本語(全角文字)を IBM i で扱うときの文字コードの話を、**実機で確かめた内容**と**一般知識のまま未検証の内容**に分けてまとめたものです。実機で確かめた内容の多くは、[09-02b 日本語・DBCSを実機で体験する](../part09/09-02b-japanese-dbcs.md)の実測です(確認日 2026-09-29、PUB400、IBM i 7.5、非対話の SQL 実行で確認した V2。記録は同レッスンの「実機メモ」)。

## 1. 実機で確認済みのこと

### 1-1. 「あ」のバイト列(09-02b、V2)

ひらがなの「あ」(Unicode のコード・ポイント U+3042)を、`UX'3042'` から各 CCSID の文字列に `CAST` して `HEX()` で見た結果です。

| CCSID | `HEX()` の結果 | バイト数 | 読み方 |
|---|---|---|---|
| 1208(UTF-8) | `E38182` | 3 | UTF-8 の3バイト |
| 1399 | `0E44810F` | 4 | SO(`0E`)+ DBCS 2バイト(`4481`)+ SI(`0F`) |
| 939 | `0E44810F` | 4 | 同上 |
| 930 | `0E44810F` | 4 | 同上 |

- 確認に使った文は次の形です(ソースは全部 ASCII のままです)。

  ```sql
  SELECT HEX(CAST(UX'3042' AS VARCHAR(10) CCSID 1208)) AS U1208,
         HEX(CAST(UX'3042' AS VARCHAR(10) CCSID 1399)) AS U1399,
         HEX(CAST(UX'3042' AS VARCHAR(10) CCSID 939))  AS U939,
         HEX(CAST(UX'3042' AS VARCHAR(10) CCSID 930))  AS U930
    FROM SYSIBM.SYSDUMMY1;
  ```

- **確認できたのは「あ」1文字の1例だけです。** 連続する全角文字で `0E`・`0F` がどこに入るか、半角と全角が混ざった文字列の長さがどうなるかは、確認していません(未検証(2026-09-29時点))。
- 1399 の値は、別のジョブ(ジョブの CCSID を読んでいないクライアント)で得たものです。`CHGJOB CCSID(1399)` を実行したジョブでも同じ結果でしたが、`CHGJOB` が実際にジョブの CCSID を変えたかどうかは確認できていません。

### 1-2. ジョブの CCSID と、式の CCSID は別の属性(09-02b、V2)

- `RUNSQLSTM` のバッチジョブの CCSID は **273** でした(実行リストの「Job CCSID 273」)。
- そのジョブの中で `CAST(... CCSID 1208)` は、指定どおりの結果(`E38182`)を返しました。ジョブの CCSID が 273 でも、式に CCSID を指定すればその CCSID の結果になる、という意味です。
- **確認したのは `RUNSQLSTM` のバッチジョブだけです。** 5250 の対話ジョブや、ACS の SQL ジョブの CCSID は未検証(2026-09-29時点)です。SQL でジョブの CCSID を読む方法も、`ACTIVE_JOB_INFO` の CCSID 列を1回試して NULL だったところまでで、確立していません。

### 1-3. 通らない書き方と、通る書き方(09-02b、V2)

- **`GX'0E30420F'` のようなグラフィック16進定数の直書きは失敗しました。** `GX'..'` を含む複数式の1文が、SQLSTATE 42606(ネイティブ・エラー -110、"Hexadecimal constant beginning with GX'0E30420 not valid.")で失敗しました。メッセージ ID の `SQL0110` は -110 からの推定で、画面で読んだ ID ではありません。1式だけの文は実行していません。
- **通る書き方は `UX'..'` + `CAST` + `HEX()`** です。全角文字は Unicode のコード・ポイントで書き(「あ」は `UX'3042'`)、`CAST(... CCSID nnnn)` で目的の CCSID にして、`HEX()` で中身を読みます。
- `GX'..'` がどういう形なら通るのか(SO・SI なしの DBCS 2バイトを並べる形かどうか)は、試していません(未検証)。
- もう1つ、`CAST(UX'3042' AS GRAPHIC(1) CCSID 1200)` と `CAST(UX'3042' AS CHAR(1) CCSID 1399)` を1文にまとめた文が SQLSTATE 42611(ネイティブ・エラー -604)で失敗しています。**どちらの式が原因かは切り分けていません**(メッセージ ID `SQL0604` は推定)。

| ID | 原因 | 対処 |
|---|---|---|
| `SQL0110`(SQLSTATE 42606、ID は推定) | `GX'0E30420F'` の直書き | `UX'3042'` + `CAST` + `HEX()` に書き直す |
| `SQL0604`(SQLSTATE 42611、ID は推定) | 属性が不正。どの式か未切り分け | 式を1つずつに分けて実行する |

### 1-4. システム値・IFS・`STMFCCSID`(00-03、02-03 ほか)

- PUB400 のシステム全体の文字コード(システム値 `QCCSID`)は **273**(ドイツ語圏向けの EBCDIC)です。ホスト・コード・ページを 273 に合わせる必要があることは、一次資料(PUB400 の FAQ)と著者自身の実測に基づく確認済みの事実として、[00-03](../part00/00-03-first-signon.md)に記録されています。**個々のジョブの CCSID はシステム値 `QCCSID` とは別物**で、混同しないでください(上の1-2のとおり、確認したのは `RUNSQLSTM` のジョブだけです)。
- IFS のテキスト・ファイルは ASCII 系、特に **CCSID 1208(UTF-8)** で置かれることが多く、ソース物理ファイルのメンバー(EBCDIC 系)へ複写するときに変換が必要です。02-03 で確認済みです。
- この教材のツール類(`tools/qclsrc/txsetup.clp` の `CPYFRMSTMF`、02-09 の `CPYTOIMPF`/`CPYFRMIMPF`、03-10 の `CPYTOSTMF`、03-13 の `CPYTOIMPF`)は、いずれも **`STMFCCSID(1208)`** を明示しています。UTF-8 のタグ付きファイルに対する `CPYFRMSTMF ... STMFCCSID(1208)` が破損なく成功することは、`docs/probes.md` の「第5部TXLEGACY自体の実機検証」で確認されています(`txsetup.clp` 自身の同じ呼び出しを個別に確かめた記録は、この付録では確認していません)。他の各コマンドの検証状況は、各レッスンの実機メモを参照してください。
- **1208 は UTF-8 で、Shift-JIS(932)とは別の値です。** 配布ソース(CLP/RPG/DDS)・CSV データは ASCII 文字のみで書かれているため、「ASCII の内容を 1208 として複写しても壊れない」ことは確認済みです。**日本語の全角文字そのものを含むソースやデータを、CCSID 変換して送るところまでは、この教材では実機検証していません。**
- IFS への UTF-8 書き出し: `QSYS2.IFS_WRITE_UTF8` に `LINE => UX'3042'` を渡すと、`E3 81 82`(UTF-8 の「あ」、3バイト)が書かれました(09-02b の演習(d)の実測。SSH の `od -x` の表示は `e381 8200` で、末尾に `00` が1バイト付いて見えましたが、ファイルは3バイトでした)。読み返す `IFS_READ_UTF8` が動くことを確かめたのは ASCII のファイルだけで、「あ」を書いたファイルの読み返しは未検証です。

### 1-5. 日本語が取り出しで壊れた例(09-05)

09-05 の実測では、応答の CLOB(CCSID 1208)をジョブ CCSID の `VARCHAR` 列に取り出したところ、日本語が代替文字(`3F3F3F`)になりました。保存(CLOB・UTF-8)は正しく、取り出しの列の CCSID で壊れた、という結果です。列を `VARCHAR(60) CCSID 1208` にすれば保てるはずですが、実機では試していません(未検証)。この教材のデータ規約は、日本語の住所を `ZIPADR` 列にだけ保存し、ほかの列はローマ字とコードで保つ、です([09-05](../part09/09-05-external-api-adapter-mock.md))。

## 2. 未検証のこと(一般知識・要確認)

以下は IBM i の CCSID・DBCS に関する一般的な知識で、09-02b でも確かめていません(未検証(2026-09-29時点))。

### 2-1. CCSID の使い分け

- **932。** 一般に Shift-JIS 系の日本語文字コードとして知られていますが、IBM i の CCSID 932 と Windows のコードページ 932(cp932)が完全に同じコードポイント配置かどうかは**要確認**です。Windows との厳密な互換を語るときは **CCSID 943** が挙げられることもあり、932 と 943 のどちらを使うべきかは未検証です。
- **5035 など、日本語の IBM i で歴史的に使われてきたとされる EBCDIC 系の CCSID。** カタカナのみの SBCS 用途か、漢字を含む DBCS 混在用途かといった使い分け、現在どれが推奨されるかは**要確認**です。
- なお、930・939・1399 で「あ」が同じ `0E44810F` になったことは、上の1-1の実測のとおりです(930・939・1399 の他の文字での違いは未確認です)。

### 2-2. DDS の DBCS フィールド型

- 一般に、**`G`(グラフィック型)は SO/SI の制御バイトを伴わない純粋な DBCS データ**、**`J`(DBCS-Only)・`O`(DBCS-Open)・`E`(DBCS-Either)は SO/SI を伴う**、という違いがあるとされています。実機では確認していません。
- 混在文字列の長さが文字数ではなく**バイト数**で決まる点は、「あ」が4バイトを使った実測(1-1)と整合しますが、列の桁あふれの挙動そのものは試していません。`CRTSRCPF` の `IGCDTA(*YES)` も未検証です。

### 2-3. RPG III と DBCS(一次資料の記述)

RPG III(第4部・第5部が扱う言語)については、著者が参照した一次資料(*RPG/400 Reference*, IBM, 1994年、第16章「Using Double-Byte Character Set (DBCS) Data in RPG/400 Programs」)に、専用の章があります。

- RPG/400 は、外部記述ファイルの DBCS フィールドを**文字フィールドとして扱います**。
- DBCS の定数・リテラルは、「透過(transparent)」形式(アポストロフィ + SO で始まり、SI + アポストロフィで終わる)で書くと、内部にアポストロフィに似た文字が含まれていても正しく認識されます。
- 相互参照リスト(コンパイル・リスト)上では、DBCS を含むフィールドが**フィールド欄では `G`、キー・フィールド欄では `IGC`** と表示されます。これは RPG/400 のコンパイラーが付ける表示で、DDS のフィールド・タイプ `G` そのものとは直接同じものではありません(両者の関係は未確認です)。
- INFDS の `OUT` フィールドが **10** のとき、その装置が DBCS 出力に対応していることを示す、という説明があります。
- これらは一次資料に基づく仕様の説明であり、**この教材ではまだ RPG III で DBCS データを実際に扱うプログラムを書いていません(実機未検証)。**

### 2-4. クライアント側の表示

ACS(IBM i Access Client Solutions)の「実行SQLスクリプト」などで、日本語の文字が画面にどう表示されるか(V3)は未検証です。ACS・Mapepire の接続そのもの(P14・P40)も未検証です。日本語の文字そのものを SQL の文字列定数として直接書く実験(`'あ'` など)も行っていません。バイトが同じで表示だけ違うなら、実機ではなくクライアントの問題かもしれません。先に `HEX()` の結果を確かめてください。
