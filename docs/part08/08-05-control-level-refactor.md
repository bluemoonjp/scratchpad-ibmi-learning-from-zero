## 説明

### 旧システムの制御レベル処理: `JU0300`を読み解く

`src/legacy/qrpgsrc/ju0300.rpg`は、`JUCHUL1`(`JUTOK`+`JUDATE`でキー付けした論理ファイル)をプライマリー・ファイルとして読み、得意先ごと・日付ごとに小計を出し、最後に総合計とクロスフッティング検算を印字する、04-10で学んだRPGサイクルの本格版です。04-10では`L1`しか扱いませんでしたが、`JU0300`は`L1`・`L2`・`LR`の3段を使います。

```text
IJUCHUR
I                                              JUDATEL1
I                                              JUTOK L2
I           UDS
I                                       11  16 FTOK
```

**なぜ`L1`が`JUDATE`(日付)で`L2`が`JUTOK`(得意先)なのか——直感とは逆の割り当てに見えるかもしれません。** `ju0300.rpg`自身のヘッダー・コメントが理由を説明しています(要約): `JUCHUL1`は`JUTOK`(大分類キー)→`JUDATE`(小分類キー、得意先の中での副次キー)の順でキー付けされています。RPGは**上位の制御レベルがブレイクすると、下位の制御レベルも自動的に強制ONにする**という規則を持つため(04-10・probes.md 04-10 #3で確認済みの`L1`/`LR`の規則と同じ仕組みです)、**変化の頻度が少ない方(外側のキー、`JUTOK`)を上位の制御レベル番号にしなければなりません**。もし文字どおり「`L1`=得意先」と割り当てていたら、同じ得意先の中で日付が変わるだけの、ふつうの日付変更のたびに、余計な得意先ブレイクまで誤って強制されてしまいます。そのため`JU0300`は`L1`=`JUDATE`(日付、内側・副次)、`L2`=`JUTOK`(得意先、外側・大分類)という、`JUCHUL1`の実際のキー順に忠実な割り当てを使っています。

`C`仕様書の制御ブレイク部分の一部です。

```text
CL2                   SETOF                     90
CL2         IX        COMP 49                   90
CL2N90                ADD  1         IX      20
CL2N90                Z-ADDL2CNT     CT,IX
CL2 94                EXCPTL2BRK
CL2                   Z-ADD0         L2CNT
```

`IX`(配列`CT`の添字)を**インクリメントする前に**49と比較しているのがポイントです。`ju0300.rpg`自身のヘッダー・コメントいわく、「インクリメントしてから比較する順序だと、100人目の得意先で`IX`が(2桁の桁数を超えて)静かに桁あふれし、配列を0番目で参照してしまう」ため、比較を先に行うことで`IX`自体が50を超えて進むことを防いでいます。**ここで数え違えやすいのが、この`COMP 49`が立てる標識90が具体的に何を意味するかです。** `C`仕様書の桁位置を数えると(`RPG/400`リファレンスの`COMP`命令の規定で、標識欄は54〜55桁目が「High」(Factor 1がFactor 2より大)・58〜59桁目が「Equal」)、`90`は54〜55桁目、すなわち「High」の位置に置かれています——「`IX`が49と等しい」ときではなく「`IX`が49を**超えた**(既に50に達した)」ときだけ90がONになります。`N90`(90がOFFのとき)の`ADD`/`Z-ADD`は、したがって`IX`が49**以下**(49自身を含む)の間ずっと実行され、`IX`は0→1→…→49→50と進んで、51人目の得意先で初めて増分・格納がブロックされます。**つまり`CT`は50要素すべてが実際に使われ、「50要素中49スロットしか使わない」という非対称性は原版には存在しません**——`ju0300.rpg`自身のヘッダー・コメントが述べる「`IX`自体は50を超えて進めない」という記述とも、これで正確に一致します。

`*LDA`(ジョブに紐づくローカル・データ域)へのアクセスも、`UDS`(`I`仕様書の`U`オプション)という04-10までには出てこなかった仕組みです。`*LDA`の11〜16桁目を`FTOK`(得意先コード・フィルター)として自動的に読み込み、空白でなければ一致しない得意先の明細行(`DTL`)の印刷を抑制します。11〜16桁目という半端な位置なのは、`JU0300`を呼び出すメニュー・プログラム`MN0000C`が、すでに`*LDA`の1桁目にメニュー選択番号を`CHGDTAARA`で書き込んでいるため、それを避けて配置してあるからです(`ju0300.rpg`自身のヘッダー・コメント)。

### 新しい技法: `dow`/`if`+手続き分割(`F0805A`)

`solutions/08-05/f0805as.rpgle`のメイン・ループです。

```rpgle
read juchul1;
dow not %eof(juchul1);
  if not firstRec;
    if jutok <> prevJutok;
      l1Break();
      l2Break();
    elseif judate <> prevJudate;
      l1Break();
    endif;
  endif;
  firstRec = *off;

  gcnt += 1;
  l1cnt += 1;

  if ftok = *blanks or ftok = jutok;
    printDetail();
  endif;

  prevJutok  = jutok;
  prevJudate = judate;

  read juchul1;
enddo;

if not firstRec;
  l1Break();
  l2Break();
  grandTotal();
endif;
```

これが`L1`/`L2`/`LR`という標識に対応する部分です。`JUCHUL1`が`JUTOK`→`JUDATE`の順でキー付けされているため、レコードは自然に得意先ごと・その中で日付ごとにまとまって届きます。`prevJutok`/`prevJudate`(前のレコードの値を覚えておく変数)と、今読んだレコードの値を比べ、**`JUTOK`が変われば`L2`(得意先)ブレイクと`L1`(日付)ブレイクの両方**(上位が変わると下位も強制、という`JU0300`と同じ規則)、**`JUTOK`が同じで`JUDATE`だけ変われば`L1`ブレイクのみ**、という判定をしています。ブレイク処理(古いグループの小計を印字し、件数を繰り上げ、リセットする)は、**新しいレコードの`gcnt`/`l1cnt`への加算より前**に実行されます——これはRPGサイクル自身の「総合計時の計算は明細時の計算より先に行われる(古い、リセット前の値を使う)」という実行順序(04-10で確認済み)と正確に対応しています。ファイルの終わりに達したあと、`if not firstRec;`のブロックがもう一度`l1Break`/`l2Break`を呼び、さらに`grandTotal`を呼ぶのが`LR`処理に対応します。`firstRec`という標識は、`JUCHUL1`が0件だった場合に何も印字しない(`ju0300.rpg`自身のヘッダー・コメントが「修正6b」として説明する、指標94による空ファイル・ガードと同じ役割)ためのものです。

各ブレイク・手続きは、`clear`→`%subst`で1行組み立てて`write`するだけの単純な形です。各`%subst`の開始桁の根拠(なぜ`5`・`36`・`51`なのか)は、下の「見つかった実機の落とし穴: 列位置が1桁ずれる」でまとめて説明します——結論だけ先に言うと、`JU0300`のO仕様が書いている終了桁から`長さ-1`を引いた値と一致します。`l2Break`を見てみます。

```rpgle
dcl-proc l2Break;
  dcl-pi *n;
  end-pi;

  if ix <= 49;
    ix += 1;
    ct(ix) = l2cnt;
  endif;

  clear line;
  %subst(line:5:6)   = prevJutok;
  %subst(line:36:10) = 'CUST TOTAL';
  %subst(line:51:5)  = %editc(l2cnt:'Z');
  write qsysprt line;

  l2cnt = 0;
end-proc;
```

`if ix <= 49; ix += 1; ct(ix) = l2cnt; endif;`は、上で見た`JU0300`の`CL2 SETOF 90 / CL2 IX COMP 49 90 / CL2N90 ADD 1 IX / CL2N90 Z-ADDL2CNT CT,IX`を`if`に置き換えたものです。**このレッスンの執筆中、当初の移植(`if ix <> 49;`)には原版と1つずれた実バグがあることが分かりました。** 上の「旧システムの制御レベル処理」節で確認したとおり、原版の指標90は「`IX`が49を超えた(既に50)」ときだけONになるので、`JU0300`は`CT`の50要素すべてに格納します。ところが`if ix <> 49;`は、`ix`が既に**49**になった時点(50人目の得意先)でブロックしてしまうため、`CT`へ格納されるのは最大49件——**50人目の得意先の`L2CNT`が配列に一度も格納されません。** これは意図して移植した非対称性ではなく、`f0805as.rpgle`自身の実際のオフバイワン(1つずれ)でした(修正前のヘッダー・コメントは、これを「軽微な、直さず引き継いだ非対称性」と誤って説明していました)。`db/data/load_v1.sql`の6名の得意先ではこの境界(50人目)にはどのみち届かないため、本レッスンの「差分0」確認(V2)はこのズレを一度も通っておらず、検出していませんでした。**`solutions/08-05/f0805as.rpgle`自体を`if ix <= 49;`(原版どおり、IXが50に達するまで格納を許す)に修正済みです**——ただしこの修正自体は実機での再コンパイル・再実行(V2)をまだ経ておらず、`db/data/load_v1.sql`の6名データではこの境界そのものに一度も届かないため、実機で真に確認する手段が今のところありません。

### `%XFOOT`とクロスフッティング検算

`grandTotal`の中で、`CT`配列(得意先ごとの`L2CNT`を集めたもの)の合計を`GCNT`(1件ずつ独立に数えた総件数)と突き合わせます。

```rpgle
xtot = %xfoot(ct);
xfootMatch = (xtot = gcnt);
```

`%XFOOT`は「指定した数値配列式の全要素の合計を返す」組み込み関数です(`ilerpgref75.txt`)。`CT`は50要素の配列で、実際に使われなかったスロットは宣言時の`inz(0)`のままなので、6名の得意先しかいなくても`%xfoot(ct)`は安全に全50要素を合計できます。`JU0300`の`XFOOTCT XTOT 50`(`E`仕様書の`XFOOT`命令コード)と、やっていることは同じです——**2つの独立した集計方法(1件ずつの累積と、配列への格納・合計)が一致するかを確かめる、古典的なクロスフッティング検算**です。

### `*LDA`への直接アクセス: RPG IVの`DTAARA`

`**FREE`にも`UDS`相当の自動読み込み機能自体はあります——`ilerpgref75.txt`(16329行目)は`dcl-ds *n dtaara(*auto); ...; end-ds;`という、無名のデータ構造に`*LDA`を自動的にロード・セーブする書き方を、固定形式の`UDS`の自由形式版として明示しています。ただし`F0805A`がこのリポジトリで実際にコンパイル・実機確認したのは、`*AUTO`ではなく、`*LDA`へのアクセスを名前付きデータ構造+`DTAARA`キーワード+明示的な`IN`操作で書く、次の形だけです(`*AUTO`形はこの教材では未検証です)。

```rpgle
dcl-ds ldaDs dtaara(*lda);
  filler char(10) pos(1);
  ftok   char(6)  pos(11);
end-ds;
...
in ldaDs;
```

**`pos()`は06-10のINDDSで見た同じキーワードです。** 06-10では標識データ構造の中で「DDS側の標識番号Nをここに割り当てる」という専用の意味で使いましたが、ここでは一般のデータ構造のサブフィールドに対する、より広い用法――そのサブフィールドが構造内の何バイト目から始まるか――で使っています。

**このキーワードの書き方には、実機で見つかった落とし穴があります。** `F0805A`の初回コンパイルは`RNF7064`(severity 30、"The Factor 2 operand LDADS of IN or OUT is not a data area")で失敗しました。原因は、最初の下書きが`dtaara('*lda')`(引用符付きの文字列リテラル)と書いていたことです——コンパイラーはこれを「`*LDA`という名前のデータ域」を指す文字列リテラルとして扱おうとします(実在しない、不正なオブジェクト名です)。正しくは**引用符の無い`*lda`**(予約キーワード)です。`ilerpgref75.txt`(16345-16351行目)の実例で確認済みです。

```text
DCL-DS LDA_DS DTAARA(*LDA);
     SUBFLD CHAR(600);
END-DS;

IN LDA_DS;
OUT LDA_DS;
```

一次資料いわく、「The data structure is explicitly based on the *LDA. Since it is not a data area data structure, it must be handled using IN and OUT operations.」(このデータ構造は`*LDA`に明示的に基づいており、データ域データ構造そのものではないため、`IN`/`OUT`操作で扱う必要がある)。`F0805A`は読むだけ(書き込みはしない)なので`in ldaDs;`のみで十分です。

### 見つかった実機の落とし穴: 列位置が1桁ずれる

**特性検定の一番の教訓は、ここに出ます。** `golden-master.md`自身が、`JU0300`のO仕様書について次の注記を残しています。

> `src/legacy/qrpgsrc/ju0300.rpg`のO仕様が各項目の**終了桁**として書いている数字は`JUNO`10桁目・`JUTOK`20桁目・`JUDATEZ`32桁目・`JUTAN`42桁目...。**ただし、これらの終了桁から項目の長さを引いて逆算した開始桁は、下の実際の印字(コード・ブロック)で観測される開始桁より1桁小さい**(例: `JUNO`は終了桁10・長さ6なので逆算した開始桁は5だが、実際に印字されるのは6桁目からである...)。この1桁のずれの原因(装置ファイルの制御バイトなど)は未確認・未解明のままである。

つまり`JU0300`自体、**ソースが書いている桁位置と、実際に印字される桁位置が1つずれている**という、レガシー・コード側の既知の(原因不明な)クセです。`F0805A`の最初の下書きは、この`golden-master.md`が記録した「実際に観測される」桁(例: `JUNO`なら6桁目)をそのまま`%subst`の開始桁として使いました——理屈のうえでは正しいはずでした。

ところがその後の実機接続で、同じ接続内の`JU0300`自身の出力と`F0805A`の出力を突き合わせたところ、**`F0805A`の印字全体が、`JU0300`の実際の印字より、さらにもう1桁右にずれていた**ことが判明しました。`golden-master.md`のコード・ブロックが記録している「観測される開始桁」自体が、すでに1回分の+1のずれを含んだ値だったため(この事実を明示する注記自体は、この発見の**あと**で`golden-master.md`に追記されたものです)、`F0805A`の`%subst`の桁をその値からそのまま決めると、同じ+1のずれがもう一度重なったのだろうと考えられます。**修正は経験的なものです**——`printDetail`/`l1Break`/`l2Break`/`grandTotal`の`%subst`開始桁を、すべて1桁ずつ左へ(`golden-master.md`の観測値から-1)ずらしたところ、続く接続で`F0805A`の出力は`JU0300`の実際の出力と完全に一致しました(接続ごとの詳しい経緯は下の「実機メモ」を参照してください)。**このずれが起きる仕組みそのものは、著者側でさらに調べても特定できておらず、未解明のままです。** 「隠れた制御バイト」のような特定の技術的な原因は確定していません——確定しているのは「経験的に-1の補正が必要で、実機での厳密なバイト単位の`diff`で確認した」という事実だけです。

最終的に確認できた`printDetail`(明細行を印字する手続き)です。

```rpgle
dcl-proc printDetail;
  dcl-pi *n;
  end-pi;

  clear line;
  %subst(line:5:6)  = juno;
  %subst(line:15:6) = jutok;
  %subst(line:25:8) = %editc(judate:'Z');
  %subst(line:37:6) = jutan;
  write qsysprt line;
end-proc;
```

この最終的な開始桁(`5`・`15`・`25`・`37`)は、`JU0300`のO仕様が文字どおり書いている終了桁からそのまま逆算した開始桁(`JUNO`なら終了桁10・長さ6で5桁目)と、数字の上で一致しています。**これは偶然ではなく、単純な引き算の結果です**——`golden-master.md`自身の注記どおり「観測される開始桁 = O仕様の逆算値 + 1」であり、今回の修正は「`F0805A`の開始桁 = 観測される開始桁 − 1」だったので、差し引きすると`F0805A`の最終的な開始桁は結局O仕様の逆算値と同じ数字に戻ります。**まだ分かっていないのは、この算数の外側にある本物の疑問**——なぜ`JU0300`自身の実際の印字が、そもそもO仕様の逆算値より1桁右にずれるのか、という点です。この根本原因は未解明のままです。

**この経緯が教えてくれるのは**、特性検定では**文書化された記録(`golden-master.md`の数字)をコードにそのまま持ち込むだけでは不十分**で、**実際に動かした結果同士を突き合わせて初めて確認できる**ということです——`golden-master.md`というテキストも、あくまで「ある時点の実際の出力を書き写したもの」であり、それ自体を疑ってかかる姿勢が必要でした。

### 命名について: `F0805A`

`JU0300`は部・レッスン番号を持たない旧システムのオブジェクト名(付録E §4)ですが、これを書き直した`F0805A`は、**旧システムの「意図的な例外」の系譜を継がず**、付録E §3.1.1の通常のパターンにそのまま従います。

> 第6部以降...先頭の1文字...`F`(RPG IV `**FREE`)...`F0603A`(06-03)、`F0612A`(06-12)...これらは`C`(CL)・`R`(RPG III)と同じ、3.1の骨格の延長です。

これは、`F0608A`(06-08、業務ニックネーム`ZAHIK4`)が`R0409A`(04-09、`ZAHIK3`)を`**FREE`で書き直したときと同じ前例です——`F0608A`も、書き直した対象(`R0409A`)が04-09の演習用オブジェクト名だったのに対し、部・レッスン番号ベースの命名をそのまま使いました。`F0805A`の**業務ニックネーム**(本文中だけで使う説明用の呼び名、付録E §3.1)は「`JU0300`近代化版」です——実機に作られるオブジェクト名はあくまで`F0805A`であり、`JUCINQ3`・`ZAHIK3`と同じく、コード中に`CALL PGM(JU0300近代化版)`のような形で出てくることはありません。

### 1. `l1Break`・`grandTotal`を自分で書いてみる

上の「説明」節で`printDetail`と`l2Break`の実際のコードを見ました。同じ3行の型(`clear line;` → `%subst`で組み立て → `write qsysprt line;`)で、残り2つの手続きを自分で書いてみてください。
