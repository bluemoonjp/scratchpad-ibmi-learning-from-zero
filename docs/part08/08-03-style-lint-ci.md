## 説明

### スタイル・ガイドを機械的ルールに翻訳する: `rpglint.json`

`rpglint`(`@halcyontech/rpglint`、vscode-rpgle拡張機能のCLI版)は、RPGのソースを読み、設定ファイル(`rpglint.json`)に書かれたルールに違反していないかを検査する道具です。このリポジトリでは`templates/part08-project/.vscode/rpglint.json`として、次の内容で用意されています。

```json
{
  "indent": 2,
  "NoOCCURS": true,
  "NoSELECTAll": true,
  "NoSQLJoins": true,
  "NoGlobalSubroutines": true,
  "NoUnreferenced": true,
  "NoCTDATA": true,
  "RequiresParameter": true,
  "StringLiteralDupe": true,
  "PrettyComments": true,
  "SpecificCasing": [
    { "operation": "if", "expected": "*LOWER" },
    { "operation": "dcl-s", "expected": "*LOWER" },
    { "operation": "dcl-pr", "expected": "*LOWER" }
  ]
}
```

各ルールのだいたいの意味は次のとおりです。

| キー | だいたいの意味 | 確認状況 |
|---|---|---|
| `indent` | インデントの幅(半角スペース数)。ここでは2。 | 一般知識、要確認 |
| `NoOCCURS` | RPG IIIの多重発生データ構造(`OCCURS`)を禁止する。 | 一般知識、要確認 |
| `NoSELECTAll` | 埋め込みSQLで`SELECT *`を禁止する。 | 一般知識、要確認 |
| `NoSQLJoins` | 埋め込みSQLで`JOIN`構文を禁止する。 | 一般知識、要確認 |
| `NoGlobalSubroutines` | 大域スコープのサブルーチン(`BEGSR`/`ENDSR`)を禁止する。 | **確認済み**。実際のメッセージ:「Subroutines should not be defined in the global scope.」 |
| `NoUnreferenced` | 宣言したのに一度も参照されないフィールドを禁止する。 | **確認済み**。実際のメッセージ:「No reference to definition.」 |
| `NoCTDATA` | RPG IIIのコンパイル時配列(`CTDATA`)を禁止する。 | 一般知識、要確認 |
| `RequiresParameter` | `dcl-proc`で宣言された**プロシージャー**を、括弧を付けずに呼び出すと指摘する(実際のメッセージ:「Procedure calls require brackets.」)。`exsr`によるサブルーチン呼び出しは、そもそもプロシージャーの呼び出しではないため対象外——本文中で扱う`exsr`呼び出しに対してこのルールの指摘が出ないのは、ルールが効いていないのではなく、対象外の構文だから、という判定条件どおりの結果です(`dist/index.js`自身のコードを直接読んで確認)。 | **確認済み** |
| `StringLiteralDupe` | 同じ文字列リテラルが複数回書かれているのを禁止する(定数化を促す)。 | **確認済み**。実際のメッセージ:「Same string literal used more than once. Consider using a constant instead.」 |
| `PrettyComments` | コメント(`//`)の書式を統一する。判定条件は下で詳しく扱います。 | **確認済み** |
| `SpecificCasing` | `if`・`dcl-s`・`dcl-pr`の大文字・小文字を指定どおりに統一する(ここでは全部小文字)。 | **確認済み**。実際のメッセージ:「Does not match required case.」 |

「確認済み」と付けた6つ(`RequiresParameter`を含む)は、`dist/index.js`自身のコードを直接読み、判定条件・実際のメッセージ文言を確認したものです。残り(`indent`・`NoOCCURS`・`NoSELECTAll`・`NoSQLJoins`・`NoCTDATA`)は、`rpglint`の一次資料(README自身にもルールごとの詳しい説明が無い)にルールの完全な一覧・判定条件が見つからず、ルール名からの一般的な推測にとどまります——気になる場合は、インストールした`node_modules/@halcyontech/rpglint/dist/index.js`自身を読めば、正確な判定条件を追えます。

**設定ファイルを書くときの実際の落とし穴(この教材自身が踏んだ経験)。** `templates/part08-project/.vscode/rpglint.json`の最初のバージョンには、実は2つのバグがありました。(1) `NoIndicators`・`NoSQLJoinInWhere`・`RequireBlockIf`・`IncludeComment`という4つのキーは、このバージョン(0.27.0)には存在しないルール名でした——`rpglint`は、知らないキーを黙って無視します(エラーにも警告にもなりません)。`NoSELECTAll`と対になる「SQLのJOINを禁止する」ルールの正しい名前は`NoSQLJoins`でした。(2) `SpecificCasing`の`expected`値も、最初は`"lower"`のような裸の文字列でしたが、これはCLの特殊値の書式(`*LOWER`のようにアスタリスクを付ける)が必要で、そうでない場合は大文字・小文字を問わずすべての出現が誤検出される、という実バグがありました。**どちらも、このリポジトリの`templates/part08-project/.vscode/rpglint.json`では既に修正済みです**——このレッスンでは、この修正済みのファイルをそのまま使ってください。自分で設定ファイルを一から書く場合は、バージョンが変わればルール名も変わりうる(黙って無視されるだけで、教えてはくれません)ことを覚えておいてください。

### `PrettyComments`の正確な判定条件

`PrettyComments`は、READMEにも詳しい説明がありません。実際に`rpglint`自身のソース(`dist/index.js`)を読んで確認したところ、判定はとても単純でした——**コメント記号`//`の直後の1文字が、半角スペースでも、もう1つの`/`でもない場合に違反になります。** 言い換えると、`// 得意先名`のように直後に半角スペースを1つ置くか、`///得意先名`のように3連スラッシュにするかのどちらかであれば許可され、`//得意先名`や、区切りを目立たせる`//===...===`のような罫線コメントは、内容によらず必ず違反になります。

この教材の多くのソース(`jucsrv.rpgle`を含む)は、この罫線コメントの書式を使っています。下の「実演」で、実際に`JUCSRV`のコピーに対してこの指摘を0件にします。

### `rpglint`をPCで実行する

`rpglint`はnpmパッケージ(`@halcyontech/rpglint`)として公開されており、PUB400への接続なしに、PCローカルのnpm/npxだけでインストール・実行できます。

```sh
npx --yes @halcyontech/rpglint
```

`.vscode/rpglint.json`を置いたプロジェクトのルートで、このコマンドを引数なしで実行します。**`rpglint`は、カレント・ディレクトリー配下の`**/rpglint.json`という形のファイルを自動的に探します。** そのため、設定ファイルの置き場所は1箇所に絞ってください——複数箇所に置くと、どれが使われるのか探索が曖昧になります。このレッスンでは、正式な置き場所である`.vscode/rpglint.json`だけを使います。(pnpmを使っている場合は`pnpm dlx @halcyontech/rpglint`でも同じ結果になることを確認済みです。)

### 「0にする」の基準と、リンターがコンパイラーの代わりにはならないこと

`rpglint`は、コード全体を意味的に理解するコンパイラーではなく、設定したルールに沿って構文を軽く読む道具です。**したがって「指摘を0件にする」というのは、あくまで「設定した個々のルールに関する限り違反が無い」という意味にとどまります。** たとえば、`CHAIN`の検索結果を素の標識フィールド(`ind`型)で受ける書き方は、この設定ファイルのどのルールにも該当しないため、`rpglint`では一切指摘されません。ところがこの書き方は自由形式RPGとしてそもそも無効で、実際に`CRTBNDRPG`にかけると`RNF5191`(結果フィールドはデータ構造でなければならない、の趣旨。重大度30)でコンパイルそのものが失敗します。**リンターの指摘が0件であることと、コンパイルが通ることは、互いに独立した、別々の確認です。** どちらか一方だけで済ませず、両方を確かめる習慣を付けてください。

### 08-04より前という制約: 振る舞い非破壊的なリファクタリングに限る

上の「新出」中核概念(3)のとおり、本レッスンでは動作を変えるリファクタリングを扱いません。**`JUCSRV`に対しては、コメントの書式を直すだけにとどめ、`getCustName`・`pingJucsrv`・`countCustOrders`という3つのエクスポート手続きの名前・シグネチャー・戻り値は一切変えません。** ロジックそのものの書き換えや、標識・制御構造の作り直しのような、動作に影響しうる変更は、08-04でテストの安全網(`TESTKIT`)を用意した後、または08-05/08-05bが教える特性検定の手法を使ってから行ってください。

### PCローカルの実行とGitHub Actionsの対応

`.github/workflows/source-check.yml`(`templates/part08-project/.github/workflows/source-check.yml`)は、このリポジトリで次の内容で用意されています。

```yaml
name: source-check

# PUB400には一切接続しない、ローカルの構文・リント検査のみのワークフロー
# (08-01の演習で使うPCからのgit pushとは別の、PC/CI側だけで完結する確認)。

on:
  push:
  pull_request:

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
      # @halcyontech/rpglint(vscode-rpgleのリンターのCLI版)。設定ファイルは
      # `.vscode/rpglint.json`に置くこと(このCLIはプロジェクト・ルート配下の
      # `**/rpglint.json`を自動的に探す)。`npx --yes`/`pnpm dlx`での無引数
      # 実行はPCローカルで実際に確認済み(docs/probes.mdの08-03節参照)。この
      # `npm i -g`によるグローバル・インストール後の`rpglint`単体呼び出しと
      # いう組み合わせ自体は、bin用のシバン行(`#!/usr/bin/env node`)を
      # 確認しただけで、CI上で実際に動かして確認したわけではない。
      - name: Run rpglint
        run: |
          npm i -g @halcyontech/rpglint
          rpglint
```

GitHub Actionsは、GitHubに備わっているCI(継続的インテグレーション)の仕組みです。`.github/workflows/`配下にYAML形式のファイルを置くと、指定した事象(ここでは`on: push`・`pull_request`)が起きるたびに、GitHubが用意した仮想マシン(`runs-on: ubuntu-latest`)上で`steps`に書いた手順を順番に実行します。`uses:`はGitHubや他の開発者が公開している既製の「アクション」を呼び出す指定(`actions/checkout@v4`はリポジトリーの中身をその仮想マシンへ取り込む、`actions/setup-node@v4`はNode.js/npmの実行環境を用意する、という役割です)、`run:`はシェル・コマンドをそのまま実行する指定です。

**この最後の2行(`npm i -g @halcyontech/rpglint`→`rpglint`)は、PCであなたが手で打つ`npx --yes @halcyontech/rpglint`と、本質的に同じ検査です。** インストールの仕方(グローバル・インストール vs その場限りの実行)が違うだけで、検査する内容もルール・ファイルも同じです。**このワークフローはPUB400には一切接続しません**——YAML自身のコメントにもその旨が明記されています。`.github/workflows/source-check.yml`として`myproject`に置いておけば、GitHubへpushするたびに(GitHubリポジトリーとして公開している場合)自動的にこの検査が走るようになります。このレッスンでは、ファイルを置くところまでを扱います。実際にGitHubへ登録してCIを動かすかどうかは任意です——GitHubアカウント自体は、このレッスンの必須条件ではありません。

**この実演はPCだけで完結します。PUB400には一度も接続しません。**

1. まだPC側に08-01の「A. 本筋」(`myproject`という本物のPCプロジェクト)を用意していなければ、先に08-01を行ってください。

2. `templates/part08-project/.vscode/rpglint.json`を、`myproject/.vscode/rpglint.json`としてコピーします(上の「説明」のとおり、既に2つの実バグが見つかり修正済みの版です)。

3. `myproject`のルートで、`rpglint`を実行します。

   ```sh
   npx --yes @halcyontech/rpglint
   ```

   初回はnpxが`@halcyontech/rpglint`をその場でダウンロードするため、少し時間がかかります。`src/qrpglesrc/jucsrv.rpgle`(08-01でコピーしたコピー)に対して、次の形の結果になるはずです。

   - 件数: **12件**。
   - すべて`PrettyComments`(「Comments must be correctly formatted.」)——`jucsrv.rpgle`の`//===...===`という罫線コメントの書式に対する指摘です。
   - `SpecificCasing`(大文字・小文字)の指摘は**1件もありません**——`jucsrv.rpgle`の`dcl-s`/`if`はすべて既に小文字で書かれています。

4. 指摘を直します。`jucsrv.rpgle`の中で`rpglint`が指摘した12行(`//===...===`・`//---...---`という罫線コメントの行)それぞれの`//`の直後に半角スペースを1つ挿入してください(`//===...===` を `// ===...===`のように)。既に`//`の直後に半角スペースがある他のコメント行には触れる必要がありません——コメントの中身(意味)は変えません、書式だけの変更です。**`getCustName`・`pingJucsrv`・`countCustOrders`という3つのエクスポート手続きの名前・シグネチャー・戻り値には一切触れません。**

5. もう一度`rpglint`を実行し、指摘が0件になったことを確認します。

   ```sh
   npx --yes @halcyontech/rpglint
   ```

6. コメントだけの変更をコミットします(08-01のgitの復習です)。

   ```sh
   git add .vscode/rpglint.json src/qrpglesrc/jucsrv.rpgle
   git commit -m "Add rpglint.json; fix PrettyComments in jucsrv.rpgle"
   ```

   **この時点でPUB400側の`JUCSRV`を再ビルドする必要はありません。** コメントはコンパイル結果に一切影響しないため、PC側のソースを直しただけで、このレッスンの目標(リント指摘を0にする)は達成できます。08-01の方法でこの変更をPUB400へpush・再ビルドすることもできますが(任意)、このレッスンの必須手順ではありません。

7. `.github/workflows/source-check.yml`(上の「説明」参照)を`myproject/.github/workflows/source-check.yml`としてコピーし、コミットします。

   ```sh
   git add .github/workflows/source-check.yml
   git commit -m "Add CI: rpglint on push/PR"
   ```

## 演習

**F0803S: 意図的にリント違反を仕込んだ配布見本を、自分で直す演習です。** どこに何個の違反があるかはここでは明かしません——`rpglint`を実際に実行し、その出力を読んで、1つずつ自力で見つけて直してください。

1. 教材リポジトリーのPC側クローン(08-01手順A3で作った、この教材自身のクローン)から、`src/qrpglesrc/f0803s.rpgle`を`myproject/src/qrpglesrc/`へコピーします。

2. `myproject`のルートで`rpglint`を実行し、出力を読みます。

   ```sh
   npx --yes @halcyontech/rpglint
   ```

   **`jucsrv.rpgle`は上の「実演」で既に0件になっているはずなので、ここで出る指摘はすべて`f0803s.rpgle`に対するものです。**

3. 指摘を1つずつ直してください。`f0803s.rpgle`は`*SRVPGM`ではなく、エクスポートされた手続きを1つも持たない独立したプログラムです——「エクスポートされる手続きの名前・シグネチャー・戻り値を変えない」という08-03の制約は、そもそも指す対象(エクスポートされた手続き)が無いため、この演習にはその字面どおりには及びません(ファイル自身のヘッダー・コメントにもその旨が書かれています)。ただし、この制約の本来の理由(08-04で自動テストの安全網ができるまでは、動作を変えた場合に壊れても気づく手段が無いこと)はこのファイルにも等しく当てはまります。そのため、安心して大域サブルーチンを`dcl-proc`へ書き換える、リテラルを定数にする、といった構造そのものの書き換えを行ってよいのは、あくまで**外から観測できる入出力を変えない**範囲でです。`custCode`を受け取り、得意先名と注文件数を印字するという入出力の形(パラメーター・印字レイアウト)は変えないでください——模範解答もこの前提で作られています。

4. すべての指摘が0件になったら完了です。自分の答えを、`solutions/08-03/f0803s.rpgle`(模範解答)と見比べてください。

5. **発展(任意)**: リント指摘が複数残ったまま(修正**前**)の`f0803s.rpgle`でも、実はコンパイルは通ることを自分の手でも確かめられます。5250で、`~/ibmi-kyozai`(02-04で取り込み済みの、この教材自身のクローン)の`src/qrpglesrc/f0803s.rpgle`を、08-01と同じ形でSRCSTMFから直接コンパイルしてください(IFS上のパスはSSHで別途入る必要はなく、5250のコマンド行から`SRCSTMF()`パラメーターで直接指定できます——08-01の「実演C」参照)。

   ```text
   CRTBNDRPG PGM(<自分のユーザー名>1/F0803S) SRCSTMF('/home/<自分のユーザー名>/ibmi-kyozai/src/qrpglesrc/f0803s.rpgle') TGTCCSID(*JOB)
   ```

   **`TGTCCSID(*JOB)`を忘れないでください**(08-01で確認したとおり、`git clone`直後のファイルはCCSID 1208〔UTF-8〕タグ付きで、これを指定しないと`RNS9380`になります)。コンパイルが通ったら、実行してみてください。

   ```text
   CALL PGM(<自分のユーザー名>1/F0803S) PARM('C00001')
   ```

   リント指摘が複数残ったままのファイルでも、コンパイル・実行の両方が問題なく成功するはずです——これが「リント指摘とコンパイル・エラーは別物」という中核概念(2)の、自分の手で確かめる実演です(このレッスンの必須手順ではありません)。この手順を行った場合はPUB400上にオブジェクトが1つ作られるので、片付けとして`DLTPGM PGM(<自分のユーザー名>1/F0803S)`を忘れずに実行してください。

## 実機メモ

**このレッスンの必須手順はPUB400に一切接続しません(演習5の発展〔任意〕を除く)。** 以下はすべてPCローカルでの確認であり、実機(IBM iハードウェア)の確認段階(V1/V2/V3)の対象ではありません。

- **確認日: 2026-09-29。PCローカル、PUB400への接続なし。** `@halcyontech/rpglint`(npm、v0.27.0、2024-12-03公開、vscode-rpgle拡張機能の開発元によるCLI版、依存パッケージ0件)が実在し、PCローカルのnpm/pnpmだけでインストール・実行できることを確認済みです。学習者向けの本文が案内する`npx --yes @halcyontech/rpglint`(プロジェクト・ルートで、`.vscode/rpglint.json`を置いて引数無しで実行)という、この具体的な起動のされ方そのものを、実際にこの形で(祖先ディレクトリーに競合する`package.json`が無い、クリーンな状態で)確認済みです。`pnpm dlx @halcyontech/rpglint`という対応する形も同様に確認済みです。
- **`PrettyComments`の判定条件**: `rpglint`自身のソース(`dist/index.js`)を直接読んで確認しました(READMEには記載がありません)。「`//`の直後の1文字が半角スペースでも`/`でもない場合に違反」という条件で、`jucsrv.rpgle`の全ての`//`直後に半角スペースを1つ挿入した写しを作って実際にリントし、エラー0件に到達できることをPCローカルで確認済みです(`src/qrpglesrc/jucsrv.rpgle`自身は書き換えていません)。
- **`jucsrv.rpgle`のリント結果**: 修正済みの`rpglint.json`でリントすると12件のエラーが出て、**その全件が`PrettyComments`**です。`SpecificCasing`(大文字・小文字)の違反は1件もありません——`jucsrv.rpgle`の`dcl-s`/`if`はすべて既に小文字で書かれています。
- **`F0803S`(見本・模範解答)**: PCローカルで実際に`rpglint`を実行して確認済みです。具体的な違反の個数・内訳は、演習の性質上ここには書きません——学習者自身が`rpglint`を実行して確認してください。模範解答(`solutions/08-03/f0803s.rpgle`)は指摘0件を確認済みです。見本・模範解答とも、(このレッスンとは別に)実際にPUB400で`CRTBNDRPG`によりHighest Severity 00でコンパイルでき、`CALL`で正しく実行できることも確認済みですが、印字結果そのものをバイト単位で見本と模範解答とで比較検証したわけではありません(未検証のまま)。
- **`rpglint.json`自体に見つかった2つの実バグ**: (1) `NoIndicators`・`NoSQLJoinInWhere`・`RequireBlockIf`・`IncludeComment`という4つのキーは、`rpglint` 0.27.0には存在しないルール名でした(`dist/index.js`自身のルール名辞書を直接読んで確認)。存在しないキーは黙って無視されます。`NoSQLJoinInWhere`の正しい名前は`NoSQLJoins`です。(2) `SpecificCasing`の`expected`値は、CLの特殊値形式(`*LOWER`/`*UPPER`)が必要で、`"lower"`のような裸の文字列を渡すと、大文字・小文字を問わず常にすべての出現が誤検出されます。どちらも`templates/part08-project/.vscode/rpglint.json`では既に修正済みで、本文はこの修正済みのファイルをそのまま使います。
- **一次資料ギャップ**: `rpglint`自体(ルールの完全な一覧・挙動の詳細)には、このリポジトリの`work/design/refs/`に一次資料がありません。今回PCローカルに実際にインストール・実行し、`dist/index.js`自身を直接読んで確認した内容(上記の`PrettyComments`・`RequiresParameter`の判定条件・`SpecificCasing`の値の書式・存在しないルール名の扱い・6つのルールの実際のメッセージ文言)だけが確認済みであり、それ以外(`indent`・`NoOCCURS`・`NoSELECTAll`・`NoSQLJoins`・`NoCTDATA`の詳しい判定条件)は「一般知識、要確認」として扱っています。
