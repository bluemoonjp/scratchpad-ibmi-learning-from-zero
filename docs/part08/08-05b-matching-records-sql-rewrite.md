## なぜ学ぶか

**一致レコード処理(M1/MR)は、標識ベースの制御レベル処理と並んで、IBM iの保守現場の古いRPG/400資産にしばしば残っているレガシー技法です。** これをSQLへ書き換えられることには、それ自体で実務上の価値があります。08-05は`JU0300`(制御レベル処理)を対象にしましたが、このカリキュラムで一致レコード処理を使っているレガシー・プログラムは`ZA0500`です(付録E 4節「在庫引当(一致レコード処理)」。同じ在庫引当を扱う読解用の`ZA0510`は、確認したところM1/MRを使っていません)。本節はこのカリキュラムの中で、`ZA0500`のM1/MR処理そのものと向き合う回です。**この技法は、第10部の総合演習C([10-03](../part10/10-03-modernization-devbase.md))でも再び使います。10-03は、今の`ZA0500`(M1/MR構造のまま)を旧プログラムとして差し替えます。本節が扱うのは、あくまで**今の**`ZA0500`(05-13完了後、M1/MR構造のまま)についてです。

08-05で確認した「基準の出力を取ってから変える」という**特性検定**の考え方は、本節でもそのまま使います(復習であり、新出には数えません)。今回新しいのは「何に書き換えるか」の方です——`ZA0500`のM1/MR処理を、SQLの**2カーソル・マージ**という技法に置き換えます。**実務の書き換えでは、通常は単純なJOIN1本で十分です**(下の「なぜJOINではなく2カーソルなのか」参照)。あえて手動の2カーソルで書くのは、JOINの裏でM1/MRが内部で行っている「2つの流れを付き合わせる」仕組みそのものを、技法として理解するためであり、これは実務での推奨実装ではなく、このレッスンだけの教育的な選択です。

## 新出

- 中核概念:
  1. 一致レコード処理(M1/MR)→SQLの2カーソル・マージという対応。`JUCHUD`(明細)を駆動するカーソルと、`JUCHUM`(見出し)を追従させるカーソルを、キー順(`JUNO`)に沿って手動で付き合わせることで、M1/MRのサイクル機構が内部で行っている「両方の流れが同じキー順に並んでいることを前提に、片方が遅れていたら進める」というマージ結合を、明示的な手続きとして再現します。
- 構文:
  1. **2カーソルの同時FETCH(ラグ追従)パターン**——`DECLARE C1/C2 CURSOR FOR ... ORDER BY`で駆動側・追従側の2本のカーソルを宣言し、駆動側(`C1`)を1行進めるたびに、追従側(`C2`)のキーがまだ駆動側より小さい間だけ`C2`を進める、という書き方です。カーソルが尽きたことは`SQLSTATE = '02000'`(該当行なし)で検出します(この値自体もこのパターンの一部として扱い、新出は本項目1件だけに数えます)。`DECLARE CURSOR FOR`・`OPEN`・`FETCH INTO`・`CLOSE`という構文自体は06-13/06-14の復習ですが、**2本のカーソルを、片方が片方に追従する形で組み合わせて回す**という使い方はこのレッスンが初出です。
- **既習の応用(新出に数えない)**: `CRTSQLRPGI OBJTYPE(*PGM)`と`SET OPTION`(06-13で既出)、`CHAIN`(extenderなし、04-07)、`%subst`/`%char`/`%trimr`(06-06)、そして**CLの`PARM()`の型不一致という03-08の教訓を、`JU0900C`→`ZA0500`よりもう1段呼び出し先の`C0805B`→`Q0805B`で再適用すること**(05-13チケット1と同じ種類の問題が、別の場所でもう一度起こり得ることの確認)。`TXSNAP`(`CPYSPLF`)・`CMPPFM`・SQLの`EXCEPT`による比較手法自体も、05-08で確立・08-05で復習済みのまま、本節でも実際に使います(`CMPPFM`が主たる根拠、`EXCEPT`が補助——08-05と同じ位置づけです)。

### `ZA0500`のM1/MR処理(05-03の復習)

`src/legacy/qrpgsrc/za0500.rpg`のF仕様書・I仕様書・C仕様書の該当部分です。

```text
     FJUCHUD  IP  F      27            DISK
     FJUCHUM  IS  F      26            DISK
     IJUCHUD  AA  01
     I                                        1   6 JUNO    M1
     IJUCHUM  AA  02
```

F仕様書の3桁目(ファイル・タイプの次の欄)を見ると、`JUCHUD`(明細)は`IP`(**P**rimary、主ファイル)、`JUCHUM`(見出し)は`IS`(**S**econdary、従ファイル)です。`IJUCHUD`・`IJUCHUM`のI仕様書は、どちらも`JUNO`に`M1`(マッチング・フィールド1)を付けています。`JUCHUD`(明細、`01`インジケーター)と`JUCHUM`(見出し、`02`インジケーター)は、どちらも`JUNO`の昇順に並んでいることが前提で、RPG/400のサイクルは主ファイル・従ファイルを同時に読み進めながら、`JUNO`が一致した組だけを`MR`(Match Record)インジケーターでON にします。C仕様書の`C 01 MR GOTO PROCLN`が、`01 MR`(=明細行かつ一致した組)のときだけ在庫引当の処理(`PROCLN`)へ分岐させている行です——見出し側(`02`)だけの検出や、一致しない明細行は、この分岐に入らず`GOTO SKPALL`へ流れます。

### `Q0805B`の2カーソル・マージ(実装)

`solutions/08-05/q0805bs.sqlrpgle`(`Q0805B`)は、この仕組みを2本の埋め込みSQLカーソルで手動再現します。`JUCHUD`は`JUNO`/`JULINE`の複合キー、`JUCHUM`は`JUNO`単独キーのファイルなので(`db/v1/juchud.pf`・`db/v1/juchum.pf`のキー指定)、どちらも`ORDER BY`でその順序を明示すれば、M1/MRが前提とする「キー順に並んでいること」を満たせます。

```rpgle
exec sql
  DECLARE C1 CURSOR FOR
    SELECT JUNO, JULINE, JUSHO, JUSU
      FROM JUCHUD
      ORDER BY JUNO, JULINE;

exec sql
  DECLARE C2 CURSOR FOR
    SELECT JUNO
      FROM JUCHUM
      ORDER BY JUNO;
```

`C1`(`JUCHUD`)が**駆動側**です。1回のループで必ず1行`FETCH`し、そのつど処理します(`za0500.rpg`の主ファイル=`IP`という役割をそのまま引き継いでいます)。`C2`(`JUCHUM`)は**追従側**で、毎回進めるのではなく、「`C2`が読んでいる見出しの`JUNO`(`hJuno`)が、`C1`の今の行の`JUNO`(`lJuno`)よりまだ小さい」間だけ進めます。1件の見出しに対して複数の明細行(`JULINE`が1、2、3…)が対応し得るため、明細側が進んでも見出し側をすぐには進めない、という非対称な組み方が要点です。

ループに入る前に、両方のカーソルを**1回だけ先に`FETCH`**しておく「プライミング」が必要です。まだ何も比較していない最初の時点では`lJuno`(`C1`側)と`hJuno`(`C2`側)のどちらにも値が入っていないため、比較のしようがありません。

```rpgle
exec sql OPEN C1;
exec sql OPEN C2;

exec sql FETCH C1 INTO :lJuno, :lJuline, :lJusho, :lJusu;
if SQLSTATE = '02000';
  eof1 = *on;
endif;

exec sql FETCH C2 INTO :hJuno;
if SQLSTATE = '02000';
  eof2 = *on;
else;
  haveHeader = *on;
endif;
```

これで`lJuno`/`hJuno`とも`C1`/`C2`の最初の行の値がそろい、`haveHeader`も(見出しが1件でも読めていれば)`*on`になります。ここから先が、本節の新出構文であるメイン・ループです。

```rpgle
dow not eof1;
  // Advance the header cursor while it still lags behind this line's
  // JUNO - see header, "TWO-CURSOR MERGE".
  dow not eof2 and hJuno < lJuno;
    exec sql FETCH C2 INTO :hJuno;
    if SQLSTATE = '02000';
      eof2 = *on;
      haveHeader = *off;
    endif;
  enddo;

  if haveHeader and hJuno = lJuno;
    processLine();
  endif;
  // else: unmatched line, silently skipped - see header.

  exec sql FETCH C1 INTO :lJuno, :lJuline, :lJusho, :lJusu;
  if SQLSTATE = '02000';
    eof1 = *on;
  endif;
enddo;
```

`haveHeader and hJuno = lJuno`が、`za0500.rpg`の`01 MR`ゲートに相当します。もし`JUCHUD`のある行の`JUNO`に対応する`JUCHUM`の見出しが存在しなければ(`db/data/load_v1.sql`の実データにはこのケースはありません)、その行は黙ってスキップされます——`01`だけが立って`MR`が立たない場合、元のM1/MRサイクルでも同じ行が処理されないのと同じ挙動です。

### `processLine`(在庫引当そのものは無変更)

在庫を引き当てる判断ロジック自体は`za0500.rpg`から一切変えていません。

```rpgle
dcl-proc processLine;
  dcl-pi *n;
  end-pi;

  chain lJusho zaikom;
  if not %found(zaikom);
    statusText = 'NOTFOUND';
    printLine();
    return;
  endif;

  avail = zasu - lJusu;
  if avail < minqty;
    statusText = 'SHORT';
  else;
    statusText = 'OK';
    if rmode = '*LIVE';
      zasu = avail;
      update zaikor;
    endif;
  endif;

  printLine();
end-proc;
```

`chain lJusho zaikom;`に`(E)`拡張子が付いていない点も、`za0500.rpg`の素の`CHAIN`をそのまま踏襲したものです。

**ロック・リークも、あえて直さず引き継いでいます。** `SHORT`のとき、または見つかったが`*LIVE`でないときの分岐に、`UNLOCK`が一つもありません。これは`za0500.rpg`自身に元から`UNLOCK`が無いことをそのまま再現したもので、**バグではなく意図的な選択です**。対照的に、07-05の`solutions/07-05/zaisrv.rpgle`の`reserve()`は、まさにこの種の隙間(SHORT分岐でロックが残る)を実際に見つけて`UNLOCK`を1回追加する修正をしています。同じ種類の欠陥を、一方(`zaisrv.rpgle`)は直し、もう一方(`Q0805B`)はあえて直さない——**特性検定が要求するのは「出力が元とバイト単位で一致すること」であり、`UNLOCK`を足すことはその範囲を超えた機能改善になってしまうため、ここでは見送っています。** こうした本来の改善は、忠実な移植の**先**を扱う場で行うべき仕事で、第10部の総合演習C([10-03](../part10/10-03-modernization-devbase.md))が行います(`ZAISRV`の`reserve()`に在庫の引き当てを任せ、`ZA0500`自身はロックを抱えない構成にし、`ZA0ORIG`を控えに同じ名前で差し替えます)。

### なぜJOINではなく2カーソルなのか

`SELECT D.JUNO, D.JUSHO, D.JUSU FROM JUCHUD D JOIN JUCHUM M ON D.JUNO = M.JUNO ORDER BY D.JUNO, D.JULINE`のような単純なJOINでも、同じ結果セットを1本のカーソルで取り出せます(**読解用として挙げるだけで、このリポジトリではコンパイル・実行していません**)。しかし、JOINはM1/MRが内部で行っている「2つの流れを、それぞれの位置を保ったまま付き合わせる」という仕組み自体を隠してしまいます。このレッスンの目的はM1/MRという**技法**の対応先を理解することなので、`Q0805B`はあえて手動の2カーソル・マージを選んでいます(`solutions/08-05/q0805bs.sqlrpgle`冒頭コメント)。

### `RMODE`/`MINQTY`:もう1段深いところにあった、同じ型不一致

`Q0805B`の`dcl-pi`は次のとおりです。

```rpgle
dcl-pi *n;
  rmode  char(10);
  minqty packed(5:0);
end-pi;
```

03-08で学んだとおり、OPM系の`CALL`で`PARM()`に裸のリテラルを書くと、**数値リテラルは既定でパック10進`(15 5)`(8バイト)として渡され**、**文字リテラルは32バイト未満なら32バイトに埋められて渡されます**。`Q0805B`の`rmode`(`char(10)`)・`minqty`(`packed(5:0)`、3バイト)という2つの受け側の型・長さを踏まえると、裸のリテラルで直接`CALL`したときに何が起きるかは、次の演習2で自分で予想してみてください。これは05-13チケット1で見た「`JU0900C`の`&MINQTY`(3,0)と`ZA0500`の`*ENTRY PLIST`(5,0)の食い違い」と**同じ種類の問題**(呼び出し側と受け側で型・長さの合意が取れていない)が、1段深いところ(`Q0805B`を直接呼ぶ側)でもう一度現れる、という話です。**このリポジトリの実機検証でも、実際にこの食い違いを踏んで実行時エラーを起こしています**(下の「実機メモ」参照)。`Q0805B`を安全に呼ぶには、呼び出し側が`&MINQTY`を`*DEC LEN(5 0)`の**CL変数として宣言してから**渡す必要があります——これが演習の課題です。

### 1. 2カーソル・マージを手で追う(紙上演習、5250不要)

本節唯一の新出構文(2カーソルの同時FETCH、ラグ追従パターン)を、実機を使わずに手で追ってみます。`db/data/load_v1.sql`の実データから、`JUCHUD`(明細、`C1`)の先頭5行と`JUCHUM`(見出し、`C2`)の先頭3件は次のとおりです。

| C1の現在行 | 入る前のhJuno | hJuno < lJuno? | 進めた後のhJuno | processLine? |
|---|---|---|---|---|
| J00001/1 | J00001 | ? | (変化なし) | ? |
| J00001/2 | J00001 | ? | (変化なし) | ? |
| J00002/1 | J00001 | ? | ? | ? |
| J00003/1 | ? | ? | ? | ? |
| J00003/2 | J00003 | ? | (変化なし) | ? |

<details><summary>答え合わせ</summary>

| C1の現在行 | 入る前のhJuno | hJuno < lJuno? | 進めた後のhJuno | processLine? |
|---|---|---|---|---|
| J00001/1 | J00001 | いいえ(J00001はJ00001未満ではない) | J00001のまま | 呼ぶ(J00001=J00001) |

### 2. 予想してから試す:裸のリテラルで`Q0805B`を直接呼ぶとどうなるか

05-08と同じ「予想してから試す」の形です。`Q0805B`の`dcl-pi`(上の「説明」参照)と、03-08で学んだCLのリテラル渡しのルールを踏まえて、次のコマンドを実行すると何が起きるか、**先に予想してから**実際に試してください。

```text
CALL PGM(<自分のユーザー名>1/Q0805B) PARM('*TEST' 5)
```

<details><summary>予想の方向性</summary>

`'*TEST'`は文字リテラルなので32バイトに埋められて渡され、`char(10)`の`rmode`はその先頭10バイトを読むだけなので問題になりません。一方`5`は裸の数値リテラルなので、既定でパック10進`(15 5)`(8バイト)として渡されます。`Q0805B`の`minqty`は`packed(5:0)`(3バイト)で宣言されているため、渡された8バイトのうち**先頭3バイトだけ**を`minqty`として読みます。その3バイトには有効な符号ニブルが入っておらず、`processLine`内の`if avail < minqty;`で不正な値を使おうとして、10進データ・エラー(`MCH1202`)で異常終了するはずです。

</details>

実際に試し、`DSPJOBLOG`で`MCH1202`(10進データ・エラー)が記録されていることを確認してください(このリポジトリの実機検証でも、まったく同じ原因・同じ文で同じエラーを実際に踏んでいます——下の「実機メモ」参照)。**対話的に実行しているので、応答待ちの照会メッセージが出るかもしれません。** 出た場合は`C`(取消)で応答してください(05-11で確認した`RPG0907`の`(C G S D F)`応答形式と同種の扱いですが、`MCH1202`がILEプログラムの対話セッションで具体的にどう表示されるかは、このリポジトリではまだ確認していません——未検証)。**この演習は必ず対話的な5250セッションで試してください。** もし`SBMJOB`でバッチ投入する場合は、`docs/style-guide.md`のPUB400作法どおり、必ず`INQMSGRPY(*DFT)`・`LOG(4 00 *SECLVL)`を付けてください(応答できない照会メッセージでジョブがハングするおそれがあります)。

### 3. `C0805B`を書く:`RMODE`/`MINQTY`を正しい型で渡す

`Q0805B`を安全に呼び出す小さなCLプログラム`C0805B`を、自分で書いてください。パラメーターは受け取らず(あとの演習4ではパラメーター無しで呼びます)、内部で`'*TEST'`用に固定した値を使う、という単純な作りで構いません。要件は次のとおりです。

- `&RMODE`を`TYPE(*CHAR) LEN(10)`で宣言し、`'*TEST'`を設定する。
- `&MINQTY`を`TYPE(*DEC) LEN(5 0)`で宣言し、`5`を設定する——**なぜ`(5 0)`でなければならないか、`Q0805B`の`dcl-pi`の`minqty packed(5:0)`宣言を根拠に説明できるようにしてください。** `solutions/05-13/ju0900c-ticket1.clp`の`&MINQTY`宣言・`CHGVAR VAR(&MINQTY) VALUE(5)`(`ju0900c-ticket1.clp`は`ZA0500`を`5,0`に合わせて修正した版です)が、同じ考え方の実例として参考になります。**05-13のチケット1で自分が`ZA0500`側を`3,0`に狭める修正を選んでいた場合でも(この場合`JU0900C`自体は変更されていないはずです)、自分のその`ZA0500`/`JU0900C`をそのまま参考にしないでください** ——`C0805B`が合わせるべき相手は`Q0805B`の`dcl-pi`(`5,0`固定)であり、自分が05-13でどちらの側に合わせたかとは無関係です。
- `Q0805B`を無修飾の`CALL PGM(Q0805B) PARM(&RMODE &MINQTY)`で呼び出す(`*LIBL`で解決させ、ライブラリー名をソースに直接書き込みません——`docs/style-guide.md`「ライブラリーの使い分け」。`Q0805B`自身が`ZAIKOM`などを無修飾で参照しているのと同じ考え方です)。

`C0805B`のソースは、08-01で作った自分のgitプロジェクト(またはその複製)の中に`c0805b.clp`のようなファイルとして書いてください——コンパイル用のメンバーだけに直接書き込むと、gitの追跡対象から外れ、このあとの「段階ごとにコミット」ができません。書いたらSSH経由で作業用のディレクトリーへ置き、次のように`<自分のユーザー名>1/QCLSRC(C0805B)`へ取り込んでからコンパイルしてください。

```sh
system "CPYFRMSTMF FROMSTMF('/home/<自分のユーザー名>/<作業ディレクトリー>/c0805b.clp') TOMBR('/QSYS.LIB/<自分のユーザー名>1.LIB/QCLSRC.FILE/C0805B.MBR') MBROPT(*REPLACE) STMFCCSID(1208)"
```

```text
CRTCLPGM PGM(<自分のユーザー名>1/C0805B) SRCFILE(<自分のユーザー名>1/QCLSRC) SRCMBR(C0805B)
```

本文にはコード全体を貼りません(`docs/style-guide.md`の方針どおりです)。書けたら実行し、実演の手順5で確認したものと同じ12行が`MCH1202`無しで印字されることを確認してください。**このリポジトリの検証ハーネス自身も、`Q0805B`を実行するために同じ理由で作った小さなCLプログラム(`verify/part08-05-f0805a/src/q0805bh.clp`、`Q0805BH`)を使っており、実機で正しく動くことを確認済みです。** ただしこれは学習者向けの演習用オブジェクトではなく、この教材の検証ハーネス自身が使う検証専用のオブジェクトです(`&LIB`パラメーターを受け取る作りなど、細部はここでの要件とも異なり、このカリキュラムの一部でもありません——08-04・08-05の実機メモが繰り返す「検証ハーネス自身の方針、`docs/probes.md`参照」というのと同じ扱いです)。自分の`C0805B`を書き終えたあとの参考として読む分には構いませんが、そのままコピーするのではなく、まず自分で書いてみてください。

### 4. `TXSNAP`+`CMPPFM`で差分0を確認する

05-08・08-05で使った`TXSNAP`/`CMPPFM`/`src/sql/05-08-compare.sql`の手順をそのまま再利用します(復習、新出ではありません)。

1. **`<自分のユーザー名>1/TXRESET`を実行します。** 実演の手順4で説明したとおり、これはgolden-master.mdと同じ数字を得るためだけではなく、`JUCHUM`の到着順が`JUNO`順と一致した状態・`JUSU`に無効なデータが残っていない状態を保証するための、この比較そのものの前提です。

2. `ZA0500`(`JU0900C`経由、`RMODE='*TEST'`)をBEFORE役として撮ります。`JU0900C`・`ZA0500`はどちらもOPM(呼び出し元と同じ活性化グループ)なので、素直な`OVRPRTF`/`DLTOVR`で十分です。

   <details><summary>RPG III を通らないルートの人へ(演習4の手順2)</summary>

   ルートでは、`JU0900C` は OPM の CL、`ZA0500` は ILE RPG(`DFTACTGRP(*YES)`)です。どちらも既定の活性化グループで動くので、呼び出し元と同じ活性化グループで動く点は、RPG III 版と同じはずです。`ZA0500` が `DFTACTGRP(*YES)` で 00 highest severity になることは実機で確認しました(part05-lggold、2026-10-04)。素直な `OVRPRTF`/`DLTOVR` で足りる、という書き方そのものは、非対話の検証では確かめられていません(検証の接続では `CPYSPLF FILE(QSYSPRT)` が `CPF3303` で失敗するため)。**この点は未検証(2026-10-04時点)** です。

   </details>

   ```text
   OVRPRTF FILE(QSYSPRT) SPLFNAME(ZA0500B) HOLD(*YES)
   CALL PGM(<自分のユーザー名>1/JU0900C) PARM('*TEST' '<自分のユーザー名>1')
   TXSNAP LABEL(BEFORE) LIB(<自分のユーザー名>1) SPLF(ZA0500B)
   DLTOVR FILE(QSYSPRT)
   ```

3. `C0805B`経由の`Q0805B`(`RMODE='*TEST'`)をAFTER役として撮ります。**`Q0805B`は`ACTGRP(*NEW)`のプログラムです**——08-05の`F0805A`と同じ理由で、コマンド行(対話ジョブの既定の活性化グループ)で発行した`OVRPRTF`が、`CALL`で新しく作られる`Q0805B`自身の活性化グループの中の`QSYSPRT`オープンまで届くかどうかは自明ではないため、**`OVRSCOPE(*JOB)`を付けて防御的に対処します**(この組み合わせ自体は、08-05の`F0805A`と同様、このリポジトリではまだ実機確認していません——未検証)。

   ```text
   OVRPRTF FILE(QSYSPRT) SPLFNAME(ZA0500B) HOLD(*YES) OVRSCOPE(*JOB)
   CALL PGM(<自分のユーザー名>1/C0805B)
   TXSNAP LABEL(AFTER) LIB(<自分のユーザー名>1) SPLF(ZA0500B)
   DLTOVR FILE(QSYSPRT)
   ```

   **`BEFORE`/`AFTER`という同じラベルを使うのは意図的です。** `05-08-compare.sql`のエイリアス(`QTEMP.SNAPB`/`QTEMP.SNAPA`)は、このラベルをそのまま前提にしています。05-08で撮った`TXSNAPT`の内容はこの手順で上書きされますが、05-08自体の演習は既に終わっているはずなので問題ありません。`WRKSPLF`に`ZA0500B`という名前のスプールが見当たらない場合は、実際に付いた名前を確認し、`TXSNAP`の`SPLF()`をその名前に合わせてください。**この`DLTOVR`(既定の呼び出しレベル)が、直前の`OVRSCOPE(*JOB)`で付けたジョブ・レベルのオーバーライドまで消してくれるかどうかは未検証です**——次の演習5(発展)やこのあとの別レッスンで`QSYSPRT`を使う前に、必ずこのセッションを一度サインオフしてサインオンし直してください(08-05の実演・片付けと同じ注意です)。

4. **まず`CMPPFM`で、行の並び順まで含めて比較します。** `CMPPFM FILE(<自分のユーザー名>1/TXSNAPT) MBR(BEFORE) TOFILE(<自分のユーザー名>1/TXSNAPT) TOMBR(AFTER)`のような形です(08-05と同じく、**`CMPPFM`自体、この教材ではまだ実機で一度も実行されておらず(P17未実施)、パラメーターの正式な綴りも未確認です。`CMPPFM`を単独で(`F4`を使って)呼び出し、プロンプトの実際の指定名を確認してから使ってください**)。**この比較を`CMPPFM`から始める理由があります**——次の手順のSQLの`EXCEPT`は集合演算なので**行の並び順を見ません**し、**同じ内容の行が複数あれば1行に潰してしまいます**。2カーソル・マージの追従ロジック(`hJuno < lJuno`の判定)を書き違えると、行の**中身**を1つも変えないまま**並び順や件数だけ**が崩れる、という間違いが起こり得ますが、そのバグは`EXCEPT`だけでは検出できないおそれがあります。**`CMPPFM`で差分が無いことを、本レッスンの「差分0」の主たる根拠とします。**

5. (補助的な確認)`src/sql/05-08-compare.sql`には`COUNT(*)`で件数を確認するステップがコメントとして入っています。**まずこれを取り出して実行し、`SNAPB`・`SNAPA`がそれぞれ12行のはずであることを確認してください。** ACSの「実行SQLスクリプト」で本体を実行するときは、`<自分のライブラリー>`を`<自分のユーザー名>1`に置き換えます。05-08で学んだとおり、`EXCEPT`の結果が2つとも0行であること自体は「差分なし」の証拠にはなりません——比較の仕組み自体が壊れていて、両方とも同じ(空の)ものを比較している可能性があるからです。**件数が両方とも12行であることまで確認して初めて、そのあとの`EXCEPT`が両方向とも0行であることが「差分が無い」ことの補強になります。ただし上で説明したとおり並び順の違いはこれでは検出できないため、`CMPPFM`の代わりにはなりません。**

6. 差分0を確認できたら、コミットしてください(演習3で作った自分の作業リポジトリーへ、`TXSNAP`/`CMPPFM`の確認結果を短いメモとして残す形で構いません)。**手順1の`TXRESET`を飛ばしていた場合、`CMPPFM`・`EXCEPT`のどちらも差分0にならないことがあります。** そのときは`TXRESET`を実行してから手順2〜5をやり直してください(`ZA0500`・`Q0805B`とも`RMODE='*TEST'`で実行しているため、この時点で`ZAIKOM`自体は書き換わっていないはずです)。**この「`TXSNAP`+`CMPPFM`で差分0を確認する」手順自体は、このリポジトリのどの接続でもまだ実機確認していません**(下の「実機メモ」参照)。

### 5. (発展)追従カーソルを「毎回進める」に変えてみる

`Q0805B`の`C2`(追従カーソル)を進める`dow not eof2 and hJuno < lJuno;`という条件を、試しに「`C1`が1行進むたびに`C2`も必ず1回`FETCH`する」形に変えたら、どの行の処理結果が変わる(または行が増減する)と予想しますか?**先に予想してから**、実際に試してください。08-04の演習2と同じ考え方で、`~/ibmi-kyozai`の`solutions/08-05/q0805bs.sqlrpgle`自体は書き換えず、**別の作業用パスへコピーしたもの**を編集し、`CPYFRMSTMF`(コピー先のパスに差し替え)で`Q0805B`のメンバーへ上書きしてから`REPLACE(*YES)`で再コンパイルしてください。上の演習4の`CMPPFM`・SQLの`EXCEPT`がその差分を実際に検出できることを確認できたら、実演の手順2と同じ`CPYFRMSTMF`をもう一度実行して元のソースでメンバーを上書きし、`Q0805B`を`REPLACE(*YES)`で作り直してください。**この演習もまだこのリポジトリで実機確認していません(未検証)。**
