# 04-08b RPG III の CALL・PARM・PLIST を自分で書く

> 所要時間: 75分(長め)/ 前提レッスン: 04-08 / 目標番号: 3 / 観測方法: `WRKSPLF`・`DSPJOBLOG` / 道具: 5250(SEU)/ 同時接続数: 5250×1 / 作る・変えるオブジェクト: `<USER>1/R0408BA`〜`R0408BG` / DBVER: 1 / 依存するプローブ: なし / PTF 依存: なし / 容量の目安: わずか

## ゴール

- 呼ばれる側のプログラムを、`*ENTRY PLIST` と `PARM` で書ける(`04-08b-1`)。
- 呼ぶ側のプログラムを、`CALL` と `PARM` で書ける(`04-08b-2`)。
- 呼ぶ側と呼ばれる側で `PARM` の長さ・小数点位置が食い違うと何が起きるかを、自分の手で起こして説明できる(`04-08b-3`)。

## なぜ学ぶか

`R0408A` は得意先コードを `'C00001'` と決め打ちしていました。実際の業務プログラムは、呼び出し元から渡された値を受け取って動きます。**RPG III で「値を受け取る入口」を作るのが `*ENTRY PLIST` です。**

第5部の 05-13(保守チケット)のチケット1は、`JU0900C`(CL)が渡す `MINQTY` と、`ZA0500`(RPG III)の `*ENTRY PLIST` の長さ・小数点位置を、食い違わないように直す課題です。第5部では既存のソースを**読む**ことが中心なので、`*ENTRY PLIST` を自分で書く練習は、ここで済ませておきます。このレッスンでは、呼ぶ側も呼ばれる側も RPG III の小さなプログラムを使い、05-13 と同じ現象を自分で起こして観察します。

## 新出

- 呼ばれる側の `*ENTRY PLIST` と `PARM`(受け取る変数の長さ・小数点位置を、ここで決める)
- 呼ぶ側の `CALL` と `PARM`(変数の**場所**を渡す。参照渡し)
- 長さ・小数点位置の食い違いは、コンパイルでも呼び出しでも検査されない
- 命令: `CALL`・`PARM`・`PLIST`・`RETRN`

## 説明

### 呼ばれる側: `*ENTRY PLIST`

呼ばれる側の C 仕様書の先頭に、次の2種類の行を並べます。

| 行 | Factor 1 | 命令コード | Factor 2 | 結果フィールド | 長さ | 小数 |
|---|---|---|---|---|---|---|
| 入口の宣言 | `*ENTRY`(18桁目) | `PLIST` | (なし) | (なし) | | |
| パラメーター1個 | (なし) | `PARM` | (なし) | 受け取る変数名(43桁目) | 49〜51桁 | 52桁 |

- `PARM` は書いた順に、呼ぶ側の `PARM` と1対1で対応します。
- **`PARM` の結果フィールドに、長さ(49〜51桁)と、数値なら小数点位置(52桁)を書く**ことで、その変数が新しく定義されます。文字なら小数点位置は空欄、数値なら `0` でも必ず書きます(書かないと文字型になります)。
- `RETRN` は、呼び出し元へ**すぐに**戻ります。プログラムを終わらせたいときは、その前に `SETON LR` を実行します(`LR` が ON にならないまま戻ると、プログラムは開いたファイルなどを残したまま待機します)。

### 呼ぶ側: `CALL` と `PARM`

```text
C                     CALL 'R0408BA'              85
C                     PARM           CODE
C                     PARM           NAME
C                     PARM           RC
```

- `CALL` の Factor 2 にプログラム名を**引用符付きのリテラル**で書きます。ライブラリー・リスト(`*LIBL`)から探すので、呼ばれる側のあるライブラリーが `*LIBL` に入っている必要があります。
- 続く `PARM` の結果フィールドに、**すでに定義してある変数**を書きます。ここでは長さを書かず、変数の場所が呼ばれる側に渡ります。
- `CALL` の LO 標識(56〜57桁、ここでは `85`)は、呼び出しが**失敗したとき**に ON になります。後の実演のとおり、呼ばれるプログラムが見つからないときにも、呼ばれる側が異常終了したときにも ON になりました。

### 長さは検査されない

**コンパイラーは、呼ぶ側の `PARM` と呼ばれる側の `PARM` の長さ・小数点位置が合っているかを見ません。呼び出しの時にも見ません。** 03-08 で見た「コマンド行の `CALL` の罠」と同じ仕組みです。渡されるのは変数の先頭の場所だけなので、呼ばれる側は自分の宣言した長さのぶんだけ、その場所から読み書きします。

- 呼ぶ側が短く、呼ばれる側が長ければ、呼ぶ側の**隣の領域**を読み書きします。
- 数値では、隣の領域のバイトが数字として不正であれば、呼ばれる側が計算に使ったときに10進データ・エラーになります。
- RPG III が C 仕様書で作る数値の変数は、**パック10進数**です(実機のコンパイル・リストの相互参照で、`5,0` の変数が `P(5,0)` と表示されました)。パック10進数は、5桁なら3バイト、3桁なら2バイトを使います。

## 実演

### 1. 呼ばれる側 `R0408BA`(得意先コードから得意先名を返す)

1. `WRKMBRPDM FILE(<自分のユーザー名>1/QRPGSRC)` で `R0408BA`(`RPG`)を作る。
2. 次を、桁位置に注意しながら入力する(`src/qrpgsrc/r0408ba.rpg` と同じ内容です)。

   ```text
   ....+....1....+....2....+....3....+....4....+....5....+....6....+....7....+....8
         * R0408BA - called side: look up a customer name by code.
         * PARM 1 PCODE 6 in, PARM 2 PNAME 30 out, PARM 3 PRC 1,0 out
         * (0 = found, 1 = not found).
        H
        FTOKUIM  IF  E           K        DISK
        C           *ENTRY    PLIST
        C                     PARM           PCODE   6
        C                     PARM           PNAME  30
        C                     PARM           PRC     10
        C                     MOVE *BLANKS   PNAME
        C           PCODE     CHAINTOKUIM               99
        C   99                MOVEL'NOTFOUND'PNAME
        C   99                Z-ADD1         PRC
        C  N99                MOVELTOKNM     PNAME
        C  N99                Z-ADD0         PRC
        C                     SETON                     LR
        C                     RETRN
   ```

   - `TOKUIM` は `CHAIN` でキー(`TOKCD`)から読みます。F 仕様書の16桁目は `F`(全手続き)にします。空欄のままだと、`TOKUIM` が「プライマリー・ファイル」の扱いになり、コンパイルが止まります(実機で確認した `QRG2100`・`QRG5092`。`R0407A` の `FTOKUIM  IF  E` と見比べてください)。
   - 3つの `PARM` は、コード(6桁の文字)・名前(30桁の文字)・結果コード(1桁の数値。0=見つかった、1=無い)です。`PNAME` の30は、`TOKUIM` の `TOKNM` と同じ長さです。
   - `MOVE *BLANKS PNAME` で、先に名前を空白にしています。`MOVEL` は、短い文字を入れても残りの桁を空白にしないためです。
3. コンパイルする(`CRTRPGPGM`。04-01 と同じ手順です)。

### 2. 呼ぶ側 `R0408BB`

1. `R0408BB`(`RPG`)を作り、次を入力する(`src/qrpgsrc/r0408bb.rpg` と同じ内容です)。

   ```text
   ....+....1....+....2....+....3....+....4....+....5....+....6....+....7....+....8
         * R0408BB - calling side: pass a customer code, print the name.
         * Calls R0408BA. RC is set to 9 first so that a change is visible.
        H
        FQSYSPRT O   F     132            PRINTER
        C                     MOVEL'C00001'  CODE    6
        C                     MOVE *BLANKS   NAME   30
        C                     Z-ADD9         RC      10
        C                     CALL 'R0408BA'              85
        C                     PARM           CODE
        C                     PARM           NAME
        C                     PARM           RC
        C                     EXCPT
        C                     SETON                     LR
        OQSYSPRT E
        O                         CODE       6
        O                                    8 '  '
        O                         NAME      38
        O                                   40 '  '
        O                         RC        41
        O                 85                55 'CALL FAILED'
   ```

   `RC` は、呼ばれる側が書き換えたことが分かるように、最初に `9` を入れています。`85` は `CALL` の失敗を受け取る標識で、失敗したときは `CALL FAILED` と印字します。
2. コンパイルし、`CALL PGM(R0408BB)` を実行する。**呼ばれる側 `R0408BA` のあるライブラリーが `*LIBL` に入っている必要があります**(入っていなければ `ADDLIBLE` で追加してください)。
3. `WRKSPLF` で、次のように印字されることを確認する。

   ```text
   C00001  ACME TRADING CO                 0
   ```

   得意先名が入り、`RC` は `9` から `0` に変わりました。呼ばれる側が、呼ぶ側の変数を書き換えたのです(参照渡し)。

### 3. 呼ばれる側が存在しないとき

`DLTPGM PGM(<自分のユーザー名>1/R0408BA)` で `R0408BA` をいったん消し、`R0408BB` をもう一度実行してみてください。ジョブ・ログに `MCH3401`(`Cannot resolve to object R0408BA.`)が出て、`85` が ON になり、`CALL FAILED` と印字されます(実機で確認)。確認したら、`R0408BA` をコンパイルし直しておきます。

### 4. 長さが食い違うと: 数値(05-13 と同じ現象)

1. 呼ばれる側 `R0408BC`(発注が要るかの判定。`QTY` は `5,0`)を作る(`src/qrpgsrc/r0408bc.rpg` と同じ内容です)。

   ```text
   ....+....1....+....2....+....3....+....4....+....5....+....6....+....7....+....8
         * R0408BC - called side: reorder check. QTY is 5,0.
         * PARM 1 QTY 5,0 in, PARM 2 FLG 1 out (R = reorder, O = ok).
        H
        C           *ENTRY    PLIST
        C                     PARM           QTY     50
        C                     PARM           FLG     1
        C           QTY       COMP 10                     90
        C   90                MOVEL'R'       FLG
        C  N90                MOVEL'O'       FLG
        C                     SETON                     LR
        C                     RETRN
   ```

   `QTY COMP 10` の結果は LO 標識(56〜57桁)の `90` です。`QTY` が10より小さければ `90` が ON になり、`FLG` に `R`(発注)、そうでなければ `O` を入れます。
2. 呼ぶ側 `R0408BD` を作る(`src/qrpgsrc/r0408bd.rpg` と同じ内容です)。**`QTY` を `3,0` で宣言している点が、`R0408BC` の `5,0` と食い違っています。**

   ```text
   ....+....1....+....2....+....3....+....4....+....5....+....6....+....7....+....8
         * R0408BD - calling side: QTY is 3,0 but R0408BC expects 5,0.
         * Experiment: the length mismatch is not checked.
        H
        FQSYSPRT O   F     132            PRINTER
        C                     Z-ADD5         QTY     30
        C                     MOVEL'-'       FLG     1
        C                     CALL 'R0408BC'              85
        C                     PARM           QTY
        C                     PARM           FLG
        C                     EXCPT
        C                     SETON                     LR
        OQSYSPRT E
        O                         QTY        5
        O                                    7 '  '
        O                         FLG        8
        O                 85                25 'CALL FAILED'
   ```

3. どちらもコンパイルする。**コンパイルはどちらも問題なく通ります**(最高重大度 00。実機で確認)。
4. `CALL PGM(R0408BD)` を実行する。**メッセージ `RPG0907`(10進データ・エラー)が出ます。** `(C G S D F)` の応答を求められたら `C`(取消)で答えてください。
5. `WRKSPLF` の印字と `DSPJOBLOG` を確認する。

   ```text
     005  -      CALL FAILED
   ```

   ジョブ・ログには、次の順に並びます(実機で確認)。

   ```text
   RPG0907: R0408BC 700 decimal-data error in field (C G S D F).
   RPG9001: Error RPG0907 caused program R0408BC to stop.
   ```

   `700` は `R0408BC` の文番号(ソースの7行目、`QTY COMP 10`)です。原因は次のとおりです。

   - 呼ぶ側の `QTY`(3桁のパック10進数)は2バイトです。
   - 呼ばれる側は、`QTY` を5桁のパック10進数(3バイト)として読みます。3バイト目は、呼ぶ側の `QTY` の隣にある、まったく別の変数のバイトです。
   - そのバイトが、パック10進数の末尾として不正だったため、計算(`COMP`)で10進データ・エラーになったと考えられます(隣のバイトの中身までは確認していません)。
   - 呼ぶ側の `QTY` 自体は壊れておらず(`005`と印字)、`FLG` は `-` のままです。`R0408BC` が異常終了したので、`CALL` の LO 標識 `85` が ON になり、`CALL FAILED` が印字されました。

   05-13 のチケット1(`JU0900C` の `MINQTY` 3,0 と `ZA0500` の 5,0)で起きた `RPG0907`(文8100)と、**同じ現象を、RPG III 同士で再現したものです。**

## 演習

1. (読む)`R0408BB` と `R0408BA` の `PARM` を、上から順に見比べて、対応表を作ってください。「呼ぶ側の変数名 / 長さ / 呼ばれる側の変数名 / 長さ」の4列で3行です。
2. (直す)`R0408BD` の `QTY` を、`R0408BC` に合わせて直してください。再コンパイルして実行すると、次のように印字されます。**直す場所は、C 仕様書の1か所(`QTY` の長さ)だけです。**

   ```text
      00005  R
   ```

   `RPG0907` が出なくなり、`5` は10より小さいので `R`(発注)が返ります。
3. (自分で書く)呼ばれる側 `R0408BF` と、呼ぶ側 `R0408BG` を、自分で書いてください。
   - `R0408BF`: 数量 `QTY`(`5,0`)と単価 `PRICE`(`7,0`)を受け取り、明細合計 `TOTAL`(`9,0`)に `QTY × PRICE`(`MULT`)を返す。
   - `R0408BG`: `3` と `1500` を渡して呼び、`TOTAL` を編集コード `1` で印字する。`4,500` と印字されれば合格です。
   - ヒント: 呼ばれる側の `PARM` は3個で、長さ・小数点位置は上のとおりに書きます。呼ぶ側では、`Z-ADD` で3つの変数を長さ・小数点位置つきで定義してから `CALL` します。**呼ぶ側の定義を `R0408BF` の `PARM` とそろえる**のを忘れないでください。
4. (応用)文字の長さを食い違わせると、どうなるでしょう。`R0408BE`(`src/qrpgsrc/r0408be.rpg`)は、`R0408BA` の30桁の `PNAME` に対して、**10桁の `NAME`** を渡します。すぐ後ろに、`GUARD`(`'GUARD'` を入れた10桁の文字)を宣言してあります。実行する**前に**、`NAME`・`GUARD`・`RC` に何が印字されるか予想し、実行して予想と比べてください。

   <details><summary>答え</summary>

   実機では、次のように印字されました(`R0408BA` は、30桁の名前を、10桁の `NAME` の場所へ書き込みます)。

   ```text
   /ACME TRADI/NG CO     /0
   ```

   - `NAME` には、名前の最初の10文字 `ACME TRADI` だけが見えます。
   - **`GUARD` の中身は `NG CO     `(名前の11〜20文字目)に書き換わりました。** `'GUARD'` は消えています。
   - どのメッセージも出ず、`CALL` の LO 標識も ON になりませんでした。**文字の長さの食い違いは、黙って隣の変数を壊します。** 数値のように10進データ・エラーで気づけるとは限らないぶん、たちが悪い食い違いです。
   - このとおりに隣の変数が壊れるのは、この実験で `NAME` の直後に `GUARD` を宣言したからです(実機では、宣言順に並んでいました)。一般には、隣に何があるかをソースだけから決めつけてはいけません。

   </details>

模範解答(演習2・3)は `solutions/04-08b/` にあります。

## 実機メモ

- 確認日: 2026-09-30。**V2(非対話の SSH バッチで、コンパイルと実行を確認)。** `<USER>2` で `CRTRPGPGM` した `R0408BA`〜`R0408BG` はすべて最高重大度 00 でコンパイルできた(F 仕様書16桁目の `F` を抜かした最初の版は `QRG2100`・`QRG5092` で止まったので、上の説明に書いた)。
- `R0408BB` は `C00001  ACME TRADING CO                 0` を印字した。`R0408BG` は `4,500` を印字した。
- 呼ばれる側が無いとき(`R0408BB` を `R0408BA` 未作成の状態で実行)は `MCH3401` が出て、LO 標識 `85` が ON になり `CALL FAILED` と印字された。
- 数値の食い違い(`R0408BD` → `R0408BC`)は、`RPG0907`(`R0408BC` の文700)→ `RPG9001` の順に出て、呼ぶ側では LO 標識 `85` が ON になり `CALL FAILED` が印字された。RPG 同士でも、CL 対 RPG(05-13、`RPG0907`、文8100)と同じ現象になることを確認した。バッチでは `CHGJOB INQMSGRPY(*DFT)` により、照会メッセージへ既定の `C` が自動で返っている。
- 修正版(`QTY` を `5,0` にした `R0408BD`)は、`00005  R` を印字した。
- 文字の食い違い(`R0408BE`)は、メッセージ無しで `GUARD` が上書きされた(演習4の答え)。
- **未確認(V3)**: 5250 の対話ジョブで `RPG0907` の照会メッセージに `C` で答えたときの画面の見え方。上の手順は、バッチでの結果と、`RPG0907` の一般的な挙動(付録B)に基づく。
- 食い違いに気づいたら [Issue](https://github.com/bluemoonjp/scratchpad-ibmi-learning-from-zero/issues) で教えてください。
