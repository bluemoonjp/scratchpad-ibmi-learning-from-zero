# 04-08b RPG III の CALL・PARM・PLIST を自分で書く

> 所要時間: 75分(長め)/ 前提レッスン: 04-08 / 目標番号: 3 / 観測方法: `WRKSPLF`・`DSPJOBLOG` / 道具: 5250(SEU)/ 同時接続数: 5250×1 / 作る・変えるオブジェクト: `<USER>1/R0408BA`〜`R0408BG` / DBVER: 1 / 依存するプローブ: なし / PTF 依存: なし / 容量の目安: わずか

## ゴール

- 呼ばれる側のプログラムを、`*ENTRY PLIST` と `PARM` で書ける(`04-08b-1`)。
- 呼ぶ側のプログラムを、`CALL` と `PARM` で書ける(`04-08b-2`)。
- 呼ぶ側と呼ばれる側で `PARM` の長さ・小数点位置が食い違うと何が起きるかを、自分の手で起こして説明できる(`04-08b-3`)。

## なぜ学ぶか

`R0408A` は得意先コードを `'C00001'` と決め打ちしていました。実際の業務プログラムは、呼び出し元から渡された値を受け取って動きます。**RPG III で「値を受け取る入口」を作るのが `*ENTRY PLIST` です。**

第5部の 05-13(保守チケット)のチケット1は、`JU0900C`(CL)が渡す `MINQTY` と、`ZA0500`(RPG III)の `*ENTRY PLIST` の長さ・小数点位置を、食い違わないように直す課題です。第5部では既存のソースを**読む**ことが中心なので、`*ENTRY PLIST` を自分で書く練習は、ここで済ませておきます。このレッスンでは、呼ぶ側も呼ばれる側も RPG III の小さなプログラムを使い、05-13 と同じ現象を自分で起こして観察します。

## 新出

- 呼ばれる側の `*ENTRY PLIST` と `PARM`(受け取る変数の長さ・小数点位置を、ここで決める)
- 呼ぶ側の `CALL` と `PARM`(変数の**場所**を渡す。参照渡し)
- 長さ・小数点位置の食い違いは、コンパイルでも呼び出しでも検査されない
- 命令: `CALL`・`PARM`・`PLIST`・`RETRN`

なお、`CALL` のエラー標識(失敗の検出)、パック10進数のバイト数、10進数データ・エラー(`RPG0907`)は、上の3つの概念を確かめる道具として、その場で説明します。

## 説明

### 呼ばれる側: `*ENTRY PLIST`

呼ばれる側の C 仕様書の先頭に、次の2種類の行を並べます。

| 行 | Factor 1 | 命令コード | Factor 2 | 結果フィールド | 長さ | 小数 |
|---|---|---|---|---|---|---|
| 入口の宣言 | `*ENTRY`(18桁目) | `PLIST` | (なし) | (なし) | | |
| パラメーター1個 | (なし) | `PARM` | (なし) | 受け取る変数名(43桁目) | 49〜51桁 | 52桁 |

- `PARM` は書いた順に、呼ぶ側の `PARM` と1対1で対応します。
- **`PARM` の結果フィールドに、長さ(49〜51桁)と、数値なら小数点位置(52桁)を書く**ことで、その変数が新しく定義されます。長さは右づめで書きます。たとえば `PARM           PRC     10` の `10` は「長さ10」ではなく、51桁目の `1`(長さ1)と52桁目の `0`(小数点以下0桁)です。`PNAME  30` の `30` は、49〜51桁の右づめで長さ30です。文字なら小数点位置は空欄、数値なら `0` でも必ず書きます(`Z-ADD` の結果フィールドと同じ規則で、省くと文字型の扱いになります。04-04 の `QRG7044`)。
- `RETRN` は、呼び出し元へ**すぐに**戻ります。プログラムを終わらせたいときは、04-01 と同じく、その前に `SETON LR` を実行します。この教材の呼ばれる側(`R0408BA`・`R0408BC`)は、どれも `SETON LR` の次の行が `RETRN` です(`LR` を ON にしないで戻ったときの挙動は、このレッスンでは試していません。04-01 で見た、`LR` を ON にしないとサイクルが止まらない話とは別の場面なので、ここでは必ず `SETON LR` を書いてください)。

### 呼ぶ側: `CALL` と `PARM`

```text
C                     CALL 'R0408BA'              85
C                     PARM           CODE
C                     PARM           NAME
C                     PARM           RC
```

- `CALL` の Factor 2 にプログラム名を**引用符付きのリテラル**で書きます。ライブラリー・リスト(`*LIBL`)から探すので、呼ばれる側のあるライブラリーが `*LIBL` に入っている必要があります。
- 続く `PARM` の結果フィールドに、**すでに定義してある変数**を書きます。ここでは長さを書かず、変数の場所が呼ばれる側に渡ります。
- `CALL` のエラー標識(56〜57桁、ここでは `85`。`COMP` で LO(より小さい)を書く桁と同じ場所ですが、`CALL` ではエラー標識の意味になります)は、呼び出しが**失敗したとき**に ON になります。後の実演のとおり、呼ばれるプログラムが見つからないときにも、呼ばれる側が異常終了したときにも ON になりました。

### 長さは検査されない

**コンパイラーは、呼ぶ側の `PARM` と呼ばれる側の `PARM` の長さ・小数点位置が合っているかを見ません。呼び出しの時にも見ません。** 03-08 で見た「コマンド行の `CALL` の罠」とは別の話ですが、同じ「参照渡し」の性質から来ています。渡されるのは変数の先頭の場所だけなので、呼ばれる側は自分の宣言した長さのぶんだけ、その場所から読み書きします。

- 呼ぶ側が短く、呼ばれる側が長ければ、呼ぶ側の**隣の領域**を読み書きします。
- 数値では、隣の領域のバイトが数字として不正であれば、呼ばれる側が計算に使ったときに10進数データ・エラーになります。
- RPG III が C 仕様書で作る数値の変数は、**パック10進数**です(実機のコンパイル・リストの相互参照で、`5,0` の変数が `P(5,0)` と表示されました)。パック10進数は、5桁なら3バイト、3桁なら2バイトを使います。

## 実演

### 準備

- `WRKLIBL` で、`<自分のユーザー名>1` がライブラリー・リストに入っていることを確認する。`R0408BA` が `TOKUIM` を開き、`R0408BB` が `R0408BA` を探すので、どちらも `*LIBL` から見つかる必要があります(見つからないと、04-06 の `RPG1216` のように止まることがあります)。入っていなければ `ADDLIBLE LIB(<自分のユーザー名>1)` で追加してください。
- 04-06〜04-08 を済ませていれば、`TOKUIM` に `C00001`(`ACME TRADING CO`)が入っています。
- プログラムは、`<自分のユーザー名>1` を現行ライブラリーにして作ります(`CHGCURLIB CURLIB(<自分のユーザー名>1)`)。

### 1. 呼ばれる側 `R0408BA`(得意先コードから得意先名を返す)

1. `WRKMBRPDM FILE(<自分のユーザー名>1/QRPGSRC)` で `R0408BA`(`RPG`)を作る。
2. 次を、桁位置に注意しながら入力する(`src/qrpgsrc/r0408ba.rpg` と同じ内容です)。

   ```text
   ....+....1....+....2....+....3....+....4....+....5....+....6....+....7....+....8
         * R0408BA - called side: look up a customer name by code.
         * PARM 1 PCODE 6 in, PARM 2 PNAME 30 out, PARM 3 PRC 1,0 out
         * (0 = found, 1 = not found).
        H
        FTOKUIM  IF  E           K        DISK
        C           *ENTRY    PLIST
        C                     PARM           PCODE   6
        C                     PARM           PNAME  30
        C                     PARM           PRC     10
        C                     MOVE *BLANKS   PNAME
        C           PCODE     CHAINTOKUIM               99
        C   99                MOVEL'NOTFOUND'PNAME
        C   99                Z-ADD1         PRC
        C  N99                MOVELTOKNM     PNAME
        C  N99                Z-ADD0         PRC
        C                     SETON                     LR
        C                     RETRN
   ```

   - `TOKUIM` は `CHAIN` でキー(`TOKCD`)から読みます。`FTOKUIM  IF  E` の `IF` の2文字目、つまり F 仕様書の16桁目の `F`(全手続き)は、`R0407A` と同じ書き方で、落とさないでください。空欄のままだと、コンパイルが止まります(実機の最初の版で `QRG2025`・`QRG2100`・`QRG5092` が出ました。`R0407A` の `FTOKUIM  IF  E` と見比べてください)。
   - 3つの `PARM` は、コード(6桁の文字)・名前(30桁の文字)・結果コード(1桁の数値。0=見つかった、1=無い)です。`PNAME` の30は、`TOKUIM` の `TOKNM` と同じ長さです。
   - `MOVE *BLANKS PNAME` で、先に名前を空白にしています。`MOVEL` は、短い文字を入れても残りの桁を空白にしないためです。
3. コンパイルする(`CRTRPGPGM`。04-01 と同じ手順です)。

### 2. 呼ぶ側 `R0408BB`

1. `R0408BB`(`RPG`)を作り、次を入力する(`src/qrpgsrc/r0408bb.rpg` と同じ内容です)。

   ```text
   ....+....1....+....2....+....3....+....4....+....5....+....6....+....7....+....8
         * R0408BB - calling side: pass a customer code, print the name.
         * Calls R0408BA. RC is set to 9 first so that a change is visible.
        H
        FQSYSPRT O   F     132            PRINTER
        C                     MOVEL'C00001'  CODE    6
        C                     MOVE *BLANKS   NAME   30
        C                     Z-ADD9         RC      10
        C                     CALL 'R0408BA'              85
        C                     PARM           CODE
        C                     PARM           NAME
        C                     PARM           RC
        C                     EXCPT
        C                     SETON                     LR
        OQSYSPRT E
        O                         CODE       6
        O                                    8 '  '
        O                         NAME      38
        O                                   40 '  '
        O                         RC        41
        O                 85                55 'CALL FAILED'
   ```

   `RC` は、呼ばれる側が書き換えたことが分かるように、最初に `9` を入れています。`85` は `CALL` の失敗を受け取る標識で、失敗したときは `CALL FAILED` と印字します。
2. コンパイルし、`CALL PGM(R0408BB)` を実行する。**呼ばれる側 `R0408BA` のあるライブラリーが `*LIBL` に入っている必要があります**(入っていなければ `ADDLIBLE` で追加してください)。
3. `WRKSPLF` で、次のように印字されることを確認する。

   ```text
   C00001  ACME TRADING CO                 0
   ```

   得意先名が入り、`RC` は `9` から `0` に変わりました。呼ばれる側が、呼ぶ側の変数を書き換えたのです(参照渡し)。

### 3. 呼ばれる側が存在しないとき

`DLTPGM PGM(<自分のユーザー名>1/R0408BA)` で `R0408BA` をいったん消し、`R0408BB` をもう一度実行してみてください。ジョブ・ログに `MCH3401`(`Cannot resolve to object R0408BA.`)が出て、`85` が ON になり、`CALL FAILED` と印字されるはずです(実機では、`R0408BA` がまだ作られていない状態で確認しました)。確認したら、`R0408BA` をコンパイルし直しておきます。

### 4. 長さが食い違うと: 数値(05-13 と同じ現象)

1. 呼ばれる側 `R0408BC`(発注が要るかの判定。`QTY` は `5,0`)を作る(`src/qrpgsrc/r0408bc.rpg` と同じ内容です)。

   ```text
   ....+....1....+....2....+....3....+....4....+....5....+....6....+....7....+....8
         * R0408BC - called side: reorder check. QTY is 5,0.
         * PARM 1 QTY 5,0 in, PARM 2 FLG 1 out (R = reorder, O = ok).
        H
        C           *ENTRY    PLIST
        C                     PARM           QTY     50
        C                     PARM           FLG     1
        C           QTY       COMP 10                     90
        C   90                MOVEL'R'       FLG
        C  N90                MOVEL'O'       FLG
        C                     SETON                     LR
        C                     RETRN
   ```

   `QTY COMP 10` の結果は、LO(より小さい)を書く56〜57桁の `90` です。`QTY` が10より小さければ `90` が ON になり、`FLG` に `R`(発注)、そうでなければ `O` を入れます。
2. 呼ぶ側 `R0408BD` を作る(`src/qrpgsrc/r0408bd.rpg` と同じ内容です)。**`QTY` を `3,0` で宣言している点が、`R0408BC` の `5,0` と食い違っています。**

   ```text
   ....+....1....+....2....+....3....+....4....+....5....+....6....+....7....+....8
         * R0408BD - calling side: QTY is 3,0 but R0408BC expects 5,0.
         * Experiment: the length mismatch is not checked.
        H
        FQSYSPRT O   F     132            PRINTER
        C                     Z-ADD5         QTY     30
        C                     MOVEL'-'       FLG     1
        C                     CALL 'R0408BC'              85
        C                     PARM           QTY
        C                     PARM           FLG
        C                     EXCPT
        C                     SETON                     LR
        OQSYSPRT E
        O                         QTY        5
        O                                    7 '  '
        O                         FLG        8
        O                 85                25 'CALL FAILED'
   ```

3. どちらもコンパイルする。**コンパイルはどちらも問題なく通ります**(最高重大度 00。実機で確認)。
4. `CALL PGM(R0408BD)` を実行する。**メッセージ `RPG0907`(10進数データ・エラー)が出ます。** `(C G S D F)` の応答を求められたら、返信欄に `C`(取消)を入れて Enter を押してください。`(C G S D F)` の他の答えは 04-12 で扱うので、今は `C` だけ覚えます。`C` のあとは、コマンド行に戻って、次の確認に進みます(5250 の対話ジョブでの見え方は未検証です。実機メモを参照)。
5. `WRKSPLF` の印字と `DSPJOBLOG` を確認する。

   ```text
     005  -      CALL FAILED
   ```

   ジョブ・ログには、次の順に並びました(実機で確認。呼ぶ側が `CALL` のエラー標識で失敗を受けたので、この実行のジョブ・ログには `CPF9999` は出ませんでした)。

   ```text
   RPG0907: R0408BC 700 decimal-data error in field (C G S D F).
   RPG9001: Error RPG0907 caused program R0408BC to stop.
   ```

   `700` は `R0408BC` の文番号(ソースの7行目、`QTY COMP 10`)です(ここの本文どおりの行数で入力した場合。行数がずれると、番号もずれます)。この `RPG0907` の原因は、次のように考えられます。

   - 呼ぶ側の `QTY`(3桁のパック10進数)は2バイトです。値 `5` は、16進で `005F` の形(末尾の `F` が符号)で入っています。
   - 呼ばれる側は、`QTY` を5桁のパック10進数(3バイト)として読みます。3バイト目は、呼ぶ側の `QTY` の隣にある、まったく別の変数のバイトです。呼ばれる側は `QTY` を読むだけで書かないので、隣の変数は書き換わりません。
   - 3桁ぶんの `005F` を5桁ぶんとして読むと、符号の `F` が数字の位置に来ます。数字の位置に `F` があるので、隣のバイトの中身に関係なく、計算(`COMP`)で10進数データ・エラーになったと考えられます(これはバイトの並びからの推定で、実機で中身を見て確かめたわけではありません)。逆に、呼ぶ側を長く(5,0)、呼ばれる側を短く(3,0)した場合にどうなるかは、試していません。
   - 呼ぶ側の `QTY` 自体は壊れておらず(`005`と印字)、`FLG` は `-` のままです。`R0408BC` が異常終了したので、`CALL` のエラー標識 `85` が ON になり、`CALL FAILED` が印字されました。

   05-13 のチケット1(`JU0900C` の `MINQTY` 3,0 と `ZA0500` の 5,0)で起きた `RPG0907`(文8100)と、**同じ現象を、RPG III 同士で再現したものです。** 対応は次のとおりです。

   | | 05-13(チケット1) | このレッスン |
   |---|---|---|
   | 呼ぶ側の宣言 | `JU0900C`(CL)の `DCL VAR(&MINQTY) TYPE(*DEC) LEN(3 0)` | `R0408BD` の `QTY` 3,0 |
   | 呼ばれる側の宣言 | `ZA0500` の `*ENTRY PLIST` の `MINQTY` 5,0 | `R0408BC` の `QTY` 5,0 |
   | 使うバイト数(パック10進数) | 呼ぶ側 2、呼ばれる側 3 | 呼ぶ側 2、呼ばれる側 3 |
   | 結果 | `RPG0907`(文8100) | `RPG0907`(文700) |

   05-13 のチケット1の直し方も、ここで直したのと同じです。両方の宣言を、同じ長さ・小数点位置にそろえます。

## 演習

1. (読む)`R0408BB` と `R0408BA` の `PARM` を、上から順に見比べて、対応表を作ってください。「呼ぶ側の変数名 / 長さ / 呼ばれる側の変数名 / 長さ」の4列で3行です。
2. (直す)`R0408BD` の `QTY` を、`R0408BC` に合わせて直してください。再コンパイルして実行すると、次のように印字されます。**直す場所は、C 仕様書の1か所(`QTY` の長さ)だけです**(先頭のコメントの「3,0」は、直さなくてかまいません)。

   ```text
   00005  R
   ```

   `RPG0907` が出なくなり、`5` は10より小さいので `R`(発注)が返ります。
   続けて、値を変えて試してください(この2つの出力は、実機では試していません)。`R0408BD` の `Z-ADD5` を `Z-ADD20` にすると、20 は10以上なので、`FLG` は `O` になるはずです。`R0408BB` の `'C00001'` を、`TOKUIM` にない `'C99999'` にすると、`NAME` は `NOTFOUND`、`RC` は `1` になるはずです。
3. (自分で書く)呼ばれる側 `R0408BF` と、呼ぶ側 `R0408BG` を、自分で書いてください。
   - `R0408BF`: 数量 `QTY`(`5,0`)と単価 `PRICE`(`7,0`)を受け取り、明細合計 `TOTAL`(`9,0`)に `QTY × PRICE`(`MULT`)を返す。
   - `R0408BG`: `3` と `1500` を渡して呼び、`TOTAL` を編集コード `1` で印字する。`4,500` と印字されれば合格です。
   - ヒント:
     - 呼ばれる側の `PARM` は3個で、長さ・小数点位置は上のとおりに書きます。`MULT` の結果フィールド `TOTAL` には、長さを書きません(`PARM` で定義済みだからです)。
     - 呼ぶ側では、`Z-ADD` で3つの変数(`TOTAL` は `Z-ADD 0` で構いません)を長さ・小数点位置つきで定義してから `CALL` します。**呼ぶ側の定義を `R0408BF` の `PARM` とそろえる**のを忘れないでください。
     - `R0408BB` をコピーして直すと、`FQSYSPRT`・`85` 標識・O 仕様書の形をそのまま使えます。編集コードは 04-08 を見返してください。
4. (応用)文字の長さを食い違わせると、どうなるでしょう。`R0408BE`(`src/qrpgsrc/r0408be.rpg`)を作ります。`R0408BA` の30桁の `PNAME` に対して、**10桁の `NAME`** を渡します。すぐ後ろに、`GUARD`(`'GUARD'` を入れた10桁の文字)を宣言してあります。

   ```text
   ....+....1....+....2....+....3....+....4....+....5....+....6....+....7....+....8
         * R0408BE - calling side, NAME is 10 long but R0408BA writes 30.
         * Experiment: the length mismatch is not checked. GUARD is the field
         * declared right after NAME.
        H
        FQSYSPRT O   F     132            PRINTER
        C                     MOVEL'C00001'  CODE    6
        C                     MOVE *BLANKS   NAME   10
        C                     MOVEL'GUARD'   GUARD  10
        C                     Z-ADD9         RC      10
        C                     CALL 'R0408BA'              85
        C                     PARM           CODE
        C                     PARM           NAME
        C                     PARM           RC
        C                     EXCPT
        C                     SETON                     LR
        OQSYSPRT E
        O                                    1 '/'
        O                         NAME      11
        O                                   12 '/'
        O                         GUARD     22
        O                                   23 '/'
        O                         RC        24
        O                 85                40 'CALL FAILED'
   ```

   O 仕様書の `'/'` は、値の境目を見やすくするための区切りです。実行する**前に**、`NAME`・`GUARD`・`RC` に何が印字されるか予想し、実行して予想と比べてください。予想のヒントは次の3つです。この実験では、変数は宣言した順に並ぶものとして考えます。
   - `R0408BA` の `MOVEL TOKNM PNAME` は、渡された場所から30文字ぶんを書きます。
   - `NAME` の場所は10文字ぶんしかありません。
   - `RC` は別の `PARM` なので、渡される場所が別です。`R0408BA` は最後に `PRC` へ `0` を入れます。

   <details><summary>答え</summary>

   実機では、次のように印字されました(`R0408BA` は、30桁の名前を、10桁の `NAME` の場所へ書き込みます)。

   ```text
   /ACME TRADI/NG CO     /0
   ```

   - `NAME` には、名前の最初の10文字 `ACME TRADI` だけが見えます。
   - **`GUARD` の中身は `NG CO` と空白5個(名前の11〜20文字目)に書き換わりました。** `'GUARD'` は消えています。
   - 名前の21〜30文字目は空白で、その空白の行き先は `GUARD` の後ろの領域です(何があるかは確認していません)。`RC` は `R0408BA` が最後に `0` を入れるので、`0` と印字されます。
   - どのメッセージも出ず、`CALL` のエラー標識も ON になりませんでした。**文字の長さの食い違いは、黙って隣の変数を壊します。** 数値のように10進数データ・エラーで気づけるとは限らないぶん、たちが悪い食い違いです。
   - このとおりに隣の変数が壊れるのは、この実験で `NAME` の直後に `GUARD` を宣言したからです(この実験では、宣言順に並んでいるように見えました)。壊れた領域は `GUARD` だけとは限りません(名前の21〜30文字目は `GUARD` のさらに後ろへ書かれています)。一般には、隣に何があるかをソースだけから決めつけてはいけません。

   </details>

模範解答(演習2・3)は `solutions/04-08b/` にあります。

## 実機メモ

- 確認日: 2026-09-30。確認したバージョン: IBM i V7R5M0(PUB400、コンパイル・リストの表示による)。**V2(非対話の SSH バッチで、コンパイルと実行を確認)。** 検証は `<USER>2` で行いましたが、本文の手順は `<USER>1` で作る形です(どちらでも同じ手順です)。 `<USER>2` で `CRTRPGPGM` した `R0408BA`〜`R0408BG` はすべて最高重大度 00 でコンパイルできた(F 仕様書16桁目の `F` を抜かした最初の版は `QRG2100`・`QRG5092` で止まったので、上の説明に書いた)。
- `R0408BB` は `C00001  ACME TRADING CO                 0` を印字した。`R0408BG` は `4,500` を印字した。
- 呼ばれる側が無いとき(`R0408BB` を `R0408BA` 未作成の状態で実行)は `MCH3401` が出て、エラー標識 `85` が ON になり `CALL FAILED` と印字された。
- 数値の食い違い(`R0408BD` → `R0408BC`)は、`RPG0907`(`R0408BC` の文700)→ `RPG9001` の順に出て、呼ぶ側ではエラー標識 `85` が ON になり `CALL FAILED` が印字された。RPG 同士でも、CL 対 RPG(05-13、`RPG0907`、文8100)と同じ現象になることを確認した。バッチでは `CHGJOB INQMSGRPY(*DFT)` により、照会メッセージへ既定の `C` が自動で返っている。
- 修正版(`QTY` を `5,0` にした `R0408BD`)は、`00005  R` を印字した。
- 文字の食い違い(`R0408BE`)は、メッセージ無しで `GUARD` が上書きされた(演習4の答え)。
- **未検証(2026-09-30時点、V3)**: 5250 の対話ジョブで `RPG0907` の照会メッセージに `C` で答えたときの画面の見え方。本文の手順は、バッチでの結果と、付録B(`RPG0907` は `(C G S D F)` を求める照会メッセージ)の記述から書いたものです。
