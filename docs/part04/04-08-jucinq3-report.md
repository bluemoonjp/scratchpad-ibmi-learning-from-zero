## なぜ学ぶか

**ここまでの部品(`CHAIN`・`READ`・`IFxx`・`GOTO`/`TAG`)を組み合わせれば、実用的な帳票プログラムが書けます。** 03-09 で CL 版(`JUCINQC`)を作った「得意先の受注一覧」を、ここでは RPG III の帳票として作ります(通し例3)。`JUCINQ` コマンドの CPP は、第6部(06-12)で RPG IV 版(`F0612A`)に差し替えます——`R0408A` 自体は得意先コードを固定リテラルで持ち、`*ENTRY PLIST` も無いため、このままではコマンドの CPP にはなれません。あわせて、04-02 で予告した**編集コード**を詳しく扱います。

## 新出

- 編集コード(数値の表示形式。1〜4、およびゼロのときの表示)
- 複数のファイル(`TOKUIM`・`JUCHUM`)を1つのプログラムで扱う

## 説明

### 編集コードの一覧

O 仕様書38桁目の編集コードは、数値フィールドの**印刷時の見た目**を決めます。

| 編集コード | 桁区切り(,) | 小数点 | 値がゼロのとき |
|---|---|---|---|
| (空白) | なし | なし(整数部のみ) | 0が並ぶ |
| 1 | あり | あり | 残る |
| 2 | あり | あり | 空白 |
| 3 | なし | あり | 残る |
| 4 | なし | あり | 空白 |

`1`〜`4` は「桁区切りの有無」と「ゼロのときに空白にするか残すか」の組み合わせです。実機で `1738.00`(小数2桁の数値)にそれぞれ試したところ、次のようになりました。

| 編集コード | 表示結果 |
|---|---|
| 1 | `1,738.00` |
| 3 | `1738.00`(桁区切りなし) |

また、値が `0.00` のとき、編集コード `2` では**空白**になり、編集コード `1` では**残ります**(一次資料の編集コード早見表による。「ゼロのとき空白にするかどうか」は偶数番号の編集コード側の性質で、`R0402A` の `TOTAL` は非ゼロ(`1738.00`)だったため、この性質自体はこのレッスンでは実演していません)。小数点以下の桁数がある場合、残る側は `.00` のように先頭に `0` を付けずに残ります(編集コード `3` で実機確認、一次資料の記述とも一致)。小数点以下の桁数が0のフィールド(`JUDATE`など)では、残る側の編集コードは一の位に `0` 一桁だけを印字します(06-12での実機確認による)。

**A・B・C・D、および J・K・L・M という編集コードもあります。桁区切り・ゼロ時の表示の規則はそれぞれ1・2・3・4と同じで、違うのは値が負のときの符号の付き方です**(A〜Dは`CR`、J〜Mは固定位置のマイナス記号。なお1〜4自体は負の値でも符号を表示しません)。**通貨記号(`$`)は編集コードの規則そのものとは別に指定する機能で、1〜4を含むどの編集コードにも付けられます。**この教材ではA〜D・J〜M・通貨記号のいずれも扱いません。

### 複数のファイルを1つのプログラムで扱う

```text
FTOKUIM  IF  E           K        DISK
FJUCHUM  IF  E                    DISK
```

F 仕様書は、必要なだけ複数書けます。`TOKUIM`(得意先マスター、`CHAIN` でキー・アクセス)と `JUCHUM`(受注マスター、`READ` で順に読む)を、両方入力ファイルとして宣言しています。

## 実演

1. `WRKMBRPDM FILE(<自分のユーザー名>1/QRPGSRC)` で `R0408A`(`RPG`)を作る。
2. 次を、桁位置に注意しながら入力する(`src/qrpgsrc/r0408s.rpg` と同じ内容です)。

   ```text
   ....+....1....+....2....+....3....+....4....+....5....+....6....+....7....+....8
         * R0408A - JUCINQ3: order inquiry report for one customer.
        H
        FTOKUIM  IF  E           K        DISK
        FJUCHUM  IF  E                    DISK
        FQSYSPRT O   F     132            PRINTER
        C                     MOVEL'C00001'  CUST    6
        C           CUST      CHAINTOKUIM               99
        C   99                MOVEL'NOTFOUND'TOKNM
        C           LOOP      TAG
        C                     READ JUCHUM                   98
        C   98                GOTO ENDLP
        C           JUTOK     IFEQ CUST
        C                     EXCPT
        C                     ENDIF
        C                     GOTO LOOP
        C           ENDLP     TAG
        C                     SETON                     LR
        OQSYSPRT E
        O                         TOKNM     30
        O                                   32 '  '
        O                         JUNO      38
        O                                   40 '  '
        O                         JUDATE    48
   ```

   得意先コード `CUST`(ここでは `'C00001'` に固定)を `TOKUIM` から `CHAIN` で探し、得意先名を取得します。次に `JUCHUM` を先頭から順に `READ` し、**得意先コードが一致する注文だけ**を印刷します(03-09 の CL 版 `JUCINQC` と、同じ絞り込みロジックです)。

3. コンパイルして `CALL PGM(R0408A)` を実行し、`WRKSPLF` で次のように印刷されることを確認する(02-06・03-09 で確認した結果と一致します)。

   ```text
   ACME TRADING CO                 J00001  20260901
   ACME TRADING CO                 J00003  20260905
   ```

## 演習

1. `'C00001'` を `'C00003'` に変えて再コンパイル・実行し、`J00004`・`J00008` の2件が印刷されることを確認してください。
2. `JUDATE` の O 仕様書の行に、編集コード `3`(38桁目に `3`)を追加してみてください。数値のままなので見た目はほぼ変わりませんが、`F4` プロンプトで編集コードの入力欄を確認する練習になります。
3. (発展)存在しない得意先コード(`'C99999'`)を指定すると、`TOKNM` は `NOTFOUND` になりますが、受注の絞り込み(`JUTOK IFEQ CUST`)には何も一致しないため、明細行が1件も印刷されません。実際に試して確認してください。

## 実機メモ

- 確認日: 2026-09-25。**`R0408A` を `<USER>2` で実際に `CRTRPGPGM` でコンパイル(Highest Severity 00)し、実行して `ACME TRADING CO J00001`/`J00003` の2行が正しく印刷されることを確認した。**
- 編集コードの表(1〜4)は、`TOTAL`(`1738.00`)に編集コード `1`/`3` を適用する実機テストで、桁区切りの有無を確認した。
- **【訂正、2026-09-28】ゼロ時の表示について、「編集コード1は空白・2は0が残る」という当初の記述は逆だった。** 第6部06-12(別レッスン)の検証で、ゼロ値を渡したフィールド(`EDTCDE(3)`)が実機で可視の`0`を印字し、空白にならなかったことがきっかけで発覚した。一次資料(ILE RPG言語リファレンス・RPG/400リファレンスの編集コード早見表、両方とも同じ内容)を確認したところ、**奇数(1・3)がゼロ残高を表示し、偶数(2・4)がゼロを空白にする**のが正しい仕様だった。当初の記述の実機生ログは残っておらず(該当接続の結果JSONは本レッスン執筆当時の一時ファイルで保存されていない)、一次資料と06-12での独立した実機再確認の両方から訂正した。あわせて「J・K・L・Mは通貨表示用」という記述も誤りで、実際は負の値の符号表示方法(CR・固定位置のマイナス記号)の違いだった(浮動マイナス記号はN〜Qという別の4つの編集コード。通貨記号はどの編集コードとも独立した機能)。詳細は`docs/probes.md`を参照。
- **追加確認(2026-09-28、同日の別接続)**: RPG III(O仕様書、`R0402A`と同じ書き方)で、小数2桁の値をゼロに固定し、編集コード1〜4を並べて実機で印字するプローブを実施した。**編集コード3(残す側、桁区切りなし)は`.00`(先頭に`0`を付けない)と印字され、編集コード4(空白にする側)は完全な空白だった**——一次資料の記述・上記の訂正内容と一致する。編集コード1・2は同じ接続で試したが、桁区切り対応の編集コード同士を10桁未満の間隔で並べたため、印字位置が一部重なるプローブ側の設計ミスがあり、正確な文字までは確認できなかった(詳細は`docs/probes.md`)。
- **このレッスンの検証中に、`<USER>2/JUCHUM` の実データが本来の2倍(16件)になっているという問題を発見した。** 原因は `tools/qclsrc/txsetup.clp` の設計ミスで、`FORCE(*YES)` で再実行すると、既存データを消さずに `load_v1.sql` を再投入してしまい、`UNIQUE` 制約のない `JUCHUM` のキー(`JUNO`)で重複が発生していた。**`txsetup.clp` を修正し(データ投入の直前に `reset_v1.sql` で全件削除するようにした)、`FORCE(*YES)` を2回連続実行しても重複しないことを実機で確認した。** 詳細は `docs/probes.md` を参照。この調査の過程で、`R0408A` 自体のロジックは最初から正しかったことも確認できている。
