## なぜ学ぶか

**ここまでのレッスンで、たくさんのコンパイル・エラー(`QRG` で始まるメッセージ)を見てきました。** 実は、エラーには大きく2種類あります。**コンパイル時のエラー**(桁がずれている、命令の書き方が違う、など)と、**実行時のエラー**(プログラムは正しくコンパイルされたが、実行中に想定外のデータや状況に遭遇した)です。実行時エラーは、コンパイル・エラーよりやっかいです。**RPG III は、多くの実行時エラーに対して「どうしますか?」と聞いてくる照会メッセージを出しますが、バッチ(非対話)ジョブではこれに誰も答えられず、ジョブが永遠に止まってしまいます。**

## 新出

- コンパイル・メッセージの重大度(Severity)と、生成基準を超えると失敗すること
- 実行時エラーの照会メッセージ(`INQUIRY`、重大度99)
- ゼロ除算(`RPG0102`)と、そのハング
- `COMP` による事前チェック(実行前に危険な条件を弾く)
- `DSPLOG`(履歴ログ)による実行時エラーの追跡

## 説明

### コンパイル・メッセージの読み方

これまで何度も見てきたとおり、コンパイル・リストの末尾には「Message Summary」(重大度別の件数)と「Final Summary」があります。**生成基準の重大度(既定で9)を超えるメッセージが1つでもあると、オブジェクトは作られません。** 重大度00〜09は「参考情報」、10以上は「要修正」と考えてください。

### 実行時エラーは照会メッセージになることがある

```text
C                     Z-ADD10        NUM     30
C                     Z-ADD0         ZERO    30
C           NUM       DIV  ZERO      ANSWER  30
```

これは10を0で割ろうとするコードです。**コンパイルは通りますが、実行すると `RPG0102`(重大度99、`INQUIRY`)というメッセージが出て、プログラムが止まります。** 実際のメッセージ本文は次のとおりです。

```text
RPG0102 99  INQUIRY   <プログラム名> <行番号> tried to divide by zero (factor 2) (C G S D F).
```

`(C G S D F)` は、`C`(取消)・`G`(継続)・`S`(ステップ)・`D`(ダンプ)・`F`(応答形式変更)のいずれかで**応答することを求めている**という意味です。**5250 の対話セッションなら画面にこのメッセージが出て応答できますが、SSH 経由のバッチ・ジョブのような非対話環境では誰も応答できず、ジョブが止まったままになります。** これは 04-06 で見た `RPG1216`(ファイルの暗黙オープン失敗)とまったく同じ種類の問題です。

**`DIV` の結果標識(`+`/`-`/`Z`。結果の符号を示す)は、ゼロ除算そのものを防いでくれません。** ゼロ除算は、結果標識の指定の有無にかかわらず発生します。

### 正しい対処: 割る前にチェックする

```text
C           ZERO      COMP 0                        60
C  N60      NUM       DIV  ZERO      ANSWER  30
C   60                MOVEL'DIV0ERR' MSG    10
```

`COMP` で除数(`ZERO`)がゼロかどうかを**先に**確認し、ゼロなら標識60を ON にします。`DIV` の行を `N60`(60が OFF のとき)で条件付けることで、**ゼロ除算そのものを実行しないようにします。** 標識60が ON のときは、代わりにエラー・メッセージを表示します。**「エラーが起きてから対処する」のではなく「エラーが起きる条件を先に弾く」のが、RPG III での基本的な考え方です。**

### 実行時エラーの調べ方

もし対話画面ではない経路(サブミット・ジョブなど)でプログラムが止まって応答がなくなったら:

1. `WRKACTJOB` で、止まっていそうなジョブを探す。
2. `DSPJOB OPTION(*PGMSTK)` で、そのジョブがどのプログラムのどこで止まっているかを確認する。
3. `DSPJOBLOG OUTPUT(*PRINT)`(または止まっているジョブそのものの `DSPJOBLOG`)で、実際に出ているメッセージを確認する。

これは 04-06 で `RPG1216` のハングを調べたときに実際に使った手順です。照会メッセージでジョブが止まっている場合、`WRKJOB` からそのジョブに対して応答するか、`ENDJOB` で終了させます。

### STRDBG(デバッガー)

`STRDBG PGM(<プログラム名>)` で、対話的なデバッガーを起動できます。行の途中で処理を止める(ブレークポイント)、変数の中身を見る、といった操作ができます。**これは対話的な5250セッションでの操作が前提のため、このレッスンでは操作方法の説明にとどめます。** 実際の操作は、ご自身の5250セッションで試してください。

## 実演

1. `WRKMBRPDM FILE(<自分のユーザー名>1/QRPGSRC)` で `R0412A`(`RPG`)を作る。次を入力する(`src/qrpgsrc/r0412s.rpg` と同じ内容です)。

   ```text
   ....+....1....+....2....+....3....+....4....+....5....+....6....+....7....+....8
         * R0412A - check the divisor before DIV (avoid RPG0102 inquiry).
        H
        FQSYSPRT O   F     132            PRINTER
        C                     Z-ADD10        NUM     30
        C                     Z-ADD0         ZERO    30
        C           ZERO      COMP 0                        60
        C  N60      NUM       DIV  ZERO      ANSWER  30
        C   60                MOVEL'DIV0ERR' MSG    10
        C                     EXCPT
        C                     SETON                         LR
        OQSYSPRT E
        O                N60      ANSWER    10
        O                 60      MSG       25
   ```

2. コンパイルして(Highest Severity 00 を確認)`CALL PGM(R0412A)` を実行し、`WRKSPLF` で `DIV0ERR` と印刷されることを確認する。

## 演習

1. `ZERO` を `Z-ADD0` から `Z-ADD2` に変えて再コンパイル・実行し、正常に `5`(10÷2)が印字されることを確認してください。
2. `COMP` の行を一時的にコメントアウトし(`N60` の条件も外して)再コンパイル・実行してみてください。**ジョブが応答を返さなくなる**(照会メッセージで止まる)ことを確認したら、`WRKACTJOB` でそのジョブを見つけて `ENDJOB` で終了させてください。確認後は元に戻してください。

## 実機メモ

- 確認日: 2026-09-25。**ゼロ除算が実際に `RPG0102`(重大度99、`INQUIRY`)を発生させ、SSH 経由の非対話バッチ・ジョブがハングすることを実機で確認した。** 実際のメッセージ本文(`... tried to divide by zero (factor 2) (C G S D F).`)は、止まったジョブの `DSPJOBLOG` からではなく、`DSPLOG PERIOD(...)` で当該時刻のシステム履歴ログを調べて確認した(止まったジョブ自体は SSH 接続の終了とともに自動的に片付いており、個別の `DSPJOBLOG` では追えなかった)。**これは 04-06 で見つけた `RPG1216`(暗黙オープン失敗)と同じ種類の問題であることが実機で裏付けられた。**
- `DIV` の結果標識(`+`/`-`/`Z`)は結果の符号を示すものであり、ゼロ除算の検出・防止には使えないことを実機で確認した(結果標識を指定していても `RPG0102` は発生した)。
- **`COMP` で除数を事前にチェックし、条件標識で `DIV` をスキップする防御パターンを実機で検証した。** `CRTRPGPGM`(Highest Severity 00)・実行の両方を確認し、`DIV0ERR` が正しく印字され、ハングしないことを確認した。
- `STRDBG` の対話的な操作そのもの(ブレークポイント設定・変数表示)は、実際の5250デバイスを必要とするため、このセッションの SSH バッチ経由では検証していない(一次資料に基づく記述)。
