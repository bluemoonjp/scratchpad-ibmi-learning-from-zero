# スタイル・ガイド

この教材のレッスン・ツール・サンプルを書く(直す)ときの共通ルールです。誤りの指摘や1レッスンの手直し程度であれば読む必要はありませんが、新しいレッスンを書く、既存のレッスンの構成を変える、といった貢献をする場合は目を通してください。[`CONTRIBUTING.md`](../CONTRIBUTING.md)も合わせて参照してください。

## レッスンの構成

各レッスンは、次の順で節を並べます(`##` 見出し)。

```
# NN-MM タイトル
> 所要時間 / 前提レッスン / 目標番号 / 観測方法 / 道具 / 同時接続数 /
  作る・変えるオブジェクト / DBVER / 依存するプローブ / PTF 依存 / 容量の目安

## ゴール
## ウォームアップ
## なぜ学ぶか
## 新出
## 説明
## 実演
## 演習
## セルフチェック
## 片付け
## まとめ
## 実機メモ
```

すべての節が毎回必要なわけではありません。たとえば各部末のチェックポイント(例: [04-13](part04/04-13-checkpoint-stock-list.md))は複数レッスンの総合演習なので、「ウォームアップ」「新出」「実演」を省き、代わりに演習を厚くしています。実際に何を省くかは、既存のレッスンで一番近い性格のものを手本にしてください。

節ごとの狙いは次のとおりです。

- **ゴール**: 確認 ID(例 `03-07-1`)を1〜3個。読者が「これができるようになる」と一目でわかる書き方にします。
- **ウォームアップ**: 前回の復習を2〜3問、`<details>` で答えを畳みます。
- **なぜ学ぶか**: 現場でどう使われるか、この先のどのレッスンで効いてくるかを書きます。
- **新出**: 中核概念は3つ、コマンド等は6つまでに絞ります。それ以外(読めればよいもの)は本文中で「読解用」として区別します。
- **説明**: 概念 → (必要なら)Windows/Linux 等との比較 → IBM i の実物、の順。英語画面には訳を添えます。
- **実演**: 番号付きの手順。コマンドはそのままコピーできる形にし、各手順で読者が見るはずの画面・出力を示します。
- **演習**: 例題を読む → 修正・穴埋め → 独力で → 応用、の順で難度を上げます。模範解答は `solutions/NN-MM/` に置き、本文には貼りません。
- **セルフチェック**: チェックボックス形式。自分で採点できる基準にします。
- **片付け**: 作ったオブジェクトの削除・スプールの後始末など。総称名( 例 `DLTPGM PGM(<USER>1/R04*)` )を使います。
- **まとめ**: 用語の英日対訳表、次のレッスンへの案内。
- **実機メモ**: 確認日・確認したバージョン・**まだ実測していない事項**を書きます。次の節で詳しく説明します。

## 断定しない: 実機メモと検証段階(V1/V2/V3)

この教材は「実機で確かめていないことを、確かめたかのように書かない」ことを最優先します。[`docs/probes.md`](probes.md)で使っている3段階の表記を、レッスンの実機メモでもそのまま使います。

- **V1(コンパイル確認)**: 実機でコンパイルが通り、最高重大度が許容範囲であることまで確認した。
- **V2(実行結果の一致)**: 非対話(バッチ/SSH)で実行し、出力が期待どおりであることまで確認した。
- **V3(対話操作)**: 5250 の画面操作・SEU・STRDBG など、対話でしか確認できない部分。この教材の検証ハーネス(`verify/`)は非対話でしか実機に接続しないため、V3 の部分は一次資料の記述と、レッスン本文の「実演」を読者自身が5250で試すことに委ねます。

未検証の内容を書く場合は、実機メモに **「未検証(YYYY-MM-DD時点)」** と明記し、断定形を避けてください(「〜のはずです」「〜と考えられます」)。検証済みになったら、確認日と何を確認したか(V1のみか、V2まで済んだか)を実機メモに書き直します。未検証のレッスンは、検証が済むまで `main` ブランチに公開しません(`draft/partNN` ブランチに置きます)。

## メッセージ ID・トラブルシューティング

出会うことが分かっているメッセージ ID(コンパイル・エラー、実行時エラー)は、本文中の表(ID → 原因 → 対処)で扱います。すでに分かっている広範なパターンは[付録B](appendix/b-message-ids.md)・[付録C](appendix/c-troubleshooting.md)に集約しているので、個別レッスンからはそちらへリンクしてもかまいません。

## オブジェクトの命名

- 演習用のオブジェクトは6文字、「種別1文字 + 部2桁 + 課2桁 + 連番1文字」の形式にします。
  - 種別: `C`=CL、`R`=RPG III、`V`=固定形式 RPG IV、`F`=`**FREE`、`Q`=SQLRPGLE、`M`=モジュール、`D`=DSPF、`P`=PRTF、`W`=作業用の PF・LF・表、`K`=コマンド、`B`=バインダー・ソース、`T`=テスト、`Z`=その他
  - 連番: `A`〜`R` は学習者が自分で書く用、`S`〜`Z` は配布する見本(模範解答等)
  - 例: `R0401A`(第4部01課の学習者用 RPG III)、`C0511S`(第5部11課の配布 CL)
- サンプル・データベースの業務ファイルは、上記の型に従わない固定名を使います(例: `TOKUIM`・`SHOHIM`・`JUCHUM`・`ZAIKOM`。詳しくは[付録E](appendix/e-naming.md)2節)。旧システム(第5部)も、現場でよくある命名をそのまま再現しています(`TK0100`・`JU0300`・`ZA0500`・`MN0000C` 等)。これらは意図的な例外なので、6文字の型に合わせ直す必要はありません。
- **`JUCINQ3`・`ZAHIK3`のような通し例の呼び名は、実際にコンパイルするオブジェクト名ではありません。** これらはレッスン本文中だけで使う説明用のニックネームで、実機に作る実体は `R0408A`(JUCINQ3)・`R0409A`(ZAHIK3)のように、上記の部・レッスン番号ベースの名前です(コード中に `CALL PGM(JUCINQ3)` のような形で出てくることはありません)。ニックネームと実名の対応は各レッスンの「作る・変えるオブジェクト」欄で確認してください。
- 教材の道具(自動化ツール)は `TX` プレフィックス(`TXSETUP`・`TXLOAD`・`TXRESET`・`TXMIGR`・`TXSNAP`・`TXLEGACY` 等)。
- 学習者が演習の中で自分の道具として作るもの(`EXPSRC`・`SETENV`・`BACKUP`・`JUMSGF` 等)は、レッスン内で説明が付いていれば自由な名前でかまいません。
- 詳しくは[付録E](appendix/e-naming.md)を参照してください。

## ライブラリーの使い分け

学習者が使う3つのライブラリーの役割は[01-04](part01/01-04-objects-and-libraries.md)で説明済みです。新しいレッスンを書く際は、この役割分担と矛盾しないようにしてください。

- `<USER>1`: 開発用。この教材の大半の演習はここで行います。
- `<USER>2`: 本番役(第5部以降で使います)。
- `<USER>B`: SAVF(バックアップ)の置き場。本番役ではありません。

ソースにライブラリー名を書き込まないでください(`*LIBL` で解決します)。本文中でコマンド例を示すときは、必ず読者自身のライブラリー名で修飾した形にします。

## 配布ソースの文字・書式(`scripts/check.mjs` が検査する内容)

`src/` 以下の、実機のメンバーに取り込むソース(CL・DDS・RPG III・固定形式 RPG IV)は、次を守ってください。`node scripts/check.mjs` が commit 前に機械的に検査します(ただし `git ls-files` で追跡しているファイルだけを見るので、新規ファイルは先に `git add` してから実行してください)。

- ASCII 文字だけを使う。ソース内のコメントは英語で書く(日本語の説明はレッスン本文側に書く)。
- 改行は LF(`.gitattributes` で強制)。タブは使わない。
- 1行80桁以内(`CVTRPGSRC` の出力だけは100桁まで許容)。
- CCSID 273 で位置が変わる可変文字(`@ # $ [ ] { } | ! \ ^ ~`)を使わない。CL では `*CAT`/`*EQ`、SQL では `CONCAT`/`<>` のように、可変文字に頼らない書き方にします。
- **SQL の数値の並びは、コンマの直後に空白を1つ置く。** PUB400 は `QDECFMT` の小数点がコンマになっている(ドイツ語圏ホスト)ため、`SUBSTR(x,1,200)` のようにコンマの直後へ数字を続けて書くと、`1,200` がひとつの小数リテラルとして誤読され `SQL0104` になる(一次資料: `cl_commands_75.txt` 4583-4600行目、`RUNSQL` の `Decimal point` パラメーターの注記。実機で `verify/lib/clgen.mjs` の `VFYLOG` 書き込みSQLがこれで実際に失敗し、2026-09-26 に発見・修正した)。`SUBSTR(x, 1, 200)` のように空白を入れておけば、小数点がコンマでもピリオドでも問題なく動く。第6部の埋め込みSQL・第8部のDDL・第9部のSQLルーチンを書くときは、この規則を必ず守ること。

## PUB400 での作法

新しいレッスンや演習を書くときは、次を破る手順を学習者に教えないでください(PUB400 は共有の練習機です)。

- 他人のオブジェクト・ジョブを走査するコマンド(`WRKACTJOB`、`*ALLUSR` を対象にした汎用検索など)。
- `INLPGM`/`INLMNU` の変更。
- `QSYSOPR` や他の利用者への `SNDMSG`。
- ループする・常駐するジョブ。
- バッチ投入(`SBMJOB`)には、必ず `INQMSGRPY(*DFT)` と `LOG(4 00 *SECLVL)` を付ける(非対話ジョブが応答できない照会メッセージでハングするのを防ぐため。[付録C](appendix/c-troubleshooting.md)にこのパターンの詳しい説明があります)。
- SSH はパスワード認証を基本とし、認証に2回失敗したら接続をやめる(連続失敗で IP が一時遮断されるため)。SSH の中では画面系のコマンドを使わない(`OUTPUT(*PRINT)` 等に置き換える)。

## 用語・表記

- IBM 日本の公式表記に合わせます: ライブラリー、パラメーター、ユーザー、ディレクトリー、スプール・ファイル、ジョブ・ログ、対話式ジョブ、表示装置ファイル、サービス・プログラム、活動化グループ、バインディング・ディレクトリー、命令コード、演算仕様書(C仕様書)、標識、固定形式。
- 本文は です・ます調。
- コマンド名・オブジェクト名・メッセージ ID は半角の等幅(バッククォート)で書きます。
- 画面は英語のまま載せ、訳を添えます。
- **個人が特定できる情報(実在のユーザー名、実在のライブラリー名、メール・アドレス)は一切書きません。** 常に `<USER>`・`<USER>1`・`<USER>2`・`<USER>B` のプレースホルダーを使います。commit・push 前には必ずこれらのパターンで grep してください。

## 同時接続数・容量の目安

各レッスンの案内文にある「同時接続数」「容量の目安」は、読者が事前に見積もれるようにするための情報です。

- 同時接続数の基本は 5250×1。SSH や VS Code、ACS を併用するレッスンは、実際に必要な本数を書きます(例: 02-04 は「5250 + SSH」)。
- 容量の目安は「0」「わずか」「数十 KB」のように大まかで構いません。片付け(該当レッスンの「片付け」節)を忘れないよう、容量を使う演習には必ず片付け手順を書きます。
