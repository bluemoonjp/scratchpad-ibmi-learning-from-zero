## なぜ学ぶか

現場には、「画面の操作をしている人を待たせたくない処理」がたくさんあります。要求だけ先に渡しておき、別のジョブが時間のあるときに取り出して処理し、答えは別の入れ物に置いておく。**要求元と処理側が、待ち合わせずに連携する**、という形です。IBM iでは、この受け渡しの入れ物として、**データ待ち行列**(`*DTAQ`)が昔から使われています。

同じ形は、09-03から09-05で作ってきたAPIの「入口」の裏側にも現れます。たとえば、時間のかかる集計を、いったん受け付けて、あとで結果を返す。このとき、処理側が**常駐して、ずっと待ち続けるジョブ**になってしまうと、PUB400のような共有の練習機では迷惑になります([スタイル・ガイド](../style-guide.md)が、ループする・常駐するジョブを禁じています)。そこでこのレッスンは、**有限回・有限待ちで、必ず自分で終わるワーカー**を作ります。「夜間の処理」も、`ADDJOBSCDE`(定期実行の登録)は使わず、手で`SBMJOB`する、と決めます。

もう1つ、バッチ・ジョブ固有の問題があります。バッチの中で出した通知(`SNDPGMMSG`の既定)や`DSPLY`は、意図しない場所(`QSYSOPR`のメッセージ・キュー)へ行くおそれがあります(この点は設計上の理由で、この教材では実機で再現していません。未検証(2026-09-29時点))。`QSYSOPR`や他の利用者へメッセージを送るのは、PUB400では作法違反です。そこで、**自分専用のメッセージ・キューを作り、ワーカーの通知をそこへ送る**のを、このレッスンの型にします。

このレッスンで作る要求・応答・通知・ログの型は、第10部の総合演習E(API。低在庫アラートのJSONを夜間にIFSへ出す課題。設計は設計メモ(このリポジトリーの公開範囲外)。第10部は未執筆)の骨格になる計画です。このレッスンのワーカーは、IFSへは書きません。

## 説明

### 同期と非同期(Windows/Linuxとの比較)

WindowsやLinuxでは、処理を別の担当に渡すとき、メッセージ・キュー(RabbitMQ、Azure Service Busなど)や、パイプ・ソケットを使うことがあります。関数を直接呼ぶ(同期)と、相手が終わるまで呼び出し側が待ちますが、キューに要求を置いて帰る(非同期)なら、呼び出し側は待ちません。

IBM iのデータ待ち行列は、その仲間です。特徴は次のとおりです。

- **OSの部品**です。ミドルウェアを入れる必要はありません。
- 入れ物には、**属性**があります。このレッスンでは、最大の長さ128バイト・先入れ先出し(`*FIFO`)にします。
- 中身は、**メッセージ(データ)**です。ここでは、先頭の単語で処理が決まる、文字列にします。

### 全体の流れ

```text
 (SSH: db2)                   (バッチ・ジョブ C0906A)
  SEND_DATA_QUEUE  --->  Z0906A (要求)  --->  QRCVDTAQ ... 処理 ...
                                                   |  QSNDDTAQ
  RECEIVE_DATA_QUEUE <---  Z0906B (応答)  <-------+
                                                   |  INSERT / SNDPGMMSG
                         W0906A (ログ表)  <-------+
                         Z0906C (自分のメッセージ・キュー) <--+
```

ワーカーが受け付ける要求(128バイトまで。先頭の単語で決まります)は、次のとおりです。

| 要求 | ワーカーの動作 | 応答 |
|---|---|---|
| `ECHO 文字列` | そのまま返す | `ECHO 文字列` |
| `EXIST 名前` | `CHKOBJ`で、自分のライブラリーにその名前の`*FILE`があるか調べる | `EXIST 名前 FOUND`または`EXIST 名前 MISSING` |
| `STOCK 商品コード` | `ZAIKOM`の在庫数を、ログ表`W0906A`に書く | `STOCK 商品コード LOGGED` |
| `END` | 終了する | `BYE 理由 件数`(後処理が最後に送る) |
| それ以外 | | `UNKNOWN 要求の文字列` |

`STOCK`の応答に、在庫数は入りません。CLには、SQLの`SELECT INTO`で結果を変数に受ける手段がないので、在庫数はSQLの`INSERT ... SELECT`で、ログ表に直接書きます(ソースの注記どおりです)。

### ライブラリーは、明示する(待ち行列の場合)

`SEND_DATA_QUEUE`には、待ち行列の名前とは別に、`DATA_QUEUE_LIBRARY`を渡します。実機で、次のことが分かりました。

- ライブラリーを**省いて**呼ぶと、`*LIBL/Z0906P`という名前を探しにいき、`SQLSTATE 42704`「DATA QUEUE '*LIBL/Z0906P' NOT FOUND」で失敗しました(検証のSSHの`db2`)。原因は、そのジョブのライブラリー・リストに、待ち行列のライブラリーが無かったためだと推測しますが、SSHのジョブのライブラリー・リストは測っていません(未検証(2026-09-29時点))。
- 一方、バッチ・ジョブ(検証のCLラッパー。`CURLIB`が開発用ライブラリー)の中では、`DATA_QUEUE_LIBRARY => '*LIBL'`と**明示して**送った要求(`ECHO HELLO-LIBL`)が、キューに入り、ワーカーに処理されました。つまり`'*LIBL'`という指定そのものが拒まれるのではなく、**そのジョブのライブラリー・リストから探して、見つかるかどうか**で決まる、と推測しています(観測したのは、SSHで省くと`42704`になったことと、バッチで`'*LIBL'`を明示した要求が処理されたことだけです)。`db2`(SSH)で`'*LIBL'`を明示した形は、実機では試していません(未検証(2026-09-29時点))。

どちらにせよ、この教材の決まりは同じです。**待ち行列のライブラリーは、ソースや`.sql`に書き込まず、呼ぶ側が値として渡します**(09-04の`EXTERNAL NAME`の節で、ライブラリー名をソースに書かなかったのと同じ考え方です)。ワーカー`C0906A`は、ライブラリー名を`PARM`(引数)で受け取り、`QRCVDTAQ`・`QSNDDTAQ`・`RUNSQL`・`SNDPGMMSG`のすべてに、その値を使います。ソースに、ライブラリー名は1つも書かれていません。

なお、SQLファイル[`src/sql/09-06-dtaq.sql`](../../src/sql/09-06-dtaq.sql)は、ライブラリーを文字列(`'MYLIB'`。自分の開発用ライブラリーに書き換えます)で渡す形で書いてあります。`RUNSQLSTM`の`DFTRDBCOL`は、未修飾名の作成先を決めるだけで、`CURRENT SCHEMA`はユーザー名のままでした(09-02までの確認)。**そのため、`CURRENT SCHEMA`を渡す形は、使いません。**この動作は、実機で確かめていません(未検証(2026-09-29時点))。このレッスンの実演は、`db2`で、ライブラリー名を文字列で渡す形(検証した形)を使います。

### `RECEIVE_DATA_QUEUE`は表関数

`QSYS2.RECEIVE_DATA_QUEUE`は、`TABLE(...)`で呼ぶ**表関数**です。返す列は次のとおりです(検証で、作成した表の列の型を確認しました)。

| 列 | 型 | 意味 |
|---|---|---|
| `MESSAGE_DATA` | `CLOB(64512)` CCSID 273 | メッセージ本体(ジョブのCCSIDの文字列) |
| `MESSAGE_DATA_UTF8` | `CLOB(64512)` CCSID 1208 | 同じ本体を、UTF-8で見るための列(型は確認。実際の表示内容は、検証で空欄に見えたため、確かめていません。未検証(2026-09-29時点)) |
| `MESSAGE_DATA_BINARY` | `BLOB(64512)` | 同じ本体を、バイト列で見たもの |
| `KEY_DATA` | `VARCHAR(256)` | キーつきキューのキー(検証のキューは、キー無しでした) |
| `SENDER_JOB_NAME` | `VARCHAR(28)` | 送り手のジョブ名(練習用のキュー`Z0906P`で`INCLUDE_SENDER_ID`が`NO`と読めました。`Z0906A`・`Z0906B`では見ていません。検証の結果は`NULL`でした) |
| `SENDER_CURRENT_USER` | `VARCHAR(10)` | 送り手のユーザー(同じく`NULL`でした) |

指定できる引数と、実機で分かったことは、次のとおりです。**名前つきの引数で書きます。**

- `DATA_QUEUE`・`DATA_QUEUE_LIBRARY`: 待ち行列と、そのライブラリー。
- `WAIT_TIME`: 待つ秒数。**空のキューでも、この時間だけ待ち、0行を返します。エラーにはなりません**(検証)。ここに大きな値・無期限を入れないことが、このレッスンの規律です。
- `REMOVE`: `'YES'`(取り出して、キューから消す)または`'NO'`(見るだけ)。**省くと、取り出して消しました**(検証。`'NO'`で見たメッセージは、次の呼び出しでも取り出せました)。`'YES'`・`'NO'`以外を書くと、`SQLSTATE 22023`「REMOVE MUST BE 'YES' OR 'NO'」です。

位置で引数を並べた形(`('Z0906P', ライブラリー, 5)`)を試したところ、この`22023`になりました。**3番目の位置は`WAIT_TIME`ではない**ということです(どの位置が`REMOVE`なのかを確かめる照会は、0行で、位置の対応は確認できていません。未検証(2026-09-29時点))。`SEND_DATA_QUEUE`のほうは、位置で書いた形(`MESSAGE_DATA`、`DATA_QUEUE`、`DATA_QUEUE_LIBRARY`の順)も動きましたが、迷わないよう、このレッスンでは名前つきを基本にします。

**ワーカーが送った応答**は、`MESSAGE_DATA`で、**128バイトに、右側が空白で埋められた形**で返ってきます(検証。`MESSAGE_DATA_BINARY`の16進数が、文字列のあとに`40`の空白で埋まっていました)。これは、ワーカーが`QSNDDTAQ`に、長さ128の`&REPLY`を、いつも固定で渡しているためです(ソースの`RLEN`・`&REPLY`)。**SQLの`SEND_DATA_QUEUE`で送った要求は、空白で埋まりません**(検証。`RECEIVE_DATA_QUEUE`で見た`PROBE-NAMED`は11バイト、`DATA_QUEUE_ENTRIES`の`END`は3バイトでした)。応答を比べるときは、空白に注意します。

### ワーカー`C0906A`の骨格

[`src/qclsrc/c0906a.clp`](../../src/qclsrc/c0906a.clp)は、[`juyakc.clp`](../../src/qclsrc/juyakc.clp)(03-13)と同じ、4つの区画で書かれています。

(命名の例外: 配布する見本は連番`S`〜`Z`が決まりですが、このワーカー`C0906A`と模範`C0906B`は、実機で検証した名前(`C0906A`)と、片付けの`DLTPGM`・`RMVM`・`CHKOBJ`の手順が同じ名前を指すことを優先して、`A`・`B`のままにしています。)

| 区画 | `JUYAKC` | `C0906A`(`SUBR`) | やること |
|---|---|---|---|
| 前処理 | front | `PRE` | 「開始」を、ログ表と自分のメッセージ・キューに記録する |
| 本処理 | main | `MAIN` | 要求を1件処理し、応答用キューに答えを送る。要求ごとに記録する |
| 後処理 | back | `POST` | 「終了の理由と処理件数」を記録し、**最後に**`BYE 理由 件数`を送る |
| エラー処理 | error | `ERRSUBR` | 失敗を記録し、`ERROR worker failed`を送って、静かに終わる |

`main`の外側の繰り返しは、有限です。どれか1つが成り立てば、`POST`へ進んで終わります。

- 処理した要求が`MAXMSG`(10)件に達した(理由`MAX`)。
- 空の待ちが、合計で`MAXIDLE`(6)回に達した。1回の待ちは`WAITSEC`(20)秒なので、最大で2分です。**要求が届いた待ちがあっても、回数はゼロに戻りません**(理由`IDLE`)。
- `END`要求を処理した(理由`END`)。

つまり、このワーカーは、待ちの2分と、最大10件を処理する時間より長くは、生きられません。**常駐しません**。実機で確かめたのは、`END`で終わる経路だけです。処理数の上限(`MAX`)・待ちの回数の上限(`IDLE`)・エラー処理の経路は、実行して確かめていません(未検証(2026-09-29時点))。

`QRCVDTAQ`は、`PARM(&QIN &LIB &DLEN &DATA &WAITSEC)`の形で呼んでいます。ソースのコメントは「戻ってきた長さが0なら、待ち時間が過ぎて何も来なかった」と読んでいます。これが実機で正しいか(待ちが切れたときに、長さが本当に0になるか)は、この経路を実行していないので、確かめていません(未検証(2026-09-29時点))。**`WAITSEC`に負の値を入れると、無期限に待つ、というのが`QRCVDTAQ`の仕様だと理解していますが、この教材の一次資料では確かめていません(未検証(2026-09-29時点))。**どちらにしても、負の値は使いません。

**要求の文字列は、SQLの文の中に、そのまま貼り付けられます。** ログの1行を書く`LOG`区画が、すべての要求の先頭30バイトを`INSERT`文に貼り付け、`STOCK`は商品コードも貼り付けます。だから、**どの要求にも、シングル・クォートを含めてはいけません**。08-07の「コマンド注入」と同じ話です。クォートを含む要求は、ログの失敗が`MONMSG`で握りつぶされるので、ログ表の行とメッセージが、エラーの表示なしに失われる、とソースから読めます(実機では確かめていません。未検証(2026-09-29時点))。

### 自分のメッセージ・キューへの通知

`LOG`区画は、1つの節目ごとに、2つのことをします。ログ表`W0906A`に1行入れることと、`SNDPGMMSG MSG(...) TOMSGQ(&LIB/Z0906C) MSGTYPE(*INFO)`で、自分のメッセージ・キュー`Z0906C`へ通知を送ることです。どちらの命令にも、それぞれ`MONMSG`が付いていて、**ログの失敗でワーカーが止まらず、エラー処理が自分自身を呼んで、ループすることもない**作りです(ソースを読んだ設計上の主張で、失敗の経路は実行していません。未検証(2026-09-29時点))。

メッセージ・キュー`Z0906C`は、`CRTMSGQ`で自分で作った、自分専用のキューです。通知はそこに溜まるので、あとで`QSYS2.MESSAGE_QUEUE_INFO`で読めます。`QSYSOPR`や、他の利用者には、何も送りません。

### `SBMJOB`の指定(検証で確定した形)

```text
SBMJOB CMD(CALL PGM(<自分のユーザー名>1/C0906A) PARM('<自分のユーザー名>1')) JOB(C0906A) JOBQ(QGPL/QBATCH) CURLIB(<自分のユーザー名>1) INLLIBL(*JOBD) INQMSGRPY(*DFT) LOG(4 00 *SECLVL)
```

- `INQMSGRPY(*DFT)`・`LOG(4 00 *SECLVL)`: 03-12のとおりです(スタイル・ガイドの決まり)。
- `CURLIB`・`INLLIBL(*JOBD)`: ジョブが使うライブラリーを、こちらから明示します。
- **`JOBQ(QGPL/QBATCH)`は、必ず書きます。** ジョブ・キューを指定せず、既定(ユーザー名と同じ名前のジョブ・キュー、`QGPL`)に投入した検証では、ジョブが**2分以上たっても動かず**(検証の1回。2回目の18:36の実行で、9件の要求が要求用キューに残り、ログ表は空でした。待ち時間は、検証の待ちの合計から計算した約135秒です。1回目の17:35の実行は、結果の回収に失敗していて、この点の証拠にはなりません)、`JOBQ(QGPL/QBATCH)`を指定すると、投入した直後に動きました(3回目)。既定のキューが動かなかった原因は、調べていません(未検証(2026-09-29時点))。学習者の環境で、既定のキューが動くかどうかも分かりません。

<details><summary>ヒント・答え</summary>

ワーカーを、要求が**1件も無い**状態で動かし、「空の待ちが、合計で上限に達して終わる」経路を確かめます。**この演習は、実機で試していません。**

<details><summary>答え</summary>

読み取れる範囲の予想です(**すべて、実行して確かめていません。未検証(2026-09-29時点)**)。5秒の待ちが6回続き、約30秒後に終わるはずです。ログ表を作り直していれば、`PRE`の1行、`WAIT`の6行(`timeout, empty waits so far 1`から`6`まで)、`POST`の1行(`end why=IDLE handled=00000`)ができ、応答用キューには`BYE IDLE 00000`が1件入るはずです(ログ表を作り直さなかった場合は、これらの行が、前回の行の後ろに続きます)。**この経路が動くかどうかは、`QRCVDTAQ`が、待ち時間が切れたときに、要求を返さずに戻ってくるかどうかで決まります。** ソースは、呼ぶ前に`&DLEN`を0にしています。長さが0のままなら、待ちが切れたものとして扱うので、`QRCVDTAQ`が何も書き換えずに戻ってきても、待ちの経路に入ります。逆に、`QRCVDTAQ`が待ち時間の切れたときに、長さを0以外にしたり、エラーにしたりする場合は、この予想は外れます(そうなるかどうかは、確かめていません)。

</details>

### 演習(d): 紙の上で

1. 「夜間に、このワーカーを動かしたい」と頼まれました。`ADDJOBSCDE`を使わないのは、なぜですか。代わりに、何をしますか。
2. ワーカーが、ライブラリー名をソースに書かず、`PARM`で受け取るのは、なぜですか。ライブラリーを変えたいとき、何を変えますか。
3. ワーカーが、要求の処理数(`MAXMSG`)と、待ちの回数(`MAXIDLE`)の**両方**に、上限を持つのは、なぜですか。片方だけだと、何が困りますか。
4. 応答の`STOCK P00002 LOGGED`は、在庫数を含みません。なぜですか。在庫数は、どこで見ますか。

<details><summary>答え</summary>

1. 定期実行の登録は、常駐・繰り返しの仕組みで、この教材の決まり(ループする・常駐するジョブを作らない)に反し、PUB400での権限も確認していないからです。「夜間」は、実行する人が、その時間に、`SBMJOB`を手で1回打つ、と定義します。骨格は`JUYAKC`(03-13)と同じで、`PRE`・`MAIN`・`POST`・`ERRSUBR`の4つの区画です。
2. 待ち行列のライブラリーは、ジョブごとのライブラリー・リストや、環境(開発用・本番役)で変わるので、ソースに書き込むと、環境を変えたときに、別の場所の待ち行列を見に行ってしまうからです(実演の「ライブラリーは、明示する」の考え方)。変えたいときは、`SBMJOB`の`PARM('...')`の値と、`CURLIB`を変えます。
3. 処理数の上限だけだと、要求が1件も来ないとき、永遠に待ちます(常駐と同じです)。待ちの回数の上限だけだと、要求が途切れずに来続ける間は、待ちが起きないので、いつまでも終わりません。この2つの上限と、終了要求(`END`)で、どの場合でも、有限の時間で終わります。実機で確かめたのは、`END`の経路だけです(未検証(2026-09-29時点))。
4. CLには、`SELECT INTO`で、SQLの結果を変数に受ける手段がないからです。在庫数は、SQLの`INSERT ... SELECT`で、直接ログ表`W0906A`に書き、要求元は、そのログ表から読みます(実演の手順7。`PHASE`が`STOCK`の行)。

</details>

## まとめ

| 英語 | 日本語 |
|---|---|
| Data queue (`*DTAQ`) | データ待ち行列(要求・応答を渡す入れ物) |
| FIFO | 先入れ先出し(入れた順に取り出す) |
| Worker | ワーカー(要求を取り出して処理する、短命のジョブ) |
| Sentinel message | 終了要求(ワーカーに終わりを知らせる、特別なメッセージ。ここでは`END`) |
| Job queue | ジョブ・キュー(投入したジョブが、動き出すまで待つ場所) |
| Message queue (`*MSGQ`) | メッセージ・キュー(通知を溜める、自分専用の入れ物) |
| Synchronous / Asynchronous | 同期 / 非同期(待ち合わせる / 待ち合わせない) |

- 新しいメッセージ ID: `CPC0815`・`CPC9801`・`CPC2191`・`CPF2105`・`CPC1221`・`CPC7309`(未検証)(このレッスンの意味で)と、`SQLSTATE 42704`・`22023`(`-443`)。
- 決まり: ワーカーは、有限回・有限待ちで、必ず終わる(常駐しない)。「夜間」は、手動の`SBMJOB`(`ADDJOBSCDE`を使わない)。`SBMJOB`には、`JOBQ(QGPL/QBATCH)`・`CURLIB`・`INLLIBL(*JOBD)`・`INQMSGRPY(*DFT)`・`LOG(4 00 *SECLVL)`を付ける。待ち行列のライブラリーは、ソースに書かず、値として渡す。バッチの通知は、自分のメッセージ・キューへ。ジョブの完了は、ログ表とメッセージ・キューで判定する。`END`は最後の要求として送る。
