## なぜ学ぶか

第9部の目標は、この教材で作ってきた仕組み(`JUCSRV`・`ZAISRV`・受注や在庫のデータ)を、外の世界から呼べる形にすることです。外の世界の共通語は、たいてい**JSON**です。REST APIの応答も、他システムへ渡すデータも、設定ファイルも、テキストの中括弧`{ }`と角括弧`[ ]`で書かれた入れ子のデータ形式で流れます。

Db2 for iには、JSONを**SQLだけで**作る関数(`JSON_OBJECT`・`JSON_ARRAYAGG`)と、JSONを表の行に戻す表関数(`JSON_TABLE`)があります。RPGで文字列を1文字ずつ連結してJSONを組み立てる代わりに、SQL 1本で「表→JSON」と「JSON→表」を往復できます。ここで作る道具は、次のレッスンで直接効いてきます。

- [09-04](09-04-api-boundary-sql-routines.md)(SQLルーチン)では、JSONを返すSQL関数(`JUCHU_INQUIRY_JSON`)を作ります。中身は、このレッスンの手順2のSQLの応用です。
- [09-05](09-05-external-api-adapter-mock.md)(外部API)では、APIの応答(JSON文字列)を`JSON_TABLE`で読み解きます。
- [09-06](09-06-data-queues-async.md)(データ待ち行列)では、データ待ち行列へメッセージを送ります(そのメッセージはJSONではなく、短い文字列です)。

**なお、このレッスンは`.sql`スクリプトとして実行することを前提にしています。** JSONのパス式には`$`や`[*]`のような、EBCDICの一部のコード・ページで位置が変わる文字が出てきます([スタイル・ガイド](../style-guide.md)の可変文字の項)。実機では、`db2`経由と、IFS上の`.sql`を`RUNSQLSTM SRCSTMF`で実行する経路で、そのまま動くことが確認できました(下の「説明」)。ACSは未検証(2026-09-29時点)です。CLやRPGのソース・メンバーに写す経路も試していません。このレッスンでは、CL・RPGのソースには`$`や`[`・`]`・`{`・`}`を書かない、という方針を保ちます。

## 新出

- 中核概念(3つ):
  1. **「組み立てる」と「戻す」は対になっている。** 表の行から JSON を作るのが`JSON_OBJECT`・`JSON_ARRAYAGG`、JSON から行を作るのが`JSON_TABLE`です。往復して元に戻るかを確かめるのが、このレッスンの演習の狙いです。
  2. **波かっこ`{ }`は手で打たず、必ず関数で組み立てる。** 値の引用符やエスケープ、数値と文字列の区別を、関数が正しく面倒を見てくれるからです(理由は「説明」で、実機の反例つきで扱います)。
  3. **`NESTED PATH`は、親子の入れ子を、1回の`JSON_TABLE`呼び出しで「親の項目を繰り返した行」に畳む。** 親と子を別々の表として扱わずに済みます。
- 構文・道具(6つ):
  1. `JSON_OBJECT('キー': 値, ...)`(JSONのオブジェクトを作る。キー名は文字列リテラル)
  2. `JSON_ARRAYAGG(式 ORDER BY ...)`(複数行を、JSONの配列に集約する)

  4. `JSON_TABLE(文書, パス COLUMNS(列 型 PATH パス))`(JSON から行を作る表関数)
  5. `NESTED PATH パス COLUMNS(...)`(配列の各要素を、親の行に対応づけて展開する)
  6. `QSYS2.IFS_WRITE_UTF8`(テキストをIFSへ UTF-8 で書き出すプロシージャー)
- **復習(前のレッスンで扱った項目。新出に数えない)**: `SET SCHEMA`・`WITH`(共通表式)・`INSERT ... SELECT`・`CAST`・`RTRIM`は、02-06までのSQLの復習として使います。`RUNSQLSTM SRCSTMF`は08-01・08-07で使いました。
- **読解用(新出に数えない。読めれば十分)**:
  - `EXCEPT`(2つの問い合わせの差を取る集合演算)。演習3の解答で使います。
  - パス式の`lax`モード。構造が合わないとき、エラーを無視して NULL を返すモードです(IBM Docsの記述による。実機では確認していません。`lax`が既定のモードかどうかも未検証(2026-09-29時点)です。このレッスンでは、パス式の先頭に毎回`lax`と書いています)。
  - `JSON_OBJECT(KEY 'k' VALUE 値)`という別の書き方(実機で文として通ることだけを確認しました。ただし数値リテラルの出力が、`{"k":"1"}`(文字列)と`{"ok":1}`(数値)で食い違いました。原因は未検証(2026-09-29時点)です。[09-04](09-04-api-boundary-sql-routines.md)では、`RUNSQL`の中でリテラルの数値を渡すと文字列になる例も見つかっています。下の「出力が違うとき」も読んでください)。
  - `JSON_ARRAY`(値を並べて配列を作る関数)。09-05の`apimock.sql`で実行確認済みです(V2)。
  - `QSYS2.IFS_READ_UTF8`(IFSのファイルを行ごとの表として読む表関数)。

## 説明

### JSONとは、入れ子のテキスト

JSONは、オブジェクト(名前と値の組の集まり、`{ }`で囲む)と配列(値の並び、`[ ]`で囲む)の2つを入れ子にできる、テキストのデータ形式です。たとえば受注1件は、こう書けます。

```json
{"orderNo":"J00001","orderDate":20260901,"lines":[{"line":1,"product":"P00001","qty":2,"unitPrice":1580.00},{"line":2,"product":"P00003","qty":5,"unitPrice":480.00}]}
```

ヘッダー(受注番号・日付)が1つ、明細(`lines`)が複数、という「1対多」を、1つの文書にまとめられるのがJSONの強みです。表(`JUCHUM`と`JUCHUD`)に分けて持つ形と、JSON文書1つに畳む形の間を、SQLで行き来します。

Windows/Linuxの世界には、`jq`のようなJSON専用コマンドや、各言語のJSONライブラリーがあります。IBM iでも同じ仕事を、Db2 for iのSQL関数がやってくれます。データがもともとDb2の表にあるので、いったん外へ出さずに、データベースの中で変換できるのが利点です。

### 波かっこを手で打たない理由

「JSONは結局ただの文字列だから、`'{"orderNo":"' CONCAT JUNO CONCAT '"}'`のように連結すればよいのでは」と思うかもしれません。動くことは動きます(ただし、連結で組み立てたJSON文書そのものは、実機では実行していません。実機で通ったのは、`{"a":1}`のような固定の文字列リテラルだけです)。実機でも、`{"a":1}`のような文字列リテラルは、`db2`経由でも、IFS上の`.sql`を`RUNSQLSTM SRCSTMF`で実行する経路でも壊れずに通りました(バッチ`part09-01-02-json`)。それでも手で組み立てない理由は、次の3つです。

1. **値の引用符・エスケープを、手では正しく面倒見きれない。** `JSON_OBJECT`は、数値は引用符なしの数値のまま出力します。実機の出力でも、`line`は`1`、`unitPrice`は`1580.00`と引用符なしで出ました。文字列の値に含まれる`"`などを自動でエスケープする点は、標準の仕様からの推論で、値に引用符を含む入力は実機では試していません(未検証(2026-09-29時点)。実機で観察したエスケープは、後述の、既にJSONの文字列を二重にエスケープする場合だけです)。連結でこれを再現しようとすると、入力に引用符が混ざった瞬間に壊れると考えられ(これも推論で、未検証)、壊れ方は入力次第です。SQL文を文字列連結で組み立てると危険なのと同じ理屈(08-07のコマンド注入と同じ考え方)です。
2. **入れ子の構造を、括弧の対応で間違えやすい。** `JSON_ARRAYAGG`の中に`JSON_OBJECT`を入れる形なら、関数の入れ子が、そのままJSONの入れ子になります。
3. **CL・RPGのソースに写すと、位置が変わる文字を踏む。** このバッチのジョブのCCSIDは273でした(システム全体の既定のCCSIDは、問い合わせても値が返らず、確認できていません)。`$ [ ] { }`の16進は、`5B 63 FC 43 DC`でした(`HEX('lax $.a[*]{}')`は`93 81 A7 40 5B 4B 81 63 5C FC 43 DC`)。そのジョブでは`$`が`5B`、`[`が`63`、`]`が`FC`、`{`が`43`、`}`が`DC`です。`.sql`をそのまま`RUNSQLSTM`に渡す経路では壊れませんでしたが、ソース・メンバー(CL・RPG)に写す経路は、この教材ではまだ実機で確かめていません。だから、この種の文字を含む式は`.sql`スクリプトの中にだけ置く、という運用にしています。

なお、次の点は**やってはいけません**。この`.sql`を`iconv`でUTF-8に変換し、CCSID 1208のタグを付けて`RUNSQLSTM`に渡すと、`SQL0330`(文字変換不可)で失敗しました(実機確認済み)。読みたくなる方法ですが、「元のファイルのまま(CCSID 273のタグで)実行する」のが確認できた経路です。

### `FORMAT JSON`が要る理由: 二重にエスケープされる

明細(`JUCHUD`)を`JSON_ARRAYAGG`で配列にして、それを外側の`JSON_OBJECT`の値に入れる場面を考えます。**`FORMAT JSON`を付けないと、内側の配列は「ただの文字列」として扱われ、もう一度エスケープされます。** 実機の結果は次のとおりでした(2つを並べます)。

```text
FORMAT JSON あり(正しい入れ子)
{"orderNo":"J00001","customer":"C00001","lines":[{"line":1,"product":"P00001","qty":2},{"line":2,"product":"P00003","qty":5}]}

FORMAT JSON なし(文字列として二重エスケープされる)
{"orderNo":"J00001","lines":"[{\"line\":1},{\"line\":2}]"}
```

なしの場合は、`lines`の値が引用符で囲まれた文字列になり、中の`"`がすべて`\"`になっています。これは**エラーにならない**ところが厄介です。文法は正しく、結果もJSONとして有効なので、SQLは何も文句を言いません。受け取った側が`lines`を配列として読もうとして、初めて壊れます。「既にJSONである値を入れるときは、`FORMAT JSON`を付ける」と覚えてください(上の2つは、`orderNo`以外の項目が少し違う別々の問い合わせの結果です。結果の違いを生む原因は、`FORMAT JSON`の有無です)。

### `JSON_TABLE`と`NESTED PATH`: 1回で親子を行に戻す

`JSON_TABLE`は、JSON文書とパス式を受け取って、行の集合として返す表関数です。パス式は`$`が文書全体、`$.orderNo`がその中の`orderNo`、`$.lines[*]`が`lines`配列の全要素を表します。

```sql
JSON_TABLE(文書, 'lax $'
  COLUMNS(ORDER_NO CHAR(6) PATH 'lax $.orderNo',
          NESTED PATH 'lax $.lines[*]'
          COLUMNS(LINE_NO INT PATH 'lax $.line', ...)))
```

`NESTED PATH`を使うと、配列の要素1つにつき1行ができ、その行に親の項目(`ORDER_NO`など)が繰り返されます。実機では、全12明細行が`J00001`〜`J00008`の受注番号つきで、1回の呼び出しで得られました。`NESTED PATH`を使わずに、親と子を別々に取り出して自分で結合し直すことも考えられますが、その必要がありません。

### `RUNSQLSTM`は`SELECT`を実行できない

`RUNSQLSTM`(SQL文の入ったソースを一括で実行するCLコマンド)は、結果を表示する`SELECT`単独文を実行できません。`SELECT`単独文を含む`.sql`を`RUNSQLSTM SRCSTMF(...)`で実行したところ、`SELECT`は`SQL0084`(SQL statement not allowed)、重大度30で拒否されました。このレッスンの各`SELECT`も同じになるはずです(このレッスン現行のスクリプト全体は、`RUNSQLSTM`で流していません)。結果を見るには、次の2つの道があります。

- **ACSの「実行SQLスクリプト」(このレッスンの道具)**: `SELECT`の結果が画面の表に出ます。**ただし、ACSの画面での操作と表示は、この教材ではまだ実機で確認していません(V3、未検証(2026-09-29時点))。**
- **`INSERT ... SELECT`で表に入れてから、`db2`で読む**: `RUNSQLSTM`で確認できた、実行可能な形です。実機の検証では、SQLを`INSERT INTO 作業表 SELECT ...`の形に包み、あとで`db2`(SSH上のSQLコマンド)で表を読みました。JSONは`CAST(... AS VARCHAR(2000))`で文字列にしてから入れました。

このレッスンの実演の手順は、ACSで`SELECT`を直接実行する形で書いていますが、**期待される出力は、実機で確認できた等価な形の実行結果(`db2`での同じ`SELECT`、または`INSERT ... SELECT`)から取ったものです**(上の`SQL0084`の実験が、`SELECT`をそのまま`RUNSQLSTM`に渡した唯一の実行例です)。手順4の表は、`CONCAT`で連結した文字列の結果から組み直したものです(`SELECT T.*`そのものは実行していません)。

### 未修飾の名前は、接続の現行スキーマで解決される

スクリプトの表名(`JUCHUM`など)は、ライブラリー名なしで書いてあります。実機では、`RUNSQLSTM`の`DFTRDBCOL(ライブラリー)`を指定すると、未修飾名で作った検証用のオブジェクトがそのライブラリーにできました。同じ実行で、未修飾の`JUCHUM`・`JUCHUD`も見つかりました(ただし、`DFTRDBCOL`が名前の解決先を決める仕組みかどうかは、切り分けていません)。一方、`CURRENT SCHEMA`(現行スキーマ)そのものは**ユーザー名のまま**でした。ACSで実行するときも、何もしなければ、表は自分のユーザー名と同名のスキーマで探されるはずです。そのため、スクリプトの先頭に次の文を置いています。

```sql
SET SCHEMA <自分のユーザー名>1;
```

**ACSでこの文が期待どおり効くかは、この教材では実機で確認していません(V3、未検証(2026-09-29時点))。** 確認できたのは、`RUNSQLSTM`の`DFTRDBCOL`を指定した経路だけです。`SET SCHEMA`が効かない場合は、表名を`<自分のユーザー名>1.JUCHUM`のように、ライブラリーで修飾して書き直してください。

### `IFS_WRITE_UTF8`: JSONをIFSへ書き出す

作ったJSONを、ファイルとしてIFSへ置きたい場面があります。`QSYS2.IFS_WRITE_UTF8`は、SQLのプロシージャー呼び出しで、テキストを UTF-8(CCSID 1208)のIFSファイルに書きます。実機では、次の呼び出しが成功し、7バイトのファイルがCCSID 1208のタグつきで作られ、`IFS_READ_UTF8`で`LINE_NUMBER`と`LINE`が読み戻せました。

```sql
CALL QSYS2.IFS_WRITE_UTF8(PATH_NAME => '/home/<自分のユーザー名>/work/w.json',
                          LINE => '{"a":1}',
                          OVERWRITE => 'REPLACE',
                          END_OF_LINE => 'NONE');
```

- パスは`/home/<自分のユーザー名>/...`と絶対パスで書きます。SQLの文字列の中の`$HOME`を展開させる形は試していません(未検証(2026-09-29時点))。
- 書き出し先のディレクトリーは、あらかじめ存在している必要があります(02-03で作った`work`を使います)。
- 組み立てたJSON(`JSON_OBJECT`の結果)を`LINE`に渡す形は、この教材では実機で確認していません(未検証(2026-09-29時点))。確認できたのは、文字列リテラルと`UX'3042'`(全角の「あ」)を渡す形で、後者はUTF-8の`E3 81 82`が書かれました。
- `IFS_WRITE_UTF8`が使えない環境では、`CPYTOIMPF`(02-09)が代替になるかもしれません。ただし、このPUB400では`IFS_WRITE_UTF8`が使えたので、`CPYTOIMPF`の実演はしません。

## 実演

以下は**ACSの「実行SQLスクリプト」**での操作です。`src/sql/09-02-json.sql`の対応する文を、**1つずつ**選んで実行します(全体を一度に実行しないでください)。**ACSの画面操作は未検証(V3)です。** SSHの`RUNSQLSTM`で代替する方法は、手順の後にまとめます。各手順の「期待される結果」は、実機で確認した等価な実行結果です(上の「説明」を参照)。

1. **表を探す先を決める。** スクリプトの先頭の文(文0)の`<your dev library>`を`<自分のユーザー名>1`に書き換えて実行します。

   ```sql
   SET SCHEMA <自分のユーザー名>1;
   ```

   エラーなしで完了すれば準備完了です。エラーになる、または以降の手順で表が見つからない場合は、上の「説明」のとおり、表名を`<自分のユーザー名>1.JUCHUM`の形で修飾してください。

2. **受注1件を、JSON文書1つに組み立てる**(文1)。

   ```sql
   SELECT JSON_OBJECT(
            'orderNo': M.JUNO,
            'orderDate': M.JUDATE,
            'lines': (SELECT JSON_ARRAYAGG(
                               JSON_OBJECT('line': D.JULINE,
                                           'product': D.JUSHO,
                                           'qty': D.JUSU,
                                           'unitPrice': D.JUTNK)
                               ORDER BY D.JULINE)
                        FROM JUCHUD D
                       WHERE D.JUNO = M.JUNO) FORMAT JSON
          ) AS ORDER_JSON
     FROM JUCHUM M
    WHERE M.JUNO = 'J00001';
   ```

   期待される結果(1行):

   ```text
   {"orderNo":"J00001","orderDate":20260901,"lines":[{"line":1,"product":"P00001","qty":2,"unitPrice":1580.00},{"line":2,"product":"P00003","qty":5,"unitPrice":480.00}]}
   ```

   `orderDate`は数値のまま(引用符なし)、`unitPrice`は`1580.00`のまま出ています。`JUDATE`が数値列(`8S 0`)であることを、そのまま反映した結果です。

3. **`FORMAT JSON`を外した反例を見る**(文1b)。

   期待される結果(実機での確認結果。ACSの表示は未検証): 1つ目の`CALL`が成功し、2つ目の`SELECT`が、`LINE_NUMBER`が`1`、`LINE`が`{"a":1}`の1行を返します。

**ACSが使えない・`SELECT`の結果を見られないときの代替。** 代替は完全ではありません。実機で確認できた経路は次の2つで、手順ごとに使える範囲が違います。

- **SSHの`db2`で`SELECT`を直接実行する**: 手順2・手順5に相当する`SELECT`は、この形で実行し、結果を確認しました(表名だけライブラリー修飾つき)。手順4の`SELECT T.*`と、手順6の`VALUES`を、そのままの形で`db2`に流した記録はありません(未検証(2026-09-29時点))。手順7は、`db2`から`CALL`と読み戻しをした確認があります。
- **`RUNSQLSTM`で、`INSERT ... SELECT`にして表へ入れる**: `SELECT`単独文は`SQL0084`で拒否されるので、結果を入れる表を先に作り、`INSERT ... SELECT`で入れてから、`db2`で表を読みます。手順2の形は、たとえば次のようになります(表名`W0902A`は演習4と同じで、片付けで削除します。この`CREATE TABLE`と、この形の全体は、実機では実行していません(未検証(2026-09-29時点)))。

```sql
CREATE TABLE <自分のユーザー名>1.W0902A (JUNO CHAR(6) NOT NULL, DOC VARCHAR(2000));

INSERT INTO <自分のユーザー名>1.W0902A (JUNO, DOC)
  SELECT M.JUNO,
         CAST(JSON_OBJECT('orderNo': M.JUNO,
                          'lines': (SELECT JSON_ARRAYAGG(
                                             JSON_OBJECT('line': D.JULINE,
                                                         'product': D.JUSHO,
                                                         'qty': D.JUSU)
                                             ORDER BY D.JULINE)
                                      FROM <自分のユーザー名>1.JUCHUD D
                                     WHERE D.JUNO = M.JUNO) FORMAT JSON)
              AS VARCHAR(2000))
    FROM <自分のユーザー名>1.JUCHUM M;
```

手順3の形(`INSERT ... SELECT`+`CAST`)は実機で確認しました。手順4・手順5・手順7を`RUNSQLSTM`でそのまま動く形に包んだものは、確認していません。`RUNSQLSTM`は、実行リストのスプール・ファイルも残します(片付けを参照)。

`RUNSQLSTM`の実行コマンドは、実機で確認できた形が次のとおりです。検証用の道具(ハーネス)が、この形の`.sql`をIFSへ書いて実行しました。`ERRLVL(40)`を付けている点に注意してください(下の「出会うメッセージ ID」の`SQL7905`)。

```text
system "RUNSQLSTM SRCSTMF('$HOME/work/q0902.sql') COMMIT(*NONE) NAMING(*SQL) DFTRDBCOL(<自分のユーザー名>1) ERRLVL(40)"
```

- ファイルの文字コードは、CCSID 273のタグのファイルで実行できたことが確認できています(前述の`iconv`変換はしません)。**自分で書いたファイルのタグが何になっているかは、確認できていません。** UTF-8(1208)のタグのファイルは`SQL0330`で失敗しました。SSHのシェルや手元のエディターで書いたファイルは、別のタグになることがあります。タグの確認と設定の方法(`attr`や`setccsid`など)は、この教材では試していません(未検証(2026-09-29時点))。
- シェルのヒアドキュメントで書く場合は、区切り語を引用符で囲んでください(たとえば`<<'END'`)。囲まないと、シェルがJSONパスの`$`を展開して、中身が変わります。
- **自分でSSHのシェルから`.sql`を書き出す手順(`cat`とヒアドキュメント等)そのものは、学習者の環境では未検証(2026-09-29時点)です。** 確認したのは、検証ハーネスが同じ役割の`.sql`を書いて`RUNSQLSTM`に渡した経路だけです。

## 出会うメッセージ ID

| メッセージ | 原因 | 対処 |
|---|---|---|
| `SQL0084`(SQL statement not allowed、重大度30) | `RUNSQLSTM`で、`SELECT`単独文を実行しようとした(実機では、`SELECT`単独文を含む`.sql`で発生を確認) | `INSERT ... SELECT`で表に入れる形に包む。または、ACSの「実行SQLスクリプト」で実行する |
| `SQL7905`(重大度20) | 表を作ったが、ジャーナルされていない(実機で見たのは、著者の検証用ライブラリーに作った作業表の場合。`W0902A`で出るか、`<自分のユーザー名>1`のジャーナルの有無で違うかは、未検証(2026-09-29時点))。`ERRLVL(40)`を付けて実行した場合は、後続の文が実行された。ただし実行リストの集計では、この`SQL7905`は警告ではなくエラー1件として数えられ、「20 level severity errors found」とも出た | `ERRLVL(40)`を付けて実行し、表が壊れたわけではないことを確認します。`ERRLVL`を省略した場合(既定は10)に止まるかどうかは、未検証(2026-09-29時点)です |
| `SQL7956`(重大度0) | 「n rows inserted in 表」という、行の挿入の完了通知 | 情報メッセージ。何もしません |
| `SQL0330`(Character conversion cannot be performed、重大度30) | `.sql`を`iconv`でUTF-8(CCSID 1208)に変換して、`RUNSQLSTM`に渡した | `iconv`変換をやめ、元のファイル(CCSID 273のタグ)のまま実行する |
| `SQL0104` | リストのコンマの直後に数字を続けて書いた(例: `1,200`)。PUB400は小数点がコンマなので、1つの小数リテラルと読まれる | コンマの直後に空白を1つ置く(`1, 200`)。[スタイル・ガイド](../style-guide.md)の該当項。一般則で、このレッスンの式では発生させていません |

## 出力が違うとき

- **`lines`の値が`"[{\"line\":1},...]"`のように、引用符つきの文字列になり、`\"`だらけになる**: `FORMAT JSON`を付け忘れています。手順3が、まさにこの状態です。
- **ACSで、表が見つからない(または、思っていない表を読んでいる)**: 現行スキーマの問題です。手順1の`SET SCHEMA`が効いていないか、書き換えを忘れています。表名を`<自分のユーザー名>1.JUCHUM`と修飾して試してください。この確認は、この教材では実機でしていません(V3、未検証)。
- **`RUNSQLSTM`で実行したのに、何も表示されない**: `SELECT`は`SQL0084`で拒否されます。`INSERT ... SELECT`に包んで、表を読んでください。
- **`SQL7905`で重大度20と出て、失敗したかと思った**: `ERRLVL(40)`を付けて実行したときは、後続の文が実行されました(実機で確認済み)。ただし、実行リストではエラー1件として数えられます。`ERRLVL`を付けない場合(既定は10)は、重大度20のメッセージで実行が止まる可能性があります(未検証(2026-09-29時点))。
- **`CHAR`の列を`CHAR()`関数などで連結すると、途中に空白が残る**: 整数の列を`CHAR()`で文字にすると、空白が付いたことを、実機の連結結果(`J00001/C00001/1 /P00001/2`)で確認しました。`CHAR(6)`の列は、この結果では6桁が埋まっていて、空白が付くかどうかは確認できていません(未検証(2026-09-29時点))。結果を文字列として使うなら、`RTRIM`(または`TRIM`)で削ってください。JSONの中に入れる値は、`JSON_OBJECT`に列をそのまま渡せば、この心配は要りません(手順2)。
- **`JSON_OBJECT(KEY 'k' VALUE 1, ...)`の`1`が、`"1"`と引用符つきで出た**: 実機の検証で、`KEY ... VALUE`形式の`KEY 'k' VALUE 1, KEY 'v' VALUE 'x'`の結果が`{"k":"1","v":"x"}`と、数値が文字列になって出ました。ところが、`VALUES JSON_OBJECT(KEY 'ok' VALUE 1)`は`{"ok":1}`と数値のままでした。**この違いの原因は切り分けていません(未検証(2026-09-29時点))。** 列を渡す形(手順2)では数値は数値のまま出ることを確認したので、リテラルを直接渡すときは、結果を目で確かめてください。なお、[09-04](09-04-api-boundary-sql-routines.md)では、`RUNSQL`の中でリテラルの数値を`JSON_OBJECT`に渡すと、`"qty":"2"`のように文字列になり、小数点がコンマになる例を観察しました(`db2`経由のリテラルは数値のままでした)。同じ書式でも、実行する経路で出方が違う可能性があります。
- **`.sql`を`iconv`でUTF-8にすると、`SQL0330`で失敗する**: 前述のとおり、変換せず元のファイルのまま実行してください。
- **ACSの画面での見た目が、上の結果と違う**: 期待される結果は、ACSではなく`db2`・`RUNSQLSTM`の経路で確認した値です。文字列の中身(JSONそのもの)は同じはずですが、ACSでの表示形式(桁区切り・引用符の扱い)は未検証です。

### 演習1(例題を読む)

手順5(文3)のSQLを、**1行ずつ読んで**、次の3つを説明してください。

- どこが「組み立てる」側で、どこが「戻す」側ですか。
- `FORMAT JSON`を外すと、どこがどう壊れますか(手順3の結果と結びつけてください)。
- `NESTED PATH`を外して、`lines`を1列(`lines VARCHAR(500) FORMAT JSON PATH 'lax $.lines'`のような列)にしたら、結果の行数は何行になりますか。

<details><summary>ヒント</summary>

組み立ては`WITH DOCS`の中、戻しは`JSON_TABLE`です。行数の問いは、受注は8件あるので、`NESTED PATH`が無ければ、明細ではなく受注の数(8行)になるはず、という見通しを立ててください(この1つ目の見通しも、実機で確かめてはいません)。

</details>

<details><summary>答え</summary>

- 「組み立てる」側は`WITH DOCS AS (...)`の中(`JSON_OBJECT`と`JSON_ARRAYAGG`)、「戻す」側は`JSON_TABLE(...)`です。
- `FORMAT JSON`を外すと、`lines`が配列ではなく引用符つきの文字列になり、中の`"`が`\"`になります。すると`JSON_TABLE`の`$.lines[*]`は、配列の要素として展開できません。エラーは出ず、期待と違う結果になるはずです(手順3の結果からの推論で、この形は実機では実行していません)。
- `NESTED PATH`を外して`lines`を1列にした場合、1つの文書につき1行になるので、受注の件数と同じ8行になる見込みです(未検証(2026-09-29時点))。採点の目安は、3つの問いそれぞれに、理由つきで答えられたかどうかです。

</details>

### 演習3(独力: 往復で何も失われていないか)

手順5の結果(12行)を、元の`JUCHUD`と、目で比べるのではなく、SQLで機械的に比べてください。

- 元にあって戻った行にないものが、0行であること。
- 戻った行にあって元にないものが、0行であること。

ヒント: `EXCEPT`を、向きを変えて2回使います。`JUCHUD`側は`JUNO, JULINE, JUSHO, JUSU`の4列、戻した側は`JUNO, LINE_NO, PRODUCT, QTY`です。`JUNO`は`CHAR(6)`同士、`JULINE`と`LINE_NO`の型が違う点も気にしてみてください(比較が期待どおりに動くかは、未検証です)。判定の目安は、両方向の結果が0行になることです。0行にならない場合は、返った行を見て、どの列が違うかを説明できれば十分です。

## 実機メモ

- **確認日: 2026-09-29。バッチ`part09-01-02-json`(1回の接続。記録は[プローブ記録](../probes.md)の「第9部」の節)、PUB400、IBM i 7.5(V7R5M0)。** 検証は、著者の検証用ライブラリーに対して`db2`(SQLの`collect`)と、IFS上の`.sql`を`RUNSQLSTM SRCSTMF`で実行する経路の2つで行いました。学習者の`<自分のユーザー名>1`での再現は、個別には確認していません(08-07の実機メモと同じ扱いです)。ジョブのCCSIDは273でした。
- **V2で確認できたこと**: `JSON_OBJECT`のコロン書式(`'orderNo': M.JUNO`)と、`FORMAT JSON`つきの入れ子(`lines`が配列で出る。数値は引用符なし)。`FORMAT JSON`なしでは`"lines":"[{\"line\":1},{\"line\":2}]"`と二重にエスケープされること。`JSON_TABLE`の`NESTED PATH`が、全12明細行を親の項目つきで1回の呼び出しで返すこと(結果は`J00001`〜`J00008`)。`VALUES JSON_OBJECT(KEY 'ok' VALUE 1)`が`{"ok":1}`になること。`$ [ ] { }`を含むSQLが、`db2`経由でも、CCSID 273のタグの`.sql`を`RUNSQLSTM SRCSTMF`で実行する経路でも壊れずに動いたこと。`RUNSQLSTM`が`SELECT`単独文を`SQL0084`で拒否すること(`SELECT`単独文を含む`.sql`で確認。重大度30)。表が未ジャーナルの`SQL7905`(重大度20)が、`ERRLVL(40)`つきの実行では、後続の文が動くこと(実行リストの集計ではエラー1件と数えられ、`ERRLVL`の既定値での動作は未検証(2026-09-29時点))。`IFS_WRITE_UTF8`が文字列リテラル`{"a":1}`と`UX'3042'`で成功し、`IFS_READ_UTF8`で読み戻せたこと。`.sql`を`iconv`でUTF-8(CCSID 1208タグ)にして`RUNSQLSTM`に渡すと`SQL0330`で失敗したこと。
- **手順の期待される結果は、レッスンのスクリプトの文そのものを実行した結果ではありません。** 取り方は、手順4の直前の説明のとおりです(手順2・5は`db2`で同じ形、手順3は`INSERT ... SELECT`+`CAST`、手順4は`CONCAT`連結の値からの組み直し)。**その後、スクリプトには、文0(`SET SCHEMA`)・文1b・文4を追加し、文1・文3から`customer`キーを外して確認済みの形に揃えましたが、直したスクリプトの全文を一度に流したことはありません**(文0と文4のプレースホルダーは、実行前に書き換えが要ります)。
- **`SET SCHEMA <自分のユーザー名>1;`(文0)は、実機で確認していません(未検証(2026-09-29時点))。** 確認したのは、`CURRENT SCHEMA`がユーザー名のままであること(検証の出力の`SCHEMA <USER>`)と、`RUNSQLSTM`の`DFTRDBCOL`を指定した実行で、作られたオブジェクトが`DFTRDBCOL`のライブラリーにでき、未修飾の`JUCHUM`・`JUCHUD`も同じ実行で見つかったことの2つだけです(仕組みは切り分けていません)。
- **`KEY ... VALUE`形式の数値の出方の食い違いは、未切り分けです(未検証(2026-09-29時点))。** `KEY 'k' VALUE 1, KEY 'v' VALUE 'x'`を含む実行では`{"k":"1","v":"x"}`(`VALUE 1`が文字列に)、単独の`VALUES JSON_OBJECT(KEY 'ok' VALUE 1)`では`{"ok":1}`でした。同じ書式で結果が違う理由(実行の経路の違いか、同じ文の中の`'x'`との組み合わせか)は調べていません。
- **未検証(2026-09-29時点)**: ACS「実行SQLスクリプト」での実行(P14はV3のままです。PUB400自身の127.0.0.1へのポート接続の試験は、すべて3秒のタイムアウト(exit 28)で、開いているか閉じているかを区別できませんでした)。組み立てたJSON・表の列を`IFS_WRITE_UTF8`の`LINE`に渡す形と、`LINE`の長さの上限。表の列(`VARCHAR`)のJSONを`JSON_TABLE`で読む形。演習2〜4のSQL。学習者が自分のSSHシェルから`.sql`を書く手順。7.5より前の版での動作。
