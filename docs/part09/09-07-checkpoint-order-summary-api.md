## 説明

### 全体の形: 「提供」「取得」「文書」

Windows・Linuxで言えば、SQL関数の入口は、アプリが直接呼ぶ「データベースのビュー・ストアド関数」に近く、HTTPで公開する入口(REST)は、その前に置く窓口に近い、という関係です(一般的な例えで、実機の確認はありません)。

このレッスンは、3つの部分に分かれています。

| 部分 | 何をするか | 使うもの | 実機での確認 |
|---|---|---|---|
| 提供 | 受注サマリーを返す入口を、1つのSQL関数にする | `ORDER_SUMMARY_JSON`([`solutions/09-07/09-07-summary.sql`](../../solutions/09-07/09-07-summary.sql)) | V2(バッチ`part09-07-checkpoint`) |
| 取得 | 外部APIの応答を、アダプター経由で取り込み、記録を確かめる | 09-05の`JUHTTPSV`・`APILOG`(モック経路) | 部品はV2(09-05)。**このレッスンの手順としての通し実行は、未検証(2026-09-29時点)** |
| 文書 | 上の2つを、11節の設計書に書き、テスト証拠を付ける | [API設計テンプレート](../templates/api-design.md) | (文書なので実機の確認は無い。証拠の値は「提供」の結果) |

「提供」の側のAPIは、HTTPではありません。**呼び出し元がSQLで`SELECT ORDER_SUMMARY_JSON(3) ...`と書くと、JSON文字列が返る**、というSQLの入口です。HTTPで公開するには、IWSなど別の仕組みが要ります(後の読解用の囲み)。この違いは、設計書の「1. 目的・呼び出し元」と「7. 実行環境の制約チェックリスト」に、はっきり書きます。

### `ORDER_SUMMARY_JSON`を読む

関数の全文は[`solutions/09-07/09-07-summary.sql`](../../solutions/09-07/09-07-summary.sql)にあります。骨組みは、次の3つの項目を持つ`JSON_OBJECT`です。

- `requested`: 引数`P_N`をそのまま返す(「何件頼まれたか」を、応答自身に残す)。
- `latestOrders`: 受注の新しい順に、`P_N`件。各件が`orderNo`・`orderDate`・`customer`・`lineCount`(明細の件数)・`amount`(明細の`JUSU * JUTNK`の合計)を持つ。`JSON_ARRAYAGG(... ORDER BY R.RN)`で配列にし、外側の`JSON_OBJECT`に入れるので`FORMAT JSON`が要る(09-02)。
- `lowStockCount`: 在庫が発注点を下回る商品の件数(`ZAIKOM.ZASU < SHOHIM.SHOHAT`)。

設計上の判断を、4つ挙げます。設計書の「3. 業務ロジックの置き場所」に、そのまま書く内容です。

1. **基本の表だけを使う。** `JUCHUM`・`JUCHUD`・`SHOHIM`・`ZAIKOM`を直接読みます。09-04の`LOW_STOCK`・`JUCHU_INQUIRY_JSON`は呼びません。理由は、これらを先に作っていなくても動くようにするためです(09-04の片付けで消していても、この関数は作れます)。代わりに、「発注点を下回る」という条件が`LOW_STOCK`と**2か所に**書かれることになります。二重保守の芽です(演習(d)で扱います)。
2. **戻り値は`VARCHAR(4000) CCSID 1208`。** 4000バイトを超える件数を頼まれたときの振る舞いは、試していません(未検証(2026-09-29時点))。全8件(`N`=20)の結果は798バイトでした(結果ファイルの`Q20`の行の文字数を数えた値。すべてASCIIなので、バイト数も同じ。`part09-07-checkpoint` 19:22)。1件あたり約100バイトなので、20件でも4000バイトに収まる、という見込みは外挿です。
3. **`SPECIFIC ORDSUMJSN`を付ける。** 09-04と同じ理由です。実体の名前が予想でき、`TXCHECK`が`CHKOBJ`で確かめられます(実機では、実体は`*SRVPGM`の`ORDSUMJSN`、属性`CLE`、テキスト`SQL FUNCTION ORDER_SUMMARY_JSON`でした)。
4. **`P_N`の検証はしない。** `0`なら`"latestOrders":null`が返ります(実機で確認)。負の数・`NULL`・大きすぎる数の振る舞いは、試していません(未検証(2026-09-29時点))。設計書の「2. 入力・出力の形」に、「呼び出し元が1〜20で渡す」のような約束を書くか、関数に検証を足すかは、設計判断です。

`amount`は、確認したすべての実行(`db2`の呼び出し、バッチの`RUNSQL`)で、`6040.00`のように、コンマではなくピリオドで出ました(V2)。理由は、検証で切り分けていません。仮説は、金額を列の値から計算しているから、です(09-04では、リテラルの数値を`JSON_OBJECT`に渡すと、`RUNSQL`・`RUNSQLSTM`の中で文字列とコンマになりました。09-04の実機メモ)。`requested`は引数`P_N`の値で、呼び出しに書いたリテラル(`3`)から来ますが、バッチの`RUNSQL`でも`"requested":3`と数値で出ました。

### 呼び出しの3つの形と、確かめた範囲

同じ関数を、呼び出し方によって、確かめた範囲が違います。**混ぜて読まないでください。**

| 呼び出し | 確かめた範囲 |
|---|---|
| SSHの`db2`から、ライブラリーで修飾して呼ぶ(`<自分のユーザー名>1.ORDER_SUMMARY_JSON(2)`) | 新しいジョブから実行し、期待どおりのJSONが返った(V2)。`N`=2だけ |
| CLプログラムの中の`RUNSQL`(バッチ・ジョブ)から、修飾あり(`NAMING(*SQL)`)・なし(ライブラリー・リスト経由)の両方 | `N`=3・1・20・0の結果を、表に入れて確かめた(V2)。5250の対話式ジョブではない |
| `db2`・5250・ACSから、ライブラリーを付けずに呼ぶ。`RUNSQLSTM`の`.sql`の中で無修飾に呼ぶ形も同じ | 未検証(2026-09-29時点)。新しいジョブでは、`SQL0204`になるおそれがあります(09-04で、関数の本体から無修飾の関数を呼ぶと別ジョブで`SQL0204`になった、という実機結果があります。呼ぶ側の無修飾とは別の話ですが、同じ考え方で、修飾して呼んでください) |

この教材では、**ライブラリーで修飾して呼ぶ**形を基本にします(09-04の決まりと同じです)。`RUNSQLSTM`の`DFTRDBCOL`は、既定のスキーマを決めるもので、SQLパスにライブラリーを足すとは確かめていません(保存された`SQL_PATH`はライブラリーを含みません)。

### 設計書のフォーマットと、公開の方法の比べ方(読むだけ)

APIの設計書を決まった書式で書く方法の1つが、**OpenAPI**(HTTPのAPIを、YAMLまたはJSONで記述する仕様)です。**この教材では、OpenAPIの文書も、下の公開方法も作りません**(第9部の「読んで設計する」層。[第9部の扉](index.md))。このレッスンの設計書は、テンプレートの11節を日本語で埋める形です。以下は、「もしこの関数を外に公開するなら」と比べるための読解用の表で、どれもPUB400で使えるかは未検証(2026-09-29時点)です(サーバーの作成や受信ポートの開放は、設計上できない想定でした。一次資料で確認できたのはIWSの概要だけで、ほかは一般的な説明です)。

| 方法 | 何か | 確認の程度 |
|---|---|---|
| IWS(Integrated Web Services) | ILEの業務ロジックを、SOAP・RESTのWebサービスとして公開する、IBM iに組み込みの仕組み。サーバーの作成と配備の権限が要る想定 | 一次資料(IWSサーバーの解説書の序文・目次)で確認。PUB400での可否は未検証(2026-09-29時点) |
| Apache + RPG CGI | HTTPサーバーが、要求ごとにRPG等のプログラムを起動して応答を作る | 設計資料の一覧にある名前だけ。仕組みは未検証(2026-09-29時点) |
| Mapepire | IBM i上のデーモンにクライアントがSQLを送る仕組み。HTTPのAPIではない | PUB400の8076番へは、3秒のタイムアウトで開閉を区別できなかった(P40、V3。[09-01](09-01-api-overview-pub400.md)) |

比べる軸は、**入口がHTTPかSQL接続か**、**サーバーを立てる必要があるか**、**認証をどこでするか**(SQL接続ならIBM iのユーザー・プロファイル。HTTPなら別の認証を重ねることが多い)、**契約(入出力の形)をどう書くか**(SQL関数なら、シグネチャーと戻りのJSONの形。HTTPなら、OpenAPIのような文書)の4つです。設計書の「5. 認証・権限」「6. 版管理」「7. 実行環境の制約チェックリスト」に効きます。SQL関数の側には、HTTPの`minimum`・`maximum`に当たる検証がありません(上の「読む」の4)。HTTPで公開するなら、その検証を入口の側に持たせる設計になります。

**警告(共有データ)**: この関数は、あなたの`JUCHUM`・`JUCHUD`・`ZAIKOM`の**現在の中身**を読みます。09-04の演習で作った受注`J09901`〜`J09903`が残っていると、最新の受注が`J09901`になり、下の期待値と食い違います。09-04の[片付け](09-04-api-boundary-sql-routines.md#片付け)の手順1が済んでいることを、手順1で確かめてください。

**このレッスンの検証は、バッチ・ジョブ(CLプログラムの中)と、SSHの`db2`で行いました**。5250の対話式ジョブで打つ形(`TXCHECK`・`CALL`など)は、実機では確かめていません。以下、確認していない形には、その旨を書きます。

### 公開設計書: 受注サマリーAPI

以下が、テンプレートの11節を埋めた記入例です。**値は、確認した結果(バッチ名`part09-07-checkpoint`、2026-09-29)と、設計上の想定を、はっきり分けて書いてあります。** 「想定」「未検証」と書いた項目は、実機で確かめていない、あなたの現場で決める項目です。

#### 1. 目的・呼び出し元

- 目的: 直近の受注N件(受注番号・受注日・得意先・明細数・金額)と、発注点を下回る商品の件数を、1回の呼び出しで、1つのJSON文書として返す。
- 呼び出し元(想定): 社内の画面(ダッシュボード)や別システム。SQLの接続を持てるもの。HTTPしか話せない呼び出し元には、この関数は直接は使えません。
- 呼び出し頻度・同時実行数(想定): 画面の表示ごと。同時実行数は見込みがなく、測っていません(未検証(2026-09-29時点))。

#### 2. 入力・出力の形

- 入力: `P_N`(`INTEGER`、必須)。最新から何件取るか。妥当性: 0以上を想定(負の数・`NULL`の振る舞いは未検証(2026-09-29時点))。4000バイトの戻り値の上限から、呼び出し元は1〜20の範囲で渡す、と約束する(想定。関数自身は検証しません)。
- 出力(成功時、`P_N`=2、実機の出力):

  ```json
  {"requested":2,"latestOrders":[{"orderNo":"J00008","orderDate":20260912,"customer":"C00003","lineCount":2,"amount":6040.00},{"orderNo":"J00007","orderDate":20260911,"customer":"C00006","lineCount":1,"amount":4450.00}],"lowStockCount":2}
  ```

- 空・0件・該当なし: **正常系として扱う。** `P_N`が0のとき、`"latestOrders":null`を返し、`lowStockCount`は返す(実機で確認)。受注の表が空のときも同じ形になると考えられますが、確認していません(未検証(2026-09-29時点))。

#### 3. 業務ロジックの置き場所

- 新規に書いた(既存のRPGには無い集計)。`JUCHUM`・`JUCHUD`・`SHOHIM`・`ZAIKOM`を読むだけ(`READS SQL DATA`)。
- 境界: `LANGUAGE SQL`の関数。実体は`*SRVPGM`の`ORDSUMJSN`(実機で確認)。
- 5250との共有: しない。API専用に新規に書いた集計で、5250のプログラムとは共有していません。二重保守のリスク: 「発注点を下回る」という条件が、`LOW_STOCK`(09-04)と2か所にあります。抑え方は、`LOW_STOCK`を呼ぶ形に置き換えること(演習(d)。未検証(2026-09-29時点))。

#### 4. エラー・ステータスの規約

- 見つからない: エラーにしない(0件は正常系)。
- 権限がない: SQLの権限エラーになる(具体的な`SQLSTATE`は、確認していません。未検証(2026-09-29時点))。
- 入力が不正: この関数は検証しない(上の2)。検証を足す場合の型として、09-04の`JUCHU_REGISTER`が二重登録で`SIGNAL SQLSTATE '75001'`を返す作りがあります(実機で確認)。
- 内部エラー: SQLのエラーがそのまま返る。IBM iのジョブ・ログのメッセージ(`CPF`・`MCH`等)や、ライブラリー名・ジョブ名は、呼び出し元に見せない、という方針を、入口(将来HTTPで公開するなら、その層)で守る想定です。
- ログ: この関数は`READS SQL DATA`で、記録を書きません。呼び出しの記録(誰が・いつ)は、入口の側(呼び出し元、またはHTTPの層)に持たせる想定です(09-05の`APILOG`のような表が参考になります)。

#### 5. 認証・権限

- 認証: SQLの接続のIBM iユーザー・プロファイルに任せる(この関数自身は認証を持たない)。HTTPで公開する場合は、別の認証を、入口に置く。
- 権限: この関数の実行権限を、呼び出し専用のプロファイルに絞るかどうかは、現場で決める項目です。権限の付与のコマンドは、この教材では実機で試していません(未検証(2026-09-29時点))。
- 監査: 必要かどうかは、現場で決める(想定)。

#### 6. 版管理

#### 8. 冪等性(呼び出しをやり直しても安全か)

- 読むだけなので、何度呼んでも、データが変わらない限り同じ結果を返します(設計上の性質。`READS SQL DATA`)。呼び出し元が、通信の失敗で、そのまま再試行してよい。
- 対比: 書き込みの手続きは別の設計が要ります。09-04の`JUCHU_REGISTER`は、同じ受注番号の2回目を`SQLSTATE 75001`(`SQL0438`)で断り、明細は増えませんでした(実機で確認)。ただし、1回目の途中で失敗すると、ヘッダーだけが残った例があります(原子性が無い。`SQL0407`の実例)。書き込みのAPIを設計書に書くときは、「二重に呼ばれたとき」と「途中で失敗したとき」の両方を、書いてください。

#### 9. 量・頻度の上限

- 1回の応答の大きさ: 戻り値は`VARCHAR(4000)`。全8件(`N`=20)で798バイト(実測、`part09-07-checkpoint` 19:22)。件数の上限は、呼び出し側で1〜20と約束する(想定。1件約100バイトからの外挿で、4000バイトを超えたときの振る舞いは未検証(2026-09-29時点))。

## 出力が違うとき

- **`latestOrders`が、配列ではなく、`"[{\"orderNo\"...}]"`という文字列になっている。** 関数のソースの`FORMAT JSON`が抜けています(09-02)。配布のソースには付いています。自分で書き換えたなら、`JSON_ARRAYAGG(...)`の閉じ括弧のあとの`FORMAT JSON`を確かめてください。
- **最新の受注が`J00008`ではなく、`J09901`などになる。** 09-04の演習で入れた受注が残っています。09-04の片付けの手順1をやり直してください。
- **`lowStockCount`が2ではない。** `ZAIKOM`の在庫が、初期状態と違います(`reserve`を呼んだなど)。`<自分のユーザー名>1/TXRESET LIB(<自分のユーザー名>1)`で戻します。
- **`amount`の小数点がコンマになる、または数値が文字列になる。** 金額を、列の値ではなく、リテラルから作っていないか確かめてください(09-04。`RUNSQL`・`RUNSQLSTM`の中でリテラルの数値を`JSON_OBJECT`に渡すと、文字列とコンマになった)。配布の関数では、確認したすべての実行で、ピリオドの数値になりました。
- **呼ぶと`SQL0204`になる。** ライブラリーで修飾しているか、関数が作られているか(手順3)を確かめてください。`RUNSQLSTM`の`.sql`の中で無修飾に呼んだ場合も、同じ原因の可能性があります(未検証(2026-09-29時点))。
- **`RUNSQLSTM`で`SELECT`を実行して`SQL0084`。** `SELECT`は`db2`かACSで実行します。
- **`TXCHECK`が、PASS3件ではなく、FAILが混ざる。** 手順3で、実体が`*SRVPGM`の`ORDSUMJSN`として在るかを確かめます。`TXCKM`の行(名前・型)が、実際のものと合っているかも確かめます。
- **`TXCHECK`が「could not query the manifest」になる。** 同じジョブで2回目に呼んでいる可能性があります。サインオフ・サインオンし直してください(08-08の提案。09-07では未確認。未検証(2026-09-29時点))。`TXCKM`が無いときも、この文言になる可能性があります(ソースからの推測)。
- **PASSの行の文言が、この教材と違う。** 手順7で自分が入れた`CKDESC`の文字列が、そのまま出ます。件数と要約の形(3件PASS・failed 0・2行に分かれる要約)が合っていれば、問題ありません。
- **ACS・VS Codeから呼べない、または表示が違う。** V3です(未検証(2026-09-29時点))。接続できなくても、本編は成立します。無理に設定を変えないでください。

### 演習(a): 例題を読む(紙の上)

手順5の表(`N`=1・3・20・0)を見て、次に答えてください。

1. `N`を0にしたとき、`latestOrders`が空の配列`[]`ではなく`null`になるのはなぜですか(ヒント: `JSON_ARRAYAGG`に、行が1行も渡らないとき)。呼び出し元は、この違いに、どう備えますか。
2. 受注が、全8件ではなく、1000件になったとします。`N`に1000を渡すと、何が起きそうですか。設計書のどの節に、何を書きますか。
3. `lowStockCount`が、`N`に関係なく、いつも同じなのはなぜですか。

<details><summary>解答例</summary>

1. `latestOrders`の`JSON_ARRAYAGG`は、条件(`R.RN <= P_N`)に合う行が0行のとき、空の配列ではなく`NULL`を返すからです(実機の結果が、そうなっています。一般にそうなる、という説明は、この教材では確かめていません)。呼び出し元は、`latestOrders`が配列のときと`null`のときの、両方を受け取れるように書きます(設計書の「2. 入力・出力の形」に、0件は`null`と明記する)。
2. 戻り値が`VARCHAR(4000)`なので、4000バイトを超える件数を頼まれたときの振る舞いが問題になります。実際の振る舞い(エラーか、切り捨てか)は、確かめていません(未検証(2026-09-29時点))。設計書の「2. 入力・出力の形」に、`P_N`の範囲の約束(1〜20など)を書き、「9. 量・頻度の上限」に、その理由(4000バイト)と、超えたときは未検証であることを書きます。
3. `lowStockCount`は、受注ではなく、`SHOHIM`と`ZAIKOM`から数えるからです。`N`は、`latestOrders`の件数だけを決めます。

</details>
