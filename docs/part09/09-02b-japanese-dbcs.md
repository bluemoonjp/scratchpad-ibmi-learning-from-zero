## ゴール

- 09-02b-1: `UX'3042'`(ひらがなの「あ」)を、CCSID 1208(UTF-8)・1399・939・930の文字列に変換し、`HEX()`の結果(`E38182`と`0E44810F`)を読み分けられる。

## なぜ学ぶか

第4部・第5部の旧システムは半角カナと英数字の世界でしたが、現場のデータには漢字の氏名・住所・摘要が入ります。IBM iでは、その全角の日本語が**どのCCSIDで、何バイトを使って**入っているかを読み違えると、桁あふれや文字化けが起きます。第9部の[09-05](09-05-external-api-adapter-mock.md)(外部APIから受け取る日本語のJSON)でも、まったく同じ問題に出会います。実際、09-05の実測では、応答のCLOB(CCSID 1208)をジョブCCSIDのVARCHAR列に取り出したところ日本語が代替文字(`3F3F3F`)になりました。

このレッスンの中心は「配布ソースはASCIIのまま保つ」という方針(付録J)を守りながら、それでも**日本語の1文字が実機の中でどんなバイト列になるか**を、`HEX()`という物差しで確かめることです。日本語の入力が画面でできなくても、`UX'3042'`という16進表記(Unicodeのコード・ポイント)だけで、実機側の結果を目で読めます。

## 新出

- 中核概念(3つ):
  1. **同じ文字「あ」でも、CCSIDによってバイト列が違う。** 実測では、CCSID 1208(UTF-8)では`E38182`(3バイト)、CCSID 1399・939・930では`0E44810F`(4バイト)でした。後者は、シフトアウト(SO、`0E`)+DBCSの2バイト(`4481`)+シフトイン(SI、`0F`)という並びです。
  2. **ジョブのCCSIDと、式・列のCCSIDは別の属性である。** PUB400で著者が調べたジョブ(`RUNSQLSTM`のバッチジョブ)は273(付録Jによるとドイツ語圏向けのEBCDIC)でした。そのジョブの中で`CAST(... CCSID 1208)`は、指定したCCSIDの結果(`E38182`)を返しました。`CAST(... CCSID 1399)`が`0E44810F`を返したことも実測していますが、そのときのジョブのCCSIDは読んでいません。
  3. **日本語を試すときの入口は`UX'..'`で、結果は`HEX()`で読む。** `GX'..'`の直書きは通りませんでした(実測、下の手順5)。通る入口(`UX'..'`)と通らない入口を実機で見分ける体験がこのレッスンの核心です。
- コマンド・構文(新規1つ、上限6つ以内):
  1. `CAST(式 AS VARCHAR(n) CCSID nnnn)`(CCSIDを指定した変換)
- 既習の応用(新出に数えない):
  - `UX'3042'`(Unicodeのコード・ポイントを並べた文字列定数。09-02で既習)
  - `HEX(式)`(バイト列を16進で見る。05-11で既習。ここではCCSIDの読み分けが新しい使い方です)
  - `QSYS2.IFS_WRITE_UTF8`(演習(d)のみ。09-02で紹介済み)

**読解用(新出に数えない。このレッスンでは実機で確かめていません)**:

- `GX'..'`(グラフィック定数)、`GRAPHIC(n)`型、CCSID 1200(UTF-16)。**`GRAPHIC(1) CCSID 1200`を含む1文は失敗しました**(SQLSTATE 42611)が、原因がどの部分かは切り分けていません(手順6)。
- CCSID 932・943・5035の使い分け、DDSのDBCSフィールド型`G`・`J`・`O`・`E`、CRTSRCPFの`IGCDTA(*YES)`。付録Jの「一般知識(このカリキュラムではまだ実機未検証)」のままで、**このレッスンでも確認していません**(未検証(2026-09-29時点))。
- SO・SIの詳しい規則(たとえば連続する全角文字で`0E`と`0F`がどこに入るか)。

### Windows/Linuxとの比較

IBM i上で実測できたのは、「あ」が1208では`E38182`(3バイト)、1399・939・930では`0E44810F`(4バイト)になる、という1例だけです。以下は**一般知識であり、実機・Windowsでは未確認**です(未検証(2026-09-29時点))。UTF-8はWindowsやLinuxでも同じ規則で、「あ」は`E3 81 82`になるはずです(BOMの有無など保存の設定にも左右されます)。IBM iのEBCDIC系の日本語CCSID(930・939・1399)は、半角と全角が混ざる文字列(混在文字列)で、全角の区間を**SOとSIではさむ**方式だと説明されます。この場合、列の長さは文字数ではなく**バイト数**で決まるので、全角1文字が4バイトを使うことがあります(上の1例は実測)。UTF-8には、この「はさむ」概念がありません(一般知識)。

### 実機の物差し: `HEX()`

```sql
SELECT HEX(CAST(UX'3042' AS VARCHAR(10) CCSID 1208)) AS U1208,
       HEX(CAST(UX'3042' AS VARCHAR(10) CCSID 1399)) AS U1399,
       HEX(CAST(UX'3042' AS VARCHAR(10) CCSID 939))  AS U939,
       HEX(CAST(UX'3042' AS VARCHAR(10) CCSID 930))  AS U930
  FROM SYSIBM.SYSDUMMY1;
```

`UX'3042'`は、ひらがな「あ」のUnicodeコード・ポイントU+3042です。`CAST`で各CCSIDの文字列にしてから`HEX()`で見ることで、**ソースは全部ASCIIのまま**、実機が内部でどのバイトを持つかがわかります。

## 実演

ACSの「実行SQLスクリプト」を開きます(接続設定そのものは[09-01](09-01-api-overview-pub400.md)で扱う内容で、このレッスンの著者はACS接続を実機で確認できていません。V3、未検証(2026-09-29時点))。**各SQLは1文ずつ実行してください。**

**ACSにつながらない場合(未検証(2026-09-29時点))**: 手順2・5・6のSQLは、5250の`STRSQL`([02-06](../part02/02-06-sql-inquiry.md))でも打てるはずですが、著者は試していません。`RUNSQLSTM`は単独の`SELECT`を実行できない(SQL0084、実測)ので、使うなら`INSERT ... SELECT`で自分のライブラリーの表に結果を入れる形になり、表を作る手間が増えます。どの経路も使えない場合は、このレッスンの実演は行えません。本文の実測値を読むだけにしてください。

1. **5250のジョブのCCSIDを確認します(任意)。** 5250のコマンド行で`DSPJOB OPTION(*DFNA)`を実行し、CCSIDの値を記録します。著者が実測したのは`RUNSQLSTM`のバッチジョブ(実行リストの「Job CCSID 273」)で、273でした。**ここで読む値は5250のジョブのものであり、ACSのSQLジョブの値ではありません(別のジョブです)。** 5250のジョブとACSのSQLジョブが273かどうかは未検証(2026-09-29時点)です。SQLでこの値を読む方法は、`ACTIVE_JOB_INFO`のCCSID列を1回試したところNULLでした。他の方法は未検証(2026-09-29時点)です。

2. **「あ」を4つのCCSIDに変換して、`HEX()`で見ます。**

   ```sql
   SELECT HEX(CAST(UX'3042' AS VARCHAR(10) CCSID 1208)) AS U1208,
          HEX(CAST(UX'3042' AS VARCHAR(10) CCSID 1399)) AS U1399,
          HEX(CAST(UX'3042' AS VARCHAR(10) CCSID 939))  AS U939,
          HEX(CAST(UX'3042' AS VARCHAR(10) CCSID 930))  AS U930
     FROM SYSIBM.SYSDUMMY1;
   ```

   期待する結果(実機確認済み、V2):

   | U1208 | U1399 | U939 | U930 |
   |---|---|---|---|
   | `E38182` | `0E44810F` | `0E44810F` | `0E44810F` |

   `E38182`は3バイト、`0E44810F`は4バイト(`0E`=SO、`4481`=「あ」、`0F`=SI)です。

3. **(任意)ジョブのCCSIDとの関係を読みます。** 手順2の`CAST`の結果は、ジョブのCCSIDに依存しませんでした(実測。ただし`CHGJOB CCSID(1399)`が効いたかどうかは確認できていません)。このレッスンでは、ジョブのCCSIDは変えずに進めます。

4. **ACSの画面で「あ」を目で見ます(V3、未検証(2026-09-29時点))。**

   ```sql
   VALUES CAST(UX'3042' AS VARCHAR(10) CCSID 1208);
   ```

   結果の列に「あ」と表示されるはずです(未検証)。表示されない、または別の文字になった場合は、下の「出力が違うとき」に自分の見たものを書き留めてください。日本語の文字そのものをSQLの文字列定数として直接書く実験(`'あ'`など)は、著者は行っていません(未検証)。この教材は`UX'..'`で書きます。

5. **通らない書き方を体験します。**

   ```sql
   SELECT HEX(GX'0E30420F') FROM SYSIBM.SYSDUMMY1;
   ```

   著者の実機では、`GX'0E30420F'`を含む複数の式を並べた1文が失敗しました(V2)。**上の1式だけの文は、そのままの形では実行していません(未検証(2026-09-29時点))。**

   ```text
   SQLSTATE: 42606
   -110: Hexadecimal constant beginning with GX'0E30420 not valid.
   ```

   メッセージID`SQL0110`は、ネイティブ・エラー-110からの推定で、画面で読んだIDではありません(未検証(2026-09-29時点))。SOとSIをつけた4バイトを`GX'..'`に直書きしても通りません。手順2の`UX'..'`+`CAST`が、通る書き方です。**GX定数がどういう形なら通るのか(SO・SIなしのDBCS2バイトを並べる形かどうか)は、このレッスンでは試していません(未検証)。**

6. **通らなかったもう1つの例を確認します(原因は切り分けていません)。**

   ```sql
   SELECT HEX(CAST(UX'3042' AS GRAPHIC(1) CCSID 1200)) AS G1200,
          HEX(CAST(UX'3042' AS CHAR(1) CCSID 1399)) AS TRUNC1399
     FROM SYSIBM.SYSDUMMY1;
   ```

   実機ではこの1文全体が`SQLSTATE 42611`(結果JSON上のネイティブ・エラー-604、Attributes not valid)で失敗しました。メッセージID`SQL0604`は、-604からの推定です。**`GRAPHIC(1) CCSID 1200`の部分が原因なのか、`CHAR(1) CCSID 1399`の部分が原因なのかは、1文にまとめてしまったため切り分けていません(未検証(2026-09-29時点))。** 「あ」は1399で4バイトを使うので、`CHAR(1)`(1バイト)には収まらないはずだ、という予想は立てられますが、予想にすぎません。演習(c)で、自分で1つずつ試して確かめます。

## 出力が違うとき

- **`U1399`などが`0E44810F`でない**: `UX'3042'`の綴りを確かめてください(`3042`、`UX`は大文字)。`VARCHAR(10)`の長さを`1`や`2`に縮めていませんか(演習(c)の症状です)。
- **`SQL0110`が出ない、別のメッセージが出る**: ACSは著者が使ったdb2のCLIと違うクライアントなので、メッセージ文が違って見える可能性があります(未検証(2026-09-29時点))。SQLSTATE(`42606`)を合わせて確認してください。
- **手順4で「あ」が別の文字や□に見える**: 未検証の部分です。ACS側のフォント・表示設定が原因である可能性を疑い、`HEX()`の結果が手順2と同じかどうかを先に確認してください(バイトが同じで表示だけ違うなら、実機ではなくクライアントの問題です)。

### (c) 独力: DBCSの切り詰めを予測して直す

「あいう」(`UX'304230443046'`)について、次の順で考えます。

1. CCSID 1208に変換すると何バイトですか。
2. CCSID 1399に変換すると何バイトですか(SOとSIは全体で1組だけ、と仮定してよい)。
3. `CAST(UX'304230443046' AS VARCHAR(n) CCSID 1399)`で、`n`をどこまで小さくしたら失敗(または切り詰め)が起きるか予想し、実際に`n`を変えて試してください。手順6の`CHAR(1)`の件も、`GRAPHIC(1) CCSID 1200`と別々の文に分けて確かめてください。
4. 結果が失敗・切り詰めだったとき、どう直しますか。

<details><summary>解答(予想の部分は未検証)</summary>

1. 3文字×3バイトで9バイトです(UTF-8の規則からの計算。実機での実行は未検証(2026-09-29時点))。
2. 「あ」が全角1文字で2バイトなので、3文字で6バイト、SOとSIで2バイト、合計8バイトと予想できます。連続する全角文字を1組のSO・SIではさむという仮定に基づく予想で、**実機の結果は未検証(2026-09-29時点)**です。
3. 上の予想では、`n`が8以上なら収まり、7以下で収まらなくなるはずです。ただし、失敗(エラー)になるのか、切り詰められて成功するのかは、この教材では確認していません(未検証)。手順6で`CHAR(1) CCSID 1399`にした文が失敗したこと(原因は未切り分け)は、この観点の手がかりの1つです。
4. 長さ`n`を、変換後の**バイト数**(SO・SIを含む)以上にします。文字数ではなくバイト数で数える、が要点です。

この設問の答えは予想であり、正解は自分で測った結果です。3は、失敗と切り詰めのどちらの結果になっても妥当な観測です。自分の実行結果は、[実機メモ](#実機メモ)の形式で記録しておくと、次の読者が確認済み・未検証を区別できます。

</details>

### (d) 応用: UTF-8のファイルに書く(任意)

`QSYS2.IFS_WRITE_UTF8`で、「あ」をIFSに書き出して、バイト数を確かめます。

```sql
CALL QSYS2.IFS_WRITE_UTF8(PATH_NAME => '/home/<自分のユーザー名>/j0902b.txt',
                          LINE => UX'3042',
                          OVERWRITE => 'REPLACE',
                          END_OF_LINE => 'NONE');
SELECT * FROM TABLE(QSYS2.IFS_READ_UTF8(PATH_NAME => '/home/<自分のユーザー名>/j0902b.txt'));
```

<details><summary>解答</summary>

著者の実機確認(2026-09-29、別パス)では、同じ形の`IFS_WRITE_UTF8`が成功し、`E3 81 82`(UTF-8の「あ」、3バイト)が書かれました。`IFS_READ_UTF8`が動くことを確かめたのは、ASCIIのファイル(`{"a":1}`)だけです。「あ」を書いたファイルを`IFS_READ_UTF8`で読み返したことはなく、`LINE_NUMBER`と`LINE`の2列を返す点も、ASCIIのファイルでの結果です。「あ」の読み返しと、その画面表示は未検証(V3、2026-09-29時点)です。SSHで`od -x`を実行したときの著者の実測は、`e381 8200`(小文字、末尾に`00`が1バイト付く。ファイルは3バイト)でした。学習者の環境でも同じ表示になるかは未検証(2026-09-29時点)です。SSHの使い方は02-04です。

## 実機メモ
