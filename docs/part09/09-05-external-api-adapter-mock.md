## なぜ学ぶか

現場の「外部APIを呼ぶ処理」は、ほとんどが「呼ぶ処理」と「その結果を使う処理」の2つに分かれます。どちらも、テストのたびに本物の相手を呼んでいたのでは、遅く、相手に迷惑で、失敗の再現もできません。そこで、呼ぶ処理を**アダプター**という1つのプログラムに閉じ込め、相手が本物かモック(あらかじめ用意した応答)かを、設定の1行で切り替えます。呼ぶ側のプログラムは、どちらが返してきたのか知らなくて済みます。

PUB400は共有の練習機です。同じIPアドレスから大量に外へ通信すると、ほかの利用者にも迷惑になるおそれがあります(この点は、この教材では確かめていません。未検証(2026-09-29時点))。このレッスンの「まずモック。実通信は手で、1回ずつ」という作法は、その現実への対応でもあります。

ここで作る`JUHTTPSV`・`APILOG`と、応答を`JSON_TABLE`で読む考え方は、09-07の受注サマリーAPIの「取得」の手順で再利用する計画です(09-07はまだ書かれておらず、この計画は未検証(2026-09-29時点))。非対話のバッチ・ジョブから完了を通知する話は、ここでは扱いません。09-06(データ待ち行列)で扱います。

## 説明

### アダプター層とは(Windows/Linuxとの比較)

WindowsやLinuxの開発では、外部のWebサービスを呼ぶコードの手前に「インターフェース」を置き、テストのときは偽物(スタブ、モック・サーバー)に差し替える、というやり方をよく使います。差し替えの方法は、設定ファイル、環境変数、依存性の注入(DI)などです。

IBM iのこの教材では、同じことを**表の1行**で行います。`APICFG`という1行だけの表に`APIMODE`(`MOCK`か`REAL`)があり、`JUHTTPSV`は呼ばれるたびにそれを読みます。プログラムの作り直しも、ライブラリー・リストの入れ替えも要りません。SQLの1文(`UPDATE`)で切り替わります。

これまでの09-03・09-04は、**自分のロジックを外に公開する側**(インバウンド)でした。09-05は逆に、**外のサービスを自分から呼ぶ側**(アウトバウンド)です。この部で扱う相手は、郵便番号から住所を返す公開API(zipcloud)です。

### 3つの表

`db/mock/apimock.sql`([ソース](../../db/mock/apimock.sql))が、次の3つの表を作ります。

| 表 | 役割 | 主な列 |
|---|---|---|
| `APICFG` | 設定。1行だけ。 | `APIMODE`(`MOCK`/`REAL`)、`BASEURL`(APIのURL。郵便番号の手前まで) |
| `APIMOCK` | モックの応答。郵便番号ごとに1行。 | `ZIP`(主キー)、`HTTPST`(HTTPの状態コード)、`ZIPADR`(住所の文字列)、`BODY`(応答本文。`CLOB(8000) CCSID 1208`) |
| `APILOG` | 呼び出しの記録。呼び出しごとに1行。 | `LOGID`(自動採番)、`LOGTS`(時刻)、`APIMODE`、`ZIP`、`URL`、`RC`(結果コード)、`HTTPST`、`RESPLEN`(応答の長さ)、`SQLST`(SQLSTATE)、`RESP`(応答本文。`CLOB(32000) CCSID 1208`) |

`APIMOCK`には、次の4行が入ります。「失敗」も行で表すのが、ここでの設計です。

| `ZIP` | `HTTPST` | 意味 | `BODY` |
|---|---|---|---|
| `1000001` | 200 | 見つかった(成功) | `results`に住所が1件入ったJSON |
| `9999999` | 200 | 見つからない、を表すモックの約束。本物のzipcloudが、存在しない郵便番号に`results`が`null`・HTTP 200で答える、というのは著者の想定です(存在しない郵便番号での実通信は行っておらず、未検証(2026-09-29時点)) | `results`が`null`のJSON |
| `9999504` | 504 | ゲートウェイ・タイムアウト(サーバーの失敗) | 空 |
| `9999404` | 404 | 見つからない(HTTPの失敗) | 空 |

5つ目の呼び出し(`1234567`)は、`APIMOCK`に行が無い郵便番号です。これは「モックの用意漏れ」を表し、結果コード`NOMOCK`になります。

`apimock.sql`の応答本文は、`JSON_OBJECT`・`JSON_ARRAY`で組み立てています。ソースに波かっこ・角かっこを書かないためです(CCSID 273で位置が変わる文字。[スタイル・ガイド](../style-guide.md)、09-02)。日本語の住所は、モックには入れていません(すべてローマ字。理由は「モックでは見つからない不具合」の節)。

### `JUHTTPSV`の流れ

`src/qrpglesrc/juhttpsv.sqlrpgle`([ソース](../../src/qrpglesrc/juhttpsv.sqlrpgle))は、郵便番号(7桁)を受け取り、結果コード(8桁)を返します。中身は3つの段に分かれます。

1. **どちらのモードか。** `APICFG`の1行から`APIMODE`と`BASEURL`を読みます。行が読めなければ、安全側の`MOCK`にします。
2. **モックか実通信か。**
   - `MOCK`: `APIMOCK`から、郵便番号に合う行の`HTTPST`と`BODY`を読みます。行が無ければ(`SQLSTATE`が`02000`)`NOMOCK`。`HTTPST`が400以上、または0なら`HTTPERR`。それ以外は`OK`。
   - `REAL`: `QSYS2.HTTP_GET`を**1回**呼びます。`SQLSTATE`が`00000`(または、切り詰めの`01004`)なら`OK`、それ以外は`HTTPERR`(`01004`を`OK`とみなす分岐は、ソースを読んだだけで、実機では確かめていません。未検証(2026-09-29時点))。
3. **記録する。** どの場合も、`APILOG`に1行入れます。そのあと、`LENGTH(RESP)`で、応答の長さを更新します。

結果コード(`RC`)は3つです。

| `RC` | 意味 | このレッスンでの再現 |
|---|---|---|
| `OK` | 応答が`APILOG`に保存された(`results`が`null`でも、`OK`です) | `1000001`・`9999999` |
| `HTTPERR` | モックの行が失敗の状態(400以上・0)、または実通信が失敗した | `9999504`・`9999404` |
| `NOMOCK` | モックのとき、`APIMOCK`に行が無い | `1234567` |

**このプログラムは、JSONを解析しません。** 応答の文字列をそのまま`APILOG`に入れるだけです。JSONのパス式(`$`・`[*]`)は、CL・RPGのソースに書かない、という09-02・09-04の決まりに従い、別の`.sql`(演習(b)で自分で書きます)が読みます。

**読み取れる注意点(コードの読み方。実行で確かめていない部分を含みます)**: `REAL`のとき、`HTTPST`に入る値は、**応答から読んだ値ではありません**。`QSYS2.HTTP_GET`は本文だけを返し、状態コードを返さないので、プログラムは「エラーにならなければ200」と決めて入れています(ソースの`wSt = 200`)。応答のHTTPの状態を本当に知るには、`HTTP_GET_VERBOSE`(読解用の囲み)が要ります。また、実通信が**失敗した**ときの動作(`HTTPERR`になり、`SQLST`に`SQLSTATE`が入るはず)は、実機では確かめていません(未検証(2026-09-29時点))。実通信は、成功した1回だけを確認しました。

### CLOBホスト変数と`SQL0312`

HTTPの応答本文は、長さが決まっていません。SQLでは`CLOB`(大きな文字データ)、RPGでは`sqltype(clob:32000)`で宣言したホスト変数で受け取ります。

```text
dcl-s resp sqltype(clob:32000) ccsid(1208);
```

- `clob:32000`は、最大32000バイトを表します。
- `ccsid(1208)`は、UTF-8で持つ、という指定です。応答本文はUTF-8で来ます(実機で確認した応答のヘッダーが`content-type text/plain;charset=utf-8`でした。読解用の囲み)。

このように宣言すると、コンパイラーがこの名前の変数を、長さを持つ形(RPGから見ると`resp_len`が使える)に作り替えます。`resp_len = 0;`と、RPGの文で書いたところは、コンパイルできました(実機で確認)。

**ここに落とし穴があります。** SQLの文の中に`:resp_len`と書くと、プリコンパイラーが次のエラーにします(1回目のコンパイルで実際に出ました)。

```text
SQL0312 30 ... Position 44 Variable RESP_LEN not defined or not usable for reason code 1.
```

(重大度30。`...`は途中を省いた印です。)プリコンパイラーは、`resp_len`を、SQLの文の中では使えない変数と判断しました。`resp_len`は、RPGの文の中では使えます。SQLの文の中では`:resp`だけを使います。応答の長さは、次のように、保存したあとでSQLに数えさせます。

```text
exec sql
  INSERT INTO APILOG (..., RESP) VALUES (..., :resp);
exec sql
  UPDATE APILOG SET RESPLEN = LENGTH(RESP)
    WHERE LOGID = IDENTITY_VAL_LOCAL();
```

`IDENTITY_VAL_LOCAL()`は、直前の`INSERT`が振った`LOGID`(自動採番の値)を返す関数です。ここでは「いま入れた行」を指すために使っています。

### モックでは見つからない不具合がある

モックは便利ですが、本物と同じではありません。このレッスンの実機の結果には、次の違いがありました。

- **形が違う。** モックの本文は改行なしの1行(148バイト)、本物は`tab`と改行で整形された287バイトでした。本物には`kana1`〜`kana3`もありました。
- **`status`の型が違う。** モックでは`"status":"200"`(文字列)、本物では`"status": 200`(数値)でした。モックの数値が文字列になったのは、09-04の「リテラルの数値が`JSON_OBJECT`で文字列になる」現象と同じ場面(`RUNSQLSTM`で流したSQL)です。原因は09-04と同じく未確認です。`JSON_TABLE`の`STATUS INT PATH`は、どちらからも`200`を読めました。
- **日本語がモックには無い。** 本物の住所は日本語です。モックはローマ字だけにしてあるので、次の節の文字化けを、モックでは絶対に再現できません。

だからこそ、実通信を(1回だけ)試す価値があります。ただし、実通信を試すときには、次の作法を守ってください。

### 実通信の作法(この教材の決まり)

- **まずモックで完成させる。** 実通信は、モックで動いたあとの、最後の確認だけです。
- **実通信は、手で、1回ずつ。** ループ、`SBMJOB`(バッチ投入)、自動の繰り返しのテストから、実通信を呼ばないでください。失敗しても、続けて何度も呼ばないでください。原因は、まずモックで再現して調べます。
- 共有機のIPアドレスから大量に呼ばない、というのは、このレッスン独自の決まりです(スタイル・ガイドには書かれていません)。PUB400が外向きのHTTPS通信をどう扱うか(制限や許可)は、この教材では確認していません(未検証(2026-09-29時点))。試す前に、PUB400の利用条件を、自分で確認してください。
- 相手のサービス(zipcloud)の利用条件は、この教材では確認していません(未検証(2026-09-29時点))。試す前に、自分で確認してください。

### 日本語が入った応答の結果(実機で確認した1回分)

著者が確認した実通信の応答には、日本語(住所)が含まれていました。結果は次のとおりです。

| 見たもの | 結果 |
|---|---|
| `APILOG.RESP`(`CLOB(32000) CCSID 1208`)の16進数 | `7B0A09226D657373616765223A206E756C6C2C...`で始まり、住所の値のところに、`東京`のUTF-8のバイト列`E69DB1 E4BAAC`が、そのまま入っていました。**CLOBはUTF-8のバイトを保っています。** |

つまり、**保存(CLOB・UTF-8)は正しく、取り出しの列のCCSIDで壊れる**、という結果です。列を`VARCHAR(60) CCSID 1208`にすれば保てるはずですが、これは実機で試していません(未検証(2026-09-29時点))。この教材のデータ規約は、日本語の住所を`ZIPADR`列にだけ保存し、ほかの列はローマ字とコードで保つ、です。文字コードの基礎は[09-02b](09-02b-japanese-dbcs.md)と[付録J](../appendix/j-dbcs.md)を参照してください。

### 読解用の囲み: `HTTP_GET`の詳しいエラー情報

IBM Docsに、`HTTP_GET`の有用なエラー情報は、ACSの「実行SQLスクリプト」で実行しないと得られない(`STRSQL`では得られない)、という記載があります(第9部の扉の「道具」にも書きました)。この教材の実機確認は、`db2`(SSH)経由でした。`db2`で`SQLSTATE`が見えるかどうかは、IBM Docsに記載を確認しておらず、失敗する呼び出しも実機で行っていないので、未検証(2026-09-29時点)です。詳しい情報がACSでどう見えるかも、確認できていません(V3。未検証(2026-09-29時点))。実通信の失敗を調べるときは、まず`APILOG.SQLST`を見ます。ACSで同じ文を実行し直す方法はありますが、それは実通信をもう1回することになり、「失敗しても繰り返さない」に反します。この教材は、その手順を勧めません。

## 実演

前提: `<自分のユーザー名>1`に、`QRPGLESRC`(ソース物理ファイル。06-01b/06-03で作成済み)があること。SSHの`$HOME/ibmi-kyozai`が最新であること(`git pull`)。`(SSH)`はSSH、`(5250)`は5250の操作です。**このレッスンの検証は、バッチ・ジョブ(CLプログラムの中)で行いました。**5250の対話式ジョブで、同じ`CRTSQLRPGI`・`CALL`を打つ形は、実機で確かめていません(未検証(2026-09-29時点))。

## 演習

演習は、ふつうの実行を確かめる問題(a)・(b)・(c)と、紙の上の問題(d)です。スタイル・ガイドの4段階との対応は、次のとおりです。例題は実演の手順そのもの、(a)が「修正・穴埋め」(失敗の行を自分で増やす)、(b)が「独力」(`JSON_TABLE`の`.sql`を書く)、(c)が「応用」、(d)が紙の上の確認です。

### 演習(a): 失敗の応答を増やして、`APILOG`に残す

`APIMOCK`に、失敗の行を2つ足します。「タイムアウト」は、HTTPの応答が返ってこなかった場合です。ここでは、次のように表します。

- `9999408`: 状態コード408(Request Timeout。要求がタイムアウトした)
- `9999000`: 状態コード0(応答そのものが無かった、という約束にする)

1. 次の`INSERT`を、`db2`で実行してください。コンマの直後に、空白を入れます。

   ```sh
   db2 "INSERT INTO <自分のユーザー名>1.APIMOCK VALUES ('9999408', 408, '', CAST('' AS CLOB(8000) CCSID 1208))"
   db2 "INSERT INTO <自分のユーザー名>1.APIMOCK VALUES ('9999000', 0, '', CAST('' AS CLOB(8000) CCSID 1208))"
   ```

2. 5250で、`CALL PGM(<自分のユーザー名>1/JUHTTPSV) PARM('9999408' '        ')`と、`PARM('9999000' '        ')`の2回を呼んでください(手順4で`CHGCURLIB`をしたセッションで)。
3. 手順6の照会を、もう1度実行し、新しい2行の`RC`・`HTTPST`・`RESPLEN`・`SQLST`を、予想と比べてください。

<details><summary>答え</summary>

`INSERT`の形は、`apimock.sql`の`9999504`・`9999404`の行(実機で確認済み)と同じです。次の行が増えるはずです(**この2行そのものは、実行して確かめていません。ソースの読み方からの予想です。未検証(2026-09-29時点)**)。

| ZIP | RC | HTTPST | RESPLEN | SQLST |
|---|---|---|---|---|
| 9999408 | HTTPERR | 408 | 0 | 00000 |
| 9999000 | HTTPERR | 0 | 0 | 00000 |

理由: モックの行は、読めたので`SQLSTATE`は`00000`です。`HTTPST`が400以上(408)、または0(9999000)なので、`elseif wSt >= 400 or wSt = 0`が真になり、`HTTPERR`です。本文が空なので、`RESPLEN`は0です。`NOMOCK`(モックに行が無い)との違いは、`SQLST`が`02000`ではなく`00000`であることと、`RC`です。同じ状態コード0でも、`NOMOCK`は「用意漏れ」、`HTTPERR`は「用意した失敗」です。

実際に、実通信がタイムアウトしたときには、`APILOG`にどう残るのか(`SQLST`の値など)は、モックでは分かりません(未検証(2026-09-29時点))。

</details>

### 演習(d): 紙の上で

1. `JUHTTPSV`は、なぜ`INSERT`で`RESPLEN`に0を入れ、そのあとで`UPDATE`で長さを入れているのですか。`INSERT`に`:resp_len`を使わないのは、なぜですか。
2. `REAL`モードで`APILOG.HTTPST`が200になっているのは、どこで決まっていますか。相手が404を返したとき、`APILOG`は、どうなると考えられますか(ヒント: `QSYS2.HTTP_GET`は、何を返しますか)。
3. モックで気づけず、実通信でだけ気づける不具合を、このレッスンの結果から2つ挙げてください。

<details><summary>答え</summary>

1. `resp_len`は、RPGの文の中では使えても、SQLの文の中の変数としては認められないからです(`SQL0312`、実機で発生)。SQLの文の中で使えるのは`:resp`だけです。そこで、`INSERT`のときは0を入れておき、`LENGTH(RESP)`で、保存した本文から長さを数えます。どの行かは、`IDENTITY_VAL_LOCAL()`で指します。
2. ソースの`wSt = 200`(`SQLSTATE`が`00000`または`01004`のとき)です。`HTTP_GET`は本文だけを返し、状態コードを返しません。相手が404を返したときの動作は、実機で確かめていません。IBM Docsに直接の記載を確認していないため、断定できません(未検証(2026-09-29時点))。HTTPの状態を確実に知りたいなら、ヘッダーも返す`HTTP_GET_VERBOSE`を使う、という設計になります(読解用の囲み。`RESPONSE_HTTP_HEADER`に`HTTP_STATUS_CODE`があることは確認済み)。
3. (i) 日本語の住所を、ジョブのCCSIDの`VARCHAR`列に取り出すと`3F3F3F`になること(モックはローマ字だけ)。(ii) 本物の応答が、整形された(タブ・改行のある)、`"status"`が数値のJSONで、長さや形がモックと違うこと(ほかに、`kana1`〜`kana3`があること)。

</details>
