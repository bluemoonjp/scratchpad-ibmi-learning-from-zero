## なぜ学ぶか

**第4部までは、いつも白紙のソース・メンバーから、自分で新しいプログラムを書いてきました。** 実際の保守の現場はそうではありません。**既に動いている(あるいは、動いているように見えて実は怪しい)他人のプログラムを渡され、それを壊さずに直す**のが仕事のほとんどです。しかも古いプログラムほど、標識だらけで、コメントが古いまま放置されていたり、そもそも間違っていたりします。

第5部では、`src/legacy/` に用意した小さな「旧システム」を使って、この現実に近い形で保守を練習します。得意先照会(`TK0100`)、受注一覧(`JU0300`)、在庫引当(`ZA0500`、バッチ・ドライバー `JU0900C` から呼ばれる)、そしてこれらをまとめるメニュー(`MN0000C`)です。**`src/legacy/tickets/` には、05-13 のチェックポイントであなたが実際に調査・修正する保守チケットが3本、既に起票されています。** 今日はそれを解決する回ではありません。まずは、旧システムを安全に手元へ入れ、これから12レッスンかけて使う「保守の作法」を身につけます。

## 説明

### 保守の5つの習慣

保守作業には、新規開発とは違う独自の作法があります。この部を通じて繰り返し使うので、ここで一度まとめて押さえておきます。

- **変更は最小にする**: 「ついでに」整理・リファクタリングしたくなっても我慢します。直す範囲が広いほど、意図しない副作用が起きる可能性が広がります。
- **本番ソースを直接直さない**: 03-11 で学んだ `SETENV`(`*DEV`/`*PRD` の切り替え)を思い出してください。この教材では `<USER>1` が開発用、`<USER>2` が本番役という約束でした。本番役のソースをその場で書き換えるのではなく、開発用の複写(コピー)で直し、テストしてから、正式な手順(05-12 で学びます)で本番役へ移送します。今日の時点ではまだ「本番役」は登場しませんが、この原則は05-08以降、実際に手を動かして守ります。
- **`SAVF` へ退避する**: 何かに触る前に、まず今の状態を保存しておきます。あとで見るとおり、`TXLEGACY` 自身がこの習慣を体現しています。
- **改修記録を残す**: 何を・なぜ・いつ変えたかを、ソースの近くに書き残します。実は `za0500.rpg` のヘッダー・コメント自体が、この教材のリポジトリーの中にある改修記録の実例です。2026-09-26 の見直しで見つかった4つの不具合が、それぞれ「何が間違っていたか・なぜそう直したか」という形で日付付きの `FIXED` コメントとして残っています。これは今日あなたが書くものではなく、**「改修記録とはこういうものだ」という実例として読んでおいてください。**
- **入口から追う**: 知らないプログラムを読むとき、いきなり `ZA0500` や `JU0900C` を開きたくなりますが、実際の利用者はメニュー(`MN0000C`)から辿り着きます。**入口(利用者が実際に呼び出す場所)から順にトレースする**ことで、呼び出し関係・パラメーターの受け渡し・データの流れが自然に見えてきます。実際、`src/legacy/tickets/` の3本のチケットは、どれも「調査・修正の進め方」の1番目に `DSPPGMREF`・`DSPDBR` で呼び出し関係を確認する(05-07 の手法)ことを挙げています。これは偶然ではなく、この部全体の調査の進め方そのものです。

### `TXLEGACY` というツール

`TXLEGACY`(`tools/qclsrc/txlegacy.clp`)は、`TXSETUP`(02-05)と同じ発想の、この教材専用のツールです。`PARM(LIB CLONEDIR FORCE)` の3つを取ります。

1. `LIB/TXLEGST` という状態データ域があるか確認します。**なければ新規投入**、あれば `FORCE(*YES)` かどうかで分岐します。
2. `FORCE(*YES)` でなければ、「already loaded」とメッセージを出して**何もせず終了**します。
3. `FORCE(*YES)` なら、**再構築の前に**、`TK0100 TK0100D JU0300 ZA0500 MN0000C MN0000D FLDREF FLDREFR` を `<USER>B`(01-04 で確認した、SAVF の置き場。`RTVJOBA CURUSER` で取れるサインオン・プロファイル名自体に `B` を付けて求めるので、`<USER>1`/`<USER>2` のどちらで作業していても同じ `<USER>B` になります)に、日付入りの名前(`LG` + `QDATE`、例 `LG260926`)の `SAVF` として退避します。
4. `FLDREF`(DDS の共通フィールド定義)→ `FLDREFR`(RPG の `/COPY` メンバー。**これはソース・メンバーとして取り込まれるだけで、単体ではコンパイルされません**)→ `TK0100D`/`MN0000D`(表示装置ファイル。RPG プログラムが外部レコード様式を解決できるよう先に作る)→ `TK0100`/`JU0300`/`ZA0500`(RPG)→ `JU0900C`/`MN0000C`(CL)の順に、ソースを取り込んでコンパイルします。
5. 最後に `TXLEGST` を `'Y'` にして完了します。

**注意: `TXLEGACY` は `ZA0510`(05-04 で読む配列・DS・エラー処理の教材)、`db/v2/juchum.pf`(05-09 で使うスキーマ追加)、`JUBADD`(05-11 で使う演習用ファイル)は、まだ投入しません。** これらは、それぞれの回で個別に扱います。「今日入るもの」と「あとで入るもの」を区別しておいてください。

**`FORCE(*YES)` の退避は、メッセージが言うほど万能ではありません。** よく見ると次のような限界があります。

- 退避対象のオブジェクト一覧に **`JU0900C` が入っていません**(在庫引当バッチ・ドライバーが退避対象から漏れています)。
- `FLDREFR` は前述のとおり**単体のオブジェクトではなく `QRPGSRC` の中のソース・メンバー**です。`SAVOBJ` はオブジェクトを退避するコマンドなので、この指定が実際に何を退避しているのか(あるいは、そもそも見つからず失敗しているのか)は、このセッションでは実機確認できていません。
- `SAVOBJ` の直後には `MONMSG MSGID(CPF0000)`(何のエラーでも黙って先へ進む)があり、そのすぐ後に無条件で「退避しました」というメッセージを送ります。**つまり `SAVOBJ` が実際に失敗していても、成功メッセージが出ます。**

これは欠陥探しではなく、**保守の習慣そのものの実例です。** ログのメッセージを鵜呑みにせず、`DSPSAVF` で実際に中身を確認する。ここでも「改修記録・裏付けを取る」習慣がそのまま活きます。

### 参考: SEU の行コマンド(保守に効くコマンド)

03-01 では `F15`(検索)だけを扱いました。保守の現場で**既存の(自分で書いていない、時には数百行ある)ソースを直す**ときは、シーケンス番号欄に直接入力する短い「行コマンド」を知っているかどうかで作業速度が大きく変わります。この先(05-08 以降)、実際に他人のソースへ行を足したり削ったりする機会が増えるので、ここでまとめておきます。

| 行コマンド | 意味 |
|---|---|
| `C` | この行をコピーする(貼り付け先に `A`/`B` を指定する) |
| `Cn` | この行から `n` 行をまとめてコピーする |
| `CC` | 最初の `CC` から次の `CC` までの範囲をまとめてコピーする |
| `M`/`Mn`/`MM` | `C`/`Cn`/`CC` と同じ考え方の「移動」版(コピー元は削除される) |
| `A` | コピー・移動の対象を、この行の**後**に置く |
| `B` | コピー・移動の対象を、この行の**前**に置く |
| `D`/`Dn`/`DD` | この行(`n` 行、または `DD` で挟んだ範囲)を削除する |
| `RP`/`RPn` | この行を直後に複製する(`RPn` は `n` 回) |

**覚え方**: 行コマンドの文字自体は `C`/`M`/`D`/`A`/`B`/`RP` の6種類だけです。そのうち `C`/`M`/`D` は「単一行(`C`)」「`n` 行(`Cn`)」「範囲(`CC`)」という同じ3段階の指定方法を共有しています。

**`F13`(セッション既定値の変更)・`F14`(検索・置換オプション)**: このレッスンの目標にある「SEUの生産性コマンド」のうち、行コマンド以外の2つです。`F13` は編集セッション全体の既定値を変更する画面を、`F14` は検索・置換の条件を指定する画面を、それぞれ開きます(画面の中身の詳細は実機未確認です)。**さらに次を探す・置き換えるだけなら `F16`(検索の繰り返し)・`F17`(置換の繰り返し)を使います。**

**このセッションでは実機の5250画面で確認していません**(下の「実機メモ」参照。5250の対話操作はこの教材の検証方針上、自動化していません)。行コマンドの綴り・`F13`〜`F17`の役割は、IBM公式マニュアル「ADTS for AS/400: Source Entry Utility」(SC09-2605-00)で確認済みですが、実際の画面操作は学習者自身の5250セッションで確認してください。

## 実演

**手順4・6(`TXLEGACY`のコンパイル、`FORCE`を指定しない初回ロードでの実行)は、検証ハーネス経由で実機確認済みです(下の「実機メモ」を参照)。** ただし手順1〜3・7(手動での `git pull`・`ADDPFM`・`CPYFRMSTMF`、`DSPDTAARA`/`WRKOBJPDM` での確認)は、このセッションでは手順に書いたとおりの形では実行しておらず、同等の結果を別の方法(ファイルのアップロード+`CPYTOSTMF`、`RTVDTAARA`)で確認したにとどまります。手順5(`LASTCD` の作成)は、このセッションでは一度も実行していません。手順8・9(2回目の実行、`FORCE(*YES)` 退避)はまだ未検証、手順10〜12(5250でのメニュー操作・SEUの行コマンド)は対話操作(V3)のため、このセッションでは検証できていません。学習者ご自身の5250セッションで、実際に試しながら進めてください。

1. SSH で接続し、`~/ibmi-kyozai` が最新であることを確認する(`git pull`)。`git sparse-checkout set src db tools`(02-04)で既に `tools/`・`src/` 全体が対象なので、追加のスパース設定は不要です。`exit` で 5250 に戻る。
2. 5250 のコマンド行で、`TXLEGACY` のソースを取り込む(`QCLSRC`・`QCMDSRC` は 02-05/03-11 で既に作成済みです)。

   ```text
   ADDPFM FILE(<自分のユーザー名>1/QCLSRC) MBR(TXLEGACY) SRCTYPE(CLP) TEXT('Load legacy system')
   ADDPFM FILE(<自分のユーザー名>1/QCMDSRC) MBR(TXLEGACY) SRCTYPE(CMD) TEXT('TXLEGACY command')
   ```

3. SSH でもう一度接続し、ソースを取り込む。

   ```sh
   system "CPYFRMSTMF FROMSTMF('/home/<自分のユーザー名>/ibmi-kyozai/tools/qclsrc/txlegacy.clp') TOMBR('/QSYS.LIB/<自分のユーザー名>1.LIB/QCLSRC.FILE/TXLEGACY.MBR') MBROPT(*REPLACE) STMFCCSID(1208)"
   system "CPYFRMSTMF FROMSTMF('/home/<自分のユーザー名>/ibmi-kyozai/tools/qcmdsrc/txlegacy.cmd') TOMBR('/QSYS.LIB/<自分のユーザー名>1.LIB/QCMDSRC.FILE/TXLEGACY.MBR') MBROPT(*REPLACE) STMFCCSID(1208)"
   ```

4. 5250 に戻り、プログラムとコマンドをコンパイルする。

   ```text
   CRTCLPGM PGM(<自分のユーザー名>1/TXLEGACY) SRCFILE(<自分のユーザー名>1/QCLSRC) SRCMBR(TXLEGACY)
   CRTCMD CMD(<自分のユーザー名>1/TXLEGACY) PGM(*LIBL/TXLEGACY) SRCFILE(<自分のユーザー名>1/QCMDSRC) SRCMBR(TXLEGACY)
   ```

   `PGM()` に `*LIBL` を指定する理由は 02-05 のとおりです(ライブラリー名を決め打ちしないため)。

5. **`TXLEGACY` 自身は作りませんが、`TK0100` が実行時に必要とするデータ域は作ります。** `tk0100.rpg` のヘッダー・コメントが明記しているとおり、`LASTCD`(直前に照会した得意先コードを覚えておく、6桁の名前付きデータ域)がないと `TK0100` は動きません。`TXLEGACY` はこれを作らないので、ここで手動で作ります。

   ```text
   CRTDTAARA DTAARA(<自分のユーザー名>1/LASTCD) TYPE(*CHAR) LEN(6)
   ```

6. `TXLEGACY LIB(<自分のユーザー名>1)` を実行する(コマンド名をそのまま打ちます。`CLONEDIR` は省略すれば自分のホーム・ディレクトリーから自動的に決まります)。ジョブログに `TXLEGACY: loading legacy system into library ...` から `TXLEGACY: done. ...` までのメッセージが並ぶことを確認する。
7. `DSPDTAARA DTAARA(<自分のユーザー名>1/TXLEGST)` を実行し、値が `Y` になっていることを確認する。`WRKOBJPDM LIB(<自分のユーザー名>1)` で `TK0100`・`TK0100D`・`JU0300`・`ZA0500`・`JU0900C`・`MN0000C`・`MN0000D`・`FLDREF` が並んでいることも確認する。**`FLDREFR` はここには出てきません**(`QRPGSRC` の中の1メンバーであり、独立したオブジェクトではないためです)。
8. もう一度 `TXLEGACY LIB(<自分のユーザー名>1)` を実行し、「already loaded」のメッセージだけが出て何も再構築されないことを確認する。
9. 今度は `TXLEGACY LIB(<自分のユーザー名>1) FORCE(*YES)` を実行し、`<自分のユーザー名>1B` に `LG` + 今日の日付という名前の `SAVF` ができることを確認する。`DSPSAVF FILE(<自分のユーザー名>1B/LG......)` で、実際に何が退避されたかを自分の目で確認してください(**説明で触れたとおり、期待どおりに8個すべてが入っているとは限りません**)。
10. `CALL PGM(<自分のユーザー名>1/MN0000C) PARM('<自分のユーザー名>1')` でメニューを起動する。**`PARM` を省略しないでください。** `MN0000C` は `PGM PARM(&LIB)` で引数を1つ宣言しており、`CALL` に渡す引数の個数が宣言と合わないと `CPD0172` になることが、これまでのセッションの実機確認(`docs/probes.md`)で分かっています。
11. メニューから、1(`TK0100` - 得意先照会)、2(`JU0300` - 受注一覧)、3(`JU0900C` - 在庫引当)をそれぞれ試す。`F3` で1つ戻り、メニューでもう一度 `F3` を押すと `MN0000C` が終了します。
12. **(余裕があれば)SEU の行コマンドを試す**: `WRKMBRPDM FILE(<自分のユーザー名>1/QRPGSRC)` で `TK0100` を開き、適当な3行に `CC`/`CC` を入力してコピー範囲を指定し、末尾の行に `A` を入れて `Enter` を押す。コピーされた3行が増えていることを確認したら、その3行に `DD`/`DD` を入れて削除し、**保存せずにコマンド行へ `CANCEL`(短縮形 `CAN`)と入力して `Enter` を押し、抜けてください**(`TK0100` はこの先のレッスンでそのまま使うため、変更を残さないこと。`CANCEL` は変更ありのまま実行すると確認の `Enter` を求めてきます。取り消したい場合は `F12` でその確認自体を取り消せます)。

    **選択肢3(在庫引当)には注意してください。** `MN0000C` は `JU0900C` に空白の実行モードを渡し、`JU0900C` 側で空白は `*LIVE`(本番実行)として扱われます。つまり**選択肢3を選ぶと、`ZAIKOM`(在庫マスター)が実際に更新されます。** さらに `src/legacy/tickets/` の3本のチケットが指摘しているとおり、この経路には既知の不具合(引当結果がおかしい、まれに応答なしで固まる)があります。今日はこれを直しません。固まった場合は 04-12 で学んだ「照会メッセージへの応答」を思い出してください。

## 実機メモ

- **`TXLEGACY` が投入する旧システム一式は、コンパイル確認(V1)まで確認済みです(確認日 2026-09-26、`part05-legacy-probe`、2回接続、CONFIRMED SUCCESS)。** `FLDREF`(DDS)・`TK0100D`/`MN0000D`(DDS、表示装置ファイル)・`TK0100`/`JU0300`/`ZA0500`(RPG、いずれも Highest Severity 00)・`JU0900C`/`MN0000C`(CL)が、1回目の接続で見つかった複数の実バグ(`tk0100d.dspf` の DDS 配置2件、`za0500.rpg` の I 仕様書1件、`ju0900c.clp` の `CLOF` 除去1件。詳細は `docs/probes.md`「第5部旧システムの実機検証: `part05-legacy-probe`」)を修正した上で、2回目の接続で全てクリーンにコンパイルできることを確認しました。**`FLDREFR`(RPG の `/COPY` メンバー)は、今日投入するどのプログラム(`TK0100`/`JU0300`/`ZA0500`)からも `/COPY` されていません**(実際に `/COPY` しているのは、05-04 で別途投入する `ZA0510` だけです)。`FLDREFR` が構文的に妥当な `/COPY` メンバーであることは、同じ接続で `ZA0510`(この `/COPY` 行自体は `ZA0510` 追加時から変更されていません)が Highest Severity 00 でコンパイルできたことから間接的に確認できていますが、今日投入する `TK0100`/`JU0300`/`ZA0500` での検証ではありません。
- **`TXLEGACY` 自身(`*PGM`・`*CMD` とも)は、`FORCE` を指定しない初回ロード経路に限り、実行結果の一致(V2)まで確認済みです(確認日 2026-09-27、`part05-txlegacy-exec`、CONFIRMED SUCCESS)。** それまでの検証は、同じオブジェクト群を `file`/`cl` ステップで直接コンパイルする代替検証にとどまっていましたが、この接続で初めて `TXLEGACY` 本来の仕事(`CLONEDIR` 配下のツリーから `CPYFRMSTMF` して取り込む)を実行しました。検証ハーネスの制約上(手順をまとめた1つの CL ラッパーの**コンパイル時点**では `TXLEGACY` の `*CMD` がまだ存在せず、`TXLEGACY LIB(...)` という文字列をそのまま埋め込めない)、`RUNTXLEG` という手順が、別途コンパイルした小さな CL プログラム `TXLEGRUN`(`verify/part05-txlegacy-exec/src/txlegrun.clp`)を `CALL` する形を取りました。`TXLEGRUN` は `CLONEDIR` を渡さず(本文どおり自動導出に任せ)、`'TXLEGACY LIB(<lib>)'` という文字列を組み立てて `QCMDEXC` に渡しています。この**実行時点**では `TXLEGACY` の `*CMD` は同じ接続内の先行ステップで既に作成済みだったため、`QCMDEXC` 経由の呼び出しは実際に `*CMD` を通っています(この仕組み自体は `docs/probes.md` の要約文には出てこず、`verify/part05-txlegacy-exec/manifest.json` の実行順序と `txlegrun.clp` 自身のソースを直接読んで確認したものです)。その結果、`FLDREF`・`TK0100D`・`MN0000D`・`TK0100`・`JU0300`・`ZA0500`・`JU0900C`・`MN0000C`(独立したオブジェクト)が新規作成され、`FLDREFR`(ソース・メンバー)も取り込まれ、状態データ域 `TXLEGST` も新規作成、ジョブログが `TXLEGACY: done.` まで到達しました。同一ジョブ内で `TXLEGST` を `RTVDTAARA` すると `Y` でした。**ただし、これは `TXLEGST` がまだ存在しない初回ロードの経路だけです。** 2回目の実行(「already loaded」で何もしない経路、手順8)と `FORCE(*YES)` による再構築(`SAVF` 退避を含む、手順9)は、この接続では意図的に外して(`TXLEGST` を事前に `DLTDTAARA` してから実行)おり、まだ実機で確認していません。また取り込み元は、検証ハーネスが同じ接続内で `CPYTOSTMF` を使って用意した(実際に CCSID1208 へバイト変換した)代替ツリーであり、手順1〜3のように実際に `git pull` した `~/ibmi-kyozai` から取り込んだものではありません(同じ接続内で、変換後の `za0500.rpg` のバイト列が本物の ASCII であることを `od -x` で実測済みです。他の8ファイルについては同様の実測はしていません)。
- **選択肢3(在庫引当、`JU0900C`→`ZA0500`)の as-shipped(05-13 のチケット未修正)経路のうち、`RUNMODE='*TEST'`(`ju0900c.clp` 自身の仕様で、`*LIVE` 以外は `ZAIKOM` を更新しないドライラン扱い)での実行は、実行結果の一致(V2)まで確認済みです(確認日 2026-09-27、`part05-ju0900c-baseline`)。** `SBMJOB` ではなく直接 `CALL` で流したところ、「一部の実行で結果がおかしい」のではなく、**このデータでは毎回確実に**、1行目で `RPG0907`(10進データ・エラー)により `ZA0500` が異常終了し、`JU0900C` はこれを(`CALL PGM(ZA0500)` 直後の `MONMSG MSGID(CPF0000)` で)捕捉して `JU0900C: ZA0500 ended abnormally.` と報告した上でジョブを終了する(ハングしない)ことを確認しました。印字は0行のままでした。`RUNMODE='*TEST'` の指定どおり `ZAIKOM` は更新されず、接続前後で変化していないことも確認しています。**メニューの選択肢3が実際に渡す空白(本文どおり `*LIVE` 相当)での実行は、このセッションでは試していません。** また5250 の対話ジョブから `MN0000C` 経由で同じ経路を通したとき、未処理の `RPG0907` エスケープがどう見えるか(応答待ちのメッセージとして体感的に「固まる」ように見える可能性を含め)も、このセッションでは検証していません(V3)。

- **`FORCE(*YES)` の退避(`SAVF`)範囲の限界は、まだ実機で確認できていません(未検証、2026-09-27時点)。** ソースの読み合わせで次の3点を確認済みです: `SAVOBJ` の対象リストに `JU0900C` が含まれない、`FLDREFR` は単体オブジェクトではなくソース・メンバーである、`SAVOBJ` 直後の `MONMSG MSGID(CPF0000)` が失敗を黙って飲み込んだ上で無条件に成功メッセージを送る。上記のとおり `part05-txlegacy-exec` は初回ロード経路だけを検証しており、`FORCE(*YES)` によるこの退避経路(手順9)はまだ一度も実機で実行していません。実機で確認でき次第、`DSPSAVF` の実際の中身と合わせてここを更新します。
