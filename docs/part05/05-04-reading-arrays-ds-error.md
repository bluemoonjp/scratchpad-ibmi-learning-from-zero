## なぜ学ぶか

**古い RPG のプログラムには、業務ロジックそのものではなく、「よくある定型」を実装するためだけの部品がたくさん埋め込まれています。** 検索表、集計用の配列、状態を持つためのデータ構造、失敗を検知する標識、エラー処理専用のサブルーチン、他のコマンドを呼ぶための小技――これらは一つ一つを見ると単純ですが、初見では「これは何のために書いてあるのか」が分かりにくいものです。**保守の現場で本当に大きく汚いプログラムに出会ったとき、これらの定型を「あ、これはいつものアレだ」と見分けられるかどうかで、読む速度がまったく変わります。**

今回読む `ZA0510` は、実際の業務ロジックとしては単純な「商品コードから優先順位を引いて数量を集計する」プログラムですが、**このレッスンで学ぶ定型をほぼすべて、意図的に1本の中に詰め込んだ教材用プログラム**です(`JU0900C`→`ZA0500` の実処理チェーンには組み込まれていません)。定型の「形」を、まとまった1本で確認しましょう。

## 新出

## 説明

### E 仕様書: コンパイル時テーブルと実行時配列

```text
E                    TABPCD  6   6  6
E                    TABPRI  6   6  1 0
E                    SQ          3  7 0
```

`TABPCD`・`TABPRI` は**コンパイル時テーブル**です。ソースの一番最後に置く `**` に続くデータ行から、**コンパイル時に**中身が読み込まれます(実行時には変化しません)。小さくてめったに変わらない対応表(ここでは「商品コード→優先順位」)を、プログラムの中に焼き込んでおくのに向いています。**なぜ1つのテーブルではなく2つに分かれているか**: E 仕様書1行で2つのテーブルを交互形式でロードする高度な書き方もありますが、これは近道ではなく、RPG/400 Reference が「LOKUP with Two Tables」として説明している標準パターンです。同じ件数を持つ独立した2つのテーブルを宣言し、片方を `LOKUP` で検索し、もう片方の対応する要素を結果欄で取り出します。

`SQ` は**実行時配列**です。E 仕様書に「1レコードあたりの件数」の指定が無く(`**` データも無い)、コンパイル時には空っぽで、**実行中にプログラム自身が値を詰めていきます**。優先順位(1〜3)ごとの数量を集計するのに使われます。

### LOKUP: 表を検索する

```text
C           ZKSHO     LOKUPTABPCD    TABPRI         80
C  N80                EXSR *PSSR
C   80                Z-ADDTABPRI    PRI     10
```

`LOKUP` は「Factor 1 の値を、Factor 2 のテーブル/配列の中から探す」命令です。ここでは商品コード(`ZKSHO`)を `TABPCD` から探し、**見つかれば** 結果欄に指定した `TABPRI`(対になるテーブル)の同じ位置の要素を取り出せる状態にし、指標80を ON にします。**見つからなければ** 指標80は OFF のままです(RPG/400 Reference: 検索に失敗しても指標は自動では OFF になりません。`ZA0500` の `CHAIN` 前の `SETOF` と同じ理由で、毎回 `LOKUP` の前に `SETOF 80` しています)。見つからなかったとき(`N80`)は `*PSSR`(後述)を明示的に呼び、致命的なエラーとして扱っています。

### XFOOT: 配列を縦計する(クロスフッティング)

```text
C                     ADD  ZKSU      GQTY    90
     ...
CLR                   XFOOTSQ        XQTY    90
CLR         XQTY      COMP GQTY                     93
```

`XFOOT` は「配列の全要素を合計する」命令です。`ZAIKOM` を1件読むたびに、`SQ`(優先順位ごとの配列)に数量を足し込む一方で、`GQTY`(全体の合計)にも**別ルートで**同じ数量を足しています。ファイルの終わり(`LR`)で `XFOOT` が `SQ` の3要素を合計して `XQTY` に入れ、これを `GQTY` と `COMP` で突き合わせます。**2つの独立したルートで計算した合計が一致するかを確認する**、経理の紙の台帳でも使われる古典的な検査手法(クロスフッティング)です。一致すれば指標93が ON になり、`OK` が印字されます。

### DS の2つの宣言方法

`DS`(データ構造)は、複数のフィールドを1つのまとまりとして扱う仕組みです。`ZA0510` には、自分で中身を決める普通の `DS`(`CMDDS`・`PRIDS`)のほかに、**システムが中身を自動的に埋めてくれる特別な `DS`** が2種類あります。

```text
IPSDS       SDS
I                                       11  150STATUS
I                                       29  36 RTN
```

**プログラム状態データ構造(PSDS)**: I 仕様書18桁目に `S` を指定して宣言します。**プログラム全体について1つだけ**持ち、`STATUS`(状態コード)・`RTN`(直前にエラーが起きたルーチン名)など、決まった桁位置に自動的に値が入ります。実行時エラーを人間があとから調べるときの手がかりです。

```text
FZAIKOM  IP  E           K        DISK
F                                              KINFDS ZAINF
```

**ファイル情報データ構造(INFDS)**: こちらは I 仕様書ではなく、**F仕様書の継続行**(53桁目 `K`、54-59桁目にキーワード `INFDS`、60-65桁目に DS 名)で宣言します。**指定した1つのファイル専用**です。`ZAINF` は `ZAIKOM` 専用の `INFDS` で、`FSTAT`(そのファイルの状態コード)・`FRTN`(そのファイルの処理中にエラーが起きたルーチン名)を持ちます。**複数のファイルを開くプログラムでは、「どのファイルで何が起きたか」を知るには、ファイルごとの `INFDS` が必要**です。プログラム全体で1つの `PSDS` だけでは、どのファイルが原因かまでは分かりません。RPG/400 Reference は「INFDS」という呼び名を**ファイル単位のものだけ**に使っており、プログラム状態データ構造の方にはこの呼び名を使っていません(この2つを混同しないよう、`ZA0510` は名前も `STATUS`/`RTN`(PSDS側)と `FSTAT`/`FRTN`(ZAINF側)で意図的に分けています)。

### C 仕様書56-57桁目のエラー標識

```text
C                     CALL 'QCMDEXC'              85
```

`CALL` の56-57桁目には、**呼び出したプログラムがエラーで終了したときに ON になる標識**を指定できます。`QCMDEXC` の呼び出しが何らかの理由で失敗したことを、この標識(85)1つで検知できます。「エラーが起きたらどうするか」は指標を見て分岐すればよく、`CALL` そのものが暴走して止まることはありません。

### INFSR/*PSSR: ファイルの例外/エラー・サブルーチン

```text
F                                              KINFSR *PSSR
     ...
CSR         *PSSR     BEGSR
     ...
CSR                   ENDSR'*CANCL'
```

`*PSSR` は、RPG が実行時エラーに対して**自動的に呼び出す既定のエラー処理サブルーチン**です(名前を `*PSSR` にしておけば、何も指定しなくても存在します)。`INFSR` は、これとは別に、**特定のファイル専用**のエラー処理サブルーチンの名前を、`INFDS` と同じ形式の F仕様書継続行(54-59桁目に `INFSR`、60-65桁目にサブルーチン名)で指定する仕組みです。

`ZA0510` は `ZAIKOM` の `INFSR` として、あえて**同じ** `*PSSR` を名指ししています。つまり、「プログラム全体の既定ハンドラー」と「`ZAIKOM` 専用のハンドラー」という**別々の2つ**があるのではなく、**両方が同じ1つのサブルーチンに集約されています**。加えて、`LOKUP` が見つからなかったときも(これは RPG が自動的に発生させる「例外」ではないため)、`EXSR *PSSR` で明示的に同じサブルーチンへ処理を渡しています。`ENDSR` の Factor 2 に `'*CANCL'` を書くと、「ここでプログラムを打ち切る」という意味になります(通常の `TAG` 名を書けば、そこから処理を再開できますが、今回は致命的エラーとして扱うため打ち切ります)。

**重要な限界(04-06 で実機確認済み)**: `*PSSR`/`INFSR` は、**ファイルのオープン/クローズ処理そのものの最中に起きたエラーは捕まえられません。** 04-06 で見つかった `RPG1216`(`TOKUIM` の暗黙オープン失敗によるハング)は、`*PSSR` を追加しても解消しませんでした。RPG の既定のエラー処理に渡り、非対話ジョブでは誰も応答できない照会メッセージのまま止まります。「オープンできない」という一番手前の問題は、`*PSSR`/`INFSR` の対象外です。

### QCMDEXC: RPG から CL コマンドを実行する

```text
C                     Z-ADD57        CMDLEN 155
C                     CALL 'QCMDEXC'              85
C                     PARM           CMDDS
C                     PARM           CMDLEN
```

`QCMDEXC` は、RPG の特殊な機能ではなく、**任意の CL コマンドを1つ実行してくれる、ふつうのシステム・プログラム**です。他のプログラムと同じように `CALL`+`PARM` で呼び出します。パラメーターは2つ: (1) 実行したいコマンド文字列そのもの、(2) その文字列のうち**意味のある長さ**を示す、**15桁5小数のパック10進数**フィールド(このレッスンの目標にある「長さは15 5」がこれです)。`ZA0510` では、コマンド文字列を `CMDDS`(57バイトの `DS`)に `MOVEL` で1断片ずつ書き込んで組み立てています(初期値付きの `DS` は `PARM` に渡せないという規則があるため、実行時に組み立てる形を取っています)。組み立てているコマンドは `CHGDTAARA DTAARA(*LDA (1 20)) VALUE('ZA0510 ERROR')`(自分のジョブが持つローカル・データ域 `*LDA` の1〜20バイト目に、決まった文字列を書き込む)です。**「RPG からは書けない処理を CL コマンド経由でやらせる」という、今でも現場で使われる息の長いテクニック**です。

**注意: `QCMDEXC` で実行できる CL コマンドには制限があります。** 実機で確認済みの事実として、`SNDPGMMSG`(メッセージ送信コマンド)は、CL プログラムまたは REXX の中でしか実行できず、`QCMDEXC` 経由では(呼び出し元が RPG でも CL でも)実行できません(`CPD0031`「Command SNDPGMMSG not allowed in this setting」)。各 CL コマンドの実行可能な環境(`ALLOW` 属性)は、IBM のコマンド解説ページの「Where allowed to run」欄で確認できます。`CHGDTAARA` はここが `*ALL`(すべての環境)なので、`QCMDEXC` から安全に呼び出せます。**「任意の CL コマンドを実行できる」わけではなく、「その環境向けに許可されたコマンドだけを実行できる」**というのが正確な理解です。

### 参考: `CVTOPT`・`ALWNULL`(`CRTRPGPGM` 自身のコンパイル・オプション)

`ZAIKOM`(このレッスンで読む外部記述ファイル)には、`ZASHO`・`ZASU` のほかに `ZAUPD`(8桁の数値、`YYYYMMDD` 形式の更新日、`db/v1/zaikom.pf` 参照)という項目もあります。`ZA0510` 自身はこの項目を一度も使いませんが、**「日付に見えるが、実際にはただの8桁の数値」という、RPG III 時代によくあった表現**の実例として、ここで触れておきます。

もし外部記述ファイルが(`ZAUPD` のような数値ではなく)本物の SQL の `DATE`/`TIME`/`TIMESTAMP` 型や、可変長(`VARCHAR`)・NULL を許す列を実際に持っていたら、`ZA0510` がまさに使っている `CRTRPGPGM`(RPG III/OPM 側のコンパイル・コマンド)自身が持つ、次の2つのオプションが関係してきます(IBM Docs「Create RPG/400 Program (CRTRPGPGM)」で確認済み)。

- **`CVTOPT`(型変換オプション)**: 既定値 `*NONE` のままだと、**DATE/TIME/TIMESTAMP 型や可変長型のフィールドは、RPG/400 プログラムからは一切アクセスできません**(「ignored and not accessible in the RPG/400 program」)。`*DATETIME` を指定すると、それらは固定長の文字フィールドとして宣言され、アクセスできるようになります。
- **`ALWNULL`(NULL 値を許すか)**: 既定値 `*NO` のままだと、NULL を許す列を持つ外部記述ファイルのレコードは処理できません。`*YES` を指定すると、外部記述の入力ファイルに限り、NULL 値を含むレコードも受け付けられるようになります(ILE RPG の `ALWNULL(*USRCTL)` のような、NULL かどうかを実行時に判定する仕組みは RPG III には無く、`*YES`/`*NO` の二択だけです)。

**このレッスンでは実際には関係ありません**(`ZAIKOM` に DATE/TIME/TIMESTAMP・可変長・NULL 許容の列は無いため)。しかし `CRTRPGPGM` 自身がこれらのオプションを持つという事実は、**「RPG III(OPM)は古い言語だから SQL のモダンな型を全く扱えない」わけではない**ことを示しています(ただし ILE RPG IV のようなネイティブの `date`/`time`/`timestamp` 型は RPG III には無く、既定では固定長の文字列として扱うことになります)。この続きは、第6部 06-14b で ILE RPG 側から扱います。

7. **見つからない経路(`*PSSR`/`QCMDEXC`)を強制的に発生させる**: 出荷データの `ZAIKOM` は6商品すべてが `TABPCD` に載っているため、そのままでは `LOKUP` は一度も失敗しません。`**` データの最後の行 `P00001P00002P00003P00004P00005P00006` の**末尾6文字**(`P00006`)を、実在しないコード `P09999` に**一時的に**書き換えて再コンパイルしてください(桁数は変わらないので、他の列がずれる心配はありません)。再度 `STRDBG` で実行し、`EXSR *PSSR` の行と `*PSSR` サブルーチンの中(`MOVEL` の並び、`CALL 'QCMDEXC'` の行、指標85)にブレークポイントを置いて、`P00006` の行を読んだときに `LOKUP` が失敗し(指標80が OFF のまま)、`*PSSR` に処理が渡り、`CMDDS` が1断片ずつ組み立てられ、`QCMDEXC` が呼ばれることを確認してください。**`ENDSR '*CANCL'` によってプログラムがそこで終了するため、`LR` 時の `XFOOT`/`GTOT` 相当の出力(`PQ1`〜`XQTY`)はこの回では一切印字されません。** プログラム終了後、5250のコマンド行から `DSPDTAARA DTAARA(*LDA)` を実行し、1〜20バイト目に `ZA0510 ERROR` という文字列が実際に書き込まれていることを確認してください——`QCMDEXC` が実際にコマンドを実行し終えた、目に見える証拠です。確認後は、`P09999` を元の `P00006` に戻して再コンパイルしてください(`*LDA` の値はジョブ終了時にクリアされるので、明示的に戻す必要はありません)。

## 演習

次の5問に、自分の言葉で説明してください。答えは `<details>` で確認できます(`za0510.rpg` のヘッダー・コメントの根拠に基づく模範解答です)。

1. E 仕様書の `TABPCD`/`TABPRI` は、なぜ1つのテーブルではなく2つに分かれているのですか。

   <details><summary>答え</summary>

   RPG III の E 仕様書は、1行(46-57桁目)で2つのテーブルを交互形式でロードする高度な書き方にも対応していますが、この教材が使う生成器はその桁を実装していません。それとは別に、RPG/400 Reference が「LOKUP with Two Tables」として説明している標準パターン(同じ件数を持つ独立した2つのテーブルを宣言し、片方を `LOKUP` で検索し、もう片方の対応する要素を結果欄で取り出す)がこれにあたります。近道ではなく、正式な標準パターンです。

   </details>

2. `LOKUP` と `XFOOT` は、それぞれ何をする命令ですか。`ZA0510` ではどこでどう使われていますか。

   <details><summary>答え</summary>

   `LOKUP` は Factor 1 の値を Factor 2 のテーブル/配列から検索する命令です。`ZA0510` は商品コード(`ZKSHO`)を `TABPCD` の中から探し、見つかれば関連テーブル `TABPRI` の対応する優先順位を取り出せる状態にします(見つかった場合は指標80がON)。`XFOOT` は配列の全要素を合計する命令です。`ZA0510` は実行時配列 `SQ`(優先順位ごとの数量)を `LR` 時に `XFOOT` で `XQTY` へ合計し、レコードを読むたびに別途積み上げていた独立の合計 `GQTY` と突き合わせて、両者が一致するかを検査しています(クロスフッティング)。

   </details>

3. `PSDS` と `ZAINF` は、どちらも「エラー処理に関わる `DS`」ですが、何が違いますか。

   <details><summary>答え</summary>

   `PSDS`(I 仕様書、18桁目に `S`)は「プログラム状態データ構造」で、プログラム全体について1つだけ持つものです(`STATUS`=状態コード、`RTN`=最後にエラーが起きたルーチン名)。`ZAINF`(F仕様書の継続行、54-59桁目に `INFDS`)は「ファイル情報データ構造」で、指定した1つのファイル(ここでは `ZAIKOM`)専用のものです。複数のファイルを開くプログラムで「どのファイルの、どんな状態でエラーが起きたか」を知りたければ、ファイルごとの `INFDS` が必要になります。RPG/400 Reference は「INFDS」という語をファイル単位のものだけに使っています。

   </details>

4. `CALL 'QCMDEXC'` の56-57桁目に標識85があるのは何のためですか。

   <details><summary>答え</summary>

   `CALL` の56-57桁目は、呼び出したプログラムがエラーで終了したときに ON にする標識を指定できる欄です。`QCMDEXC` の呼び出しが何らかの理由で失敗したことを、`ZA0510` の C 仕様書の中だけで検知できるようにするためのものです。`ZA0510` 自身はこの標識を読んで分岐する処理までは書いていませんが、実際の保守現場では、この標識を `N85` で後続処理を条件付けするのが定石です。

   </details>

5. `INFSR`/`*PSSR` の関係を説明してください。また、`*PSSR` が捕まえられない実行時エラーの実例を、これまでのレッスンから1つ挙げてください。

   <details><summary>答え</summary>

   `*PSSR` は RPG が実行時エラーに対して自動的に呼び出す既定のエラー処理サブルーチンです(何も指定しなくても存在します)。`INFSR` は、特定のファイル専用にエラー処理サブルーチンの名前を F仕様書の継続行で指定する仕組みで、`ZA0510` は `ZAIKOM` の `INFSR` として同じ `*PSSR` を名指ししています。つまり `ZA0510` には別々の2つのハンドラーがあるのではなく、「プログラム全体の既定ハンドラー」と「`ZAIKOM` 専用のハンドラー」が、たまたま同じ1つのサブルーチンに集約されています。ただし、`*PSSR`(`INFSR` を含む)が捕まえられない場合があります。04-06 で実機確認された `RPG1216`(`TOKUIM` の暗黙オープン失敗)がその実例で、ファイルのオープン/クローズ時に起きたエラーは `*PSSR` が指定されていても RPG の既定のエラー・ハンドラーに渡り、非対話ジョブでは誰も応答できない照会メッセージとしてハングしました。

   </details>
