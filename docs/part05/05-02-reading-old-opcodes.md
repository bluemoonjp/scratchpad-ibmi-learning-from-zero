## 説明

### 読む順序

初めて見る RPG III プログラムを、1行目から順にすべて読もうとすると迷子になります。次の順序で当たってください。

1. **H 仕様書**: プログラム全体のオプションを見る(このレッスンでは空欄のみ)。
2. **F 仕様書**: どんなファイルを、どう(入力・出力・組み合わせ、順次・キー付き)使うプログラムかを把握する。
3. **I 仕様書**: どんなフィールドがあるか、外部ファイルのフィールド名がどう変わっているか(リネーム)を把握する。
4. **C 仕様書をまず概観する**: 宣言部分(`*LIKE`/`*NAMVAR` など)→ メイン・ループの骨格(`TAG`/`GOTO`/分岐)→ サブルーチンの一覧、の順で**細部を飛ばして**大きな流れだけを掴む。
5. **最後に、気になる箇所(標識・分岐条件)だけ詳細に読む**。

### 読む順序を `TK0100` に当てはめる

`TK0100`(`src/legacy/qrpgsrc/tk0100.rpg`)で、実際にこの順序をやってみます。

**F 仕様書**:

```text
FTK0100D CF  E                    WORKSTN
FTOKUIM  IF  E           K        DISK
FTANTOM  IF  E           K        DISK
```

この3行だけで、「画面(`TK0100D`、組み合わせ)があり、`TOKUIM`(得意先マスター)と `TANTOM`(担当者マスター)をキー付きで読む」プログラムだと分かります。`CHAIN` を使う予感がします(04-07)。

**I 仕様書**:

```text
ITANTOR
I              TANTOCODE                       TANCD
I              TANTONAME                       TANNM
```

`TANTOM` の外部フィールド名 `TANTOCODE`/`TANTONAME` は9文字あり、RPG III の6文字制限を超えるため、`TANCD`/`TANNM` という短い名前にリネームしています(21-30桁目に外部名、53-58桁目に別名)。**この時点で「`TANCD`/`TANNM` という名前が出てきたら `TANTOM` 由来だ」と分かった状態で C 仕様書に進めます。**

**C 仕様書を概観する**:

```text
C           *LIKE     DEFN TOKUPD    SAVUPD
C           *NAMVAR   DEFN           LASTCD  6
C           *LOCK     IN   LASTCD                 H1
C           LOOP      TAG
C                     EXFMTINQFMT
C   03                GOTO ENDPGM
C   KC                GOTO ENDPGM
C           TOKCD     CASEQ' '       DFLTSR
C                     CAS            LKUPSR
C                     ENDCS
C                     GOTO LOOP
C           ENDPGM    TAG
C  NH1                OUT  LASTCD
C                     SETON                         LR
```

これだけで、**メイン・ループの形**が見えます。`EXFMT` で画面を出す → `F3`(標識 `03`/`KC`)なら終了 → 入力された `TOKCD` が空白なら `DFLTSR`、それ以外なら `LKUPSR` というサブルーチンへ → `LOOP` に戻る。細かい `CHAIN` やフィールドの詰め替えは、まだ読んでいません。**この段階で「何をするプログラムか」は説明できる状態になっています。**

### 宣言部の小道具: `*LIKE`・`*NAMVAR`・`*LOCK`

C 仕様書の先頭にある3行は、宣言のための特別な Factor 1(`*LIKE`/`*NAMVAR`/`*LOCK`)です。

- **`*LIKE DEFN TOKUPD SAVUPD`**: `SAVUPD` という新しいフィールドを、`TOKUPD`(`TOKUIM.TOKUPD`、8桁0小数)と**まったく同じ型・長さ**で宣言します。型を手で書き写す必要がなく、`TOKUPD` の定義が変われば `SAVUPD` も追随します。
- **`*NAMVAR DEFN LASTCD 6`**: `*LDA`(ジョブ共通の局所域)とは別の、**名前付きデータ域**を、6桁の `LASTCD` として宣言します。05-01 で作った `LASTCD` データ域そのものです。
- **`*LOCK IN LASTCD H1`**: プログラム開始時に `LASTCD` を排他ロック付きで読み込みます(Factor 2 が `IN`)。失敗すると標識 `H1`(ホールト標識、56〜57桁目のみ)が ON になります。プログラムの終わり近くの `C NH1 OUT LASTCD` は、**ロックが取れていた場合だけ**(標識 `H1` が OFF のときだけ)書き戻す、という対になった処理です。

### `MOVE`/`MOVEL` の続き: P オペレーション拡張子

04-03 で、`MOVE`/`MOVEL` は**書き換えなかった部分に古いデータが残る**罠があり、`CLEAR` で防ぐと学びました。`TK0100` には、**`CLEAR` を使わない、もう一つの防ぎ方**が出てきます。

```text
C   50                MOVEL'NOTFOUND'TOKNM     P
```

行末の `P` が**オペレーション拡張子**(53桁目、実機の桁位置で確認済み)です。`'NOTFOUND'`(8文字)を `TOKNM`(30文字)へ `MOVEL` すると、**`P` を付けなければ残り22桁は古い値のまま**です。`tk0100.rpg` 自身のヘッダー・コメントに、まさにこの罠の実例が書かれています。

> 直前の照会で `TOKNM` に `'ACME TRADING CO'`(15文字、残り15桁は空白)が入っていたとします。`P` を付けずに `MOVEL'NOTFOUND'TOKNM` を実行すると、先頭8桁だけが `'NOTFOUND'` に書き換わり、9〜15桁目の古い値 `'DING CO'` が残ります。結果は `'NOTFOUNDDING CO'`(+空白)という、意味不明な文字列になります。

`P` 拡張子を付けると、**書き換えなかった残りの桁を自動的に空白で埋めます。** `TOKNM`(`TOKUIM` 由来、30文字)・`TANNM`(`TANTOM` 由来、20文字)への `MOVEL'NOTFOUND'.../MOVEL'NOREP'...` の行はすべて `P` 付きです。**`CLEAR` してから `MOVEL` する(04-03)のと、`MOVEL` に `P` を付ける、どちらも同じ問題への別解**だと理解してください。

### `MOVEA`(配列・標識配列への一括転記)

```text
C                     MOVEA'00'      *IN,60
```

`MOVEA`(MOVE Array)は、**配列(または配列のように並んだもの)へ一括で値を転記する**命令です。`*IN,60` は「標識配列の60番目から」という意味で、`'00'` を書き込むと**標識60・61の両方を OFF にします**(`SETOF 6061` と同じ効果)。`tk0100.rpg` 自身のヘッダー・コメントも「これは読解用のデモで、実際には何も検査していない」と明記しています。結果フィールド(43〜48桁目)の `*IN,60` は、**配列名+コンマ+添字で6文字ちょうど**という、C 仕様書の結果フィールド欄の幅制限をきれいに使い切った書き方です。

### `CABxx`: 比較して分岐する

```text
C  N50      TOKTAN    CABEQ' '       NOREP
C                     GOTO TANDN
C           NOREP     TAG
C                     MOVEL'NOREP'   TANNM     P
C           TANDN     TAG
```

`CABxx`(Compare And Branch)は、**Factor 1 と Factor 2 を比較し、条件が真なら Factor 2 の位置ではなく、結果フィールド(43〜48桁目)に書いた `TAG` へ直接ジャンプ**します。上の例は「`TOKTAN`(担当者コード)が空白なら `NOREP` へ飛ぶ」という意味です。04-06 で学んだ `GOTO`/`TAG` の**「比較付き版」**だと考えてください。分岐先は必ず `TAG` です。

### `CASxx`: 比較してサブルーチンを呼ぶ

```text
C           TOKCD     CASEQ' '       DFLTSR
C                     CAS            LKUPSR
C                     ENDCS
```

`CASxx`(Conditionally invoke a SubRoutine)は、見た目は `CABxx` に似ていますが、**結果フィールドには `TAG` ではなく `BEGSR`/`ENDSR` で定義したサブルーチン名**を書きます。`TOKCD` が空白なら `DFLTSR` を呼び、そうでなければ(`CAS` だけの無条件行)`LKUPSR` を呼びます。**`CASxx` の並びは `ENDCS` で締めくくる必要があります**(`IFxx`/`ENDIF` が対になっているのと同じ発想です)。

**この2つを混同するのは、実際に起きる典型的な間違いです。** このリポジトリーの `za0500.rpg` 自身のヘッダー・コメントに、まさにその実例が記録されています。

> `DOLIVE` は(`BEGSR`/`ENDSR` で定義した)サブルーチンではなく、ただの `TAG`(`GOTO` の飛び先)です。**サブルーチンでない飛び先に対して `CASEQ` を使うのは間違いで、正しくは `CABEQ` です。** `CASxx` の結果フィールドはサブルーチン名でなければならず、`ENDCS` も必要になりますが、どちらもこの箇所には当てはまりません。2026-09-26 の見直しで見つかり、`CABEQ` に修正されました。

**覚え方**: `CASxx` は「S」(SubRoutine)、`CABxx` は「B」(Branch=`TAG` へ分岐)。分岐先が `TAG` か `BEGSR` かを見れば、どちらの命令であるべきかが分かります。

### 標識の地図(読めればよい項目)

C 仕様書9〜17桁目(条件標識欄)には、01〜99の番号だけでなく、`LR`・`MR` のような2文字の予約標識も同じ場所に書けます。実際、`za0500.rpg` の

```text
C   01 MR             GOTO PROCLN
```

は9〜11桁目に `01`、12〜14桁目に `MR` が入っています(実機の桁位置で確認済み)。この2文字の標識には、次のような「家族」があります。

| 家族 | 意味 | このコードでの実例 |
|---|---|---|
| `KA`〜`KY` | ファンクション・キー(`KA`=F1, `KB`=F2, `KC`=F3, … `KY`=F24) | `tk0100.rpg` の `KC`(F3 の別ルート。`TK0100D` の `CF03(03)` が実質的な合図で、`KC` は読解用の二重チェック) |
| `U1`〜`U8` | 外部標識(ジョブの `SWS`(スイッチ設定)。`CHGJOB`/`CRTJOBD` で設定する。`*LDA` 由来ではない) | `tk0100.rpg` の `U1`(演出用の分岐。`tk0100.rpg` 自身のヘッダー・コメントが、`*LDA` 位置17から読むという以前の誤った説明を訂正しています) |
| `H1`〜`H9` | ホールト標識。ON のまま `LR` を迎えるとプログラムが異常終了する | `tk0100.rpg` の `H1`(`*LOCK IN` の失敗検知) |
| `OA`〜`OG` | 印刷装置ファイルの桁あふれ(04-04 の復習) | `tk0100.rpg` では未使用(`PRINTER` ファイルを持たない対話専用プログラムのため) |

**`tk0100.rpg` のヘッダー・コメントを鵜呑みにしないでください。** このソースには、実際のコード(DDS/C仕様書)と食い違う、書きかけのままの説明が残っています。

- ヘッダーは「`INQFMT` には `TOKUPD` を含む5フィールドがあり、`TOKCD` は入力専用(I)」と書いていますが、実際の `tk0100d.dspf` の `INQFMT` は `TOKCD`/`TOKNM`/`TOKZIP`/`TOKTAN` の**4フィールドのみ**で、`TOKCD` の使用法は**`B`(入出力両用)**です(`tk0100d.dspf` 自身の「Contract with tk0100.rpg」という節が、この食い違いを認めて訂正しています)。
- `mn0000c.clp` のヘッダーは(訂正前の版で)「`U1` は `*LDA` 位置17から読む」と書いていましたが、上の表のとおり `U1`〜`U8` はジョブの `SWS` で設定されるものであり、`*LDA` とは無関係です。`tk0100.rpg` 自身のヘッダーがこの誤りを訂正しています。

**これも、この部で身につけてほしい態度そのものです。コメントは書かれた時点のスナップショットに過ぎず、コードそのものより古くなっている(=信用できない)ことがあります。** 疑わしいときは、コメントではなく実際の DDS/C 仕様書の桁を数えてください。

### 参考: `*XREF`・`*LIKE`・`FNDSTRPDM`

- **`*XREF`**: `CRTRPGPGM` のコンパイル・オプションの一つで、コンパイル・リストに「どのフィールド・標識が、何行目で定義され、何行目で使われているか」という相互参照(クロス・リファレンス)を出力させます。**このレッスンには実際のリストは載せていませんが**、05-07(影響調査)につながる、「このフィールドを触っている行をすべて洗い出す」ための基本的な道具です。
- **`*LIKE`**: 上で見たとおり、既存フィールドと同じ属性で別名を宣言します。長い型定義を書き写さずに済み、元のフィールドの定義が変わっても追随します。
- **`FNDSTRPDM`**: PDM のコマンドで、**指定したソース・ファイル(またはライブラリー)の全メンバーから、文字列を検索**します。例えば `FNDSTRPDM STRING('ZASHO') FILE(<自分のユーザー名>1/QRPGSRC)` のように使います。`*XREF` が「1つのプログラムの中の相互参照」なのに対し、`FNDSTRPDM` は「複数のプログラムをまたいだ検索」です。05-07 の影響調査で本格的に使います(この段階では存在と使いどころだけ覚えておいてください。この教材のこのセッションでは実際に実行して確認していません)。

4. 同じ開始状態から `MOVE 'XYZ' FLDA P`(P拡張子あり)を実行すると?
5. `FLDB`(5A、現在値 `'AAAAA'`)に `MOVEL'ABCDEFGH' FLDB`(8文字のリテラル、結果フィールドの方が短い)を実行すると?
6. 同じ開始状態(`FLDB`=`'AAAAA'`)から `MOVE 'ABCDEFGH' FLDB` を実行すると?
7. `NUM1`(8S0、現在値 `00000042`)と同じ長さで宣言した `SAVNUM`(`*LIKE DEFN NUM1 SAVNUM`)に `MOVE NUM1 SAVNUM` を実行すると(`tk0100.rpg` の `MOVE TOKUPD SAVUPD` と同じ形)、`SAVNUM` は?
8. 標識60・61が現在どちらも ON のとき、`MOVEA'00' *IN,60` を実行すると、標識60・61はそれぞれどうなる?
9. `tk0100.rpg` の `LASTCD`(6桁の名前付きデータ域、現在値 `'C00003'`)を、空白の `TOKCD`(6A)に `MOVELLASTCD TOKCD` で転記すると、`TOKCD` は?
10. `TOKNM`(30A)に、直前の照会で `'ACME TRADING CO'`(15文字。16〜30桁目は既に空白)が入っているとします。もし `P` 拡張子を**付けずに** `MOVEL'NOTFOUND'TOKNM` を実行したら、`TOKNM` はどうなりますか(`tk0100.rpg` のヘッダー・コメント自身が書いている実例です)?

<details><summary>解答</summary>

1. `'XYZDEFGHIJ'`(左詰め、4〜10桁目は古いまま)
2. `'XYZ       '`(`XYZ` + 空白7桁)
3. `'ABCDEFGXYZ'`(右詰め、1〜7桁目は古いまま)
4. `'       XYZ'`(空白7桁 + `XYZ`)
5. `'ABCDE'`(左詰め、はみ出た右側6〜8文字目が切り捨てられる)
6. `'DEFGH'`(右詰め、はみ出た左側1〜3文字目が切り捨てられる)
7. `42`(`00000042`。同じ長さの数値同士なので、そのまま複写される)
8. どちらも OFF(`'00'` の `'0'` が「OFF」を意味し、`SETOF 6061` と同じ効果)
9. `'C00003'`(同じ長さの文字同士なので、そのまま複写される)
10. `'NOTFOUNDDING CO'`(+ 空白)。先頭8桁だけが `'NOTFOUND'` に書き換わり、9〜15桁目の古い値 `'DING CO'` がそのまま残ってしまう。**これが、実際の `tk0100.rpg` が `P` 拡張子を付けている理由です。**

</details>

| 90 | `C JUSHO CHAINZAIKOM 90`(54〜55桁目)で、`ZAIKOM` に該当商品が見つからなかったとき | 行頭の `C SETOF 9091`(54〜55桁目)で、`PROCLN` に入るたび明示的に消す | 商品コードが `ZAIKOM` に無い(`NOTFOUND`) |
