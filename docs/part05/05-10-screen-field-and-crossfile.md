## なぜ学ぶか

**保守の現場で一番多い依頼は「この画面にあの項目も出してほしい」です。** 05-09 では物理ファイルへの項目追加を扱いましたが、今回は表示装置ファイル(DSPF)への項目追加です。仕組みは同じ(様式レベル ID)ですが、対象が「データを持つファイル」ではなく「画面のレイアウト」である点が違います。さらに、今回の元ネタである `TK0100`(得意先照会)は、**担当者マスター `TANTOM` という「もう1つの、別の目的のために作られたファイル」を `CHAIN` して名前を補完する**という、他システムのファイルを読みに行く典型的な改修でもあります。そして実は、`TK0100` のソースには**この `CHAIN` 自体がすでに実装されていて、画面に表示する行だけが抜けている**という、保守でよくある「作りかけ」の状態そのものです。

## 新出

- **I 仕様書によるフィールドの改名(21〜30桁に外部名、53〜58桁にプログラム内の名前)**: RPG III のフィールド名は6桁までしか使えないため、`TANTOCODE`(9桁)のような長い外部フィールド名を、`TANCD`(6桁以下)のような短い名前に読み替える。
- (復習・応用) **DSPF の様式レベル・チェック**: 05-09 で学んだ仕組みが、表示装置ファイルにもそのまま当てはまる。
- (復習) **`CHAIN`**: 04-07 で確認済みの技法を、`TANTOM` に対して使う。

## 説明

### DSPF の様式レベル・チェック

05-09 で学んだ様式レベル ID の仕組みは、物理ファイルに限らず、**表示装置ファイル(DSPF)のレコード様式にも同じように適用されます。** `TK0100D` の `INQFMT` に出力項目を1つ追加すると、`INQFMT` の様式レベル ID が変わります。すると、**`INQFMT` を `EXFMT` している `TK0100`(コンパイル時の古い `INQFMT` の様式レベル ID を覚えたまま)は、実行時に `CPF4131` で止まります。** 直し方は05-09と同じ原理です。**変更したファイル(今回は DSPF)を先に再作成し、それを使っているプログラム(RPG)を後から再コンパイルする**、という順序を守ります。

```text
TK0100D (DSPF、INQFMT)
  └─ TK0100 (RPG、FTK0100D CF E WORKSTN で EXFMT INQFMT)
```

05-09 の `PF → LF → DSPF → RPG → CL` という一般原則のうち、今回動くのは **`DSPF → RPG`** の部分だけです。`TK0100` を使う CL は今のところ存在しない(`MN0000C` は `TK0100` を呼び出すだけで `DCLF` はしていません)ので、CL の再コンパイルは不要です。

### `TK0100` はすでに `TANTOM` を `CHAIN` している

`src/legacy/qrpgsrc/tk0100.rpg` を実際に読むと、担当者名を表示する準備はすでに終わっていることが分かります。ファイル宣言はこうです。

```text
     FTK0100D CF  E                    WORKSTN
     FTOKUIM  IF  E           K        DISK
     FTANTOM  IF  E           K        DISK
```

`TANTOM`(担当者マスター)が、`TOKUIM` と同じ形式(`IF`・外部記述・キー付き)で開かれています。実際の `CHAIN` はこの部分です(`LKUPSR` サブルーチン内)。

```text
     C  N50      TOKTAN    CABEQ' '       NOREP
     C  N50      TOKTAN    CHAINTANTOM               51
     C                     GOTO TANDN
     C           NOREP     TAG
     C                     MOVEL'NOREP'   TANNM     P
     C           TANDN     TAG
     C   51                MOVEL'NOTFOUND'TANNM     P
```

`TOKUIM` から取得した担当者コード(`TOKTAN`)が空欄なら `TANTOM` を `CHAIN` せずに `'NOREP'`(担当者なし)を、見つからなければ標識51で `'NOTFOUND'` を、`TANNM` にセットします。**つまり `TANNM` というプログラム内フィールドは、もう正しく計算されています。** ソース自身のヘッダー・コメントも、この状態を正確に言い当てています。

> INQFMT has no rep-name field: the rep name is a 05-10 addition to the screen per design.objects[0].purpose - so the TANTOM CHAIN below computes TANNM but nothing displays it yet on INQFMT.

**このレッスンの実質的な作業は、「計算済みの `TANNM` を、画面に映す項目として `INQFMT` に追加するだけ」**です。RPG 側のロジックには一切手を入れません。

### I 仕様書のフィールド改名: 21〜30桁 → 53〜58桁

`TANTOM` の外部フィールド名は `TANTOCODE`・`TANTONAME` で、それぞれ9文字あります。RPG III のフィールド名(プログラム内で使える識別子)は**6桁までしか使えない**ため、そのままでは Factor 1/2 に書けません。そこで I 仕様書で改名します。

```text
     ITANTOR
     I              TANTOCODE                       TANCD
     I              TANTONAME                       TANNM
```

`tk0100.rpg` のヘッダー・コメントによれば、**21〜30桁に外部フィールド名(`TANTOCODE`・`TANTONAME`)、53〜58桁に改名後のプログラム内フィールド名(`TANCD`・`TANNM`)**を書く形式です(RPG/400 Reference p.149/153)。**この桁位置での改名は、04-10 で実機確認済みの「制御レベル・マッチング・フィールドの改名」(53〜58/59〜62桁)とは別物**で、21〜30桁を使う今回の形自体はまだ実機コンパイルで確認できていません(下の実機メモを参照)。`TANTOCODE`(9文字、6A)→`TANCD`、`TANTONAME`(9文字、20A)→`TANNM` という対応そのものは、この改名が無いと `TOKTAN CHAIN TANTOM` や `TANNM` への `MOVEL` がそもそも書けない(6桁を超える名前は Factor に書けない)、という必然性から来ています。

## 実演

**ここから先は未検証です。DDS の追加行・再コンパイルの順序は `src/legacy/qddssrc/tk0100d.dspf`・`src/legacy/qrpgsrc/tk0100.rpg` の実ソースに基づいていますが、実機での確認はまだ行っていません(実機メモ参照)。**

1. `TK0100D` の `INQFMT` の現在のレイアウトを確認します(既存の項目は1〜7・22行目を使っており、8行目は空いています)。

   ```text
   ....+....1....+....2....+....3....+....4....+....5....+....6....+....7....+....8
        A                                  1  2'TK0100 - Customer inquiry'
        A                                  3  2'Customer code:'
        A            TOKCD          6A  B  3 17
        A                                  5  2'Name:'
        A            TOKNM         30A  O  5  9
        A                                  6  2'Zip:'
        A            TOKZIP         7A  O  6  9
        A                                  7  2'Sales rep:'
        A            TOKTAN         6A  O  7 13
        A                                 22  2'F3=Exit'
   ```

2. 8行目に、担当者名(`TANNM`)を表示する行を追加します。ラベルと出力項目は、既存の `TOKTAN` の行(7行目・13桁目)と同じ列位置の作法にそろえます。

   ```text
   ....+....1....+....2....+....3....+....4....+....5....+....6....+....7....+....8
        A                                  8  2'Rep name:'
        A            TANNM         20A  O  8 13
   ```

   `TANNM` は `TANTOM.TANTONAME`(20A)を I 仕様書で改名した項目と同じ名前・同じ長さ(20A)にします。**長さを一致させないと `QRG6033` になる**ことは 04-11 で確認済みです。

3. `TK0100D` を再コンパイルします(DSPF を先に)。

   ```text
   CRTDSPF FILE(<USER>1/TK0100D) SRCFILE(<USER>1/QDDSSRC) SRCMBR(TK0100D)
   ```

4. `TK0100`(RPG)を再コンパイルします。**RPG のソース自体は1行も変更していません。** `TANNM` はすでに `LKUPSR` サブルーチンで計算されているため、`INQFMT` に同名の出力項目ができれば、`EXFMT` 時に RPG のワークステーション・ファイルの仕組みが**名前が一致する項目を自動的に画面へ転記します**(04-11 の実機メモで確認済みの、`CHAIN` 結果が同名の画面出力項目に自動表示される、という仕組みと同じ原理)。

   ```text
   CRTRPGPGM PGM(<USER>1/TK0100) SRCFILE(<USER>1/QRPGSRC) SRCMBR(TK0100)
   ```

   **正直な注記**: 04-11 が実機確認したのは「`CHAIN` で取得した外部記述ファイルのフィールドが、同名の画面出力項目に自動表示される」ケースです。今回の `TANNM` は、`TANTOM` の `CHAIN` 結果を **I 仕様書で改名した**プログラム内フィールドであり、この具体的な組み合わせ(改名後のフィールドが WORKSTN の同名出力項目に自動表示されること)自体は、まだ実機で確かめていません。RPG のワークステーション自動転記は「今その名前を持つプログラム・フィールドの値」を転記する仕組みのはずなので、改名の有無は関係しないと考えられますが、**次の実機接続で確認してください。**

5. 5250 で `CALL PGM(<USER>1/TK0100)` を実行し、得意先コードを入力して `Enter` を押します。担当者コードが入っている得意先では担当者名が、担当者コードが空欄の得意先では `NOREP` が、`TANTOM` に存在しない担当者コードの場合は `NOTFOUND` が、8行目に表示されることを確認します。

## 演習

`JU0300`(受注一覧、`JUCHUM`/`JUCHUL1` の制御レベル集計)にも、同じ発想でもう1つ他システムのファイルを足してみてください。`JU0300` の O 仕様書の明細行(`DTL`)は次のようになっています。

```text
     OQSYSPRT E                DTL
     O                         JUNO      10
     O                         JUTOK     20
     O                         JUDATEZ   32
     O                         JUTAN     42
```

`JUTAN`(42桁目まで、担当者コード)の右に、**担当者名を追加してみてください。** 手順は `TK0100` と同じ考え方です。

1. `FTANTOM  IF  E           K        DISK` を F 仕様書に追加する(`TK0100` と同じ形)。
2. `ITANTOR` の下に、`TANTOCODE`→`TANCD`、`TANTONAME`→`TANNM` の I 仕様書改名を追加する(`TK0100` と全く同じ2行でよい)。
3. 明細処理(94標識のブロック)のどこかに、`JUTAN` をキーに `TANTOM` を `CHAIN` する行を追加する。見つからない場合の標識(例: 96)も用意し、`TK0100` と同じ要領で `'NOTFOUND'` を `TANNM` に `MOVEL`(`P` 拡張子つき)する。
4. `OQSYSPRT` の `DTL` グループに `O                         TANNM     63` のような行を足し(`QSYSPRT` は132桁の印刷装置ファイルなので余裕があります)、`JUTAN` の右に担当者名を印字する。
5. `JU0300` だけを再コンパイルする(`TANTOM` 自体は形を変えていないので、`TANTOM` 側の再作成は不要です。`JU0300` が新たに `TANTOM` を参照するようになるだけです)。

`TK0100` との違いは、`TANTOM` そのものの様式は変わらない(様式レベル ID の不一致は起きない)ため、これは05-09の「様式レベル・チェック」の演習ではなく、**「他システムのファイルを新しく参照に追加する」という、もう1つの改修パターンの練習**です。
