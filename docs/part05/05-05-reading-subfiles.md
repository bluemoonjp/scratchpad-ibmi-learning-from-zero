## なぜ学ぶか

**一覧画面には、ほぼ必ず「ページ送り」が要ります。** 得意先が6件しかない `TOKUIM` ならまだしも、実務では数百〜数千件が相手です。全件を一度に画面に送るわけにはいかないので、RPG III の時代から**サブファイル**(画面の中に複数行を保持できる特殊なレコード様式)が使われてきました。さらに、入力エラーなどを画面の主要部分を潰さずに伝える仕組みとして**メッセージ・サブファイル**があります。

このレッスンで読む `TK0100D`(`src/legacy/qddssrc/tk0100d.dspf`)は、得意先一覧のページ単位サブファイル(`SFL1`/`SFL1CTL`)とメッセージ・サブファイル(`MSGSFL`/`MSGCTL`)を両方とも定義した、コメントの非常に厚い実在のソースです。**ただし正直に言うと、これを駆動する `TK0100`(RPG)は、いまのところ `INQFMT`(得意先1件照会)のループしか実装しておらず、サブファイルの `READC`/`SFLNXTCHG` ループはまだ書かれていません**(`tk0100.rpg` 自身のヘッダーが、この欠落を「後回しにした範囲」ではなく「未解決の実在するリスク」として明記しています)。ですので、このレッスンは「動くコードを `STRDBG` で追う」だけでなく、**DDS の設計を正確に読み、動いたらどう振る舞うはずかを予測する**という、保守の現場で本当によく求められる読み方の練習になります。

## 新出

**中核(3つ)**

- `SFLSIZ`/`SFLPAG`: サブファイルの保持件数/1ページの表示件数。両者が等しいか(ページ単位)、`SFLSIZ` の方が大きいか(拡張型)で、`ROLLUP`/`ROLLDOWN` に対する RPG 側の責任が変わる。
- `READC`/`SFLNXTCHG`: 「変更されたサブファイル・レコードだけを読む」ための組。
- SFILE 継続行(F仕様書): WORKSTN ファイルにサブファイルを結びつける、RPG III で必須の書き方。

**キーワード等(読めればよい項目を含めて6つまで)**

- `SFLDSP`/`SFLDSPCTL`: サブファイルの明細/制御レコードを表示してよいことを示す。
- `ROLLUP`/`ROLLDOWN`: ページ送り/ページ戻りキー(`PAGEDOWN`/`PAGEUP` と同じキーの別名)。
- `SFLMSGRCD`/`SFLPGMQ`: メッセージ・サブファイルの表示開始行と、メッセージの取得元(プログラム・メッセージ待ち行列)。
- `QMHSNDPM`: プログラム・メッセージ送信 API(メッセージ・サブファイルへメッセージを送り込む側)。
- `SFLINZ`: 空のサブファイルでも表示を初期化する。
- 読めればよい(`TK0100D` では未使用): `ERRMSGID`(妥当性検査が失敗したフィールドに出すメッセージ、`ERRMSGID(msgid msgfile)` の形、`msgid` は引用符なし)、**検査キーワード**(`COMP`/`RANGE`/`VALUES`/`CHKMSGID` など、入力フィールドの妥当性を検査する DDS キーワードの総称。`ERRMSGID` とペアで使うのが典型)。

## 説明

### SFL1: サブファイル明細レコード様式

`TK0100D` の得意先一覧は、明細1行分を表す `SFL1` と、それを制御する `SFL1CTL` の2つのレコード様式に分かれています(サブファイルは必ずこの2枚組です)。

```text
     A          R SFL1                      SFL
     A                                      SFLNXTCHG
     A            OPT            1A  B  4  2
     A            TOKCD          6A  O  4  5
     A            TOKNM         30A  O  4 13
```

- レコード様式レベルの `SFL` キーワードが必須です(このキーワードが無いと、ただの通常レコード様式になってしまいます)。
- `SFLNXTCHG` は、**サブファイル明細レコード様式(ここでは `SFL1`)のレベルに書く**キーワードです(`SFL1CTL` ではありません)。「このレコードは変更されたものとして扱う」という指示で、`READC` が次に呼ばれたときにこの行を返す対象にします。
- `OPT` は入力可能(`B`、実は入出力兼用)な1桁のオプション欄です。`TK0100D` 自身のコメントでは「ここに `1` を入力すれば、その行の得意先コードで `INQFMT` に切り替える(`CHAIN` する)設計」とされていますが、**これは設計上の意図であり、`TK0100`(RPG)はまだこの `OPT` を読んでいません**(後述)。

### SFL1CTL: サブファイル制御レコード様式

```text
     A          R SFL1CTL                   SFLCTL(SFL1)
     A                                      SFLSIZ(10)
     A                                      SFLPAG(10)
     A                                      SFLDSP
     A                                      SFLDSPCTL
     A                                      ROLLUP(25)
     A                                      ROLLDOWN(26)
     A                                      CF03(03)
```

- `SFLCTL(SFL1)` で、どの明細レコード様式を制御するかを指定します。
- `SFLDSP`/`SFLDSPCTL` は、このファイルでは条件標識なし(常時 ON)です。`TK0100D` のヘッダー・コメントは、これを「安全な常時 ON」と説明しています。理由は、`SFLCLR`/`SFLEND` のような「クリアしてから読み込む」系のキーワードをこのファイルが一切使っていないからです(次段落)。
- **`SFLCLR`/`SFLEND` はこのファイルにありません。** IBM のサブファイルの定番パターンでは、`SFLCLR` を「クリア用の書き込み」と「表示用の書き込み」を区別する条件標識で出し分けますが、`TK0100D` は(04-11 で失敗した DDS 条件標識(桁7-16)にこれ以上依存しないという方針のため)一切の条件標識を持ちません。無条件の `SFLCLR` を書いてしまうと、**せっかく読み込んだ直後の表示用の書き込みでもサブファイルをクリアしてしまう**ため、あえて書いていません。代わりに、`TK0100` が実装されたときは「`RRN`(相対レコード番号)`1`〜`SFLPAG` を毎ページ上書きし、最後のページは残りを空白で埋める」という方式でクリアの代用をする設計です(`TK0100D` のヘッダー・コメント)。`MORE` という出力専用フィールド(`'MORE...'`/`'BOTTOM'` を `MOVEL` で書き換える、04-11 と同じ技法)が、`SFLEND` の「+/Bottom」表示の代役です。

### ページ単位(`SFLSIZ＝SFLPAG`)と拡張型(`SFLSIZ＞SFLPAG`)の違い

`SFL1CTL` は `SFLSIZ(10)` = `SFLPAG(10)`(両方とも10)です。これが**ページ単位サブファイル**で、このレッスンの表題そのものです。

- **ページ単位(`SFLSIZ＝SFLPAG`)**: サブファイルは常に「1ページ分」の件数しか保持しません。ユーザーがどちらの方向にページを送っても(`ROLLUP` でも `ROLLDOWN` でも)、**必ず RPG プログラムに制御が戻り**、プログラムが該当するページの行を(多くの場合クリアしてから、または `TK0100D` の設計のように上書きで)読み直して積み直します。`TK0100D` のヘッダーが `ROLLUP(25)`/`ROLLDOWN(26)` を「ページ単位サブファイルには両方とも必須」と書いているのはこのためです。1画面分しか保持しないので、戻るときも新しく読み直す必要があります。
- **拡張型(`SFLSIZ＞SFLPAG`)**: サブファイルに複数ページ分の件数(場合によっては該当データ全件)を一度に読み込んでおき、画面上でのページ送り・ページ戻りは**システムが**サブファイル内で既に読み込み済みの行をスクロールするだけで済ませます。プログラムが呼び出されるのは、読み込み済みの範囲を超えてさらに読み込む必要が生じたときだけです。

同じファイルの `MSGCTL`(後述、メッセージ・サブファイル制御)は `SFLSIZ(2)`/`SFLPAG(1)` で、数値のうえでは `SFLSIZ＞SFLPAG` です。ただしメッセージ・サブファイルは `SFLINZ` + `SFLPGMQ` によってプログラム・メッセージ待ち行列から自動的に再構築される特殊な仕組みで、`SFL1CTL` のような `ROLLUP`/`ROLLDOWN` は付いていません(この点は次段落以降で扱います)。「等しいか・大きいか」という数値だけでなく、**その差が実際に何を意味するファイルなのか**まで読むのが、このレッスンの狙いです。

### SFILE 継続行(F仕様書) ― 旧称「KSFILE」の訂正

`tk0100.rpg` を `TK0100D` と組み合わせて `READC` を使うには、F仕様書の**継続行**でサブファイルとファイルを結びつける必要があります。RPG/400 Reference の「Continuation Line Options Summary Chart」によれば、桁位置は次のとおりです。

- 47〜52桁目: 相対レコード番号(RRN)を受け取る数値フィールド名(このファイル記述行で使う)
- 53桁目: `K`(継続行であることを示す)
- 54〜59桁目: `SFILE`(継続行の種類)
- 60〜67桁目: 対象のサブファイル・レコード様式名(左詰め)

一次資料(RPG/400 Reference)の原文も引用します。

> If the main file-description line contains E in position 19 and WORKSTN in positions 40 through 46, this option must be used to define any subfiles to be used in the file. Positions 60 through 67 must specify, left justified the RPG/400 name of the record format to be processed as a subfile.

**この構成要素は「KSFILE」という1語のキーワードではありません。** `RPG/400 Reference` のどこにも `KSFILE` という綴りは登場しません(`tk0100.rpg` 自身のヘッダー・コメントが、設計初期の草稿がこの誤った名前を使っていたことを認めて訂正しています)。おそらくの由来は、桁位置を文章で書くと「53桁目=`K`、54〜59桁目=`SFILE`」が続けて並ぶため、視覚的に「K」+「SFILE」で「KSFILE」に見えてしまったことでしょう(このリポジトリーには、`za0500.rpg` の `CASEQ`/`CABEQ` の取り違えなど、同種の「設計初期の誤りを見つけて訂正した」記録が他にもあります)。以後はこの正式名「**SFILE 継続行**」で覚えてください。

**重要: この SFILE 継続行は、今のところ `TK0100`(RPG)には書かれていません。** `tk0100.rpg` のヘッダー・コメントは、これを「後回しにした機能」ではなく「未解決の実在するリスク」として扱っています。`FTK0100D` の主行が `E`(外部記述)・`WORKSTN` であり、`TK0100D` がサブファイル・レコード様式(`SFL1`、`MSGSFL`)を2つ定義している以上、一次資料の文言(「サブファイルを使うファイルには必ずこの継続行が要る」)がそのまま当てはまるのか、あるいは「RPG プログラム自身がサブファイルを一切操作しない場合は省略できるのか」は、**このセッションでは実機コンパイルで確認できていません。** `TK0100` をコンパイルする前に、まずこの点を検証する必要があります。

### READC / SFLNXTCHG ― 概念として

`READC`(サブファイルの変更されたレコードを読む命令)は、RPG/400 Reference では次のように説明されています。

> The READC operation can be used only with an externally described WORKSTN file to obtain the next changed record in a subfile. Factor 2 is required and must be the name of a record format defined as a subfile by the SFILE keyword on the file description specifications.

典型的な使い方は、`EXFMT`(または `WRITE`+`READ`)でサブファイル制御レコードを表示した後、`DOWEQ *IN03`(F3 が押されるまで)のようなループの中で `READC SFL1` を繰り返し呼び、**ユーザーが実際に入力・変更した行だけ**を1件ずつ受け取って処理する、というものです。`SFLNXTCHG` は、プログラム側から「次の `READC` でこの行を返してほしい」と明示的にマークするためのキーワードです。

`TK0100D` の `SFL1` は `SFLNXTCHG` を**条件標識なし(常時)**で付けています。これは「毎回、すべての行を『変更あり』として返す」ことを意味します。`TK0100D` のヘッダー・コメントいわく、`READC` 本来の「変更された行だけに絞り込む」効果が働かないだけで害はありませんが、**もし `TK0100` が将来 `READC` ループを実装するなら、返ってきたすべての行の `OPT` を毎回チェックしなければならない**(通常のような「変更された行だけ来る」という前提が使えない)、という設計上の制約になります。

このレッスンでは、`READC`/`SFLNXTCHG` の**両方とも概念として認識できればよい**という位置づけです。実際に動くループを `STRDBG` で追うことは(まだ存在しないため)できません。

### メッセージ・サブファイル(MSGSFL/MSGCTL)

```text
     A          R MSGSFL                    SFL
     A                                      SFLMSGRCD(24)
     A            MSGKEY                    SFLMSGKEY
     A            PGMQ                      SFLPGMQ
     A          R MSGCTL                    SFLCTL(MSGSFL)
     A                                      SFLSIZ(2)
     A                                      SFLPAG(1)
     A                                      SFLDSP
     A                                      SFLDSPCTL
     A                                      SFLINZ
     A            PGMQ                      SFLPGMQ
     A                                      OVERLAY
```

- `SFLMSGRCD(24)` は「メッセージは画面の24行目から上に向かって積み上がる」という指定です(24行画面の最下行)。
- `MSGSFL` の `MSGKEY`/`PGMQ` フィールドには、それぞれ `SFLMSGKEY`/`SFLPGMQ` という**フィールド・レベル**のキーワードが付きます。桁・型・行・桁位置はすべてシステムが決めるため、この2フィールドには長さ等を書きません。
- `MSGCTL` 側にも別の `PGMQ` フィールドがあり、こちらにも `SFLPGMQ`(フィールド・レベル)が付きます。**IBM の `SFLINZ` の解説は、「メッセージ・サブファイルの `SFLCTL` レコードで `SFLINZ` を指定する場合、同じレコード様式にフィールド・レベルの `SFLPGMQ` も必要」と定めています。** `MSGCTL` はこの組を満たしています。
- `SFLINZ` は「レコードが1件も無い(空の)サブファイルでも、表示のための出力操作を成立させる」ためのキーワードです。IBM のリファレンスは、`SFLDSP` を空のサブファイルに対して(`SFLINZ` なしで)使うとエラーになると警告しています。`TK0100` は通常時、メッセージ・サブファイルには何も `WRITE` しない(`MSGSFL` は通常0件)想定なので、`SFLINZ` がこの「0件でもエラーにしない」役目を果たします。
- `OVERLAY` は、`MSGCTL` を画面に書くとき、既に表示されている `INQFMT` や `SFL1CTL` を消さずに上書きする、という指定です。
- 実際にメッセージを`PGMQ`(プログラム・メッセージ待ち行列)へ送り込むのは、**RPG プログラム自身ではなく `QMHSNDPM`(プログラム・メッセージ送信 API)の役目**です。`TK0100D` の設計では、「見つからない」のような通常のエラーは(04-11 と同じ)`MOVEL` による出力フィールド書き換えで表現し、`QMHSNDPM` → `MSGCTL` の経路はそれとは別の、より本格的なエラー通知の仕組みとして用意されています。

**ここも正直に: `tk0100.rpg` の実際の C 仕様書には `QMHSNDPM` の呼び出しが一つもありません。** `TK0100` は `INQFMT` の `EXFMT` ループだけを実装しており、`MSGSFL`/`MSGCTL` への `WRITE` も `QMHSNDPM` の呼び出しも行っていません。つまり `MSGSFL`/`MSGCTL` は、`SFL1`/`SFL1CTL` と同じく「画面としては定義済みだが、RPG からまだ駆動されていない」状態です。

## 実演

1. 5250 で `WRKMBRPDM FILE(<自分のユーザー名>1/QDDSSRC)` を実行し、`TK0100D` を開いて眺める。上の「説明」で読んだ `SFL1`/`SFL1CTL`/`MSGSFL`/`MSGCTL` の実際の桁位置を、自分の目で確認する。特にヘッダー・コメントの分量(条件標識を使わない理由、`SFLCLR` を書かなかった理由)を読み切ること。
2. `WRKMBRPDM FILE(<自分のユーザー名>1/QRPGSRC)` で `TK0100` を開き、`FTK0100D CF E WORKSTN` の行と、そのヘッダー・コメントにある「SFILE 継続行がまだ無い」という記述を確認する。C仕様書を最後まで読み、`EXFMT INQFMT` のループ・`CASEQ`/`CAS`・2つのサブルーチン(`DFLTSR`/`LKUPSR`)以外に、`SFL1`/`MSGSFL` へ触れているコードが本当に無いことを確認する。
3. **`TK0100` を実行する前に、名前付きデータ域 `LASTCD` が必要です。** `tk0100.rpg` のヘッダー・コメントが明記しているとおり、`TK0100` は起動直後に `*LOCK IN` でこのデータ域をロックします。データ域が存在しないと `*LOCK IN` が失敗して標識H1がONになり、プログラムはLRで異常終了します。`05-01` の `TXLEGACY` はこのデータ域を作らないので、自分で用意してください。

   ```text
   CRTDTAARA DTAARA(<自分のユーザー名>1/LASTCD) TYPE(*CHAR) LEN(6)
   ```

4. **同じ5250セッションの中で**、`STRDBG PGM(<自分のユーザー名>1/TK0100)` を実行してからデバッグ・モードのまま `CALL PGM(<自分のユーザー名>1/TK0100)` を実行する(`STRDBG` は別セッションから呼び出したプログラムを追いかけられません。デバッグ対象の `CALL` は、`STRDBG` と同じジョブ・同じセッションで行う必要があります)。04-12 で触れたとおり、ブレークポイントの設定や変数表示の具体的な操作は、実際の5250画面を見ながら行ってください。ここでは、`tk0100.rpg` のヘッダーにある「標識の地図」(`*IN03`・`TOKCD`・標識50/51・H1・KC・U1)を手がかりに、実際の値がそのとおりに動くかを確認します。
5. 4. で `SFL1`/`MSGSFL` に関するコードを一歩ずつ追えないこと(該当するコードが無いこと)自体を確認する。これは「保守対象のプログラムが、画面ファイルの設計をすべて実装しているとは限らない」ことを実機で体験する、このレッスンの重要な部分です。

## 演習

1. **画面遷移図を書く。** `TK0100D` に実際にある CF キー・標識だけを使って、次の状態を線でつないでください。
   - 初期表示(`INQFMT` を `EXFMT`、または `SFL1CTL` を書いて一覧表示)
   - ページ送り(`SFL1CTL` の `ROLLUP(25)`/`ROLLDOWN(26)`)
   - メッセージ表示(`MSGCTL` の `OVERLAY` で既存画面の上に重ねる)
   - 終了(`INQFMT`/`SFL1CTL` 双方にある `CF03(03)`)

   `SFL1` の `OPT` 欄による行選択(1件照会への遷移)も矢印として描いてよいですが、**実装されていない(設計のみ)である旨を矢印に注記**してください。

2. **ページ送りで何件読むかを予想する。** `TOKUIM` の実データは 6 件です(04-06/04-07 の実機検証、`docs/probes.md` で確認済み)。`SFL1CTL` の実際の値は `SFLSIZ(10)`/`SFLPAG(10)` です。
   - 初回表示で、`TK0100` が(設計どおりに)`SFLPAG` 分だけ `TOKUIM` を順に読もうとした場合、何件の `READ` が成功し、何件目で終端(EOF)に達しますか? `MORE` フィールドは `'MORE...'`/`'BOTTOM'` のどちらになるはずですか?
   - その状態から `ROLLUP`(ページ送り)を押したら、読み込む件数は何件ですか?
   - もし `TOKUIM` が 25 件だったら(仮定)、`SFLSIZ＝SFLPAG＝10` のページ単位のまま、1ページ目・2ページ目・3ページ目でそれぞれ何件読みますか? 3ページ目から `ROLLDOWN` で2ページ目に戻るとき、何件**読み直す**必要がありますか?
   - 同じ25件の仮定で、もし `SFL1CTL` が `SFLSIZ(9999)`/`SFLPAG(10)`(拡張型)だったら、初回表示・`ROLLUP`・`ROLLDOWN` それぞれで何件読み込む必要がありますか?(プログラムが「最初に全件読み込む」か「読み込み済みの範囲を超えたときだけ追加で読む」か、前提を書いたうえで答えてください。)

<details><summary>解答の方針</summary>

1. 初回: 7件目の `READ` で EOF に達するので、成功する `READ` は6件。`MORE` は `'BOTTOM'`(これ以上のページが無い)。
2. 直後の `ROLLUP`: 既に最後のページなので、追加で読む行は0件です(`TK0100D` の設計どおりなら、単に同じ6件を再表示するか、ページ送りを無視することになります)。
3. 25件・ページ単位(10/10)の場合: 1ページ目=10件読む、2ページ目(`ROLLUP`)=次の10件を読む、3ページ目(`ROLLUP`)=残り5件を読んで6件目の `READ` で EOF。2ページ目に `ROLLDOWN` で戻るときは、ページ単位サブファイルは1ページ分しか保持していないため、**10件を読み直す**必要があります。
4. 25件・拡張型(9999/10)の場合、答えはプログラムがどちらの戦略を採るかによります。**「最初に全件読み込む」戦略なら、初回表示で25件(全件)読み込み、その後の `ROLLUP`/`ROLLDOWN` は0件。** **「1ページ分ずつ、読み込み済みの範囲を超えたときだけ追加で読む」戦略なら、初回は10件、2ページ目に進むときに追加で10件、3ページ目でさらに5件、という具合です。** どちらの戦略でも共通するのは、**`ROLLDOWN`(戻る方向)では追加の読み込みが0件で済む**という点です。ページ単位(3.)では戻るときも毎回読み直しが必要だったのと、ここが対照的です。

</details>

## 実機メモ

- **未検証(2026-09-26時点)。** `TK0100D`・`TK0100` はいずれも、このセッションでは実機コンパイルしていません(両ファイル自身のヘッダーに "NOT COMPILED ON REAL HARDWARE" と明記されています)。SSH 接続の予算が回復し次第、実機で確認します。
- P22(旧システムのビルド: `SNDRCVF`・ページ単位サブファイル・メッセージ・サブファイルのコンパイルと実行を含む)は、`docs/probes.md` の「未実施のプローブ」節に載っており、**このセッションではまだ一度も実施していません。**
- `verify/part05-legacy-probe/manifest.json` に、`TK0100D`→`TK0100`(および `MN0000D`→`MN0000C`、`JU0900C`)を1回の接続でまとめてコンパイルするバッチが用意済みです。ただし、このバッチは**コンパイルのみ**で、`CALL` は一切行いません(対話的な `TK0100`/`MN0000C` は SSH 経由では動かせないため、意図的に外されています)。
- `TK0100D` の SFL 系キーワードの桁位置は、`tools/gen/dspf.mjs` のジェネレーター関数(`sflRecordFormat`/`sflPgmQ`/`errMsgId`/`sflRcdNbr`)に実装ミスが見つかったため、このファイルではそれらの関数を使わず手書き・迂回している箇所があります(ファイル冒頭のヘッダー・コメント、および `tools/gen/dspf.mjs` 自身のコメントを参照)。`MN0000D` はサブファイルを持たないため、この問題の対象外です。
- 04-11 で失敗した DDS 条件標識(`CPD7410`/`CPD7606`/`CPD5238`、桁位置未解決)を踏まえ、`TK0100D` は条件標識を一切使わない設計です。このため `SFLDSP`/`SFLDSPCTL` の「常時 ON」が安全かどうかも、実機コンパイルで初めて確認できます。
- SFILE 継続行が、`TK0100` のように「サブファイル・レコード様式を定義はしているが実際には駆動しない」WORKSTN ファイルでも必須なのかどうかは、`tk0100.rpg` 自身のヘッダーが「未解決の実在するリスク」として明記している事項です。`CRTRPGPGM` で確認する前に、このソースに依存しないでください。
