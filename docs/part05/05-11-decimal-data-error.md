## なぜ学ぶか

**保守の現場で一番こわいのは、「エラーにならずに成功してしまう」変更です。** たとえば、形の似た2つのファイルの間でデータを移すときに `CPYF` の対象指定を誤り、本来ならエラーで止まるはずの型の不一致を `FMTOPT(*NOCHK)` で黙って通してしまった、というような話です。コマンド自体は正常終了(完了メッセージ)で終わり、誰も気づきません。**問題が表面化するのは、後になって別のプログラムがそのデータを使って算術(足し算・引き算など)をしようとしたときです。** ここでは、`JUCHUD`(受注明細)の数量列に、このやり方で壊れたデータを実際に仕込み、`RPG0907`(10進数データ・エラー)がどこでどう発生するかを、`QPJOBLOG` と `HEX()` を使って実際のバイトまで追いかけます。

## 新出

- `HEX()`(SQL のスカラー関数)とゾーン10進数のバイト構成
- 障害報告書(何が起きた/原因/直した内容/再発防止)の型

## 説明

### 現場でありがちな話: `*NOCHK` でデータが壊れる経緯

`CPYF` は、既定では複写元と複写先のレコード様式(フィールドの型・長さ)が一致しているかを確認し、一致しなければエラーで止まります。**`FMTOPT(*NOCHK)` を指定すると、この確認を飛ばして、バイト列をそのまま複写先に押し込みます。** 02-10 のウォームアップで既に触れたとおり、「様式が違ってもエラーにならず、列の意味を取り違えたまま複写してしまう」のが `*NOCHK` の危険性です。

具体的にどう壊れるかを、この教材のために用意した `src/legacy/qddssrc/jubadd.pf`(`JUBADD`、検証専用の「型を間違えたステージング・ファイル」)で体験します。`JUBADD` は `JUCHUD` と全く同じフィールド構成ですが、**数量を表す `JUSU` だけが `5S 0`(数値、ゾーン10進数)ではなく `5A`(文字)になっています。** `JUBADD.JUSU` に文字列 `'ABCDE'` を入れること自体は、`JUBADD` にとっては正当な操作です(文字型の列に文字を入れているだけです)。ところが、この行を `CPYF FMTOPT(*NOCHK)` で `JUCHUD` へ複写すると、**`'ABCDE'` の生のバイト列が、本来なら数字しか入らないはずの `JUCHUD.JUSU`(5S 0)にそのまま書き込まれます。** `JUCHUD` 側は何もチェックしていないので、この複写コマンド自体は正常終了します。

> **実機で確認済み**: `CPYF FMTOPT(*NOCHK)` がここで説明したとおりに動くことは実機で確認済みです(`part05-lesson-decimal`、確認日2026-09-27、詳細は実機メモ参照)。

### QPJOBLOG で実行時エラーを追う(復習 + 新知見)

`WRKACTJOB`/`DSPJOB OPTION(*PGMSTK)`/`DSPJOBLOG` で止まったジョブや失敗したバッチを調べる基本手順は、04-12 と 05-06 ですでに確認済みです。今回、**新しく押さえてほしいのは次の点です。** `src/legacy/qclsrc/ju0900c.clp` の `CALL PGM(&LIB/ZA0500) PARM(&RUNMODE &MINQTY)` には、専用の `MONMSG MSGID(CPF0000)` が付いています。

```text
             CALL       PGM(&LIB/ZA0500) PARM(&RUNMODE &MINQTY)
             MONMSG     MSGID(CPF0000) EXEC(DO)
                SNDPGMMSG  MSG('JU0900C: ZA0500 ended abnormally.')
             ENDDO
```

**つまり、`ZA0500` が `RPG0907` のような異常終了メッセージを出しても、`JU0900C` はハングせず、`TXCLOF:` まで進んで最後は普通に `RETURN` します。** バッチ・ジョブは完了扱いで終わるので、**最後のメッセージだけを見ると「無事に終わった」ように見えてしまいます。** 本当の原因(`RPG0907` とその発生元)は、ジョブ・ログの途中、「JU0900C: ZA0500 ended abnormally.」より前の行に埋もれています。**最後の行だけでなく、ジョブ・ログ全体をさかのぼって読む**必要がある、という実例です。

`QPJOBLOG`(ジョブ・ログのスプール・ファイル、`WRKSPLF` で開けます)には、失敗したプログラム名・ステートメント番号(行番号)と、`RPG0907` の本文が残ります。**その情報をソース(`za0500.rpg`)の実際の行と突き合わせ、「どのフィールドを使っていた行が失敗したか」を確認するまでは、原因を決めつけないでください。** 理由は演習の直前でもう一度触れます。

### ダンプ: 死ぬ直前の値を見る

「ダンプ」とは、プログラムが異常終了した瞬間のフィールドの中身を確認する手段のことです。このレッスンでは2つの現実的な方法を使います。

1. **`STRDBG`**(05-04・05-05 ですでに使っているデバッガー): `ZA0500` にブレークポイントを置き、`JUCHUD` の入力仕様書(`JUSU` を読み込む行)の直前で値を実際に表示する方法です。**この事故は `SUB JUSU AVAIL`(計算仕様書)よりも前、レコードを読み込む入力の段階で起きます**(実機メモ参照)——ブレークポイントは計算仕様書ではなく入力仕様書の直前に置いてください。対話的な5250セッションが必要です。
2. **ジョブ・ログ自体のメッセージの跡をたどる**(非対話バッチでも使える): `RPG0907` のようなエスケープ・メッセージは、失敗した瞬間の呼び出し履歴(どのプログラムのどの行か)を残します。04-12 で見た `RPG0102`(ゼロ除算)と同様、`RPG0907` も `(C G S D F)` の応答を求める照会メッセージとして実際に届くことは実機確認済みです(`INQMSGRPY(*DFT)` により自動的に `C`(取消)が返され、プログラムはそのまま異常終了しました)。**ただし、`D` を選んでダンプが取れるかどうかまでは確認していません**。バッチ・ジョブでは誰も応答できないため、確実なのはジョブ・ログ自体を読む方法です。

`DMPCLPGM` は CL プログラム(`JU0900C`)自身の変数(`&RUNMODE`・`&MINQTY` など)をダンプするコマンドで、**`ZA0500` の RPG 側のフィールド(`JUSU`・`AVAIL` など)は見えません。** 「どちら側の変数を見ているか」を混同しないようにしてください。

### `HEX()` でゾーン10進数を読む

`src/sql/05-11-hex.sql` を使います。

```sql
SELECT JUNO, JULINE, JUSHO, JUSU, HEX(JUSU) AS JUSU_HEX, JUTNK
  FROM JUCHUD
 WHERE JUNO = 'C05119';
```

ゾーン10進数(`5S 0` のような外部記述の数値フィールド)は、**1バイトが1桁**です。各バイトの下位4ビット(ニブル)が数字(0〜9)を表し、**最後のバイトだけは上位4ビット(ゾーン・ニブル)が符号**(`C`=正/符号なし、`D`=負、`F`=符号なし)を表します。それ以外のバイトの上位ニブルは、正常なら `F` になります。

`C0511S`(このあとの実演で使うプログラム)が仕込む `'.....'`(ピリオド5個)を EBCDIC のコード表で見ると、`.` は `X'4B'` です。つまり `HEX(JUSU)` を実行すると、**`4B4B4B4B4B` という10桁の16進数が表示されます**(実機確認済み)。これを1バイトずつ見ると、各バイトの下位ニブル(数字ニブル)が `B` になっています——**`B` は0〜9のどの数字にも対応しない、無効な値です。** ゾーン10進数は数字ニブルが必ず0〜9でなければならないため、これは正常なゾーン10進数からの明確な逸脱です。

> **実機で確認済み**: この`B`という無効な数字ニブルは、実際に10進数データ・エラー(`RPG0907`。`MCH1202`はおそらくこれのMI(マシン・インターフェース)レベルでの呼び名で、OPM RPG/400からは自分自身のメッセージ体系である`RPG0907`として報告されます)を引き起こします(`part05-lesson-decimal`、確認日2026-09-27)。**ただし、これは数字ニブルが実際に無効な場合の話です。** 演習で扱う`'ABCDE'`(数字ニブルは1〜5でいずれも有効、ゾーン・ニブルは`C`)や空白(数字ニブルは0で有効、ゾーン・ニブルは`4`)は、**実機で試したこの2パターンでは、ゾーン(符号)ニブルの値が正常なパターン(`F`/`C`/`D`)からずれていても、数字ニブル自体が0〜9の範囲に収まっていればエラーにはならず、黙って(誤った値のまま)読まれてしまいました**——こちらの方が実務ではむしろ怖いパターンです(演習参照)。

比較のため、壊れていない行の `JUSU` も見ておくと、正常なゾーン10進数がどう見えるかが分かります。

```sql
SELECT JUNO, JULINE, JUSU, HEX(JUSU) AS JUSU_HEX
  FROM JUCHUD
 WHERE JUNO <> 'C05119'
 FETCH FIRST 1 ROW ONLY;
```

### 直して再実行する

原因(壊れた行)が分かったら、`TXRESET`(`tools/qclsrc/txreset.clp`)でサンプル・データベースのデータを初期状態に戻します。`TXRESET` は `JUCHUD`・`JUCHUM` などを全件削除してから初期データを入れ直すだけの処理なので、`C0511S` が作った `JUBADD` 自体には触れません(データだけを元に戻す、02-05 で作ったツールの延長です)。

> **実機で確認済み(正直な注記)**: データを戻して `JU0900C` をもう一度実行しても、**今回植え付けた `JUSU` の破損とは無関係の別のバグにより、まだ異常終了します。** `src/legacy/qclsrc/ju0900c.clp`(as-shipped)自身のヘッダー・コメントが認めているとおり、`&MINQTY` の宣言(3,0)が `ZA0500` の `*ENTRY PLIST`(5,0)と食い違っており(05-13 保守チケット1の不具合)、この食い違いだけで最初の受注の1行目から確実に `RPG0907`(統計文8100、`AVAIL COMP MINQTY`)が発生します(`part05-ju0900c-baseline`で確認済み)。**このticket1の不具合は05-13で修正を教える設計であり、今の時点ではまだ直っていません。** つまり、この「直して再実行する」手順は今の時点では `SHORT`/`OK` の正常な印字までは到達せず、**別の統計文番号(8100)を指す、別の異常終了で止まるはずです。** これ自体が良い練習になります——「メッセージが出た」ことと「今回自分が仕込んだ原因である」ことを混同せず、統計文番号でソースの行まで必ず突き合わせてください(下記の囲み参照)。05-13まで進めば、この別件も解消します。

### 障害報告書を書く

「障害報告書」といっても、堅苦しい社内様式である必要はありません。**次の4つを短くまとめるだけの習慣**です。

1. **何が起きた**(症状。いつ、何を実行したら、何が起きたか)
2. **原因**(データのどこが、なぜ壊れていたか)
3. **直した内容**(何をどう直し、どう確認したか)
4. **再発防止**(同じことが起きないために、次からどうするか)

この事故での記入例(実機で確認済みの、実際の挙動どおり):

```text
【障害報告書(例)】
何が起きた: JU0900C から ZA0500 を呼ぶバッチ処理が、受注 C05119 の行を
            読み込んだ直後に RPG0907(10進数データ・エラー)で異常終了
            した(ジョブ・ログで確認。統計文6400、JUCHUDのJUSU入力仕様書)。
原因:       検証用ファイル JUBADD(JUSU が 5A)から JUCHUD(JUSU は 5S 0)へ
            CPYF FMTOPT(*NOCHK) で複写した際、型チェックが働かず、
            文字 '.....'(ピリオド5個)の生バイト(X'4B'×5、数字ニブルが
            無効)が JUCHUD.JUSU にそのまま入っていた(HEX(JUSU) で確認)。
            SUB JUSU AVAIL(計算仕様書)より前、レコードを読み込む段階
            (入力仕様書)で落ちている点に注意。
直した内容: 該当行を削除し(TXRESET でデータを初期状態に戻し)、
            JU0900C を再実行した。ただし再実行後も、統計文8100
            (AVAIL COMP MINQTY)を指す別の異常終了が発生した——これは
            今回の件とは無関係な、05-13 保守チケット1の不具合(未修正
            のまま)によるもので、「別件」として書き分けた。
再発防止:   型の異なるファイル間の複写に FMTOPT(*NOCHK) を使うときは、
            複写後に必ず HEX() で対象列の実際のバイトを確認する。
            ゾーン10進数は「数字ニブルが0〜9かどうか」がエラーになるか
            どうかの境目であり、符号(ゾーン)ニブルの値だけを見ても
            判断できない。
```

> **もし調査の途中で見つかったメッセージが、統計文`6400`(`za0500.rpg`64行目、`JUCHUD`のI仕様書=`JUSU`の入力)ではなく統計文`8100`(`AVAIL COMP MINQTY`)を指していたら**、それは今回仕込んだ`JUSU`の破損とは**別の話**です。`ju0900c.clp`自身のヘッダー・コメントが認めているとおり、`&MINQTY`の宣言(3,0)が`ZA0500`の`*ENTRY PLIST`(5,0)と食い違っており(05-13保守チケット1の不具合そのもの、まだ未修正)、この食い違いだけで確実に別の10進数データ・エラーを引き起こします(統計文8100、実機で確認済み——上の「直して再実行する」を参照)。**そのときは、障害報告書に「別件」として書き分けてください。** どちらの行が本当に失敗したかを、ジョブ・ログの統計文番号とソースの行番号で必ず確認してから結論を書く、というのが、この教材が一番伝えたい習慣です。
>
> **囲み: 任意 `DSPJRN`(ジャーナル)** — もし対象ファイルにジャーナルが設定されていれば、`DSPJRN` で「いつ・誰が・どんな値で」その行を更新したかまで追跡できます。ただし、**このリポジトリーのサンプル・データベースにジャーナルが設定されているかどうかは、`JUCHUD` については確認していません**(`P12`: `TOKUIM` については journal 無しと確認済みですが、`JUCHUD` 自体は個別に未確認です。実機メモ参照)。ジャーナルの設定自体はこのレッスンの範囲外とし、`DSPJRN` は「環境によっては使える、もう一段深い調査手段」として紹介するだけにとどめます。

## 実演

**この実演は実機で確認済みです**(`part05-lesson-decimal`、確認日2026-09-27、詳細は実機メモ参照)。`C0511S`(`src/qclsrc/c0511s.clp`)・`JUBADD`(`src/legacy/qddssrc/jubadd.pf`)は、コンパイル(V1)・実際の`CALL`(V2)ともに確認済みです。

1. `C0511S`(CLプログラム)と、その専用コマンド(`*CMD`)を自分の `<自分のユーザー名>1` に取り込みます(02-05 で `TXSETUP` を取り込んだのと同じ要領です)。

   ```text
   CPYFRMSTMF FROMSTMF('/home/<自分のユーザー名>/ibmi-kyozai/src/qclsrc/c0511s.clp') TOMBR('/QSYS.LIB/<自分のユーザー名>1.LIB/QCLSRC.FILE/C0511S.MBR') MBROPT(*REPLACE) STMFCCSID(1208)
   CPYFRMSTMF FROMSTMF('/home/<自分のユーザー名>/ibmi-kyozai/src/qcmdsrc/c0511s.cmd') TOMBR('/QSYS.LIB/<自分のユーザー名>1.LIB/QCMDSRC.FILE/C0511S.MBR') MBROPT(*REPLACE) STMFCCSID(1208)
   ```

   ```text
   CRTCLPGM PGM(<自分のユーザー名>1/C0511S) SRCFILE(<自分のユーザー名>1/QCLSRC) SRCMBR(C0511S)
   CRTCMD CMD(<自分のユーザー名>1/C0511S) PGM(*LIBL/C0511S) SRCFILE(<自分のユーザー名>1/QCMDSRC) SRCMBR(C0511S)
   ```

2. `C0511S`(コマンド名をそのまま打つだけです。`CALL PGM(...)` は使いません)を実行し、`JUBADD` を作らせたうえで、`JUCHUD` に壊れた行を仕込みます。`CLONEDIR` の既定値はこの教材の標準のクローン先(`~/ibmi-kyozai`)と一致していますが、他のツール(`TXSETUP` など)と同じく、明示的に渡す習慣にしておくと安全です。

   ```text
   C0511S LIB(<自分のユーザー名>1) CLONEDIR('/home/<自分のユーザー名>/ibmi-kyozai')
   ```

   **なぜ `CALL PGM(C0511S) PARM(...)` ではなく専用のコマンドを経由するのか**: `CALL` にコマンド行から直接リテラルを渡すと、文字リテラルは32バイトまでしか正しく渡らないという CL の落とし穴があります(03-08 で学んだとおりです)。`C0511S` の `CLONEDIR` パラメーター(200桁)を `CALL ... PARM()` に直接書くと、この罠にかかります——`TXSETUP` などと同じ理由で、この演習でも専用のコマンドを経由します。

   「C0511S: planted a decimal data error in JUCHUD (JUNO=C05119, JULINE=1).」のメッセージを確認します。**この時点で仕込まれる`JUSU`の生バイトはピリオド5個(`X'4B'`×5)です。**

3. `JU0900C` をバッチで流します。05-06 と同じ形で、`SBMJOB` を `F4` プロンプトで埋めます。**`RUNMODE` は `*TEST`(`*LIVE` 以外)にして、`ZAIKOM` を更新しない調査モードで実行してください。**

   ```text
   CMD(CALL PGM(<自分のユーザー名>1/JU0900C) PARM('*TEST' '<自分のユーザー名>1'))
   JOB(JU0900C)
   INQMSGRPY(*DFT)
   LOG(4 00 *SECLVL)
   ```

4. `WRKSBMJOB` でジョブが終わるのを待ち、`WRKSPLF` でそのジョブの `QPJOBLOG` を開きます。「JU0900C: ZA0500 ended abnormally.」というメッセージを探し、**それより前の行**に `RPG0907`(10進数データ・エラー)の本文と、失敗したプログラム名・統計文番号があることを確認します(**統計文`6400`のはずです**)。`za0500.rpg`の64行目(`JUCHUD`のI仕様書、`JUSU`の入力)と突き合わせてください。**`ZA0500`は1行も印字せずに終了するはずです**——`SUB JUSU AVAIL`(計算仕様書)より前、レコードを読み込む段階で落ちるためです。

5. SQL(ACS の「実行 SQL スクリプト」または `RUNSQL`)で `src/sql/05-11-hex.sql` の1本目のクエリーを実行し、`HEX(JUSU)` の値(`4B4B4B4B4B`のはず)を確認します。`JUSU` 列そのものを一緒に SELECT しても、今回は`0`と表示されるはずです(SQLはこの無効な数字ニブルも黙って読んでしまいます——RPGより緩い変換規則です)。2本目のクエリーで、正常な行の `HEX(JUSU)` と見比べます。

6. `TXRESET LIB(<自分のユーザー名>1)` でデータを初期状態に戻し、`JU0900C` を(同じ `SBMJOB` で、`RUNMODE` はやはり `*TEST` のまま)もう一度実行します。**ただし、今の時点(05-13より前)では、これでも正常に`SHORT`/`OK`は印字されません**——チケット1の不具合(`&MINQTY`の桁数不一致)がまだ直っていないため、別の統計文(`8100`)を指す別の異常終了になります(上の「直して再実行する」参照)。これ自体を観察し、統計文番号で「今回の件」と「別件」を区別できることを確認してください。

7. 手順4・5の記録をもとに、上の「障害報告書を書く」の型で、自分の言葉で1通書いてください。

## 演習

**もっと怖いケースを予想する。** `C0511S` は `'.....'`(ピリオド5個)を仕込みますが、もし代わりに**文字列 `'ABCDE'`** が入っていたら、同じように `RPG0907`(10進数データ・エラー)になるでしょうか。

1. まず予想してください。理由も書いてください。
2. `HEX()` で確かめます。EBCDIC の `A`〜`E` はそれぞれ `X'C1'`〜`X'C5'` です。各バイトの下位ニブル(数字ニブル)は `1`〜`5`、最後のバイトの上位ニブル(符号ニブル)は `C` です。正常なゾーン10進数のルール(数字ニブルは0〜9、最後のバイトの符号ニブルは `C`/`D`/`F`)と照らして、有効か無効かを考えてください。

   <details><summary>考え方</summary>

   `'ABCDE'` の各バイトの数字ニブル(1〜5)は、いずれも0〜9の範囲に収まる**有効な値**です。最後のバイトの符号ニブル(`C`)も**有効な正符号**です。つまり、ゾーン10進数として見るべき2点(数字ニブルが0〜9か、符号ニブルが有効か)は、どちらも問題ありません——**このデータは、一見「文字が紛れ込んでいる壊れたデータ」に見えても、ゾーン10進数としては完全に妥当な `+12345` という値そのものです。** 実機で確認したとおり(`part05-mch1202-corrupt`、実機メモ参照)、これは`RPG0907`のようなエラーを一切起こさず、`JUSU=12345`という(本来ありえない、異常に大きい)数量として**黙って**読み込まれ、そのまま在庫引当の計算に使われてしまいます。**空白(スペース)5文字(`X'40'`、数字ニブル`0`)も同様で、こちらは`JUSU=0`として黙って読まれます。** ピリオド5個(数字ニブル`B`、無効)との違いは、**「ニブルの値が実際に0〜9の範囲を外れているかどうか」**の一点だけです——一見どちらも「壊れたデータ」に見えても、実際にエラーになるかどうかはこの1点で決まります。

   </details>

3. 余力があれば、`c0511s.clp` の**コピー**を作り(元のファイルは変更しないでください)、`'.....'` を `'ABCDE'` や空白5個(または他の値)に書き換えて、実際に同じ手順(実演2〜5)を自分で繰り返し、予想と一致するか確認してみてください。
