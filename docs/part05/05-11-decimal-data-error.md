# 05-11 障害対応: 10進数データ・エラー

> 所要時間: 75分(長め)/ 前提レッスン: 05-10 / 目標番号: 4 / 観測方法: `QPJOBLOG`・`HEX()` / 道具: 5250(SEU/STRDBG)・SQL(ACS の「実行 SQL スクリプト」または `RUNSQL`)/ 同時接続数: 5250×1 / 作る・変えるオブジェクト: `<USER>1/C0511S`(CLP)・`<USER>1/JUBADD`(検証用 PF)、`JUCHUD`(一時的に壊れた行が入る)/ DBVER: 2 / 依存するプローブ: P12, P20, P38(いずれも未実施)/ PTF 依存: なし / 容量の目安: わずか

## ゴール

- `MCH1202`(10進数データ・エラー)が、どのデータ・どの行で起きているかを `QPJOBLOG` と `HEX()` で追える。

- 原因を直して再実行し、簡単な障害報告書を書ける。

## なぜ学ぶか

**保守の現場で一番こわいのは、「エラーにならずに成功してしまう」変更です。** たとえば、形の似た2つのファイルの間でデータを移すときに `CPYF` の対象指定を誤り、本来ならエラーで止まるはずの型の不一致を `FMTOPT(*NOCHK)` で黙って通してしまった、というような話です。コマンド自体は正常終了(完了メッセージ)で終わり、誰も気づきません。**問題が表面化するのは、後になって別のプログラムがそのデータを使って算術(足し算・引き算など)をしようとしたときです。** ここでは、`JUCHUD`(受注明細)の数量列に、このやり方で壊れたデータを実際に仕込み、`MCH1202`(10進数データ・エラー)がどこでどう発生するかを、`QPJOBLOG` と `HEX()` を使って実際のバイトまで追いかけます。

## 新出

- `CPYF FMTOPT(*NOCHK)` がデータを壊す経緯(型チェックを飛ばす複写)
- `HEX()`(SQL のスカラー関数)とゾーン10進数のバイト構成
- 障害報告書(何が起きた/原因/直した内容/再発防止)の型

## 説明

### 現場でありがちな話: `*NOCHK` でデータが壊れる経緯

`CPYF` は、既定では複写元と複写先のレコード様式(フィールドの型・長さ)が一致しているかを確認し、一致しなければエラーで止まります。**`FMTOPT(*NOCHK)` を指定すると、この確認を飛ばして、バイト列をそのまま複写先に押し込みます。** 02-10 のウォームアップで既に触れたとおり、「様式が違ってもエラーにならず、列の意味を取り違えたまま複写してしまう」のが `*NOCHK` の危険性です。

具体的にどう壊れるかを、この教材のために用意した `src/legacy/qddssrc/jubadd.pf`(`JUBADD`、検証専用の「型を間違えたステージング・ファイル」)で体験します。`JUBADD` は `JUCHUD` と全く同じフィールド構成ですが、**数量を表す `JUSU` だけが `5S 0`(数値、ゾーン10進数)ではなく `5A`(文字)になっています。** `JUBADD.JUSU` に文字列 `'ABCDE'` を入れること自体は、`JUBADD` にとっては正当な操作です(文字型の列に文字を入れているだけです)。ところが、この行を `CPYF FMTOPT(*NOCHK)` で `JUCHUD` へ複写すると、**`'ABCDE'` の生のバイト列が、本来なら数字しか入らないはずの `JUCHUD.JUSU`(5S 0)にそのまま書き込まれます。** `JUCHUD` 側は何もチェックしていないので、この複写コマンド自体は正常終了します。

> **正直な注記**: `CPYF FMTOPT(*NOCHK)` がここで説明したとおりに動くこと自体は、IBM i の一般的な知識として広く説明されている内容ですが、**このリポジトリー内の一次資料や実機コンパイルでは確認できていません**(`za0510.rpg` が `QCMDEXC` について同じ扱いをしているのと同じレベルの開示です)。実機での挙動は `docs/probes.md` の `P20` が確定させる予定です。

### QPJOBLOG で実行時エラーを追う(復習 + 新知見)

`WRKACTJOB`/`DSPJOB OPTION(*PGMSTK)`/`DSPJOBLOG` で止まったジョブや失敗したバッチを調べる基本手順は、04-12 と 05-06 ですでに確認済みです。今回、**新しく押さえてほしいのは次の点です。** `src/legacy/qclsrc/ju0900c.clp` の `CALL PGM(&LIB/ZA0500) PARM(&RUNMODE &MINQTY)` には、専用の `MONMSG MSGID(CPF0000)` が付いています。

```text
             CALL       PGM(&LIB/ZA0500) PARM(&RUNMODE &MINQTY)
             MONMSG     MSGID(CPF0000) EXEC(DO)
                SNDPGMMSG  MSG('JU0900C: ZA0500 ended abnormally.')
             ENDDO
```

**つまり、`ZA0500` が `MCH1202` のような異常終了メッセージを出しても、`JU0900C` はハングせず、`TXCLOF:` まで進んで最後は普通に `RETURN` します。** バッチ・ジョブは完了扱いで終わるので、**最後のメッセージだけを見ると「無事に終わった」ように見えてしまいます。** 本当の原因(`MCH1202` とその発生元)は、ジョブ・ログの途中、「JU0900C: ZA0500 ended abnormally.」より前の行に埋もれています。**最後の行だけでなく、ジョブ・ログ全体をさかのぼって読む**必要がある、という実例です。

`QPJOBLOG`(ジョブ・ログのスプール・ファイル、`WRKSPLF` で開けます)には、失敗したプログラム名・ステートメント番号(行番号)と、`MCH1202` の本文が残ります。**その情報をソース(`za0500.rpg`)の実際の行と突き合わせ、「どのフィールドを使っていた行が失敗したか」を確認するまでは、原因を決めつけないでください。** 理由は演習の直前でもう一度触れます。

### ダンプ: 死ぬ直前の値を見る

「ダンプ」とは、プログラムが異常終了した瞬間のフィールドの中身を確認する手段のことです。このレッスンでは2つの現実的な方法を使います。

1. **`STRDBG`**(05-04・05-05 ですでに使っているデバッガー): `ZA0500` にブレークポイントを置き、`SUB JUSU AVAIL` や `AVAIL COMP MINQTY` の直前で `JUSHO`・`JUSU`・`AVAIL` の値を実際に表示する方法です。対話的な5250セッションが必要です。
2. **ジョブ・ログ自体のメッセージの跡をたどる**(非対話バッチでも使える): `MCH1202` のようなエスケープ・メッセージは、失敗した瞬間の呼び出し履歴(どのプログラムのどの行か)を残します。04-12 で見た `RPG0102`(ゼロ除算、照会メッセージ)は `(C G S D F)` の応答で `D` を選ぶとダンプが取れましたが、**`MCH1202` が同じ応答形式で来るかどうかは実機未確認です**。バッチ・ジョブでは誰も応答できないため、確実なのはジョブ・ログ自体を読む方法です。

`DMPCLPGM` は CL プログラム(`JU0900C`)自身の変数(`&RUNMODE`・`&MINQTY` など)をダンプするコマンドで、**`ZA0500` の RPG 側のフィールド(`JUSU`・`AVAIL` など)は見えません。** 「どちら側の変数を見ているか」を混同しないようにしてください。

### `HEX()` でゾーン10進数を読む

`src/sql/05-11-hex.sql` を使います。

```sql
SELECT JUNO, JULINE, JUSHO, JUSU, HEX(JUSU) AS JUSU_HEX, JUTNK
  FROM JUCHUD
 WHERE JUNO = 'C05119';
```

ゾーン10進数(`5S 0` のような外部記述の数値フィールド)は、**1バイトが1桁**です。各バイトの下位4ビット(ニブル)が数字(0〜9)を表し、**最後のバイトだけは上位4ビット(ゾーン・ニブル)が符号**(`C`=正/符号なし、`D`=負、`F`=符号なし)を表します。それ以外のバイトの上位ニブルは、正常なら `F` になります。

`C0511S`(このあとの実演で使うプログラム)が仕込む `'ABCDE'` を EBCDIC のコード表で見ると、`A`〜`E` はそれぞれ `X'C1'`〜`X'C5'` です。つまり `HEX(JUSU)` を実行すると、**`C1C2C3C4C5` という10桁の16進数が表示されるはずです**(実機未確認、下記参照)。これを1バイトずつ見ると、各バイトの上位ニブルがすべて `C` になっています。最後のバイトだけを見れば `C5`(数字5・符号 `C`)で一見それらしく見えますが、**それより前の4バイトの上位ニブルが `F` ではなく `C`** になっている点が、正常なゾーン10進数からの逸脱です。

> **正直な注記**: ゾーン10進数の「各バイトの数字ニブルが0〜9か」「最後のバイトの符号ニブルが有効か」だけを見るのか、「最後以外のバイトの上位ニブルが `F` かどうか」まで見るのか、実際に `MCH1202` を発生させる境界がどちらなのかは、**このセッションでは実機確認できていません**(`P20`)。`'ABCDE'` の各バイトの数字ニブル(1〜5)と最後のバイトの符号ニブル(`C`)はいずれも単体では有効な値なので、**本当に `MCH1202` になるかどうかは実機で確定させる必要があります。** 演習で見る「空白」のケースは、この境界にかかわらずどちらの解釈でも無効になる、より確実な例です。

比較のため、壊れていない行の `JUSU` も見ておくと、正常なゾーン10進数がどう見えるかが分かります。

```sql
SELECT JUNO, JULINE, JUSU, HEX(JUSU) AS JUSU_HEX
  FROM JUCHUD
 WHERE JUNO <> 'C05119'
 FETCH FIRST 1 ROW ONLY;
```

### 直して再実行する

原因(壊れた行)が分かったら、`TXRESET`(`tools/qclsrc/txreset.clp`)でサンプル・データベースのデータを初期状態に戻します。`TXRESET` は `JUCHUD`・`JUCHUM` などを全件削除してから初期データを入れ直すだけの処理なので、`C0511S` が作った `JUBADD` 自体には触れません(データだけを元に戻す、02-05 で作ったツールの延長です)。データを戻したら、`JU0900C` をもう一度実行し、今度は異常終了せず `SHORT`/`OK` の判定が正しく印字されることを確認します。

### 障害報告書を書く

「障害報告書」といっても、堅苦しい社内様式である必要はありません。**次の4つを短くまとめるだけの習慣**です。

1. **何が起きた**(症状。いつ、何を実行したら、何が起きたか)
2. **原因**(データのどこが、なぜ壊れていたか)
3. **直した内容**(何をどう直し、どう確認したか)
4. **再発防止**(同じことが起きないために、次からどうするか)

この事故での記入例:

```text
【障害報告書(例)】
何が起きた: JU0900C から ZA0500 を呼ぶバッチ処理が、受注 C05119 の在庫引当中に
            MCH1202(10進数データ・エラー)で異常終了した(ジョブ・ログで確認)。
原因:       検証用ファイル JUBADD(JUSU が 5A)から JUCHUD(JUSU は 5S 0)へ
            CPYF FMTOPT(*NOCHK) で複写した際、型チェックが働かず、
            文字 'ABCDE' の生バイトが JUCHUD.JUSU にそのまま入っていた
            (HEX(JUSU) で確認)。
直した内容: 該当行を削除し(TXRESET でデータを初期状態に戻し)、
            JU0900C を再実行して正常終了(SHORT/OK の判定)を確認した。
再発防止:   型の異なるファイル間の複写に FMTOPT(*NOCHK) を使うときは、
            複写後に必ず HEX() で対象列の実際のバイトを確認する。
```

> **もし調査の途中で見つかったメッセージが、`ZA0500` の `SUB JUSU AVAIL` ではなく `AVAIL COMP MINQTY` を指していたら**、それは今回仕込んだ `JUSU` の破損とは**別の話**かもしれません。`ju0900c.clp` 自身のヘッダー・コメントは、`&MINQTY` の宣言(3,0)が `ZA0500` の `*ENTRY PLIST`(5,0)と食い違っている(05-13 保守チケット1の不具合そのもの)ことを認めています。この食い違いが原因で、`ZA0500` が本来ありえないパック10進数のバイトを読んでしまい、別の10進数エラーを引き起こす可能性もゼロではありません。**そのときは、障害報告書に「別件」として書き分けてください。** どちらの行が本当に失敗したかを、ジョブ・ログとソースの行番号で必ず確認してから結論を書く、というのが、この教材が一番伝えたい習慣です。

> **囲み: 任意 `DSPJRN`(ジャーナル)** — もし対象ファイルにジャーナルが設定されていれば、`DSPJRN` で「いつ・誰が・どんな値で」その行を更新したかまで追跡できます。ただし、**このリポジトリーのサンプル・データベースにジャーナルが設定されているかどうかは確認していません**(`P12` が未実施)。ジャーナルの設定自体はこのレッスンの範囲外とし、`DSPJRN` は「環境によっては使える、もう一段深い調査手段」として紹介するだけにとどめます。

## 実演

**ここから先は未検証です。** `C0511S`(`src/qclsrc/c0511s.clp`)・`JUBADD`(`src/legacy/qddssrc/jubadd.pf`)はいずれもこのセッションで実機コンパイル・実行できていません(実機メモ参照)。

1. `C0511S` を自分の `<自分のユーザー名>1/QCLSRC` に取り込みます(02-05 で `TXSETUP` を取り込んだのと同じ要領です)。

   ```text
   CPYFRMSTMF FROMSTMF('/home/<自分のユーザー名>/ibmi-kyozai/src/qclsrc/c0511s.clp') TOMBR('/QSYS.LIB/<自分のユーザー名>1.LIB/QCLSRC.FILE/C0511S.MBR') MBROPT(*REPLACE) STMFCCSID(1208)
   ```

   ```text
   CRTCLPGM PGM(<自分のユーザー名>1/C0511S) SRCFILE(<自分のユーザー名>1/QCLSRC) SRCMBR(C0511S)
   ```

2. `C0511S` を実行し、`JUBADD` を作らせたうえで、`JUCHUD` に壊れた行を仕込みます。`CLONEDIR` の既定値はこの教材の標準のクローン先(`~/ibmi-kyozai`)と一致していますが、他のツール(`TXSETUP` など)と同じく、明示的に渡す習慣にしておくと安全です。

   ```text
   CALL PGM(<自分のユーザー名>1/C0511S) PARM('<自分のユーザー名>1' '/home/<自分のユーザー名>/ibmi-kyozai')
   ```

   「C0511S: planted a decimal data error in JUCHUD (JUNO=C05119, JULINE=1).」のメッセージを確認します。

3. `JU0900C` をバッチで流します。05-06 と同じ形で、`SBMJOB` を `F4` プロンプトで埋めます。**`RUNMODE` は `*TEST`(`*LIVE` 以外)にして、`ZAIKOM` を更新しない調査モードで実行してください。**

   ```text
   CMD(CALL PGM(<自分のユーザー名>1/JU0900C) PARM('*TEST' '<自分のユーザー名>1'))
   JOB(JU0900C)
   INQMSGRPY(*DFT)
   LOG(4 00 *SECLVL)
   ```

4. `WRKSBMJOB` でジョブが終わるのを待ち、`WRKSPLF` でそのジョブの `QPJOBLOG` を開きます。「JU0900C: ZA0500 ended abnormally.」というメッセージを探し、**それより前の行**に `MCH1202` の本文と、失敗したプログラム名・行番号があることを確認します。`za0500.rpg` の該当行と突き合わせ、どのフィールド(`JUSU` か `MINQTY` か)が関係していたかを記録してください。

5. SQL(ACS の「実行 SQL スクリプト」または `RUNSQL`)で `src/sql/05-11-hex.sql` の1本目のクエリーを実行し、`HEX(JUSU)` の値を確認します。**`JUSU` 列そのものを一緒に SELECT すると、壊れた行では表示が乱れる(またはエラーになる)可能性があります。その場合は `HEX(JUSU)` だけを SELECT し直してください。** 2本目のクエリーで、正常な行の `HEX(JUSU)` と見比べます。

6. `TXRESET LIB(<自分のユーザー名>1)` でデータを初期状態に戻し、`JU0900C` を(同じ `SBMJOB` で、`RUNMODE` はやはり `*TEST` のまま)もう一度実行して、正常に `SHORT`/`OK` が判定されることを確認します。

7. 手順4・5の記録をもとに、上の「障害報告書を書く」の型で、自分の言葉で1通書いてください。

## 演習

**空白が入った場合を予想する。** `C0511S` は文字列 `'ABCDE'` を仕込みますが、もし代わりに**空白(スペース)が5文字**入っていたら、同じように `MCH1202` になるでしょうか。

1. まず予想してください。理由も書いてください。
2. `HEX()` で確かめます。EBCDIC の空白1文字は `X'40'` です。上位ニブル(ゾーン)は `4`、下位ニブル(数字)は `0` です。この空白が「最後以外のバイト」に入った場合と「最後のバイト」に入った場合、それぞれ、正常なゾーン10進数のルール(数字ニブルは0〜9、最後のバイトの符号ニブルは `C`/`D`/`F`)と照らして、有効か無効かを考えてください。

<details><summary>考え方</summary>

`X'40'` の下位ニブルは `0` で、これは有効な数字です。しかし上位ニブルは `4` で、**これは「最後以外のバイト」として見た場合の正しいゾーン `F` でも、「最後のバイト」の符号として有効な `C`/`D`/`F` でもありません。** どちらの位置に来ても、上位ニブルとしては無効な値です。したがって、空白5文字が `JUSU` に入った場合も、`'ABCDE'` のケースと同じ理由(数字であるべき/符号であるべき位置に無効なニブルがある)で `MCH1202` になると予想できます。**ただし、これも実機で確定した話ではありません**(上の「正直な注記」を参照)。

</details>

3. 余力があれば、`c0511s.clp` の**コピー**を作り(元のファイルは変更しないでください)、`'ABCDE'` を空白5個(または他の値)に書き換えて、実際に同じ手順(実演2〜5)を自分で繰り返し、予想と一致するか確認してみてください。

- **`C0511S`(`src/qclsrc/c0511s.clp`)には、このレッスンを書く過程で2件の実装ミスが見つかり、修正済みです。**
