## 課題

各チケットには「起票者」「症状」「調査・修正の進め方」「ヒント」が書かれています。**原因はチケット自身には書いていません。** 05-07(影響調査)・05-08/05-09/05-10(改修)・05-11(障害対応)・05-12(移送)で身につけた手順を、実際の症状から自分で辿ってください。

進め方の目安(どのチケットも共通):

1. 影響調査(05-07)で、関係するオブジェクトと呼び出し関係を確認する。
2. 原因を特定する。ソース(`src/legacy/`)を実際に読み、思い込みで判断しない。
3. 修正を検討する。**「これで直る」と決めつける前に、その修正が本当に成立するかを確認する**(チケット2のヒントを参照)。
4. 修正し、回帰確認する(05-08)。
5. 移送・切り戻しの手順を一度たどる(05-12)。

## 説明: それぞれのチケットの性格の違い

3本は難易度も性格も異なります。着手前に、何を試されているかを掴んでおいてください。

### チケット1: パラメーター不一致(比較的わかりやすい)

`JU0900C` の `CALL PGM(.../ZA0500) PARM(&RUNMODE &MINQTY)` と、`ZA0500` の `*ENTRY PLIST` を実際に見比べてください。**個数は合っていても、長さ・小数点位置が食い違っていれば、コンパイルは通ってしまいます。** 03-08 で学んだとおりです。どちらの宣言を直すべきかは、両方の値の実際の使われ方(`MINQTY` が安全在庫のしきい値としてどれだけの桁数を必要とするか)から判断してください。「3桁に合わせる」「5桁に合わせる」のどちらでも、**両方が一致してさえいれば**正解です(採点表を参照)。

### チケット2: 対策の実現可能性そのものが調査対象

これが3本の中で一番手強いです。「`OPNQRYF` の並び替え基準を`JUDATE`に変えるだけ」という一見もっともらしい対策が、**本当に成立するかどうかを確認すること自体が、このチケットの核心**です。ヒントにあるとおり、`ZA0500` は `JUCHUD`(1次ファイル)と `JUCHUM`(2次ファイル)のマッチング・レコード処理(`M1`/`MR`)を使っており、これは「両方のファイルが、同じ一致フィールドの昇順(または降順)で揃っていること」を前提にしています(05-03 で学んだとおりです)。

- `JUCHUD` に受注日(`JUDATE`)というフィールドが**実在するかどうか**を、まず自分で確認してください(`db/v1/juchud.pf` を見れば分かります)。
- 実在しない場合、「`OPNQRYF` の`KEYFLD`を`JUDATE`に変える」という対策は、そもそも**そのままでは書けません**。
- では、どう直せば受注日順の引当が実現できるか。複数の設計が考えられます。それぞれの利点・欠点を検討し、**実機で確認しないと確信が持てない部分がどこか**を明示してください。

「単純な並び替えでは成立しないと突き止め、その理由を説明できた」ところまでが、このチケットの最低到達点です。実際に動く設計まで踏み込めれば、それは加点対象です(採点表を参照)。

### チケット3: エラー処理の対象範囲を見極める

`*PSSR` を追加すれば直る、と決めつけないでください。ヒントにあるとおり、**エラーがどの段階(ファイルのオープン段階か、それより後か)で起きているかを先に特定する**必要があります。04-06 で確認したとおり、`*PSSR` はすべてのエラーを捕まえられるわけではありません(オープン時の例外は `*PSSR` を経由しないケースがあります)。エラーを捕まえたあと、RPG III から直接 CL コマンドは呼べないため、呼び出し元への通知には `QCMDEXC`(05-04 で読んだ技法)を使います。**ただし実機で確認済みのとおり、`SNDPGMMSG` は `QCMDEXC` 経由では実行できません**(`CPD0031`。呼び出し元が RPG でも CL でも、どんな深さでも実行できないと確認済みです。第7部`jucutl.rpgle`の実機検証で見つかった発見で、詳細は`docs/probes.md`とza0510.rpgのヘッダー・コメントを参照)。`QCMDEXC` で実行するコマンド自体は、`IBM` のコマンド解説ページの「Where allowed to run」欄が `*ALL` になっているものを選ぶ必要があります(`CHGDTAARA` はこれに該当し、05-04 の模範解答が採用しています)。`JUMSGF`(第3部で作った自分のメッセージ・ファイル)への新しいメッセージ ID の追加は、それ自体はメッセージの「内容」を登録するだけで、実際に送る手段(`SNDPGMMSG` または `QMHSNDPM`)が別途必要になる点に注意してください。

## 実演: 調査の出発点

各チケットについて、まず次を実行してから、自分の調査に進んでください(すべて05-07で使った手順です)。

1. `DSPPGMREF PGM(<自分のライブラリー>/*ALL) OUTPUT(*OUTFILE) OUTFILE(QTEMP/PGMREF)` で呼び出し関係を確認する。
2. 疑わしいソース(`src/legacy/qrpgsrc/za0500.rpg`・`src/legacy/qclsrc/ju0900c.clp`)を実際に開き、`*ENTRY PLIST`・`CALL`・F仕様書・条件付きの計算(C仕様書)を読む。
3. `STRDBG` でステップ実行し、実際に何が起きているかを目で追う(チケット1・3で特に有効です)。

## 実演: TXCHECK でオブジェクトの存在を機械的に確認する

`TXCHECK`(オブジェクトの存在・型だけを見る検証ツール。[付録E](../appendix/e-naming.md)参照)を、このレッスンで初めて実際に使います。**`TXSETUP`(02-05)は `TXCHECK`/`TXCKM` を作りません**——`TXLEGACY` の完了メッセージが「`TXCHECK (05-13) can later confirm these objects still exist.`」と予告しているだけで、実際にコンパイルする手順はこれまでどのレッスンにもありませんでした。まずここで自分のコピーにコンパイルします。

**TXCHECK v1 の限界を先に理解しておいてください**: `tools/qclsrc/txcheck.clp` 自身のコメントが明記するとおり、v1スコープは `CHKOBJ` によるオブジェクトの存在・型の確認だけです。**`ZA0500`/`JU0900C` は05-01の `TXLEGACY` の時点で既に存在するため、チケットに何も手を付けていなくても、このチェックは PASS します。** つまりこれは「チケットのロジックが正しく直っているか」を確認する道具ではありません。「オブジェクトを消してしまっていないか・コンパイルが割れたまま放置していないか」を確かめる、ごく軽い存在チェック(スモーク・テスト)です。**ロジックの正しさは、演習の採点表と05-08の回帰確認手法で自分の目で確かめてください。**

1. `TXCKM`(チェック項目の台帳)・`TXCHECK`(本体)・その `*CMD` をまだコンパイルしていなければ、コンパイルします(`tools/qclsrc/txcheck.clp` 自身の指示どおり、`TXCKM` を先にコンパイルしてください——`TXCHECK` の `DCLF` が実在する `TXCKM` の項目定義を必要とします)。

   ```text
   ADDPFM FILE(<自分のユーザー名>1/QDDSSRC) MBR(TXCKM) SRCTYPE(PF) TEXT('TXCHECK manifest')
   ADDPFM FILE(<自分のユーザー名>1/QCLSRC) MBR(TXCHECK) SRCTYPE(CLP) TEXT('Run per-lesson checks')
   ADDPFM FILE(<自分のユーザー名>1/QCMDSRC) MBR(TXCHECK) SRCTYPE(CMD) TEXT('TXCHECK command')
   ```

   (`system "CPYFRMSTMF ..."` で `tools/qddssrc/txckm.pf`・`tools/qclsrc/txcheck.clp`・`tools/qcmdsrc/txcheck.cmd` を取り込む手順は、05-01 の `TXLEGACY` 取り込み手順と同じ形です。)

   ```text
   CRTPF FILE(<自分のユーザー名>1/TXCKM) SRCFILE(<自分のユーザー名>1/QDDSSRC) SRCMBR(TXCKM)
   CRTCLPGM PGM(<自分のユーザー名>1/TXCHECK) SRCFILE(<自分のユーザー名>1/QCLSRC) SRCMBR(TXCHECK)
   CRTCMD CMD(<自分のユーザー名>1/TXCHECK) PGM(*LIBL/TXCHECK) SRCFILE(<自分のユーザー名>1/QCMDSRC) SRCMBR(TXCHECK)
   ```

2. `TXCKM` にこのレッスンの行を登録します(`STRSQL` または `RUNSQL`)。二重登録を避けるため、まず同じ `LESSON` の行を消してから入れ直します。

   ```sql
   DELETE FROM <自分のユーザー名>1/TXCKM WHERE LESSON = '05-13';

   INSERT INTO <自分のユーザー名>1/TXCKM
     (LESSON, SEQNBR, OBJNAME, OBJTYPE, OBJATTR, CKDESC)
   VALUES
     ('05-13', 10, 'ZA0500',  '*PGM', ' ', 'ZA0500 still exists and compiles'),
     ('05-13', 20, 'JU0900C', '*PGM', ' ', 'JU0900C still exists and compiles');
   ```

3. `TXCHECK` を、`*CMD` 経由で実行します(`CALL PGM(...) PARM(...)` ではありません。[付録E](../appendix/e-naming.md)が説明する32バイト・リテラルの罠を避けるためです)。

   ```text
   TXCHECK LESSON('05-13') LIB(<自分のユーザー名>1)
   ```

4. ジョブ・ログに `TXCHECK PASS: ...` が2件と、`TXCHECK: lesson 05-13 - 2 passed, 0 failed.` という要約が出れば、少なくとも「両方のオブジェクトが存在し、正しい型でコンパイルされている」ことが機械的に確認できたことになります。`FAIL` が出た場合は、該当するオブジェクトを削除してしまったか、まだ一度もコンパイルしていない可能性があります。

## 実機メモ

- 旧システム一式(`FLDREF`・`TK0100D`・`MN0000D`・`TK0100`・`JU0300`・`ZA0500`・`ZA0510`・`JU0900C`・`MN0000C`・`C0511S`・`JUBADD`)は、`part05-legacy-probe`(確認日2026-09-26、CONFIRMED SUCCESS、2回接続)で**V1**(コンパイルのみ、Highest Severity 00、`part05-legacy-probe DONE`まで到達)まで確認済みです。さらに `part05-txlegacy-exec`(確認日2026-09-27、CONFIRMED SUCCESS)で、`TXLEGACY`自身がCLONEDIR配下の実ツリーから自分で`CPYFRMSTMF`するという本来の経路で`FLDREF`・`FLDREFR`・`TK0100D`・`MN0000D`・`TK0100`・`JU0300`・`ZA0500`・`JU0900C`・`MN0000C`を新規作成し、`TXLEGACY: done.`まで到達したことも確認済みです。
- チケット1のバグそのものの実行結果は `part05-ju0900c-baseline`(確認日2026-09-27、CONFIRMED SUCCESS)で**V2**まで確認済みです。`JU0900C`から`ZA0500`へのas-shipped(チケット未修正)実行チェーンを実際に`CALL`したところ、`MINQTY`の桁数不一致は「まれに」ではなく**毎回確実に**1行目で発生しました。`ZA0500`は1行も印字しないまま`RPG0907`(decimal-data error)→`RPG9001`→`CPF9999`(機能検査)という経路で**異常終了**し(`JU0900C: ZA0500 ended abnormally.`)、この異常終了自体は`JU0900C`自身が元々持っている`MONMSG`(`CALL PGM(&LIB/ZA0500) PARM(&RUNMODE &MINQTY)`直後の`MONMSG MSGID(CPF0000)`、ハーネスが追加したものではない)で捕捉されるため、検証全体はハングせず`part05-ju0900c-baseline DONE`まで正常に到達しました。上の「課題」節にあるチケット1のリンク見出し(および`src/legacy/tickets/ticket1.md`本文)の「まれに」という頻度の前提は、この実測(毎回確実に発生)とは食い違っています。
- `ZA0510`の`*PSSR`/`QCMDEXC`/`CHGDTAARA(*LDA)`実行経路は `part05-qcmdexc-runtime`(確認日2026-09-27、CONFIRMED SUCCESS)で**V2**まで確認済みです(検証専用の複製`ZA0510V`——`TABPCD`の最終要素だけ書き換え、それ以外は`ZA0510`と完全に同一——で発火させ、同一ジョブ内の`VLDA`ヘルパーが`*LDA`の内容を正しく読み戻せることを確認しました)。
- **本チェックポイントの模範解答は、`part05-13-tickets`(確認日2026-09-27、CONFIRMED SUCCESS)でチケット1+3の組み合わせがV2まで確認済みです。** `solutions/05-13/ju0900c-ticket1.clp`(`&MINQTY LEN(5 0)`)+`solutions/05-13/za0500-ticket3.rpg`(チケット3の`*PSSR`、チケット1のバグは意図的に未修正のまま)を実際に組み合わせて`CALL`したところ、`RUNCOMBO`が正確に12行を印字(`OK`10・`SHORT`2・`NOTFOUND`0、手計算表と完全一致)、`RPG0907`は一切出ませんでした——**チケット1の修正が`part05-ju0900c-baseline`で確認済みの`RPG0907`を実際に解消することが実機で確定しました。** 追加のパリティ確認(`JU0900C`を介さず`ZA0500`を直接`CALL`する`RUNZA0500H`)も、`ju0900c.clp`系ファイルの`CLOF OPNID(JUCHUD)`修正後は成功し、`RUNCOMBO`と1バイトも違わない同一の12行を印字することを確認しています(チケット1採点表の「テスト・ハーネス経由と`JU0900C`経由の両方で同じ結果になることを確認した」を満たす)。
- **チケット3の`*PSSR`/`QCMDEXC`/`CHGDTAARA`機構自体は、`part05-13-pssr`(確認日2026-09-27、CONFIRMED SUCCESS)で、本物の実行時エラー(チケット1のMINQTYバグ`RPG0907`、`ZA0510V`のような手で仕込んだ発火条件ではない)から実際に発火し、`*LDA(21,20)=[ZA0500 SHORT ERR    ]`という証拠を正しく残すことを確認済みです。** ただし**この採点表の「再現確認」の文言(「05-11の手法を応用して」)を文字どおりには満たしていません**——05-11自身の破損技法(`CPYF FMTOPT(*NOCHK)`によるゾーン10進数破損)は、6パターン試した結果いずれも10進数データ・エラーを一切起こさないことが実機で確定したため(`part05-mch1202-corrupt`・`part05-decimal-screen`、`docs/probes.md`参照、05-11自身の実機メモにも記録)、確認できたのは「`*PSSR`機構自体が実際に動く」という前提条件にとどまり、「05-11の手法での再現」そのものではありません。この採点表の文言自体をどう扱うか(実測に合わせて緩めるか、05-11本文の書き直し後に別の再現経路を探すか)は、P4/Step 2-Cで判断が必要です。

- `TXCKM`(マニフェスト表、DDS)は `part05-txcheck-probe`(確認日2026-09-26、CONFIRMED SUCCESS、3回接続)で、コンパイル(メッセージ0件)だけでなく、自己参照チェック行を実際に`INSERT`し、`TXCHECK`の`DCLF`経由でその行を正しく読み戻せたこと(`TXCHECK PASS: TXCKM manifest exists (self-check)`)まで、実際の読み書きを含めて**V2**確認済みです。`TXCHECK`本体(CL)も同じ接続で**V2**(コンパイルと自己参照チェックの実行、`1 passed, 0 failed`)まで確認済みです。**ただし、これは`CALL PGM(&LIB/TXCHECK) PARM(...)`という直接呼び出し形での確認であり(`part07-05-checkpoint`での再利用時も同じくCALL形式でした)、上の手順3が使う`*CMD`ラッパー(`tools/qcmdsrc/txcheck.cmd`)自体は、どの実機検証でもまだ一度もコンパイル・実行されていません。** このレッスン固有の2行(`ZA0500`・`JU0900C`の存在チェック)を対象にした実行も未検証(2026-09-27時点)のままです。
