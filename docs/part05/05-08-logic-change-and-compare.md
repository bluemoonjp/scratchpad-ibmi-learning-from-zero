## なぜ学ぶか

**「直した」と「壊していない」は別の主張です。** 保守では、意図した1箇所の変更のつもりが、思わぬ副作用で別の行まで変わってしまうことがあります。**ゴールデン・マスター・テスト**は、変更前の「既知の正しい出力」を保存しておき、変更後の出力と機械的に突き合わせることで、この主張を検証する技法です。このレッスンでは、`tools/qclsrc/txsnap.clp`(`TXSNAP`)と `src/sql/05-08-compare.sql` という、すでに用意されている道具を実際に読み、使い、`JU0300` に税込み列を1つ追加する改修で通しの練習をします。この手法は 05-13 のチェックポイント(チケット1〜3の回帰確認)でもそのまま使います。

## 新出

### 中核(3つ)

- **ゴールデン・マスター**: 変更前の「既知の正しい出力」を保存しておき、変更後の出力と突き合わせる回帰テストの技法。**比較そのものより、「比較の対象を公平にそろえること」の方が難しい**、というのがこのレッスンの主題です。
- **`CPYSPLF` + SQL の `EXCEPT`**: `TXSNAP` はスプール・ファイルを `CPYSPLF` でデータベース・ファイルのメンバーに複写し、`05-08-compare.sql` は2つのメンバーを `EXCEPT` で突き合わせます。
- **`CMPPFM` / `git diff`**: `CMPPFM` は2つのメンバーを画面上で比較する 5250 ネイティブの道具(`EXCEPT` の対話的な代替)。`git diff` はデータではなく**ソース・コード自体**の差分を見る、まったく別の観点の確認です。

### 読めればよい項目

- `OVRPRTF SPLFNAME(...)`: 印刷装置ファイルの出力先スプール・ファイル名を上書きする。
- `CHGJOB DATE(...)`: ジョブの日付を固定する(P15 で確認予定)。

## 説明

### ゴールデン・マスターと、「公平な比較」の難しさ

ゴールデン・マスター・テストの考え方自体は単純です。**変更前に一度実行して結果を保存し(BEFORE)、変更後にもう一度実行して結果を保存し(AFTER)、2つを突き合わせる。** 難しいのは比較の理屈ではなく、**BEFORE と AFTER が「変更した箇所以外は完全に同じ条件」で実行されたと言えるかどうか**です。条件がそろっていなければ、比較結果は「コードの変更による差分」なのか「実行条件の違いによる差分」なのか区別できません。このレッスンでは、`JU0300` というプログラムを例に、そろえるべき条件を具体的に見ていきます。

### ジョブ日付を固定する理由(一般原則として)

多くの業務帳票は、印刷時の実行日をヘッダーなどに出力します。BEFORE を月曜に、AFTER を火曜に実行したら、コードを一切変えていなくても**日付の桁だけが違う**という誤った差分が出てしまいます。`CHGJOB DATE(...)` でジョブの日付を固定してから両方を実行するのは、この種の「実行環境そのものが持つ、コードと無関係な入力」を消すための一般的な習慣です。

**正直な注記**: `src/legacy/qrpgsrc/ju0300.rpg` の O 仕様書を実際に確認すると、`JU0300` は `UDATE`(ジョブ日付)を一切印刷しておらず、この帳票自体には「日付のせいで差分が出る」リスクは**ありません**。それでもここでジョブ日付固定を教えるのは、**実務で扱う帳票の多くは日付を印刷するため**、この習慣自体は一般原則として身につけておく価値があるからです。`JU0300` については、日付より先に、次の「本当に効く隠れた入力」を疑ってください。

### `JU0300` 固有の、本当に効く隠れた入力: `*LDA`

`ju0300.rpg` の I 仕様書には `UDS`(`*LDA` を自動読み込みするデータ構造)があり、**プログラム開始時に `*LDA` の11〜16桁目を `FTOK` という得意先コード・フィルターとして自動的に読み込みます。** `FTOK` が空白でなければ、一致しない得意先の明細行(`DTL`)の印刷が抑制されます。もし BEFORE と AFTER で `*LDA` の中身が違っていたら(例えば直前に別のプログラムを試して `*LDA` に何か書き込んでしまった場合)、**コードを一切変えていなくても、明細行の出方が変わってしまいます。** これは 05-07 で扱った「`QTEMP` はジョブ・スコープ」という話と同じ種類の注意で、`*LDA` もジョブに紐づく状態です。BEFORE と AFTER を同じジョブの中で、`*LDA` に何も書き込まずに連続実行すれば、この心配は避けられます。

### `OVRPRTF SPLFNAME(...)` — スプール・ファイルに分かりやすい名前を付ける

`TXSNAP` の `SPLF` パラメーターは既定で `QSYSPRT`(既定のスプール・ファイル名)を対象にしますが、`WRKSPLF` で見たときに `QSYSPRT` が何本も並ぶと紛らわしくなります。`OVRPRTF FILE(QSYSPRT) SPLFNAME(JU0300B) HOLD(*YES)` のように上書きしてから `CALL PGM(JU0300)` すると、スプール・ファイルに `JU0300B` という分かりやすい名前が付き、`HOLD(*YES)` で誤って実際の出力装置に流れることも防げます。**この上書きを使った場合は、`TXSNAP` を呼ぶときに `SPLF(JU0300B)` を明示してください**(既定の `QSYSPRT` のままでは、上書きした名前のスプールを見つけられません)。

### `TXSNAP`(`CPYSPLF`)を読む

`tools/qclsrc/txsnap.clp` は、指定した `LABEL`(`BEFORE`/`AFTER` など)を使って、**同じ物理ファイル `TXSNAPT` の別々のメンバー**にスプール・ファイルを複写します。

```text
CPYSPLF    FILE(&SPLF) TOFILE(&LIB/TXSNAPT) JOB(&JOB) +
             SPLNBR(&SPLNBR) TOMBR(&LABEL) MBROPT(*REPLACE)
```

**`TXSNAPT` は `CPYSPLF` 自身では作られません。** IBM の公式 `CPYSPLF` リファレンスで確認済みです: `TOFILE` に指定したデータベース・ファイルが実在しないと、コピー自体が失敗します(「the copy will fail」)。自動的に作られるのは**メンバー**(`TOMBR`)だけです。そのため、このレッスンでは最初の `TXSNAP` 呼び出しより前に、あらかじめ `CRTPF FILE(<USER>1/TXSNAPT) RCDLEN(133) MAXMBRS(*NOMAX)` を1回実行しておきます。`MAXMBRS(*NOMAX)` にしておくのは、`BEFORE` の次に `AFTER` という2つ目のメンバーを追加できるようにするためです(既定の `MAXMBRS(1)` のままだと2つ目のメンバー追加で失敗します)。

### `src/sql/05-08-compare.sql` を読む — 見つかった不具合と直した理由

このスクリプトの当初のバージョンには、**SQL としての誤りがありました。** `SELECT * FROM TXSNAPT BEFORE` の `BEFORE` は、標準 SQL では**そのテーブル参照の相関名(別名)**であって、**`BEFORE` というメンバーを選ぶ指定ではありません。** つまり当初の `EXCEPT` は、`BEFORE` 側も `AFTER` 側も**同じ既定メンバー**を読んでいたことになり、どんな変更を加えても常に「差分なし」と誤判定してしまう状態でした。Db2 for i で特定のメンバーを SQL から読むには、`CREATE ALIAS` を使います。

```sql
CREATE OR REPLACE ALIAS QTEMP.SNAPB FOR <自分のライブラリー>.TXSNAPT (BEFORE);
CREATE OR REPLACE ALIAS QTEMP.SNAPA FOR <自分のライブラリー>.TXSNAPT (AFTER);
```

`<自分のライブラリー>` を明示的に付けている点に注意してください。**ライブラリー名を省かないでください** — ACS の SQL 接続は既定で自分のユーザー・プロファイルと同じ名前のスキーマを探すため(SQL naming)、`FOR TXSNAPT (BEFORE)` のように書くと `<USER>1.TXSNAPT` ではなく別のスキーマを探しにいき、見つからずに失敗する可能性があります。また `CREATE OR REPLACE ALIAS` にしているのは、このスクリプトを2回目以降(演習の編集コード変更など)に再実行したときに、既に存在するエイリアスに対する「オブジェクトが既に存在する」エラーを避けるためです。

これで `QTEMP.SNAPB`/`QTEMP.SNAPA` が、それぞれ本当に `BEFORE`/`AFTER` メンバーを指すようになります(このレッスンを書く時点で `src/sql/05-08-compare.sql` はこの形に修正済みです)。**「比較が常に成功する」ことと「比較の仕組みが正しく壊れた場合を検出できる」ことは別**です。今回の税込み列の追加そのものが、その確認を兼ねています。**もし `AFTER にしかない行` の `EXCEPT` が空(0行)で返ってきたら、それは「差分なし」ではなく「比較の仕組みが壊れている」ことを疑ってください**(このスクリプトの当初のバージョンが実際にそうでした)。`05-08-compare.sql` には、両エイリアスの `COUNT(*)` を先に見るステップもコメントとして入っています(件数が明らかにおかしい場合の早期発見用です)。

```sql
SELECT * FROM QTEMP.SNAPB EXCEPT SELECT * FROM QTEMP.SNAPA;  -- BEFORE にしかない行
SELECT * FROM QTEMP.SNAPA EXCEPT SELECT * FROM QTEMP.SNAPB;  -- AFTER にしかない行
```

意図した変更(今回は税込み列の追加)が1箇所だけなら、2つ目の `EXCEPT` の結果は**その新しい列を含む行だけ**であるはずです。それ以外の行が混じっていたら、意図しない副作用です。

### `CMPPFM` — 5250 ネイティブの代替

`05-08-compare.sql` の末尾のコメントにあるとおり、`CMPPFM`(物理ファイル・メンバー比較)は、SQL を使わずに5250の画面上で2つのメンバーを直接比較できるコマンドです。ACS が使えない・SQL より5250の画面の方が慣れている、という場面での代替手段として覚えておいてください。

### `git diff` — 出力ではなくソースそのものを見る

このリポジトリー自体が git のクローンです。**出力の比較(`EXCEPT`/`CMPPFM`)が「結果が変わったこと」を示すのに対し、`git diff`(または `git diff -- src/legacy/qrpgsrc/ju0300.rpg` のようにパスを絞った形)は「コードの何が変わったか」を直接示します。** 両方を確認することで、「意図した1箇所のソース変更が、意図した1箇所の出力変更だけを生んだ」という主張を、**コードの側からも出力の側からも**裏付けられます。

## 実演

**05-01 の `TXLEGACY` で旧システムが `<USER>1` に投入済みであること、05-07 で `JUCHUM` 周りの影響範囲を確認済みであることを前提にします。ここから先の手順は実機未検証です(実機メモ参照)。**

0. **`TXSNAP` を初めて使うので、まずコンパイルします**(02-05 で `TXSETUP` を初めて使ったときと同じ手順です)。`<USER>1/QCMDSRC` がまだ無ければ `CRTSRCPF FILE(<USER>1/QCMDSRC) RCDLEN(92)` を先に実行してください。

   ```text
   ADDPFM FILE(<USER>1/QCLSRC) MBR(TXSNAP) SRCTYPE(CLP) TEXT('Snapshot a spooled file')
   ADDPFM FILE(<USER>1/QCMDSRC) MBR(TXSNAP) SRCTYPE(CMD) TEXT('TXSNAP command')
   ```

   SSH で(`~/ibmi-kyozai` が最新であることを確認してから)、`tools/qclsrc/txsnap.clp`・`tools/qcmdsrc/txsnap.cmd` を、02-05 と同じ `CPYFRMSTMF` で `<USER>1/QCLSRC(TXSNAP)`・`<USER>1/QCMDSRC(TXSNAP)` に取り込み、5250 に戻って次をコンパイルします。

   ```text
   CRTCLPGM PGM(<USER>1/TXSNAP) SRCFILE(<USER>1/QCLSRC) SRCMBR(TXSNAP)
   CRTCMD CMD(<USER>1/TXSNAP) PGM(*LIBL/TXSNAP) SRCFILE(<USER>1/QCMDSRC) SRCMBR(TXSNAP)
   ```

1. `TXSNAPT` をあらかじめ作成します(複数メンバーに備える。理由は上の説明を参照)。

   ```text
   CRTPF FILE(<USER>1/TXSNAPT) RCDLEN(133) MAXMBRS(*NOMAX) TEXT('TXSNAP snapshots')
   ```

2. **1つのジョブの中で**、ジョブ日付を固定し、`JU0300`(変更前)を実行して BEFORE を保存します(`*LIBL` の罠を避けるため、`ADDLIBLE` してから同一ジョブでライブラリー修飾なしの `CALL` を使うか、`CALL PGM(<USER>1/JU0300)` のように毎回ライブラリー修飾してください)。`CHGJOB DATE(...)` に渡す日付の書式(`MMDDYY` か `YYMMDD` か等)は、ジョブの `DATFMT` 属性に従います。`DSPJOB OPTION(*DFNA)` などで自分のジョブの日付書式を先に確認し、それに合わせてください(未確認、P15 依存)。

   ```text
   ADDLIBLE LIB(<USER>1) POSITION(*FIRST)
   CHGJOB DATE(<自分のジョブの書式に合わせた日付>)
   OVRPRTF FILE(QSYSPRT) SPLFNAME(JU0300B) HOLD(*YES)
   CALL PGM(JU0300)
   TXSNAP LABEL(BEFORE) LIB(<USER>1) SPLF(JU0300B)
   DLTOVR FILE(QSYSPRT)
   ```

3. `JU0300` のソースに、税込み列を追加します(次項)。

4. **同じジョブの中で**、再コンパイルし、AFTER を保存します。

   ```text
   CRTRPGPGM PGM(<USER>1/JU0300) SRCFILE(<USER>1/QRPGSRC) SRCMBR(JU0300)
   OVRPRTF FILE(QSYSPRT) SPLFNAME(JU0300B) HOLD(*YES)
   CALL PGM(JU0300)
   TXSNAP LABEL(AFTER) LIB(<USER>1) SPLF(JU0300B)
   DLTOVR FILE(QSYSPRT)
   ```

5. `src/sql/05-08-compare.sql` を ACS の「実行 SQL スクリプト」で実行し、`<自分のライブラリー>` を自分のライブラリー名(`<USER>1`)に置き換えてから、`CREATE OR REPLACE ALIAS` → 行数確認 → `EXCEPT` の順に結果を見ます。`AFTER にしかない行` の `EXCEPT` に、**`CUST TOTAL` の行(税込み列が増えた行)だけ**が出て、`DTL`/`DATE TOTAL`/`GRAND TOTAL` の行が1件も出ないことを確認してください。もし `DTL` 行まで差分に出ていたら、`*LDA` の `FTOK` が BEFORE/AFTER で違っていないか疑ってください。逆に **`EXCEPT` の結果が2つとも0行だったら「差分なし」と即断せず、比較の仕組み自体(エイリアスが本当に別々のメンバーを指しているか)を先に疑ってください。**

6. `CMPPFM FILE(<USER>1/TXSNAPT) MBR(BEFORE) TOFILE(<USER>1/TXSNAPT) TOMBR(AFTER)` のような形で、同じ比較を5250の画面上でも試してください(パラメーターの正式な綴りは未確認です。`CMPPFM` を単独で(F4 を使って)呼び出し、プロンプトの実際の指定名を確認してください)。

7. **ソース側の差分を、このリポジトリーの clone(`~/ibmi-kyozai`)で確認します。** SEU で編集した `<USER>1/QRPGSRC(JU0300)` は、まだ `~/ibmi-kyozai` には反映されていません。03-10 の `EXPSRC` と同じ考え方で、SSH から `CPYTOSTMF` を使い、変更後のメンバーを clone の中の実際のファイルへ書き戻してから、`git diff` を見ます。

   ```text
   system "CPYTOSTMF FROMMBR('/QSYS.LIB/<USER>1.LIB/QRPGSRC.FILE/JU0300.MBR') TOSTMF('/home/<自分のユーザー名>/ibmi-kyozai/src/legacy/qrpgsrc/ju0300.rpg') STMFOPT(*REPLACE) STMFCCSID(1208) ENDLINFMT(*LF)"
   cd $HOME/ibmi-kyozai && git diff -- src/legacy/qrpgsrc/ju0300.rpg
   ```

   ソースの変更が**手順3で意図した箇所だけ**であることを確認してください。

### `JU0300` に税込み列を足す(実演)

`JU0300` の O 仕様書には、そもそも「金額」を表すフィールドがありません(`JUCHUM`/`JUCHUR` には `JUNO`・`JUTOK`・`JUTAN`(担当者コード、6A の文字列)・`JUDATE` しかなく、単価・数量は `JUCHUD`(`JU0300` は開いていません)側にあります)。そこで、**「1件あたり手数料500円(税抜き)」という、この演習のための仮の業務ルール**を新たに置き、`L2BRK`(得意先合計)の集計件数 `L2CNT` から**税込みの手数料合計**を計算して印字する、という形で「税込み列」を追加します。データベースの形は一切変えないため、`DBVER` は1のままです(`JUCHUM` に新しい列を実際に追加する改修は、05-09 で `JUDLV` を例に扱います)。

C 仕様書の**明細レベル(空欄)の行の中**、既存の `SETON 94`・`ADD 1 L1CNT` などと同じ並びに、`RATE`(消費税率)を定義する行を追加します(04-02 の `R0402A`(`PRICE`・`RATE`・`TOTAL` による税込み価格計算、`1580 × 1.10 = 1,738.00` を実機確認済み)と同じ組み立て方です)。明細レベルの行は制御レベル(`L1`/`L2`/`LR`)の行より**前**に置く必要がある(04-10 で実機確認済みの `QRG5002` 制約、`ju0300.rpg` 自身のヘッダー・コメント5番)ため、`RATE` の再計算は**レコードを読むたびに毎回**行われます(値は常に同じなので、これ自体は無駄ではあっても害はありません)。

```text
C                     Z-ADD1.10      RATE    32
```

`L2` ブレイクの直前、`L2CNT` をリセットする前に、次の3行を追加します(`CL2 94` の条件は既存の `EXCPTL2BRK` 行と同じものを使います)。

```text
CL2 94                Z-ADD500       HANI    50
CL2 94      L2CNT     MULT HANI      SUBT    70
CL2 94      SUBT      MULT RATE      TEIKIN  92
```

`HANI`(500円、手数料単価)・`SUBT`(`L2CNT × HANI` の税抜き小計、長さ7桁0小数)・`TEIKIN`(`SUBT × RATE` の税込み合計、長さ9桁2小数、`R0402A` の `TOTAL` と同じ組み立て)です。この3行は、既存の `CL2 94 EXCPTL2BRK` より**前**に置いてください(`EXCPT` はその時点のフィールドの値を印字するため)。

O 仕様書の `L2BRK` グループに、既存の `L2CNT` の行の後、次の1行を追加します。

```text
O                                   70 '@500+10%='
O                         TEIKIN 1   85
```

`TEIKIN` には編集コード `1`(カンマ区切り・小数点2桁、`R0402A` で実機確認済みの書式)を使います。長さ9桁2小数のフィールドを編集コード `1` で印字すると、桁区切りのカンマを含めて最大12文字幅(`9,999,999.99`)になるため、終了桁を85にすると開始位置は74桁目になります。ラベル `'@500+10%='`(9文字、70桁目で終わり62桁目から始まる)と3桁分の間を空けられるので、既存の `L2CNT Z 55`(55桁目で終わる)とも含め、桁の重なりはありません。

これで、`L2BRK`(得意先ごとの合計行)にだけ新しい列が増え、`DTL`(明細)・`L1BRK`(日付ごとの小計)・`GTOT`(総合計)の各行は一切変わらないはずです。**手順5のゴールデン・マスター比較で、本当に `L2BRK` 行だけが変わったことを確認してください。**

## 演習

`JU0300` の `L1BRK`(日付ごとの小計)には、次の行があります。

```text
O                         L1CNT Z   55
```

編集コード `Z`(符号を消し、先頭のゼロを抑制する。小数点は付けない。`ju0300.rpg` 自身のヘッダー・コメントで、日付編集コード `Y` ではなくあえて `Z` を選んだ理由が説明されています)が使われています。

`L1CNT` は C 仕様書の `ADD 1 L1CNT 50`(結果フィールド指定 `50` = 長さ5桁・小数0)で定義されています。

1. `L1CNT` が `3` のとき、編集コード `Z` の印字結果を予想してください(ヒント: ゼロ抑制がどう働くか)。
2. もし `Z` を**外した**場合(編集コードなし)、印字結果はどう変わると予想しますか?
3. 予想したら、実際に `Z` を外して再コンパイルし、比較してください。**この演習の BEFORE は、税込み列を追加した後の現在の `JU0300`(`Z` あり)を、もう一度 `TXSNAP LABEL(BEFORE) ...` で撮り直したものを使ってください**(手順2で保存した BEFORE は税込み列を追加する前のものなので、そのまま使うと税込み列の有無まで差分に混ざってしまいます)。`Z` を外して再コンパイルしたものを AFTER として保存し、このレッスンで学んだ手順どおりに比較してください。差分は `L1BRK` 行だけに出るはずです。

<details><summary>解答の方向性</summary>

編集コード `Z` は先頭のゼロを抑制するので、`L1CNT=3` は `3`(先頭の余分なゼロなし)と印字されます。`Z` を外す(編集コードなし)と、フィールドの桁数分だけゼロ埋めされた形で印字されるはずです。`L1CNT` は長さ5桁・小数0で定義されているので、`00003`(5桁ぴったりのゼロ埋め)になると予想できます。

</details>
