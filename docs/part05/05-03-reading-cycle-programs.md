## なぜ学ぶか

**04-10 では、制御レベルを `L1` ひとつだけ使いました。** 実際の帳票には、「得意先ごとの小計」だけでなく「得意先の中でさらに日付ごとの小計」のように、**入れ子になった複数の小計**が必要になることがよくあります。RPG III は `L1`〜`L9` を同時に使うことでこれに対応します。今回読む `JU0300` は、まさにこの2段階(`L1`/`L2`)の実例です。

**さらに、業務システムでは「受注ヘッダー」と「受注明細」のように、2つ以上のファイルを共通のキーで組み合わせて処理する場面が頻繁にあります。** `CHAIN` で都度引くのではなく、RPG サイクル自身に両方のファイルを渡し、キーが一致するかどうかで自動的に処理を振り分けさせる仕組みが**一致レコード処理**(`M1`〜`M9`、`MR`)です。今回読む `ZA0500` はこれを使って、受注明細(`JUCHUD`)と受注ヘッダー(`JUCHUM`)を組み合わせ、在庫を引き当てます。

**この一致レコード処理は、「読めれば直せる」の核心部分でもあります。** `ZA0500` には実際に、一致レコード処理の勘所を誤ると二重処理が起きる、という実例(2026-09-26 の批評で見つかり、修正された実バグ)が残っています。これを自分でトレースできることが、今回のいちばんの目標です。

## 新出

- 一致レコード処理: プライマリー・ファイル/セカンダリー・ファイル、一致フィールド(`M1`〜`M9`)、`MR` 標識

## 説明

### JU0300: なぜ L1=日付、L2=得意先なのか

`JU0300` は `JUCHUL1`(`JUTOK`+`JUDATE` の順にキー付けした `JUCHUM` の論理ファイル)をプライマリー・ファイルとして読みます。キーは **`JUTOK`(得意先コード)が大分類、`JUDATE`(受注日)がその中の小分類** です。

```text
IJUCHUR
I                                              JUDATEL1
I                                              JUTOK L2
```

**得意先(`JUTOK`)ではなく日付(`JUDATE`)が `L1`、得意先が `L2` です。** 04-10 で `L1=JUTOK`(得意先)と習った直後だと、「得意先の方が `L1` では?」と思うかもしれません。理由は、次の RPG III の規則にあります。

> **上位の制御レベルが変わると、それより下位のレベルはすべて自動的に ON になる。**(RPG/400 Reference "Control Level Indicators (L1-L9)": "All lower level indicators are set on when a higher level indicator is set on as the result of a control break."。ただし、04-10 は制御レベルを `L1` ひとつしか使っておらず、実機で確認できたのはこの規則の特殊ケースである「`LR`(ファイル終端)が自動的に `L1` を ON にする」の1事例のみです。`L1`/`L2` のように複数の制御レベルが絡む相互作用は、04-10 でも `JU0300` 自身でも実機では未確認です。)

得意先(`JUTOK`)が変わるときは、日付(`JUDATE`)も当然変わります(前の得意先の最後の日付と、次の得意先の最初の日付が一致することはまずありません)。逆に、同じ得意先の中で日付が変わっても、得意先自体は変わりません。つまり、**「変わる頻度が低い(大分類)方が上位の番号、変わる頻度が高い(小分類)方が下位の番号」** という対応が必要です。`JUTOK` は変わる頻度が低い(大分類)ので `L2`、`JUDATE` は変わる頻度が高い(小分類)ので `L1` です。もし逆に `L1=JUTOK`・`L2=JUDATE` と書いてしまうと、得意先が変わっていないのに日付が変わるたびに `L2`(本来もっと大きな区切りのはずの番号)が ON になってしまい、意味が壊れます。**04-10 と矛盾しているのではなく、04-10 では制御レベルが1つしかなかったため、この「相対的な大小関係」が問題にならなかっただけです。**

### 実行順序とソース順序(2段階の場合)

得意先が変わる瞬間は、`L2` だけでなく `L1` も同時に ON になります(上位が変わると下位も強制的に ON)。総合計時の処理は、**下位のレベルから順に**(`L1`→`L2`→…→`LR`)実行されます。`JU0300` の C 仕様書もこの順(空欄→`L1`→`L2`→`LR`)に並んでいます。04-10 で実機確認済みなのは、このうち「空欄(明細時)の行は `L1` の行より前に書かないと `QRG5002` になる」という2項の順序制約だけで、`L2`・`LR` を含めた4項の順序全体が必須かどうかは実機未検証です。

```text
CL1 94                EXCPTL1BRK
CL1                   ADD  L1CNT     L2CNT   50
CL1                   Z-ADD0         L1CNT
CL2                   ...(配列境界チェック、省略。05-04で扱います)
CL2 94                EXCPTL2BRK
CL2                   Z-ADD0         L2CNT
```

得意先が変わる瞬間は、まず `L1` の総合計時処理(日付小計を印字し、その値を `L2CNT` に繰り込んでから `L1CNT` をリセット)が実行され、**その直後に** `L2` の総合計時処理(得意先小計を印字し `L2CNT` をリセット)が実行されます。日付小計・得意先小計の両方に印字される `JUTOK`/`JUDATE` は、**変わる前(旧グループ)の値**です(04-10 実機メモで確認済みの「総合計時はまだ新レコードのフィールドが移し替えられていない」という挙動どおり)。

**指示標識94の役割:** `JU0300` は `CL1 94`/`CL2 94` のように、すべての総合計時 `EXCPT` に標識94を追加で条件付けしています。94 は明細時に毎回 ON にされる(`C SETON 94`)ので、**1件もレコードが読まれなかった場合(空の `JUCHUL1`)だけ 94 が OFF のまま**になります。`LR` は主ファイルが空でも必ず ON になり `L1`/`L2` も強制 ON になるため、94 のガードが無いと、データが0件なのに空欄・ゼロの小計行が3行印字されてしまいます。

**「OF(総合計時)」という表記について:** 元の設計メモには「OF」という制御レベルのような表記がありましたが、C 仕様書7-8桁目に書けるのは空欄・`L1`〜`L9`・`LR` などに限られ、`OF` はその一覧にありません。`JU0300` はこれを `LR`(サイクル自身の最終レコード制御レベル。主ファイルの終わりで自動的に ON になり、`L1`/`L2` も道連れで ON にする)で実装しています。これは印字装置のオーバーフロー標識(`OA`〜`OG`)とは別物です。

### ZA0500: 一致レコード処理(M1/MR)の基本

`ZA0500` は、受注明細 `JUCHUD`(プライマリー・ファイル、F仕様書16桁目 `P`)と受注ヘッダー `JUCHUM`(セカンダリー・ファイル、16桁目 `S`)を、両方とも `JUNO`(注文番号)をキーに組み合わせます。

**用語: プログラム記述ファイル vs 外部記述ファイル。** F仕様書19桁目(File Format)には、**`F` か `E` のどちらかを必ず書きます**(RPG/400 Reference "Position 19 (File Format)": 「An entry is required in position 19」)。

```text
FJUCHUD  IP  F      27            DISK
FTOKUIM  IF  E           K        DISK
```

- **`F`(プログラム記述)**: 「レコードの中身(フィールドの桁位置・型)が、この RPG プログラム自身の I 仕様書に書かれている」という意味です(同リファレンス: 「records for the file are described within the RPG/400 program on input/output specifications」)。`JUCHUD`/`JUCHUM` はこちらで、そのため `IJUCHUD`/`IJUCHUM` に手書きの桁位置指定(`1 6 JUNO`)が必要です。24-27桁目のレコード長(`JUCHUD` なら27)も、プログラム記述ファイルだけが持つ欄です(外部記述ファイルではこの欄は空欄でなければなりません)。
- **`E`(外部記述)**: 「レコードの中身は、`DDS` 側(`db/v1/*.pf`)に定義済みで、コンパイル時にコンパイラーが自動的に取り込む」という意味です(同リファレンス: 「the compiler obtains these descriptions at compilation time」)。05-02 で読んだ `TOKUIM`/`TANTOM`(`FTOKUIM IF E K DISK`)はこちらです。フィールド名をそのまま使うか、`TANCD`/`TANNM` のように I 仕様書でリネームするだけで済み、桁位置を自分で数える必要がありません。

**この違いが実際に効いてくるのは05-09です**(様式レベル ID による自動チェックは外部記述ファイルにしか効かず、プログラム記述の `JUCHUM` はそのチェックの外側にいます)。ここでは「19桁目の1文字で、フィールド定義の出どころが変わる」という事実だけ押さえてください。

```text
IJUCHUD  AA  01
I                                        1   6 JUNO    M1
IJUCHUM  AA  02
I                                        1   6 JUNO    M1
```

- **一致フィールド**: 両方のファイルの `JUNO` に、同じコード `M1`(59-60桁目ではなく61-62桁目。制御レベルとは別欄)を付けます。RPG は、この2つのファイルの `JUNO` を比較しながら読み進めます。
- **レコード識別標識**: `01`(`JUCHUD` 側のレコードが処理されているときだけ ON)、`02`(`JUCHUM` 側のときだけ ON)。
- **`MR` 標識**: 「今処理しているのが一致したレコードかどうか」を示します。一致したペアを処理している間だけ ON、片側にしかないレコードを処理しているときは OFF です(RPG/400 Reference: "The MR indicator is set on and remains on for the complete cycle that processes the matching record ... Otherwise, the MR indicator is set off.")。

**一致レコード処理でいちばん誤解しやすい点はここです。** RPG/400 Reference は、一致したペアの処理順序をこう説明しています。

> "Whenever a record from the primary file matches a record from the secondary file, the primary file is processed first. Then the matching secondary file is processed."

つまり、**JUNO が一致した1組のペアは、「明細時サイクル」が2回に分けて実行されます。** 1回目は `JUCHUD` 側(標識01が ON)、2回目は `JUCHUM` 側(標識02が ON)。どちらの回も `MR` は ON のままです。2回目(`JUCHUM` 側)のサイクルでは、`JUCHUD` 固有のフィールド(`JUSHO`・`JUSU`・`JULINE`)は**新しく読み直されません**(2回目は同じペアに対する2回目の「立場」に過ぎず、`JUCHUD` レコードそのものを再読するわけではないからです)。**そのフィールドには、直前の1回目(`JUCHUD` 側)のサイクルの値がそのまま残っています。**

### ZA0500 の01+MR ゲート: 二重処理を防ぐ実例

`ZA0500` の在庫引当ロジックは、次の2行から始まります。

```text
C   01 MR             GOTO PROCLN
C                     GOTO SKPALL
```

これは「標識01と`MR`が両方ONのときだけ `PROCLN`(在庫引当の本体)へ飛び、そうでなければ無条件に `SKPALL`(何もしないで終わる)へ飛ぶ」という意味です。一致したペアに対する2回のサイクルを、この条件でたどってみます。

| サイクル | 標識01 | 標識02 | `MR` | `01 MR` の判定 | 結果 |
|---|---|---|---|---|---|
| 1回目(`JUCHUD` 側) | ON | OFF | ON | 真 | `PROCLN` へ(在庫を引き当てて印字) |
| 2回目(`JUCHUM` 側) | OFF | ON | ON | 偽(01がOFF) | `SKPALL` へ(何もしない) |

**もしこの `01` のガードが無く、`C MR GOTO PROCLN` とだけ書かれていたら、どうなるでしょうか。** `MR` は2回のサイクルの両方でONのままなので、1回目(`JUCHUD` 側、正しい `JUSHO`/`JUSU` を持つ)だけでなく、**2回目(`JUCHUM` 側)でも `PROCLN` が実行されてしまいます。** ところが2回目のサイクルでは `JUSHO`/`JUSU` は1回目のサイクルの値のまま残っているので、**まったく同じ商品・数量に対して `CHAIN`→在庫引当→`UPDAT` が、もう一度実行されてしまいます。** 結果は、同じ注文明細行に対する在庫の二重引き落としと、印字の重複です。これが `ZA0500` のヘッダー・コメントに記録されている、2026-09-26 の批評で見つかった実バグとその修正内容です。**`01`(レコード識別標識)と `MR`(一致レコード標識)は、それぞれ別のことを教えてくれる標識であり、両方を組み合わせて初めて「このサイクルで本当に何をすべきか」が決まる**、という一致レコード処理の勘所がここに現れています。

### 片側にしかないデータのとき

一致しないレコードは、RPG/400 Reference にこうあります。

> "Whenever records from ascending files do not match, the record having the lowest match field content is processed first."

つまり、プライマリー(`JUCHUD`)とセカンダリー(`JUCHUM`)のどちらか一方にしか無い `JUNO` があると、**JUNO の値が小さい方のファイルのレコードだけが単独で処理され**(そのファイルの識別標識だけがON、`MR` はOFF)、RPG はそのファイルだけを次に読み進めます。`ZA0500` の場合、これは `01 MR`(1回目)の条件を満たさない(`MR` がOFFだから)ので、**`01` があってもなくても、片側にしかないレコードは常に `SKPALL` に落ちます。** どんな結果になるかは、演習で実際にトレースしてください。

### 一致フィールドの順序要件(順序の検査)

一致レコード処理が正しく動くには、**両方のファイルが一致フィールドの昇順で RPG に渡される**必要があります。`JUCHUD` は `JU0900C`(05-06 で読みます)が `OPNQRYF KEYFLD((JUNO)(JULINE))` で並べ替えてから `ZA0500` に渡しますが、`ZA0500` 自身の `FJUCHUM` の F仕様書には **31桁目の `K` がありません**。04-10 で確認済みの規則(31桁目が空欄のキー付きファイルは到着順で読まれる)がここにも当てはまるので、`JUCHUM` は「キー順」ではなく**物理的な格納順(到着順)**で読まれます。出荷データではたまたま `JUCHUM` への `INSERT` 順が `JUNO` の昇順と一致しているため問題は起きませんが、**この一致は保証されたものではありません。**

もし一致フィールドが昇順でなくなったら何が起きるでしょうか。RPG/400 Reference の例外/エラー・コード表に、次のコードがあります。

```text
01031  W,D,SQ  n/a  Match field out of sequence.
```

一致フィールドの順序が崩れたレコードに出会うと、RPG の例外/エラー処理ルーチンに制御が渡されます。`ZA0500` には `INFSR`/`*PSSR`(次のレッスン05-04で学びます)が一切定義されていないため、これは RPG の既定のエラー処理に落ち、04-06 の `RPG1216`・04-12 の `RPG0102` と同じ「非対話ジョブでは誰も応答できない照会メッセージ」のパターンになる可能性が高い、という一次資料に基づく推測ができます(実機未確認)。**`JUCHUM` に `K` が無いことは、今は偶然動いているだけの弱点**だとわかります。

### FREE形式にできない部分

RPG サイクル(プライマリー・ファイルの自動読み取り、`L1`〜`L9` の制御レベル)と、一致レコード処理(`M1`〜`M9`、`MR`)は、どちらも**RPG III の「サイクル」という仕組みそのもの**に根ざした機能です。第6部で学ぶ FREE形式(自由形式)は C 仕様書相当の計算ロジックを自由な書式で書けるようにしたものですが、**サイクル自体・一致レコード処理には、FREE形式でも完全な代替がありません**([06-01b](../part06/06-01b-reading-fixed-mixed-form.md) で確認します。`JU0300`・`ZA0500` 自体は第6部以降も RPG IV へ移植されず、RPG III の教材のまま残ります)。FREE形式でこれと同じ処理をしたい場合、明示的な `READ` ループと自分で書いた比較ロジックに書き直すことになります(04-06〜04-09 で `P`/`L1`/`M1` を習う前にやっていたことと同じです)。**「サイクルが便利に自動でやってくれること」ほど、後から書き直すときに一番手間がかかる**、というのは覚えておく価値があります。

## 実演

1. `WRKOBJPDM LIB(<自分のユーザー名>1) OBJTYPE(*PGM)` で、05-01 の `TXLEGACY` によって `JU0300`・`ZA0500` が作成されていることを確認する(まだの場合は 05-01 の手順を先に済ませてください)。
2. `WRKMBRPDM FILE(<自分のユーザー名>1/QRPGSRC) MBR(JU0300)` オプション5(表示)で、実際の `JU0300` のソース(`src/legacy/qrpgsrc/ju0300.rpg` と同じ内容)を確認する。
3. **予想する**: `JUCHUL1` は `JUTOK` 昇順・`JUDATE` 昇順のキーです。`JUCHUM` の実データ(`JUNO`/`JUTOK`/`JUDATE`)は次のとおりです。

   ```text
   J00001 C00001 20260901    J00002 C00002 20260902    J00003 C00001 20260905
   J00004 C00003 20260906    J00005 C00004 20260908    J00006 C00005 20260910
   J00007 C00006 20260911    J00008 C00003 20260912
   ```

   これを `JUCHUL1` のキー順(`JUTOK`→`JUDATE`)に並べ替え、`L1BRK`(日付小計)・`L2BRK`(得意先小計)がどこで何回出るか、`GTOT`(総合計)の `GCNT`・`XTOT` がいくつになるかを、紙に書いて予想してください。

   <details><summary>予想の答え合わせ</summary>

   並べ替えた順序: `C00001/0901`→`C00001/0905`→`C00002/0902`→`C00003/0906`→`C00003/0912`→`C00004/0908`→`C00005/0910`→`C00006/0911`

   このデータは**日付がすべて異なる**ため、`L1`(日付)は毎レコード変わる境目で必ず1回ずつ `L1BRK` を出します(最初のレコードの前だけは例外で、何も出ません)。`L2`(得意先)は得意先が変わるところでだけ `L2BRK` を出します。得意先ごとの件数は `C00001=2, C00002=1, C00003=2, C00004=1, C00005=1, C00006=1`(合計8件)。`GCNT=8`、`CT` 配列の合計(`XTOT`)も `2+1+2+1+1+1=8` で一致するので `XFOOT=8 OK` が出るはずです。

   </details>

4. `CALL PGM(<自分のユーザー名>1/JU0300)` を実行し(または `MN0000C` のメニューからオプション2)、`WRKSPLF` で結果を確認する。予想と一致するか確かめてください。
5. `WRKMBRPDM FILE(<自分のユーザー名>1/QRPGSRC) MBR(ZA0500)` オプション5で `ZA0500` のソースを表示する。**`ZA0500` はこのレッスンでは実行しません。** `JU0900C`(呼び出し元、05-06 で読みます)には、`MINQTY` の桁数不一致(05-13 ticket 1)と `JUCHUM` の並び順が保証されない(05-13 ticket 2)という、まだ直っていない不具合が残っており、既定の `RMODE` は `*LIVE`(実際に `ZAIKOM` を更新する)だからです。代わりに、次の演習で紙の上でトレースします。

## 演習

`ZA0500` の C 仕様書(`C 01 MR GOTO PROCLN` / `C GOTO SKPALL`)だけを根拠に、次の3問を予想してください。答えは `<details>` を開いて確認してください。

1. `JUCHUD` に `J00099/1/P00003/4/480.00` という行が追加されたが、`JUCHUM` に `J00099` のヘッダーが**存在しない**とします。`ZA0500` はこの `JUCHUD` レコードに対してどう動きますか。

   <details><summary>答え</summary>

   `JUCHUD` 側だけにある `JUNO` なので、標識01が ON、`MR` は **OFF**(一致しなかったので)のまま、そのレコード単独のサイクルが実行されます。`01 MR` の条件は `MR` が OFF のため偽になり、`GOTO SKPALL` に落ちます。**`CHAIN` も `UPDAT` も `EXCPT` も一切実行されず、この明細行は何のエラーも出さずに静かに無視されます。** ヘッダーの無い受注明細が紛れ込んでも、`ZA0500` は気づけない、という弱点です。

   </details>

2. 逆に、`JUCHUM` に `J00099/C00002/20260915/T00001` というヘッダーが追加されたが、対応する `JUCHUD` の明細行が**1件も無い**とします。`ZA0500` はどう動きますか。

   <details><summary>答え</summary>

   `JUCHUM` 側だけにある `JUNO` なので、標識02が ON、標識01は OFF、`MR` も OFF のまま、そのヘッダー単独のサイクルが実行されます。`01 MR` の条件は `01` が OFF のため(`MR` もOFFですが、`01` がOFFの時点ですでに)偽になり、こちらも `GOTO SKPALL` に落ちます。**問1と同じく、何も起きずに無視されます。** 明細の無い受注ヘッダーがあっても在庫は動かず、エラーにもなりません。

   </details>

3. `JUCHUD`/`JUCHUM` が、この順で読まれるとします(`JUNO` 昇順): まず `JUCHUD` に `J00010`(ヘッダーなし)、次に `J00020` が両ファイルに一致してある(通常の受注)、最後に `JUCHUM` にだけ `J00030`(明細なし)があります。この3件ぶんの処理を、サイクルごとに「どのファイルの、どの標識が ON で、`PROCLN` に入るか」を表にして予想してください。

   <details><summary>答え</summary>

   | サイクル | 処理される内容 | 標識01 | 標識02 | `MR` | `PROCLN` に入るか |
   |---|---|---|---|---|---|
   | 1 | `JUCHUD` の `J00010`(単独) | ON | OFF | OFF | いいえ(`SKPALL`) |
   | 2 | `JUCHUD` の `J00020`(一致・1回目) | ON | OFF | ON | **はい** |
   | 3 | `JUCHUM` の `J00020`(一致・2回目) | OFF | ON | ON | いいえ(`SKPALL`、01がOFFのため) |
   | 4 | `JUCHUM` の `J00030`(単独) | OFF | ON | OFF | いいえ(`SKPALL`) |

   実際に在庫が動く・印字されるのはサイクル2(`J00020` の `JUCHUD` 側)だけです。片側にしかないレコード(`J00010`・`J00030`)はどちらも無視され、一致したペアの2回目(`J00020` の `JUCHUM` 側)も `01` のガードのおかげで無視されます。

   </details>

## 実機メモ

- **`JU0300`・`ZA0500` は V1(コンパイル確認)まで確認済みです(`part05-legacy-probe`、確認日 2026-09-26、2回接続)。** 1回目の接続で見つかった実バグの1つが `za0500.rpg` の I 仕様書(`IJUCHUD`/`IJUCHUM`)で、15-16桁目(Sequence 欄)が空欄だと `QRG4008` でコンパイルが停止することが判明し、`AA` を追加して修正しました(RPG/400 Reference 第8章「Positions 21-41 (Record Identification Codes)」の記述どおり)。**上の I 仕様書の抜粋も、この修正後の実ソース(`AA` あり)に合わせて更新しています。** 2回目の接続で、この修正版を含む旧システム一式が正常に作成され、`JU0300`・`ZA0500` を含む RPG 側はいずれも Highest Severity 00 だったことを確認しました。さらに `part05-txlegacy-exec`(確認日 2026-09-27)で、`TXLEGACY` 自身が CLONEDIR 配下の実ツリーから `CPYFRMSTMF` する本来の経路でも、`JU0300`・`ZA0500` を含む複数オブジェクトが同様に新規作成されることを確認しました。
- **ただし、いずれもコンパイルの確認どまりです。** `JU0300` を実際に `CALL` し、実演の手順3〜4で予想した `L1BRK`/`L2BRK`/`GTOT` の印字内容が一致するかどうか(V2)は、まだ確認していません(未検証、2026-09-27時点)。`CALL` 後に `WRKSPLF` でスプールを確認するという実演の手順そのものは、5250 の対話操作なので構造的に V3 です(この教材の検証ハーネスは非対話接続専用のため確認できません)。印字内容自体は、`qsh` の `system("CALL ...")` 経由では `QSYSPRT` 宛ての `CPYSPLF` は失敗する一方、印字内容は接続結果のテキストにそのまま現れるという既知の挙動(`docs/probes.md`「第6部の実機検証: `part06-0103-freeform`」参照)を使えば非対話でも V2 確認できる見込みがあり、次回接続で試す予定です。本レッスンの説明・トレースは、両ソースの実際の I 仕様書・C 仕様書の記述と、RPG/400 Reference(Table 41「一致レコードの選択順序」、例外コード表の `01031`)という一次資料の記述に基づいています。
- 04-10 で実機確認済みの規則「F仕様書31桁目 `K` が無いキー付きファイルは到着順で読まれる」は、このレッスンでもそのまま前提にしています。**一方、「上位の制御レベルが変わると下位も強制的に ON になる」は RPG/400 Reference に明記された規則ですが、04-10 は `L1` しか使っていないため実機で確認できたのは「`LR` が `L1` を強制 ON にする」の1事例のみで、`L1`/`L2` 間の相互作用は 04-10 でも `JU0300` 自身でも実機未確認です。** `JU0300` の `L1BRK`/`L2BRK` の印字内容そのものが未検証(V2)であることは、前項のとおりです。
- **依存するプローブ P22 は、今なお未実施です(未検証、2026-09-27時点)。** 破壊的な操作を伴うため、`docs/probes.md` の「未実施のプローブ」節が示す方針どおり、TX ツール実装(フェーズ2)と合わせて慎重に実施する予定です。
- **`JU0900C`→`ZA0500` の as-shipped(チケット未修正)実行チェーンは V2(実行結果の一致)まで確認済みです(`part05-ju0900c-baseline`、確認日 2026-09-27、`JU0900C` の `RUNMODE`(`ZA0500` 側では同じ値を `RMODE` として受け取ります)に `*TEST` を渡して実行し、`ZAIKOM` が不変であることも確認済み)。** ticket 1 のバグ(`MINQTY` の桁数不一致)は、1行目の受注データで**毎回確実に**(「まれに」ではありません)`RPG0907`(10進データ・エラー)として発生することを実測で確認しました。`ZA0500` はこのエラーで停止し(`RPG9001`)、呼び出し元の `JU0900C` がそれを「異常終了」として報告して終わります(0行印字、ハングはしません)。**`za0500.rpg` のソース順序上、クラッシュ地点(`N90 AVAIL COMP MINQTY`)は `PROCLN` ブロックの内側にあります。** そこへ到達するには、直前の `C 01 MR GOTO PROCLN` の判定が真となっている必要があるため、実際には本レッスンが説明する一致レコード処理(`01`/`MR`)の分岐は、この実行でも一度は通過しています。出荷データで `JUNO` が最小の `J00001`(`JUCHUD`・`JUCHUM` 双方とも最初に登録されているレコード、`db/data/load_v1.sql` で確認済み)について、`01 MR` が真と判定されて `PROCLN` へ分岐し、`CHAIN` が `ZAIKOM` のレコードを見つけ(標識90 OFF)、在庫計算(`Z-ADD`/`SUB`)まで実行されてから `&MINQTY` 参照でクラッシュしたことになります。**この実行で確認できていないのは、一致したペアの2回目のサイクル(`JUCHUM` 側、`01` がOFFで `SKPALL` に落ちる分岐)と、片側にしかないレコードの分岐(`MR` がOFFで `SKPALL` に落ちる分岐)の両方です。**
