# 05-07 影響調査

> 所要時間: 60分 / 前提レッスン: 05-06 / 目標番号: 4 / 観測方法: SQL の結果(`QTEMP` の OUTFILE)と `FNDSTRPDM` の一覧 / 道具: 5250(PDM)・SQL(ACS の「実行 SQL スクリプト」または `RUNSQL`)/ 同時接続数: 5250×1 / 作る・変えるオブジェクト: なし(`QTEMP` の一時ファイルのみ)/ DBVER: 1 / 依存するプローブ: P18(未実施)/ PTF 依存: なし / 容量の目安: わずか

## ゴール

- `DSPPGMREF` の `*OUTFILE` を SQL で読み、あるファイルを参照しているプログラムを一覧できる。
- `DSPDBR` で、あるファイルの上に作られている論理ファイルを一覧できる。
- `FNDSTRPDM` で、コマンド系の調査だけでは見つからない可能性のある依存関係(CL の `DCLF` など)を補う。
- 直接参照と、論理ファイル経由の間接参照の両方を辿り、「影響を受けるオブジェクトと行」を漏れなく挙げられる。

## なぜ学ぶか

**保守で一番危ないのは、「直しても大丈夫だと思っていたら、実は別のプログラムがそのファイルを使っていた」という事故です。** `JUCHUM`(受注ヘッダー)を例にすると、これを直接読むプログラムだけでなく、`JUCHUM` の上に作られた論理ファイルを読むプログラム、`DCLF` で読む CL プログラムまで、**影響の範囲は1種類の調べ方だけでは見えません。** このレッスンでは、`DSPPGMREF`・`DSPDBR`・`FNDSTRPDM` という3つの調べ方を組み合わせ、それぞれの得意・不得意を体験します。ここで身につける手順は、05-08 以降の改修すべての出発点になり、05-13 のチケット1でも「まず影響調査から」という同じ手順を使います。

## 新出

### 中核(3つ)

- **`DSPPGMREF` の `OUTPUT(*OUTFILE)` を SQL で見る**: プログラムがどのファイル・データ域を参照しているかの一覧を、`QTEMP` に落として SQL で絞り込む。**`DSPPGMREF` を実行したジョブと、`SELECT` を実行するジョブが同じでなければならない**(`QTEMP` はジョブ・スコープの特別なライブラリーで、別のジョブ・別の接続からは中身が見えないため)。
- **`DSPDBR`**: あるファイルの上に作られている論理ファイルを一覧する。物理ファイルを直接読むプログラムだけでなく、その論理ファイル経由で間接的に読むプログラムまで追うための出発点になる。
- **CL の `DCLF` も「影響を受ける」に数える**: `DCLF FILE(...)` した CL プログラムは、そのファイルを読み書きしていなくても、**そのファイルの様式が変わればコンパイルし直しが必要になる**。これを見つける確実な方法は `FNDSTRPDM`(05-02 で紹介済み)で、ソース中の `DCLF` とファイル名の組を直接探すこと。

### 読めればよい項目

- `QTEMP`(ジョブ終了で自動的に消える、ジョブ専用の作業ライブラリー。03-10 の `EXPSRC` で既に使った)。
- `*OUTFILE` の列名は環境依存(未確認)なので、まず `SELECT * ... FETCH FIRST 1 ROW ONLY` で実物を見る習慣。

## 説明

### なぜ「同じジョブ」でなければならないのか

`DSPPGMREF PGM(...) OUTPUT(*OUTFILE) OUTFILE(QTEMP/PGMREF)` を実行すると、結果は `QTEMP` という特別なライブラリーに書かれます。`QTEMP` は**ジョブごとに独立した、そのジョブが終わると自動的に消える作業ライブラリー**です(03-10 の `EXPSRC` で確認済み)。5250 のコマンド行で `DSPPGMREF` を実行し、ACS の「実行 SQL スクリプト」など**別の接続**から `SELECT * FROM QTEMP.PGMREF` をしても、**その `QTEMP` は別のジョブのものなので、何も見えません。** `DSPPGMREF` の実行と、それに続く `SELECT` は、**必ず同じジョブ・同じ接続の中で**行う必要があります(ACS の「実行 SQL スクリプト」は CL コマンドと SQL を同じセッションで混在させられるので、これに向いています)。

### `src/sql/05-07-impact.sql` を実際に読む

このレッスンの実際の調査手順は `src/sql/05-07-impact.sql` にそのまま書かれています。順に見ていきます。

**Step 0(必ず最初に実行する)**: `DSPPGMREF` の `*OUTFILE` の列名(`WHPGM`/`WHLIB`/`WHFILE`/`WHFLIB` など)は、一般的な文書からの推測のままで、**このレッスン自身ではまだ実機の実際のダンプで確認していません。** 一方 `DSPDBR` 側は、`tools/qclsrc/txmigr.clp` の別件の検証(`part05-legacy-probe`、確認日 2026-09-26)で既に実測済みで、`WHFILE`/`WHLIB` という列は**存在せず**、実際は `DSPDBR` の対象そのもの(ここでは `JUCHUM` 自身)が `WHRFI`/`WHRLI` に、従属する論理ファイル(ここでは `JUCHUL1`)が `WHREFI`/`WHRELI` に入ることが分かっています(詳しくは Step 2 で扱います)。**`DSPPGMREF` 側は依然として推測のままなので**、Step 1 以降の `WHERE` 句を信じる前に、`SELECT * FROM QTEMP.PGMREF FETCH FIRST 1 ROW ONLY` で**実物の列名を必ず先に見ます**。列名が違っていたら、以降のクエリーをその場で直してください。

**Step 1**: `WHERE WHFILE = 'JUCHUM'` で、`JUCHUM` を**直接**参照しているプログラムを探します。`JU0900C`(`DCLF FILE(JUCHUM)`)・`ZA0500`(プログラム記述で `JUCHUM` を読む、05-09 で詳しく扱います)がここに出るはずです。

**Step 2**: `DSPDBR` の結果から、`JUCHUM` の上に作られている論理ファイルを一覧します。`JUCHUL1`(`db/v1/juchul1.lf`、`PFILE(JUCHUM)`)がここに出るはずです。**`tools/qclsrc/txmigr.clp` の別件の検証(`part05-legacy-probe`、確認日 2026-09-26)で、この列名は既に実測で確定しています**: `DSPDBR` を実行した対象そのもの(`JUCHUM` 自身)は全行に繰り返し出る `WHRFI`/`WHRLI`、実際に従属する論理ファイル(`JUCHUL1`)は `WHREFI`/`WHRELI` に入ります(`WHTYPE` は従属側の種別)。**ただしこれは `tools/qclsrc/txmigr.clp` 自身の検証で判明した事実であり、このレッスンの `src/sql/05-07-impact.sql` 自体をこの列名で実行して確認したわけではありません**(同スクリプトのコメント・SELECT文は今も `WHFILE`/`WHLIB` という誤った列名のまま残っています)。Step 0 の `SELECT * FETCH FIRST 1 ROW ONLY` で実際の列と値を見て、`WHREFI`/`WHRELI` に読み替えてから読み進めてください。

**Step 3(見落としやすい、このレッスンの核心)**: Step 1 は `WHFILE = 'JUCHUM'` **という名前と完全一致するもの**しか拾いません。ところが `src/legacy/qrpgsrc/ju0300.rpg` の F 仕様書は

```text
FJUCHUL1 IP  E           K        DISK
```

であり、**`JUCHUM` という名前はどこにも出てきません。** `JU0300` は `JUCHUL1`(論理ファイル)を外部記述で開いているだけで、`JUCHUM` を直接開いてはいないのです。Step 1 の `WHERE` を `JUCHUM` のままにしていると、**`JU0300` を完全に見落とします。** 正しくは、Step 2 で見つかった論理ファイル1件ごとに、Step 1 と同じ形のクエリーを**その論理ファイル名で**もう一度実行します。`WHERE WHFILE = 'JUCHUL1'` とすれば `JU0300` が出てきます。**「直接参照」と「論理ファイル経由の間接参照」の両方を辿って初めて、影響範囲が完成します。**

**Step 4**: `DCLF` は `DSPPGMREF` から見えるのか、という問いです。**正直に言うと、これはこのセッションでは確認できていません。** `DCLF` は CL プログラムがコンパイルされるとき、外部記述ファイルの様式レベル ID を一緒に焼き込みます(05-09 で詳しく学びます)。様式レベル・チェックをするということは、コンパイル済みプログラムのどこかにそのファイルへの参照が保存されているはずなので、**`DSPPGMREF` が拾える可能性は十分にあります。** 一方、`tools/qclsrc/txmigr.clp` の冒頭コメントは、`JUYAKC` の `CPYTOIMPF FROMFILE(...)` のような**実行時にしか値が決まるコマンド・パラメーターの文字列**は `DSPPGMREF` の対象外だろう、と述べています。**この2つは性質が違います**: `DCLF` はコンパイル時に埋め込まれる束縛、`CPYTOIMPF FROMFILE(...)` は実行時に解決される単なる文字列です。実機で確認するときの検体には、`JU0900C` ではなく **`JUCINQC`(03-09 で作った自分の CL)を使ってください。** `JU0900C` は `DCLF FILE(JUCHUM)` の他にも `OVRDBF FILE(JUCHUM) ...`・`DLTOVR FILE(JUCHUM)` という行を持っており(いずれも `DCLF` した同じファイルを対象にした実行時操作で、新しい依存を増やすものではありませんが)、「`DCLF` だけの、混じりけのない検体」としては `JUCINQC`(`DCLF FILE(JUCHUM)` と `RCVF` しかない)の方が適しています。`JUCINQC` は `<USER>1` にあり、Step 1 の `DSPPGMREF PGM(<USER>1/*ALL) ...` は既にこのライブラリー全体を対象にしているので、**新しく実行し直す必要はありません。** Step 1 の結果(`QTEMP.PGMREF`)の中に、`WHFILE = 'JUCHUM'` で `JUCINQC` が(`JU0900C`・`ZA0500` と並んで)出ているかどうかを見てください。出ていれば「`DCLF` は見える」、出ていなければ「`DCLF` は死角」と確定します。**どちらの結果であっても**、次の Step 5 は必ず行ってください。

**Step 5**: `FNDSTRPDM` によるソース・テキスト直接検索です。`OPNQRYF` の `FILE()`、`OVRDBF` の `TOFILE()`、`CPYTOIMPF` の `FROMFILE()`、`QCMDEXC` で組み立てたコマンド文字列は、**実行時にしか値が決まらないため、`DSPPGMREF`/`DSPDBR` のようなコンパイル時の調査では原理的に見えません。** これは Step 4 の `DCLF` の話と違い、**確実な死角**です。`FNDSTRPDM FILE(<自分のライブラリー>/QCLSRC) STRING('JUCHUM')` のようにソースを直接検索し、ヒットした行が本当に依存を作っているか(コメントの中の言及ではないか)を、**1行ずつ目で確認**してください。

### 権限・プライバシーの原則

`DSPPGMREF`・`DSPDBR` はいずれも `PGM(<自分のライブラリー>/*ALL)`・`FILE(<自分のライブラリー>/...)` のように、**自分のライブラリーに絞って**実行します。この先 `QSYS2.*` のようなシステム・カタログ・ビューを使う調査(第8部などで登場します)でも同じ原則です。**自分のライブラリー・自分のオブジェクトに絞って調べること。他の学習者のオブジェクトを走査しない。** これは Issue #6 で指摘された、08-07 などの `QSYS2.OBJECT_PRIVILEGES`/`PROGRAM_INFO`/`USER_STORAGE` のようなライブラリー横断のシステム・ビューが、フィルターなしで実行すると他ユーザーの情報まで返してしまう(2025-08 の一斉ロックアウト事例と同じ危険)という注意を、この影響調査系のレッスン全体に広げたものです。

### 複数ライブラリーにまたがる場合の一般原則

この教材では、03-09 で作った `JUCINQC`(`JUCHUM` を `DCLF`/`RCVF` する CL)も、05-01 の `TXLEGACY` が投入する旧システムも、どちらも `<USER>1` に置く約束です(01-04 で確認した「`<USER>1` = 現在の開発用、この教科書では主にここを使う」という約束どおりです)。つまり `JUCINQC` は、第5部で作業しているのと**同じライブラリー**に、第3部から既に住んでいます。`DSPPGMREF PGM(<USER>1/*ALL) OUTPUT(*OUTFILE) OUTFILE(QTEMP/PGMREF)` を1回実行するだけで、`JUCINQC` も含めて `<USER>1` のプログラムがすべて対象になっているはずです(Step 4 で、この予想が実際に正しいかを確認します)。

**実務ではここが本当の落とし穴になります。** 現場のシステムでは、開発用・本番用・部門ごとなど、関係するオブジェクトが複数のライブラリーに分かれて置かれていることが普通です。`DSPPGMREF PGM(あるライブラリー/*ALL) ...` は、指定したそのライブラリーの中しか見てくれません。**影響調査は「今作業しているライブラリーだけ」で終わらせず、関係しそうなライブラリーごとに繰り返す**必要があります(例えば05-12以降で本番役 `<USER>2` が登場したら、`<USER>2` に対しても同じ調査を繰り返すことになります)。この教材の `<USER>1` の中では体験できませんが、原則として覚えておいてください。

## 実演

**05-01 の `TXLEGACY` で旧システムが `<USER>1` に投入済みであることを前提にします。**

1. ACS の「実行 SQL スクリプト」で、次を1つのスクリプトとしてまとめて実行します(CL コマンドと SQL を混在させられます)。

   ```text
   CL: DSPPGMREF PGM(<USER>1/*ALL) OUTPUT(*OUTFILE) OUTFILE(QTEMP/PGMREF)
   CL: DSPDBR FILE(<USER>1/JUCHUM) OUTPUT(*OUTFILE) OUTFILE(QTEMP/DBRJUCHUM)
   ```

2. まず列名を確認します(Step 0)。

   ```sql
   SELECT * FROM QTEMP.PGMREF FETCH FIRST 1 ROW ONLY;
   SELECT * FROM QTEMP.DBRJUCHUM FETCH FIRST 1 ROW ONLY;
   ```

   `src/sql/05-07-impact.sql` の `WHPGM`/`WHLIB`/`WHFILE`/`WHFLIB` と実際の列名が違っていたら、以降のクエリーをその場で直してください。

3. `JUCHUM` を直接参照しているプログラムを見ます(Step 1)。`JU0900C`・`ZA0500` が出るはずです。

4. `JUCHUM` の上の論理ファイルを見ます(Step 2)。`JUCHUL1` が出るはずです。

5. **見つかった論理ファイルごとに、Step 1 と同じクエリーをもう一度**行います(Step 3)。`WHERE WHFILE = 'JUCHUL1'` に変えて実行し、`JU0300` が出ることを確認してください。

6. Step 1(手順3)で見た `QTEMP.PGMREF` の結果をもう一度見ます。`JU0900C`・`ZA0500` に加えて、`JUCINQC`(`DCLF FILE(JUCHUM)` と `RCVF` しかない、混じりけのない検体)が `WHFILE = 'JUCHUM'` の結果に**既に出ているかどうか**を確認してください(Step 4)。これで、`DCLF` が `DSPPGMREF` から見えるかどうかを自分の目で確認できます。

7. `FNDSTRPDM FILE(<USER>1/QCLSRC) STRING('JUCHUM')`・`FNDSTRPDM FILE(<USER>1/QRPGSRC) STRING('JUCHUM')` を実行し、ヒットした行を1行ずつ確認します(Step 5)。`JUCINQC` もこの中に見つかるはずです。コメント中の言及(偽陽性)と、本当の依存を見分けてください。

8. ここまでの結果を、次のような表にまとめます(行番号はこのレッスンを書いた時点のソースで確認済みのものです)。

   | オブジェクト | 種類 | 参照の仕方 | 行(ソース) |
   |---|---|---|---|
   | `JU0900C` | CL(`<USER>1`) | `DCLF FILE(JUCHUM)` | `ju0900c.clp:33` |
   | `ZA0500` | RPG(`<USER>1`) | プログラム記述 `FJUCHUM IS F 26 DISK` | `za0500.rpg:45`(F仕様書)、`za0500.rpg:54`(`IJUCHUM` I仕様書) |
   | `JUCHUL1` | LF(`<USER>1`) | `PFILE(JUCHUM)` | `juchul1.lf:1` |
   | `JU0300` | RPG(`<USER>1`) | 外部記述 `FJUCHUL1 IP E K DISK`(`JUCHUL1` 経由) | `ju0300.rpg:133` |
   | `JUCINQC` | CL(`<USER>1`、03-09 で作成) | `DCLF FILE(JUCHUM)` | `jucinqc.clp:6` |

   `ZA0500` の I 仕様書の行(`za0500.rpg:54` 付近、`JUNO`・`JUTOK`・`JUDATE`・`JUTAN` を桁位置で拾っている箇所)まで挙げているのは、**プログラム記述ファイルには様式レベル・チェックが効かない**(05-09 のコラム参照)ため、`JUCHUM` の並びが変わったときに実際に**手で直さなければならない行**がここだからです。

   この表が、05-09 で `JUCHUM` に `JUDLV` を追加するときに「再作成・再コンパイルすべき対象」そのものになります。

## 演習

**同じ手順を `ZAIKOM` で行ってください。**

1. `DSPPGMREF`・`DSPDBR` を `ZAIKOM` 向けに実行し、直接参照しているプログラムを探してください。
2. `ZA0500`(`FZAIKOM UF E K DISK`、`CHAIN ZAIKOM`)と `ZA0510`(`FZAIKOM IP E K DISK`、`ZA0510` 自体は `JU0900C`→`ZA0500` の呼び出し連鎖には組み込まれていない独立した教材プログラムです)の**少なくとも2本**が直接参照として出るはずです。
3. `ZAIKOM` の上に論理ファイルがあるか `DSPDBR` で確認してください(`db/` 以下を見ると `ZAIKOM` には論理ファイルが定義されていないため、`JUCHUM`/`JUCHUL1` のような間接参照の段は今回は発生しない**はず**です — 実際にそうなるか、自分の目で確認してください)。
4. `FNDSTRPDM` で `ZAIKOM` を検索してください。`JU0900C` のヘッダー・コメント(`RUNMODE` パラメーターの説明に `ZAIKOM` という語が出てきます)がヒットしますが、これは**コメント中の言及であって、`JU0900C` が実際に `ZAIKOM` を読み書きしているわけではありません**(`JU0900C` は `ZA0500` を `CALL` するだけです)。ヒット=依存、と機械的に判断しないことの実例として確認してください。
5. もし 03-09 の演習(`ZAIKOM` を `DCLF`/`RCVF` して在庫数量の合計を求める CL)を自分で作って残してある場合は、それも対象に含めて探してみてください。

## 実機メモ

- **`DSPDBR` の `*OUTFILE` 列名は実測済みです。** `tools/qclsrc/txmigr.clp` の別件の検証(`part05-legacy-probe`、確認日 2026-09-26、2回接続、CONFIRMED SUCCESS)の副産物として、`DSPDBR FILE(.../JUCHUM) OUTPUT(*OUTFILE)` を実際に実行し、列名を実測しました。予想していた `WHFILE`/`WHLIB` という列は**存在せず**、実際は `DSPDBR` の対象そのもの(`JUCHUM` 自身、全行に繰り返し出る)が `WHRFI`/`WHRLI`、実際に従属する論理ファイル(`JUCHUL1`)が `WHREFI`/`WHRELI` に入ります(`WHTYPE` は従属側の種別、値は `D`)。**`JUCHUL1` が従属論理ファイルとして実際に出てくること自体は、本文 Step 2 が予想したとおりでした。** ただし、この実測は `tools/qclsrc/txmigr.clp` 自身の検証(別目的のバッチ)の一環であり、**このレッスンの `src/sql/05-07-impact.sql` 自体を実行して確認したわけではありません。** 同スクリプトのコメント・SELECT 文は今も未実測の `WHFILE`/`WHLIB` のままなので、実際に手を動かすときは Step 0 の `SELECT * FETCH FIRST 1 ROW ONLY` で確認し、`WHREFI`/`WHRELI` に読み替えてください。
- **`DSPPGMREF` の `*OUTFILE` 列名(`WHPGM`/`WHLIB`/`WHFILE`/`WHFLIB`)、Step 1・Step 3 が予想する結果(`JU0900C`・`ZA0500`・`JU0300` が実際に出ること)、Step 4(`DCLF` が `DSPPGMREF` から見えるか)、`FNDSTRPDM`(Step 5)の挙動は、いずれも未検証のままです(未検証、2026-09-27時点)。** `docs/probes.md` には `DSPPGMREF`・`FNDSTRPDM` を実際に実行した記録が一件もありません。依存するプローブ `P18`(`DSPPGMREF`・`DSPDBR`・`FNDSTRPDM` を1つのジョブでまとめて確認する)は、**`DSPDBR` 側の列名という中身の一部が上記のとおり別件で判明したものの、P18 自体はまだ実施していません**(前掲の案内欄「依存するプローブ: P18(未実施)」のとおりです)。`DSPDBR` は `part05-legacy-probe` で非対話(SSH)実行を確認済みで、`DSPPGMREF` も同じ `OUTPUT(*OUTFILE)` 形式のコマンドなので非対話で実行できるはずですが、**このセッションではまだ一度も実行していません。** さらに、**`FNDSTRPDM` が対話操作(5250画面)を要するかどうか自体、このセッションでは確認できていません。** このレッスン冒頭の「道具」欄は `5250(PDM)・SQL` と明記しており、`FNDSTRPDM` は PDM のコマンドであるため、対話的な5250セッションを前提にしている可能性が高いです(05-02 の実機メモも、`WRKMBRPDM`・SEU のような PDM 系の対話画面をV3〔対話操作〕に分類しています)。加えて、`docs/probes.md`「第6部の実機検証: `part06-0103-freeform`」が記録しているとおり、`qsh` の `system "CALL PGM(...)"` 経由で動くジョブは印刷装置ファイルへの出力が実在するスプール・ファイルにならず `CPYSPLF` で回収できないという既知の制約があり、これを踏まえると `FNDSTRPDM` の一覧結果を非対話で回収できるかどうかも未検証です。次回接続では、まず `FNDSTRPDM` が非対話で完結するかどうかから確認します。
- **`tools/qclsrc/txmigr.clp` 自体は、まだ実機でコンパイル・実行していません。** 上記の `DSPDBR` 列名確定を受けて同ファイルの冒頭コメントと本体(`WHREFI`/`WHRELI` 基準への修正)は既に直してありますが、**このセッション中に見つけて静的に直した `DCLF` の並び順に関するコンパイル阻害バグの修正を含め、修正後のソースはまだ一度も実機に接続していません。** TXMIGR 本体の検証は別途行う予定です。
