## なぜ学ぶか

**第6部の`F0605A`(06-05)は`calcTaxTotal`(税込み計算)を、`F0605A`・`F0606A`(06-05/06-06)は共通で`sendMsg`(ジョブ・ログへの観測チャネル)を、それぞれソース・コードとして一字一句重複させていました。** これは、第6部が`/COPY`/`/INCLUDE`を対象外としていた結果としての、意図的な重複です(`f0606s.rpgle`自身のヘッダー・コメントが、第6部の設計方針として`/copy`/`/include`を対象外にしていたことを明記しています)。第7部では、いよいよこの重複を解消します。ここで初めて、**ロジックを1か所にまとめ、複数のプログラムから共有する**という、ILE(統合言語環境)本来の目的に取り組みます。

そのための土台が、このレッスンで学ぶ**モジュール(`*MODULE`)**という単位です。IBM iのすべてのRPG IVプログラムは、内部的には必ず1つ以上のモジュールから作られています。第6部までは`CRTBNDRPG`という1コマンドで「ソースからいきなり`*PGM`」を作っていたため、モジュールという中間段階は意識せずに済んでいました。このレッスンでは、あえてその中間段階を表に出し、`calcTaxTotal`/`sendMsg`を**専用のユーティリティー・モジュール**(業務ニックネーム「JUCUTL」、実名`M0701B`)に集約し、それを主モジュール`M0701A`と一緒に1つのプログラム`F0701A`へ結合します。第8部で本格的に使う「JUCSRV一式」(07-02〜07-03で育てるサービス・プログラム)も、この`*MODULE`という単位の理解が前提になります。

## 新出

- 中核概念:
  1. **2段階コンパイル**: `CRTRPGMOD`(ソース→`*MODULE`)と`CRTPGM`(`*MODULE`→`*PGM`)に分かれること。`CRTBNDRPG`はこの2段階を1コマンドにまとめた近道にすぎません。
  2. **1つの`*PGM`の中で、実際にプログラム・エントリー手続き(プログラムの入り口)として使われるモジュールは1つだけ**。`CRTPGM`の`ENTMOD`パラメーターの既定値`*FIRST`は、`MODULE()`に列挙した中で最初にプログラム・エントリー手続きを持つモジュールを選ぶだけで、2本以上のモジュールがそれぞれmainプロシージャーを持っていてもそれ自体はエラーになりません(一次資料: CLコマンド・リファレンスの`ENTMOD`。エラーになるのは`ENTMOD(*ONLY)`を明示した場合だけです)。選ばれなかった側のmainロジックが黙って呼べなくなるだけなので、今回のように片方を`nomain`にしておくのが安全な設計です。
  3. **`CRTPGM`が決めること: 結合方式と活動化グループの両方**: 今回の`CRTPGM MODULE(...)`はモジュールのコードをそのまま`*PGM`へコピーする「コピー結合」です(07-02で扱う`*SRVPGM`は、実行時に別オブジェクトとして存在し続ける「参照結合」で、これとは別の仕組みです)。さらに、活動化グループ(`ACTGRP`)も、モジュール自身の`ctl-opt`ではなく`CRTPGM`コマンド自身のパラメーターで決まります(下の「活動化グループは`CRTPGM`側が決める」を参照)。
- 構文:
  - `CRTRPGMOD`(ソースから`*MODULE`を作るコマンド)
  - `CRTPGM ... MODULE(...)`(複数の`*MODULE`を1つの`*PGM`に結合するコマンド)
  - `dcl-proc`の`export`キーワード(その手続きを他のモジュールから呼べるようにする)
  - `/include`(公開する手続きのプロトタイプを、呼ぶ側・呼ばれる側の両方から読み込む共有メンバー)
  - `DSPPGM DETAIL(*MODULE)`(`*PGM`が実際にどのモジュールから構成されているかを確認するコマンド)

`QMHSNDPM`(`sendMsg`の内部で使っているAPI)は、06-06で前方参照として既に触れているため、このレッスンの新出には数えません(詳しくは下の説明を参照)。

## 説明

### `*MODULE`/`*PGM`/`*SRVPGM`を一般的な例えで整理する

| 一般的なOSの用語 | IBM iでの対応 | 特徴 |
|---|---|---|
| `.o`(コンパイル済みオブジェクト・ファイル。単体では実行できない) | `*MODULE` | `CRTRPGMOD`で作る。`CALL`で直接呼び出せない。 |
| 静的リンク済みの実行ファイル | `*PGM`(`CRTPGM MODULE(...)`) | 指定した複数の`*MODULE`のコードをそのまま**コピー**して1つにまとめる。結合後は元の`*MODULE`が無くても実行できる。 |
| `.so`/`.a`(共有ライブラリ) | `*SRVPGM`(07-02の主題) | 実行時に別オブジェクトとして存在し続け、`*LIBL`経由で**参照**として解決される(「参照による結合」)。 |

このレッスンで作るのは表の真ん中の行、**コピーによる結合**です。一番下の行(参照による結合)は07-02で扱います。

### 2段階コンパイル: `CRTRPGMOD` → `CRTPGM`

第6部までは、次のように1コマンドで済ませていました(例: 06-03の`F0603A`)。

```text
CRTBNDRPG PGM(<自分のユーザー名>1/F0603A) SRCFILE(<自分のユーザー名>1/QRPGLESRC) SRCMBR(F0603A)
```

`CRTBNDRPG`は、内部で「ソース→`*MODULE`」→「`*MODULE`→`*PGM`」という2段階を自動的にまとめて実行しているだけです。今回は、この2段階をあえて別々のコマンドとして実行します。

```text
CRTRPGMOD MODULE(<自分のユーザー名>1/M0701B) SRCFILE(<自分のユーザー名>1/QRPGLESRC) SRCMBR(JUCUTL)
CRTRPGMOD MODULE(<自分のユーザー名>1/M0701A) SRCFILE(<自分のユーザー名>1/QRPGLESRC) SRCMBR(M0701A)
CRTPGM PGM(<自分のユーザー名>1/F0701A) MODULE(<自分のユーザー名>1/M0701A <自分のユーザー名>1/M0701B) ACTGRP(*NEW)
```

`CRTRPGMOD`はソース・メンバー1本につき`*MODULE`を1つ作ります(`*PGM`はまだできません)。`CRTPGM`が、指定した複数の`*MODULE`(ここでは`M0701A`・`M0701B`の2本)を1つの`*PGM`(`F0701A`)にまとめます。

**`jucutl.rpgle`(実名`M0701B`)は、この2段階ビルドが唯一の選択肢です。** `nomain`モジュール(次項)は`CRTBNDRPG`では作れず、必ず`CRTPGM`(または`CRTSRVPGM`)で他のモジュールと結合する必要があるためです。

### mainを持てるのは1つのモジュールだけ: `M0701A`(main)と`M0701B`(nomain)

`jucutl.rpgle`(実名`M0701B`)は、ファイルの先頭でこう宣言しています。

```rpgle
ctl-opt nomain;
```

`nomain`は「このモジュールにはmainプロシージャー(プログラムの入り口となる手続き)が無い」という宣言です。中身は`calcTaxTotal`・`sendMsg`という、2本の手続き(`dcl-proc`)だけです。一次資料(ILE RPG言語リファレンス)は、`NOMAIN`キーワードについて「このモジュールはプログラム・エントリー・モジュールになれない。したがって`NOMAIN`を指定したモジュールは`CRTBNDRPG`でプログラムを作れず、`CRTPGM`でプログラム・エントリー手続きを持つ別のモジュールと結合するか、`CRTSRVPGM`を使う必要がある」と明記しています。

一方`m0701s.rpgle`(実名`M0701A`)は、`nomain`を書いていません。`/include`の直後から始まる、標識だけの素朴なコード(サイクル・メイン、`dcl-pi`なし)がそのままmainプロシージャーになります。

```rpgle
taxTotal1 = calcTaxTotal(1580);
sendMsg('M0701A: 1580 at default rate = ' + %trim(%char(taxTotal1)));

taxTotal2 = calcTaxTotal(1580 : 1.08);
sendMsg('M0701A: 1580 at rate 1.08 = ' + %trim(%char(taxTotal2)));

sendMsg('M0701A: calcTaxTotal/sendMsg ran via M0701B.');

*inlr = *on;
return;
```

**1つの`*PGM`の中で、実際にプログラム・エントリー手続きとして選ばれるモジュールは1つだけです。** `CRTPGM`の`ENTMOD`パラメーター(一次資料: CLコマンド・リファレンス)の既定値`*FIRST`は、「`MODULE()`に列挙した中で、最初にプログラム・エントリー手続きを持つモジュールを選ぶ」というだけの規則で、2本以上のモジュールがそれぞれmainプロシージャーを持っていても、それ自体はエラーになりません(エラーになるのは`ENTMOD(*ONLY)`を明示した場合だけです)。ILE RPGプログラミング・ガイドの結合例(10579行目付近)も、2本のモジュールのうち1本だけがプログラム・エントリー手続きを持つ場合について「どちらの順番で`MODULE()`に書いてもよい」とだけ述べており、両方が持つ場合にエラーになるとは述べていません。今回`M0701A`(main)・`M0701B`(nomain)という組み合わせにしているのは、**選ばれなかった側のmainロジックが黙って呼べなくなる**という事故を避けるためです。両方に`ctl-opt`無しの素朴なメインラインを書いた場合に実際どうなるか(`ENTMOD`の既定`*FIRST`がどちらを選ぶか)は、このレッスンでは実機確認していません——`verify/part07-01-modules`のマニフェストも、main×2の組み合わせは検証していません(演習3で試すのは`M0701A`単独の`CRTBNDRPG`で、これとは別の話です)。

### モジュール間で手続きを公開する: `export`と`/include`

`M0701B`(`jucutl.rpgle`)は、`calcTaxTotal`・`sendMsg`をこう宣言しています。

```rpgle
dcl-proc calcTaxTotal export;
  dcl-pi *n packed(9:2);
    amount packed(7:2) value;
    rate   packed(3:2) const options(*nopass);
  end-pi;
  ...
end-proc;

dcl-proc sendMsg export;
  dcl-pi *n;
    text char(60) const;
  end-pi;
  ...
end-proc;
```

`export`キーワードが無いと、その手続きは**同じモジュールの中からしか**呼べません。`export`を付けることで、`CRTPGM`が別のモジュールからの呼び出しを解決できるようになります。

呼ぶ側(`M0701A`)・呼ばれる側(`M0701B`)の両方が、同じプロトタイプ定義を共有する必要があります。今回はそれを`jucutlp.rpgleinc`という別メンバーに切り出し、両方のソースから`/include`しています。

```rpgle
dcl-pr calcTaxTotal packed(9:2);
  amount packed(7:2) value;
  rate   packed(3:2) const options(*nopass);
end-pr;

dcl-pr sendMsg;
  text char(60) const;
end-pr;
```

```rpgle
/INCLUDE jucutlp
```

一次資料(ILE RPG言語リファレンス)は、「アプリケーションの保守をしやすくするため、公開する手続きのプロトタイプを別のソース・メンバーに置くとよい。そうする場合は、その手続きを実装するモジュールと、それを呼び出すすべてのモジュールの両方に、そのメンバーへの`/COPY`または`/INCLUDE`を書くこと」とTipとして勧めています。**これはコンパイラーが強制するものではありません**(`jucutl.rpgle`自身の`dcl-proc`は、この共有メンバーが無くても単独でコンパイル・エクスポートできます)。共有メンバーを使うことで実際に得られる効果は、`jucutl.rpgle`自身の`calcTaxTotal`/`sendMsg`の実装(`dcl-pi`)を、この共有メンバーの宣言(`dcl-pr`)と、コンパイラーが**両方から**突き合わせてくれるようになる点です(一次資料いわく「プロシージャー・インターフェースは、対応するプロトタイプと一致していなければならない」)。呼ぶ側だけが食い違いに気づく、という事故を防げます。

`M0701A`側の呼び出し(`calcTaxTotal(1580)`・`calcTaxTotal(1580 : 1.08)`)には、`EXTPGM`も`EXTPROC`も付いていません。これは**「別の`*PGM`を呼び出す」のではなく、「同じ`*PGM`の中の、別モジュールにある手続きを呼び出す」プロトタイプ**だからです。呼び出し先は`CRTPGM`が`M0701A`と`M0701B`を結合するときに解決されます。対して、F0605A(06-05)が本物の別プログラム`R0409A`(04-09、ZAHIK3)を呼び出すときは、次のように`EXTPGM`を明示していました。

```rpgle
dcl-pr r0409a extpgm('R0409A') end-pr;
```

`EXTPROC`を指定しなかった場合、結合呼び出しの実際の呼び出し先は、一次資料(ILE RPG言語リファレンス)によれば「プロトタイプ名を大文字にしたもの」になります。ここでは`CALCTAXTOTAL`・`SENDMSG`が、`jucutl.rpgle`側で`export`された手続き名(同じく大文字化した`CALCTAXTOTAL`・`SENDMSG`)と一致しています。

### `sendMsg`の内部チャンネル

`sendMsg`は、バッチ・ジョブでは`DSPLY`が既定で`QSYSOPR`宛てになってしまうため、実行結果をジョブ・ログに残す観測チャネルとして第6部で導入した手続きです(`src/qrpglesrc/f0605s.rpgle`の「Why not DSPLY」ヘッダー・コメント、一次資料: `ilerpgref75.txt`55828行目。この技法の元になった06-05のレッスン本文自体は、この文書の執筆時点ではまだ未執筆です)。内部では**`QMHSNDPM`(Send Program Message API)を直接呼び出しており**、`jucutl.rpgle`(`M0701B`)・`F0605A`・`F0606A`はいずれもこの形です(設計段階からの経緯・実機での発見の詳細は下の「実機メモ」を参照)。呼ぶ側(`M0701A`)から見た呼び出し方(`text char(60) const`を1つ渡すだけ)は変わりません。`QMHSNDPM`自体の詳しい構文は06-09の新出事項なので、ここでは「`sendMsg`に文字列を渡すと、ジョブ・ログに`CPF9898`として残る」とだけ知っておいてください。

### 活動化グループは`CRTPGM`側が決める

`M0701A`(`m0701s.rpgle`)のソース冒頭には、次のブロックがあります。

```rpgle
/IF DEFINED(*CRTBNDRPG)
ctl-opt dftactgrp(*no) actgrp(*new);
/ENDIF
```

一見「このモジュールは活動化グループ`*NEW`で動く」と宣言しているように見えますが、**このレッスンで実際に使うビルド経路(`CRTRPGMOD`→`CRTPGM`)では、このブロックは最初から実行されません。** `*CRTBNDRPG`は、ソースを`CRTBNDRPG`コマンドで単独コンパイルしたときにだけ真になる、定義済みの条件名です。`CRTRPGMOD`でコンパイルする今回は真にならないため、`ctl-opt dftactgrp(*no) actgrp(*new);`という行そのものが試されません。

そもそも一次資料(ILE RPG言語リファレンス)は、`ACTGRP`キーワードを「`CRTBNDRPG`コマンドを使う場合にのみ有効」、`DFTACTGRP`キーワードも同様に「`CRTBNDRPG`コマンドを使う場合にのみ有効」と明記しています。`CRTRPGMOD`のパラメーター一覧(一次資料: CLコマンド・リファレンス)には、そもそも`ACTGRP`/`DFTACTGRP`というパラメーター自体がありません。

では`F0701A`の活動化グループは何が決めるのでしょうか。答えは**`CRTPGM`コマンド自身の`ACTGRP`パラメーター**です。

```text
CRTPGM PGM(<自分のユーザー名>1/F0701A) MODULE(<自分のユーザー名>1/M0701A <自分のユーザー名>1/M0701B) ACTGRP(*NEW)
```

ここで`ACTGRP(*NEW)`を省略すると、既定値は`ACTGRP(*ENTMOD)`になります。一次資料(CLコマンド・リファレンス)によれば、`ACTGRP(*ENTMOD)`はRPGLEのプログラム・エントリー・モジュール(今回は`M0701A`)を、新しい専用の活動化グループにではなく、**共有の`QILE`活動化グループ**(`STGMDL(*TERASPACE)`の場合は`QILETS`)に割り当てます。第6部の`F0605A`(06-05)・`F0606A`(06-06)は、束縛呼び出し(`calcTaxTotal`/`sendMsg`)のために`ctl-opt dftactgrp(*no) actgrp(*new);`をすでに書いており(一次資料: `ilerpgref75.txt`13422・25064-25090・25072-25074行目、束縛呼び出しには`DFTACTGRP(*NO)`が必須なため)、既定の活動化グループから明示的に外れていました。また、06-13・06-14・06-15の`Q0613A`・`Q0614A`・`Q0615A`のように、そもそも`CRTBNDRPG`を使わず`CRTSQLRPGI`で作られた`*PGM`も第6部には複数あります。**「第6部までの`*PGM`はすべて`CRTBNDRPG`の既定活動化グループで作られていた」というのは正確ではありません。** 第6部までに無かったのは、**コンパイルするコマンド(`CRTBNDRPG`/`CRTSQLRPGI`)自身とは別のコマンド(`CRTPGM`)が、モジュール自身の`ctl-opt`とは無関係に活動化グループを決める**、という今回の構図です。**「モジュール自身の`ctl-opt`ではなく、`CRTPGM`コマンド側が実際の活動化グループを決める」というのが、このレッスンの核心です。**

> **この文書の執筆時点での注記**: `CRTRPGMOD`で(`/IF DEFINED(*CRTBNDRPG)`で囲まずに)`ctl-opt actgrp(...)`を直接書いてコンパイルした場合にコンパイラーがどう振る舞うかは、このレッスン自身の実機検証では試していません。ただし第7部`part07-04b-actgrp`の実機検証(`docs/probes.md`、確認日2026-09-27)で、名前付き活性化グループ`ctl-opt actgrp('F0704AG')`を`CRTRPGMOD`に直接書いたところ、黙って無視されるのではなく**`Compilation stopped. Severity 20 errors found in program.`という診断で`CRTRPGMOD`自体が失敗する**ことが分かっています(`*NEW`固有の値までは別途確認していませんが、キーワード自体が拒否される、という結果は値には依存しないと考えられます)。また、`CRTPGM`に明示した`ACTGRP(*NEW)`について実機で確認できているのは、コンパイルがHighest Severity 00で通り`F0701A`が正しく実行される、という点までです。`F0701A`の活動化グループが実際に`*NEW`(あるいは省略時に`*ENTMOD`)になったこと自体を、クエリー等で直接確認したことはまだありません(下記「実機メモ」参照。この点を学習者自身に確認してもらう設計になっているのが演習2です)。

## 実演

**この実演で作る3つのオブジェクト(`M0701A`・`M0701B`・`F0701A`)は、著者の検証ライブラリーでの実機コンパイル・実行(下の「実機メモ」参照)まで確認済みです。**

1. SSHで接続し、`~/ibmi-kyozai`を最新にする(`git pull`)。

2. ソースを取り込む(1回の接続でまとめて行います)。`<自分のユーザー名>1/QRPGLESRC`は06-01b/06-03までに作成済みのはずです。まだ無ければ`CRTSRCPF FILE(<自分のユーザー名>1/QRPGLESRC) RCDLEN(112)`で作成してから進めてください。**`jucutlp.rpgleinc`(共有メンバー)を先に取り込んでください**——後で`jucutl.rpgle`・`m0701s.rpgle`をコンパイルするとき、`/include`先が既に存在している必要があります。

   ```sh
   system "CPYFRMSTMF FROMSTMF('/home/<自分のユーザー名>/ibmi-kyozai/src/qrpglesrc/jucutlp.rpgleinc') TOMBR('/QSYS.LIB/<自分のユーザー名>1.LIB/QRPGLESRC.FILE/JUCUTLP.MBR') MBROPT(*REPLACE) STMFCCSID(1208)"
   system "CPYFRMSTMF FROMSTMF('/home/<自分のユーザー名>/ibmi-kyozai/src/qrpglesrc/jucutl.rpgle') TOMBR('/QSYS.LIB/<自分のユーザー名>1.LIB/QRPGLESRC.FILE/JUCUTL.MBR') MBROPT(*REPLACE) STMFCCSID(1208)"
   system "CPYFRMSTMF FROMSTMF('/home/<自分のユーザー名>/ibmi-kyozai/src/qrpglesrc/m0701s.rpgle') TOMBR('/QSYS.LIB/<自分のユーザー名>1.LIB/QRPGLESRC.FILE/M0701A.MBR') MBROPT(*REPLACE) STMFCCSID(1208)"
   ```

   (取り込んだソース・メンバー名は`JUCUTLP`・`JUCUTL`・`M0701A`です。**`JUCUTL`というメンバー名からできる`*MODULE`の実名は`M0701B`であり、名前が一致しません**——`jucutl.rpgle`自身の説明のとおり、「JUCUTL」はこのレッスンの中だけで使う業務ニックネームで、実際にコンパイルするオブジェクトの実名は型+部+課+連番の規則([付録E](../appendix/e-naming.md)参照)に従っています。)

3. 5250に戻り、`CRTRPGMOD`を2回、`CRTPGM`を1回実行します。

   ```text
   CRTRPGMOD MODULE(<自分のユーザー名>1/M0701B) SRCFILE(<自分のユーザー名>1/QRPGLESRC) SRCMBR(JUCUTL)
   CRTRPGMOD MODULE(<自分のユーザー名>1/M0701A) SRCFILE(<自分のユーザー名>1/QRPGLESRC) SRCMBR(M0701A)
   CRTPGM PGM(<自分のユーザー名>1/F0701A) MODULE(<自分のユーザー名>1/M0701A <自分のユーザー名>1/M0701B) ACTGRP(*NEW)
   ```

   3つとも Highest Severity 00 になることを確認してください(著者の環境ではすべて一度目で通っています)。

4. `CALL PGM(<自分のユーザー名>1/F0701A)`を実行し、`DSPJOBLOG`で次の3行(`CPF9898`)が記録されていることを確認します。

   ```text
   M0701A: 1580 at default rate = 1738.00.
   M0701A: 1580 at rate 1.08 = 1706.40.
   M0701A: calcTaxTotal/sendMsg ran via M0701B..
   ```

   (3行目末尾の連続したピリオドは誤植ではありません。`sendMsg('M0701A: calcTaxTotal/sendMsg ran via M0701B.')`という呼び出し自体の文字列がすでに`.`で終わっており、そこに`CPF9898`のメッセージ・テキストが付け足す`.`が重なって2つ連続していると考えられます——1行目・2行目は元の文字列に`.`が無いため、付け足された1つだけが見えています。)

   1行目・2行目は`calcTaxTotal`(`M0701B`側の手続き)の戻り値、3行目は`sendMsg`(同じく`M0701B`側の手続き)が実際に呼べたことそのものの証拠です。**3行とも、モジュール境界(`M0701A`→`M0701B`)を跨いだ呼び出しの結果です。**

5. `DSPPGM PGM(<自分のユーザー名>1/F0701A) DETAIL(*MODULE)`を実行し、`M0701A`・`M0701B`の2本が表示されることを確認します。

   試しに`DSPPGM PGM(<自分のユーザー名>1/F0603A) DETAIL(*MODULE)`(06-03で`CRTBNDRPG`一発で作った単一ソース産`*PGM`)も実行してみてください。表示されるのは、プログラムと同じ名前の`*MODULE`(`F0603A`)がおそらく1本だけのはずです(`CRTBNDRPG`は内部で自動的に同名の`*MODULE`を1本作ってから結合するため)。**この`F0603A`側の結果は、このレッスンでは実機で確認していません**——自分の環境で実際に試して、`F0701A`(2本、しかもプログラムと同名ではないモジュール)との違いを確かめてください。

## 演習

1. `M0701A`に3つ目の呼び出しを追加してください(`taxTotal3 = calcTaxTotal(1580 : 1.05);` と、対応する`sendMsg`呼び出し)。追加したら**`CRTRPGMOD MODULE(<自分のユーザー名>1/M0701A) ... REPLACE(*YES)`だけを実行し、`CRTPGM`は実行せずに**`CALL PGM(<自分のユーザー名>1/F0701A)`を試してください。新しいメッセージは出ないはずです(`F0701A`はまだ古い`M0701A`のコピーのままだからです)。次に`CRTPGM PGM(<自分のユーザー名>1/F0701A) MODULE(<自分のユーザー名>1/M0701A <自分のユーザー名>1/M0701B) ACTGRP(*NEW) REPLACE(*YES)`を実行してから再度`CALL`し、初めて新しいメッセージが出ることを確認してください。**「コピーによる結合」は、モジュール単体を再コンパイルしただけでは`*PGM`に反映されず、必ず`CRTPGM`をやり直す必要がある**ことを、身をもって確認する演習です。
2. (発展)`CRTPGM`から`ACTGRP(*NEW)`を外して(`CRTPGM PGM(<自分のユーザー名>1/F0701A) MODULE(<自分のユーザー名>1/M0701A <自分のユーザー名>1/M0701B) REPLACE(*YES)`)再結合し、`CALL`してみてください。3行のメッセージ自体は変わらないはずです。**この演習のポイントは、動作(見た目の結果)が変わらないことそのものです**——活動化グループの違いは、今回のような単純なプログラムの正しさには現れず、複数プログラムの独立性(1つが異常終了したときの影響範囲など)に関わる話だからです。実際に`ACTGRP(*ENTMOD)`になったかどうかを、5250から簡単に確認する方法は、このレッスンの執筆時点ではまだ確認できていません。
3. (発展・任意)`m0701s.rpgle`の`/IF DEFINED(*CRTBNDRPG)`〜`/ENDIF`のブロックを外し、`M0701A`だけを`CRTBNDRPG`で単独コンパイルしてみてください(`M0701B`とは結合しません)。`calcTaxTotal`/`sendMsg`の実体がどこにも無いため、コンパイルまたはバインドの段階でエラーになると予想されます。実際にどのメッセージIDになるか、試す前に予想を立ててから確認し、記録しておいてください(このレッスンでは未確認です)。

## 片付け

作成した`M0701A`・`M0701B`・`F0701A`はそのまま残してかまいません。次のレッスン(07-02)は、これらを直接使わず、新しいオブジェクト`JUCSRV`を作ります。演習1で`M0701A`を書き換えた場合も、そのままで構いません。

## まとめ

| 英語 | 日本語 |
|---|---|
| Module (`*MODULE`) | モジュール |
| Program (`*PGM`) | プログラム |
| Bind by copy | コピーによる結合 |
| Bind by reference | 参照による結合 |
| Activation group | 活動化グループ |
| NOMAIN module | mainプロシージャーを持たないモジュール |
| Program-entry module | プログラムの入り口となるモジュール(1つの`*PGM`に1つだけ) |
| Export | 手続きを他のモジュールから呼べるようにする指定 |
| Bound call | 別モジュールの手続きへの、結合時に解決される呼び出し |

次のレッスン(07-02)では、`calcTaxTotal`相当のロジックを実際の`*SRVPGM`(`JUCSRV`)にまとめ、`*LIBL`経由の参照結合を扱います。
