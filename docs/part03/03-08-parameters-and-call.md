## なぜ学ぶか

CL プログラム同士は、`CALL` と `PARM` でパラメーターをやり取りします。**このやり取りは「参照渡し」**であり、また、**コマンド行から直接 `CALL` するときは、値の型が暗黙のルールで決まる**ため、思わぬ罠にはまることがあります。このレッスンでは、それを実際に体験します。

## 新出

- `PGM PARM()`(パラメーターの受け取り)
- 参照渡し
- コマンド行からの `CALL` における暗黙の型変換の罠

## 説明

### 参照渡し

CL の `CALL`/`PARM` は、値そのものではなく**変数の場所(参照)**を渡します。呼び出された側が受け取ったパラメーターの内容を書き換えると、**呼び出した側の変数も変わります**(コピーではないため)。

### コマンド行から CALL するときの罠

CL プログラムがプログラムの中から別のプログラムを呼ぶとき(`CALL PGM(X) PARM(&変数)`)は、渡す側と受け取る側で、**同じ型・同じ長さ**の変数を用意すれば安全です。ところが、**コマンド行から直接 `CALL PGM(X) PARM(値)` と打った場合**、値の型はコマンド行の解釈規則で暗黙に決まります。よく知られている落とし穴として、次のようなものがあります。

- **数値リテラル**は、既定でパック10進 `(15 5)`(15桁、小数5桁)として渡される。
- **文字リテラル**は、32バイト未満であれば32バイトに埋められて渡される。

呼び出される側のプログラムが、これと違う型・長さで `PARM` を宣言していると、**値が正しく渡らず、壊れた値になったり、エラーになったりします。**

### 対策

1. コマンド行から直接 `CALL` するのではなく、**専用の CL プログラムやコマンドを経由**して呼び出す(03-11 で「自作コマンド」として学びます)。
2. パラメーターの型・長さを、呼び出し元と呼び出し先で**必ず一致**させる。
3. 迷ったら、まず小さな実験プログラムで確かめる(このレッスンのように)。

## 実演

1. `WRKMBRPDM FILE(<自分のユーザー名>1/QCLSRC)` で `C0308T`(`CLP`。"T" は Target = 呼ばれる側)を作る。

   ```clp
   PGM        PARM(&NUM)
   DCL        VAR(&NUM) TYPE(*DEC) LEN(5 0)
   DCL        VAR(&NUMC) TYPE(*CHAR) LEN(15)
   CHGVAR     VAR(&NUMC) VALUE(&NUM)
   SNDPGMMSG  MSG('Received: ' *TCAT %TRIM(&NUMC))
   ENDPGM
   ```

2. コンパイルする。
3. **コマンド行から直接**、次を実行する。

   ```text
   CALL PGM(C0308T) PARM(123)
   ```

4. `DSPJOBLOG` を確認する。`&NUM`(`*DEC LEN(5 0)` のはず)に、`123` ではない、予想外の値が入っていないか(またはエラーになっていないか)を確認してください。**これが罠です。**

## 安全な呼び方

`C0308S`("S" は Safe)という、**CL プログラムの中から**同じ型で `CALL` するプログラムを作ります。

```clp
PGM
DCL        VAR(&NUM) TYPE(*DEC) LEN(5 0) VALUE(123)
CALL       PGM(C0308T) PARM(&NUM)
ENDPGM
```

コンパイルして `CALL PGM(C0308S)` を実行し、今度は `Received: 123` と正しく表示されることを確認してください。

## 演習

1. `C0308T` の `&NUM` の型を `*CHAR LEN(10)` に変え、対応する `SNDPGMMSG` も調整したうえで、コマンド行から `CALL PGM(C0308T) PARM('AB')`(2文字のリテラル)を実行し、`DSPJOBLOG` でどう表示されるか確認してください。
2. 同じく `*CHAR LEN(40)` にして試し、`LEN(10)` のときと結果が変わるか比べてください。

## 実機メモ

- 確認日: 2026-09-25。**「文字リテラルが32バイトに埋められる」というルールを、TXSETUP のハング修正作業で実機確認できた。** `CLONEDIR`(宣言長200文字)に13文字のリテラルを `CALL PGM(...) PARM(...)` で渡したところ、32バイトまでしか空白で埋められず、33バイト目以降に隣接パラメーターの文字列が紛れ込んで `CPYFRMSTMF` が壊れたパスでエラーになった。デバッグ出力での実測でも、リテラルの直後から空白が続き、34バイト目付近から次のパラメーターの内容が始まっていることを確認した(ほぼ32バイト境界と一致)。詳細は `docs/probes.md` の「解決: ハング修正を実機で再検証」節を参照。数値リテラルが `(15 5)` で渡されるルールは、依然としてこのセッションでは未確認(一次資料に基づく)。
- このセッションでは別の `CALL` に関する実機での発見(無修飾の `CALL` はジョブの `*LIBL` に依存する、パラメーターを一切渡さない `CALL` が `CPD0172` になった)があった。**ただし後者は SSH 経由の `system()` 呼び出しで確認したものであり、5250 の対話的コマンド行で同じことが起きるかは未確認。** 詳細は `docs/probes.md` を参照。
