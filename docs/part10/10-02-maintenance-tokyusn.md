## なぜ学ぶか

保守の仕事の大半は、「項目を1つ足してほしい」のような小さな依頼です。しかし、項目を足した物理ファイルは、そのファイルを外部記述で使うすべてのプログラムの様式レベルIDを変えます。**変更そのものは`CHGPF`の1行なのに、その前(何が影響を受けるかを調べる、戻せるように退避する)とその後(作り直す、確かめる、戻し方を用意する)が仕事の大部分です。** このレッスンでは、得意先マスター`TOKUIM`に与信限度額`TOKYSN`を足す依頼を、その全体で1回通します。

依頼の後半(受注一覧で、限度額を超える受注に印を付ける)は、既存のRPG IIIプログラム`JU0300`の小さな改修です。「小さな改修でも、ファイルを3本足し、複合キーで読む」という現場でよくある大きさを体験します。

残すものは3つです。**影響調査表**(変更の前に、何を調べたか)、**改修記録**(何をどう変え、どう確かめたか)、**移送手順書**(別の人がその通りに実行でき、元に戻せる手順)。10-01の障害報告書と同じく、直したことより、根拠と再現性を残すことが求められます。ここで書く3つの書き方は、10-03の切り戻し(`ZA0ORIG`)や、10-04の設計書の「テスト証拠」にも通じます。

このレッスンの最後で、`TOKUIM`を元の形に戻します。10-03・10-04が使う`JUCSRV`(サービス・プログラム)は`TOKUIM`を開くので、元の形のままであることを前提にしているからです。

### 状況

> 得意先ごとに与信限度額を持たせたい。受注一覧(`JU0300`)で、限度額を超える受注に印を付けてほしい。既存の得意先の限度額は、あとで営業が入れる。変更で他の帳票や画面を壊さないこと。

あなたの仕事は、影響を調べ、安全に変更し、確かめ、他の人が同じ手順で移送・切り戻しできるように書き残すことです。変更する項目は次のとおりです。

|---|---|
| 名前 | `TOKYSN`(与信限度額) |
| 型・長さ | ゾーン10進、7桁、小数点以下0桁(DDSでは`7S 0`) |

### 作業の場所と、ライブラリー・リスト

このレッスンの変更は、旧システムの一式(`TOKUIM`・`TOKUIL1`・`TK0100`・`JU0300`)が入っている`<自分のユーザー名>2`の中で行います。現場なら、本番のファイルを直接`CHGPF`せず、開発用で試してから移します。ここでは`<自分のユーザー名>2`を練習の場にして、実行した手順そのものを「移送手順書」に書きます(手順書は、別の環境へ移すときに読む人のために書きます)。

**ライブラリー・リストに注意してください。** あなたの`*LIBL`には`<自分のユーザー名>1`も入っていて、そこにも(第4部・第5部で作った)`TOKUIM`があるかもしれません。`<自分のユーザー名>1`の`TOKUIM`は`TOKYSN`を持ちません。現行ライブラリーが`<自分のユーザー名>1`のまま`JU0300`を作り直すと、`TOKYSN`が見つからないか、別のファイルの様式レベルIDを焼き込んでしまいます。**このレッスンでは、最初に`SETENV *PRD`で現行ライブラリーを`<自分のユーザー名>2`にして**(05-12と同じ仕組みです)、コンパイルと呼び出しには、ライブラリー名も付けます。

### 影響調査表の分け方(中核概念1)

05-09で学んだとおり、外部記述ファイルを使うプログラムは、コンパイル時に様式レベルIDを焼き込みます。項目が増えるとIDが変わり、再コンパイル前のプログラムは、ファイルを開いた時点で`CPF4131`になります。したがって、依存物を次の3つに分けて表に書きます。

| 分類 | 例 | 必要な作業 |
|---|---|---|
| A. レベル・チェックが効く | `TOKUIM`・`TOKUIL1`を外部記述で開くRPG・CL・ILEのプログラム、サービス・プログラム | 再コンパイル(サービス・プログラムは作り直し) |
| B. 効かない | 列名を書いたSQL、名前がコメントにあるだけのソース、手書きの項目だけの表示装置ファイル | 不要(根拠を書く) |
| C. 今は使っていないが、改修後に使い始める | `JU0300`(改修前は`TOKUIM`を開きません) | 改修の対象として、改修記録に書く |

**調べる道具にも、見落としがあります。** 表には、道具が何を見落とすかも書きます。

- `DSPPGMREF`は、`OBJTYPE`を付けずに実行した結果に、サービス・プログラムの参照が**出ません**。著者の検証では、`OBJTYPE(*SRVPGM)`を付けて別に実行したときだけ、`JUCSRV`が`TOKUIM`を参照する行として出ました(V2、2026-09-30。付けない実行は`PGM(<自分のユーザー名>2/*ALL)`の形です)。`OBJTYPE`の既定値が何かは、この検証では調べていません(一般知識、要確認)。**必ず、付けない実行と、`OBJTYPE(*SRVPGM)`を付けた実行の2回を行います。**
- 実行時にしか決まらない参照(コマンド・パラメーターの文字列)、他のユーザーのライブラリー、自分の`<自分のユーザー名>2`にないプログラムは、どちらのコマンドにも出ません(05-07)。

### 変更と切り戻しの順序(中核概念2)

順序は次のとおりです。

```text
変更:     退避(CRTDUPOBJ DATA(*YES))
          → CHGPF(TOKUIM)
          → TOKUIL1 の確認と作り直し
          → (表示装置ファイル。TK0100D は手書き項目なので今回は不要)
          → プログラムの再コンパイル(TK0100 ほか)
          → JU0300 の改修
切り戻し: DLTF(TOKUIL1) → DLTF(TOKUIM) → 退避から CRTDUPOBJ → CRTLF(TOKUIL1)
          → 新しい形で作ったプログラムを、もう一度再コンパイル
```

`TOKUIL1`は`PFILE(TOKUIM)`だけの論理ファイルで、項目リストがなく、`TOKUIM`のレコード様式`TOKUIR`を共有しています。著者の検証では、`CHGPF`の直後(まだ何も作り直していない時点)に、`TOKUIL1`も`TOKYSN`を持ち、`TOKUIM`と同じ新しい様式レベルIDになっていました。作り直して(`DLTF`と`CRTLF`)も、IDは変わりませんでした(V2、2026-09-30)。また、`CHGPF`の前に作った`TOKUIL1`用のプログラムを、`CHGPF`の直後(`TOKUIL1`を作り直す前)に呼ぶと、`CPF4131`になりました(V2)。**この手順書では、05-09の順序どおり、確認のために`TOKUIL1`を必ず作り直します**。作り直さずに、新しい形で作ったプログラムが`TOKUIL1`を使えるかどうかは、確かめていません(未検証(2026-09-30時点))。

**切り戻しは、ファイルを戻しただけでは終わりません。** `CHGPF`のあとに作り直したプログラム(このレッスンの`TK0100`など)は、新しい様式レベルIDを焼き込んでいます。退避から戻した`TOKUIM`は元のIDを持つので、新しい形で作ったプログラムは、戻したファイルに対して`CPF4131`になります(著者の検証で確認。V2。`TOKUIM`を`DCLF`・`RCVF`で読む小さなCLプログラムでの観測です)。逆に、`CHGPF`の前に作ったプログラムは、`CRTDUPOBJ ... DATA(*YES)`で戻した`TOKUIM`が元のIDを持っていたので、再コンパイルなしで動きました(同じCLプログラムでの観測。V2)。`TK0100`や、`TOKYSN`を使う`JU0300`を、戻したファイルに対して呼ぶ操作は、確かめていません(未検証(2026-09-30時点)。同じ仕組みからの推論です)。

戻らないものもあります。退避を取った後で`TOKUIM`に書いた行(得意先の追加・更新)は、退避から戻すと失われます。共有の環境では、退避から切り戻しまでの間に利用者がいない時間を選びます。**`CHGPF`の直後から再コンパイルが終わるまでは、旧プログラムが`CPF4131`になる時間帯です。**

> **読解用: `TXMIGR`の守備範囲**
>
> `TXMIGR`は、実装が`TO(2)`だけで、`CHGPF`のあと、`DSPOBJD OBJTYPE(*PGM)`の出力のうち属性が`RPG`と`CLP`のプログラムを再コンパイルします(`tools/qclsrc/txmigr.clp`のソースの記述による)。**`*SRVPGM`(`JUCSRV`など)とILEのプログラムは、この方法の対象外**です。このレッスンで`TXMIGR`を使わず、手で行うのは、そのためです(`TO(3)`は実装されていません)。

### 複合キーで`CHAIN`する(中核概念3)

改修する`JU0300`は、受注(`JUCHUL1`)を1件ずつ読むサイクル・プログラムです。限度額を判定するには、1件の受注ごとに次の3件を読む必要があります。

| 読むもの | 目的 | キー |
|---|---|---|
| `TOKUIM` | 得意先の`TOKYSN` | `JUTOK`(得意先コード。1項目) |
| `JUCHUD` | 受注の1行目の商品と数量 | `JUNO` + `JULINE`(**2項目**) |
| `SHOHIM` | 商品の現在の単価`SHOTNK` | `JUSHO`(商品コード。1項目) |

`JUCHUD`のキーは2項目なので、`CHAIN`のFactor 1に1つの項目名を書くだけでは足りません。**キー・リスト**(`KLIST`)に、キーの項目を`KFLD`で並べて名前を付け、その名前を`CHAIN`のFactor 1に書きます。

```text
     C           JKEY      KLIST
     C                     KFLD           JUNO
     C                     KFLD           JULINE
     C           JKEY      CHAINJUCHUD               97
```

`KLIST`のFactor 1の位置(18〜27桁目)にキー・リストの名前`JKEY`を書き、続く`KFLD`の行の、結果フィールドの位置(43〜48桁目)にキーの項目名を、DDSのキーの順に書きます。桁がずれるとコンパイルが通らないので、桁位置は必ず確かめてください(04-01・04-12)。`JUNO`と`JULINE`は、受注のキーの順(`JUNO`、次に`JULINE`)と同じ並びにします。

### `JU0300`の編集の大きさ(決まりごと)

この改修で足すものは、次のとおりです。**元のソースの既存の行(コメント以外)は、1行も変えません。**

| 足すもの | 数 |
|---|---|
| F仕様書(`TOKUIM`・`SHOHIM`・`JUCHUD`。いずれも入力、外部記述、キー付き、`IF  E  K  DISK`の形) | 3行 |
| `KLIST`と`KFLD`(キー・リスト`JKEY` = `JUNO` + `JULINE`) | 1行 + 2行 |
| `SETOF`(印の標識を初期化) | 1行 |
| `CHAIN`(ファイルごとに1本) | 3行 |
| `Z-ADD`(`JULINE`に1を入れる) | 1行 |
| `MULT`(数量 × 現在単価) | 1行 |
| `COMP`(限度額との比較。**判定の1行**) | 1行 |
| O仕様書(明細行に`OVER LIMIT`を出す) | 1行 |

C仕様書の追加は合計で10行です(F仕様書とO仕様書を合わせて14行)。使う標識は、95(限度超過)・96(`TOKUIM`に該当なし)・97(`JUCHUD`に1行目なし)・98(`SHOHIM`に該当なし)です。**該当なしのときは、その受注に印を付けません。**

規則は1つだけです。**受注の1行目を現在の単価(`SHOHIM`の`SHOTNK`)で評価した金額が、得意先の`TOKYSN`を超えたら印を付ける。** 次の限界は、承知の上で決めています(演習(d)の応用で扱います)。

- 見るのは**1行目だけ**です(`CHAIN`1本。全行を足すには、`SETLL`と`READE`のループが要り、追加が大きくなります)。
- 単価は、注文時の単価(`JUTNK`)ではなく、現在の単価です。
- **`TOKYSN`が0のとき(`CHGPF`直後の既存の得意先がそうです)は、全件に印が付きます。** 限度額0を「未設定」と読むか「限度額なし」と読むかは、業務の決めごとで、プログラムでは決められません。

点検の対象(採点する範囲)は、`JU0300`と`TOKUIM`だけです。`TK0100`に項目を足す編集は任意の読解で、5250が要るのでV3です(演習(e))。

### 演習(a): 例題を読む(紙の上)

次は、別の項目(`TOKUIM`に`TOKZIP2`を足す)について、同僚が作った影響調査表と手順の抜粋です(架空です)。

```text
[TK0100D の DDS 抜粋]  A            TOKNM         20A  O  6 10   (REFFLD なし。手書きの項目)

[依存物]
 TK0100   RPG III  F TOKUIM IF E K   → 再コンパイル
 TOKUIL1  LF       PFILE(TOKUIM)     → DDSを書き換えて再作成
 TK0100D  DSPF     手書き項目         → DDSを再作成
 JU0300   RPG III  TOKUIMを開かない   → 要対応(再コンパイル)
[調べた方法] DSPPGMREF PGM(LIB/*ALL) OUTPUT(*OUTFILE) を1回
[手順]  1 プログラムを再コンパイル  2 CHGPF  3 TOKUIL1 を再作成
```

1. 依存物の欄の誤りを、2つ挙げてください。
2. 「調べた方法」の欄の弱点は何ですか。
3. 手順の誤りは何ですか。

<details><summary>解答例</summary>

1. (1)`TOKUIL1`は項目リストがなく、`TOKUIM`のレコード様式を共有するので、**DDSの書き換えは要りません**(作り直しが要るかどうかを、`CHGPF`のあとに確かめる)。(2)`TK0100D`は項目が手書きで、`TOKUIM`の様式レベルIDを持たないので、**作り直しは要りません**(根拠: 例題の抜粋のように、DDSに`REFFLD`が無い)。`JU0300`は、改修前は`TOKUIM`を開かないので**影響を受けません**(改修後に使い始めるなら、分類Cとして「改修の対象」に書く)。3つのうち、2つを挙げれば十分です。
2. `*SRVPGM`が、`OBJTYPE`を付けない結果に出ないので、`OBJTYPE(*SRVPGM)`を付けた実行が抜けています。ソースの直接検索(実行時にしか決まらない参照)もありません。「調べていないこと」の欄もありません。
3. `CHGPF`より**前に**プログラムを再コンパイルしても、新しい様式レベルIDを取り込めません。順序は、退避 → `CHGPF` → `TOKUIL1` → 再コンパイルです。退避の手順もありません。

</details>
