# 06-11 サブファイル: ページ単位とメッセージ・サブファイル

## ゴール

- **load-all**(全件を先に読み込む)と**ページ単位**(必要な分だけ読み込む)、2つのサブファイル読み込み方式の違いを説明し、使い分けられる。
- 選択欄(`OPT`)付きの一覧画面を書き、`READC`で「変更された行だけ」を取り出せる。
- 通常のサブファイルとは別物の**メッセージ・サブファイル**を使い、画面自身に診断メッセージ(「不正なオプションです」等)を出せる。

## なぜ学ぶか

06-04の`F0604A`には「1つの得意先につき最大4件まで」という上限がありました。5件目以降の注文がある得意先を扱うと、そのぶんは黙って表示されない、という制約です(`ORDNO1`〜`ORDNO4`という4組の固定フィールドしか画面に無かったためです)。

**サブファイルは、この「あらかじめ何行分の枠を用意するか」という悩みそのものから解放してくれる画面部品です。** 今回作る一覧画面(業務ニックネーム: `JUCLST4`、通し例9)は、`JUCHUM`(受注マスター)の**全件**を対象にした注文一覧です。1得意先に絞るのではなく、`OPT`という選択欄を各行に持たせ、行を選んで`5`と入力すると`F0604A`(06-04、注文照会)を呼び出す(ただし後述の制約あり)、という役割分担にします。

サブファイルには2つの基本戦略があります。**load-all**(全件を一度に読み込んでからサブファイルに書き込む、単純な方式)と、**ページ単位**(画面1ページ分だけ読み込み、`PAGEDOWN`(`ROLLUP`)が押されるたびに次のページ分を追加で読み込む、件数が多いときの最適化)です。このレッスンでは、まずload-allで基本形を押さえ、そのあとページ単位をload-allの発展形として扱います。

## 新出

- 中核概念:
  1. **load-all**は「全件を先に読み込む、単純だが件数が多いと重い」方式。**ページ単位**は、その発展形(まず単純な形を知り、そのあと最適化する、という順で学びます)。
  2. サブファイルの選択欄(`OPT`)は、`READC`(Read Next Changed Record)で「ユーザーが実際に入力し直した行だけ」を取り出せる。
  3. **メッセージ・サブファイル**は、通常のサブファイル(`SFL1`)とは別物です。専用のレコード様式(`MSGSFL`/`MSGCTL`)と、専用のプログラム側の合わせ方(後述の`PGMQ`)が要ります。
- 構文:
  - `dcl-f ... workstn sfile(recfmt:rrnfield)` ── サブファイルの内部処理を有効にするRPG側の宣言。
  - `SFLSIZ`/`SFLPAG` ── サブファイルの総サイズと、1画面に見せる件数。load-allとページ単位で、この2つの値の設計がまったく変わります(後述)。
  - `readc` ── 選択欄が変更された行だけを1件ずつ取り出す。
  - `ROLLUP`/`ROLLDOWN`(`PAGEDOWN`/`PAGEUP`に対応する標識キーワード)と、サブファイルが「読み込み済みの範囲内をスクロールしているだけ」なのか「本当に次のページ分の読み込みが要る」のかの見分け方。
  - `snd-msg` ── メッセージ・サブファイルへ診断メッセージを送る自由形式オペコード。

読解できれば十分な(新出扱いしない)DDSキーワード: `SFL`/`SFLCTL`/`SFLDSP`/`SFLDSPCTL`/`OVERLAY`/`SFLMSGRCD`/`SFLMSGKEY`/`SFLPGMQ`/`SFLINZ`。行・桁の指定や`CFxx`は04-11・06-04ですでに見た形と同じです。

## 説明

### load-all: 全件を先に書き込む(`D0611A`/`F0611A`)

`src/qddssrc/d0611s.dspf`(抜粋)です。

```text
     A          R SFL1                      SFL
     A            OPT            1A  B  4  2
     A            JUNO           6A  O  4  5
     A            JUTOK          6A  O  4 13
     A            JUDATE         8S 0O  4 21
     A            JUTAN          6A  O  4 31
     A          R SFL1CTL                   SFLCTL(SFL1)
     A                                      SFLSIZ(9999)
     A                                      SFLPAG(14)
     A                                      SFLDSP
     A                                      SFLDSPCTL
     A                                      ROLLUP(25)
     A                                      ROLLDOWN(26)
     A                                      CF03(03)
     A                                      OVERLAY
```

`SFL1`(サブファイル・レコード様式そのもの、`OPT`・`JUNO`・`JUTOK`・`JUDATE`・`JUTAN`の5フィールド)と`SFL1CTL`(サブファイル制御レコード様式、`SFLCTL(SFL1)`で対応関係を宣言)の組が、サブファイルの基本単位です。`SFLDSP`/`SFLDSPCTL`はそれぞれ「サブファイル本体」「制御レコード」を表示するかどうかの指定で、このファイルでは常時ON(条件標識を付けていません)にしてあります。`ROLLUP(25)`/`ROLLDOWN(26)`は、`PAGEDOWN`/`PAGEUP`キーが押されたとき標識25/26をONにする、という宣言です。`JUNO`・`JUTOK`・`JUDATE`・`JUTAN`という名前は`JUCHUM`自身のフィールド名(`db/v1/juchum.pf`)と完全に一致させてあります。06-04の`TOKCD`/`TOKNM`と同じ「同名フィールドの自動代入」の考え方を、ここでは「読み込んだレコードをそのままサブファイルへ書く」形で使うためです(`OPT`だけは`JUCHUM`に無い、この画面独自の選択欄です)。

`OVERLAY`は、サブファイル制御レコードを画面消去なしで重ね書きするための指定です。**タイトル・列見出し(1・3行目)は`SFL1CTL`自身が持ったままですが、フッター(`MORE`・`F3=Exit`、本来なら下側)だけを別レコード様式`SFL1FTR`に分けてあります。** これは、Part 5の`TK0100D`(`part05-legacy-probe`、確認日2026-09-26)で実機確認済みの制約(サブファイル制御レコードは、自分のサブファイルの**上または下のどちらか片方**にしか位置指定付きの出力を持てない、`CPD7812`)を踏まえた設計で、`D0611A`は、この分割形で配布されています。`F0611A`は毎回`write sfl1ftr;`してから`exfmt sfl1ctl;`する、という順序を守っています。

`src/qrpglesrc/f0611s.rpgle`のロード部分です。

```rpgle
dcl-f d0611a workstn sfile(sfl1:rrn1);
dcl-f juchum disk;

dcl-s rrn1 packed(4:0) inz(0);
```

```rpgle
read juchum;
dow not %eof(juchum);
  rrn1 += 1;
  opt = *blanks;
  write sfl1;
  read juchum;
enddo;
```

`JUCHUM`を先頭から終端まで`READ`で読み切り、1件ごとに`RRN1`(`SFILE`キーワードで指定した相対レコード番号フィールド)を1つ進めて`WRITE SFL1`する、という単純な形です。**`EXFMT SFL1CTL`より前に、全件の`WRITE`が終わっています。** いったんサブファイルへ書き込んでしまえば、`ROLLUP`/`ROLLDOWN`によるページ内スクロールは、システムが自動で処理します(RPG側で「次のページを読み込む」処理を書く必要がありません)。`JUCHUM`が0件のときのために、空白1行だけのプレースホルダーを書く分岐(`if rrn1 = 0; ... endif;`)も用意されています(一度も`WRITE`されていないサブファイルに対して`SFLDSP`表示を試みるリスクを避ける、というこのソース自身の設計判断です)。

### ページ単位: load-allの発展形(`D0611AP`/`F0611AP`)

`src/qddssrc/d0611ps.dspf`は、`D0611A`とほぼ同じ内容で、内容面での違いは主に次の2行です(このほか、画面タイトルの文言も`JUCLST4`から`JUCLST4P`に変わっています)。

```text
     A          R SFL1CTL                   SFLCTL(SFL1)
     A                                      SFLSIZ(4)
     A                                      SFLPAG(3)
```

`SFLSIZ(9999)`→`SFLSIZ(4)`、`SFLPAG(14)`→`SFLPAG(3)`です。**`SFLPAG(3)`は、あえて小さい値にしてあります。** `JUCHUM`のサンプル・データは8件しかないため、`SFLPAG(14)`のままでは1ページに全件収まってしまい、ページ送りを試す教材になりません。`SFLPAG(3)`にすることで、8件が3件・3件・2件という3ページに分かれ、`PAGEDOWN`(`ROLLUP`)を実際に2回試せます。`SFLSIZ(4)`は`SFLPAG`(3)より1大きい値です。ページ単位のサブファイルで、`SFLSIZ`を`SFLPAG`より少し大きく取っておく書き方はよく見られますが、これは一般的なIBMの規則として断定できるものではなく、このソース自身が採用している設計上の選択として捉えてください。

`src/qrpglesrc/f0611ps.rpgle`は、ロード部分を`loadNextPage`という手続きに分けています。

```rpgle
dcl-c PAGESIZE 3;

dcl-s rrn1 packed(4:0) inz(0);
dcl-s eofReached ind inz(*off);
```

```rpgle
dcl-proc loadNextPage;
  dcl-pi *n;
  end-pi;

  dcl-s pageCount packed(4:0) inz(0);

  dow pageCount < PAGESIZE and not eofReached;
    read juchum;
    if %eof(juchum);
      eofReached = *on;
    else;
      rrn1 += 1;
      opt = *blanks;
      write sfl1;
      pageCount += 1;
    endif;
  enddo;
end-proc;
```

`loadNextPage`は、呼ばれるたびに最大`PAGESIZE`(3)件だけ`JUCHUM`を読んで`WRITE`し、`RRN1`を**前回の続きから**進めます(`0`に戻しません)。`JUCHUM`が尽きたら`eofReached`を`*on`にし、以後は何も読み込まなくなります。呼び出す側はこうなっています。

```rpgle
loadNextPage();
...
dow not *in03;
  write sfl1ftr;
  exfmt sfl1ctl;

  if not *in03;
    if *in25 and not eofReached;
      loadNextPage();
      ...
    endif;

    readc sfl1;
    dow not %eof(d0611ap);
      ...
      readc sfl1;
    enddo;
  endif;
enddo;
```

最初の`EXFMT`より前に`loadNextPage()`を1回呼び、**1ページ分だけ**読み込みます。以降は、`*IN25`(`ROLLUP`)がONで、かつ`eofReached`がまだ`*off`のときだけ、`loadNextPage()`をもう一度呼びます。**この設計が前提としているのは、「読み込み済みの範囲内でのスクロールならシステムだけで処理され、読み込み済みの末尾まで達して初めて`ROLLUP`がRPG側に制御を返す(標識25がONになった状態で`EXFMT`から抜ける)」という動きです。** ただし、この画面はどちらの`SFL1CTL`/`SFL1FTR`のDDSにも`SFLRCDNBR`(現在どのRRNを表示中かをRPG側から指定するキーワード)を使っていません。そのため、`loadNextPage()`で行を追加した直後に再度`EXFMT`したとき、画面が続きのページから表示されるのか、それとも1ページ目に巻き戻って表示されるのかは、対話操作でしか確認できません(下の「実機メモ」参照、V3)。

`SFL1FTR`の`MORE`欄(普通の出力フィールド)は、`loadNextPage()`が呼ばれるたびに`'MORE...'`か`'BOTTOM'`のどちらかを書き直すことで、「まだ続きがあるか」をRPG側で手動判定して表示しています。実際のDDSには、この判定自体をシステム側に任せられる専用のキーワード`SFLEND`(`SFLEND(*MORE)`)がありますが、`D0611A`/`D0611AP`はどちらも意図的に`SFLEND`を使わず、`MORE`という普通の出力フィールドと`eofReached`による手動判定で代用しています(ソース自身のヘッダー・コメントにもその旨の記載があります)。`SFLEND`自体は本レッスンの新出にも読解対象にも含めていないので、実際の開発で使う際は一次資料で別途確認してください。

**注意点(未検証のまま残る相互作用):** `RRN1`は、`SFILE(SFL1:RRN1)`宣言により`WRITE`だけでなく`READC`(選択された行を読み込む操作)からも書き込まれます。一次資料(ILE RPG言語リファレンス、`SFILE`キーワードの説明)は「`READC`または`CHAIN`操作で取り出したレコードの相対レコード番号は、`rrnfield`パラメーターで指定したフィールドに入る」と明記しています。つまり、ユーザーが`OPT`に`5`を入力した行を`READC`で読んだ直後は、`RRN1`はその選択行のRRN(読み込み済みの末尾より小さい値になり得ます)に書き換わっています。その状態で次に`ROLLUP`が押され`loadNextPage()`が呼ばれると、`RRN1 += 1`が「選択行の続き」から再開してしまう可能性があります。この相互作用が実際のページ送りにどう影響するかは、対話操作でしか確認できない(このハーネスでは検証不可能な範囲、下の「実機メモ」参照)ため、本レッスンでは断定せず**未検証(V3)**としておきます。行を選ぶ操作とページ送りを同じセッションで両方試す際は、この点に注意して自分の目で確かめてください。

### `%EOF`/`%FOUND`は表示装置ファイル名を渡す(実際にコンパイルで見つかった注意点)

06-04で見たとおり、`%EOF`・`%FOUND`は`CHAIN`・`READ`系の結果を判定するBIFです。**サブファイルを扱うプログラムでは、ここに渡す名前を間違えやすい落とし穴があります。**

```rpgle
readc sfl1;
dow not %eof(d0611a);
  ...
```

`%EOF`・`%FOUND`の引数は、一次資料(ILE RPG言語リファレンス)によれば`%EOF{(file_name)}`・`%FOUND{(file_name)}`と、どちらも**ファイル名**を要求します。`READC`の対象はサブファイルの**レコード様式**(`SFL1`)ですが、`%EOF`/`%FOUND`に渡すのはサブファイルの入れ物である**表示装置ファイル名**(`D0611A`)のほうです。

| メッセージ ID | 原因 | 対処 |
|---|---|---|
| `RNF0391` | `%EOF`にレコード様式名(`SFL1`)を渡した | 表示装置ファイル名(`D0611A`)を渡す |
| `RNF0394` | `%FOUND`に同様にレコード様式名を渡した | 同上 |

`RNF0391`は、`part06-screens-compile`(2026-09-26)の接続1回目で実際に`F0611A`自身が出したエラーです。`RNF0394`は同じ接続の中で、06-11bの`F0611BA`(一覧からの追加・変更・削除画面。`CHAIN`を使うため`%FOUND`も呼んでいます)が出したもので、原因は同じです。どちらも、`CHAIN`/`READC`の対象(サブファイル・レコード)と`%EOF`/`%FOUND`の対象(ファイル)が違う、という点を混同すると起こります。`F0611A`は修正後(接続2回目)`Highest Severity 00`でコンパイルが通りました。詳細は`docs/probes.md`を参照してください。

### オプション`5`から`F0604A`を呼ぶ ── 今はまだ得意先コードを渡さない

`F0611A`のオプション`5`は、選ばれた行の得意先コード(`JUTOK`、`READC`で自動的に画面のフィールドへ入っています)を`F0604A`へ渡す、というのが本来やりたいことです。

```rpgle
dcl-pr f0604a extpgm('F0604A') end-pr;
```

```rpgle
select;
  when opt = '5';
    callp f0604a();
```

**`F0604A`(06-04)は`dcl-f d0604a workstn;`のみで、値を受け取るパラメーター自体を持っていません**(自分の画面の`TOKCD`欄で、呼ばれるたびに得意先コードを入力し直す作りです)。そのため`F0611A`からの呼び出しは、今のところパラメーターを一切渡さない`dcl-pr`/`callp`の形にしてあります。オプション`5`を選ぶと`F0604A`の画面自体は呼び出されますが、得意先コードは自動では渡らず、`F0604A`自身の画面でもう一度入力し直すことになります。**これは意図的な、現時点での制約です。** `F0604A`にエントリー・パラメーターを持たせる(`dcl-pi`をプログラム本体用に使う)のは06-12で扱う新出構文で、その回で`F0612B`・`F0612C`という**新しいオブジェクト**を追加してこの制約を解消します(`F0604A`・`F0611A`自身は書き換えません)。`D0611AP`/`F0611AP`(ページ単位版)のオプション`5`も、まったく同じ形でパラメーターなしのままです。

### メッセージ・サブファイル: 不正なオプションを診断する

```text
     A          R MSGSFL                    SFL
     A                                      SFLMSGRCD(24)
     A            MSGKEY                    SFLMSGKEY
     A            PGMQ                      SFLPGMQ
     A          R MSGCTL                    SFLCTL(MSGSFL)
     A                                      SFLSIZ(2)
     A                                      SFLPAG(1)
     A                                      SFLDSP
     A                                      SFLDSPCTL
     A                                      SFLINZ
     A                                      OVERLAY
     A            PGMQ                      SFLPGMQ
```

`MSGSFL`/`MSGCTL`は、`SFL1`/`SFL1CTL`とは別の、**専用のペア**です。`SFLMSGRCD(24)`は「メッセージは24行目(この画面の最終行)から上に向かって積み上がる」という意味の指定で、`SFLMSGKEY`/`SFLPGMQ`とあわせ、Part 5の`TK0100D`(`src/legacy/qddssrc/tk0100d.dspf`)からそのまま踏襲したメッセージ・サブファイルの書き方です。`SFLINZ`は、`MSGCTL`自体を組み立て直す指定ではありません。**`MSGCTL`を(未初期化のサブファイルへの出力エラーを避けつつ)有効な状態に保ったまま、`PGMQ`(このプログラム自身のメッセージ・キューを指す`'*'`)を元に、メッセージ・サブファイル本体(`MSGSFL`)の中身を`WRITE`のたびに組み立て直す指定です。**

```rpgle
pgmq = '*';
```

```rpgle
dcl-proc sendInvalidOpt;
  dcl-pi *n;
  end-pi;

  snd-msg *diag 'Invalid option - use 5 for order inquiry, blank to'
    + ' skip.' %target(*self);
  write msgctl;
end-proc;
```

`snd-msg *diag ... %target(*self)`は、診断メッセージを送る自由形式オペコードです。一次資料(ILE RPG言語リファレンス)によれば、`%TARGET`を省略したときの`*DIAG`の既定値は`*CALLER`(呼び出し元)であり、`*SELF`は「現在の手続き」を指します。ここでの「現在の手続き」は、`SND-MSG`を実際に実行している`sendInvalidOpt`というサブプロシージャ自身であって、この画面を開いているメインラインではありません。

一方`PGMQ`(`'*'`)は、「この表示装置ファイルをオープンしているプログラムの、プログラム・メッセージ・キュー」を指すフィールドとして設計されています(`SFLPGMQ`というキーワードの一般的な役割で、この教材が実際に手元で参照した資料には`SFLPGMQ`自体の項目が見当たらないため、断定はできません)。**`sendInvalidOpt`という1つのサブプロシージャの`%TARGET(*SELF)`と、`SFLPGMQ`が指す「プログラム」全体のメッセージ・キューが、実際に同じ送り先を指すかどうかは、一次資料の個別の具体例には見当たらず、対話操作でしか確認できません(V3)。** コンパイル自体(`SND-MSG`という構文が通ること)はV1で確認済みですが、この組み合わせが実際に画面上へメッセージを表示するかどうかは、上記の理由でむしろ強めに未検証のままです。

**もう一つ、ソースの構造を追うだけで指摘できる、別の具体的な懸念があります。** `SFL1FTR`(`MORE`・`F3=Exit`のフッター)には`OVERLAY`が付いていません(`SFL1CTL`・`MSGCTL`にはどちらも付いています)。`F0611A`のメインラインは、外側の`dow`ループの先頭で毎回`write sfl1ftr; exfmt sfl1ctl;`を実行します。`sendInvalidOpt`が`write msgctl;`(`OVERLAY`付きなので画面を消さずに重ね書きします)でメッセージを表示させたあと、制御は外側の`dow`ループの先頭に戻り、`write sfl1ftr;`がもう一度実行されます。`SFL1CTL`自身の`OVERLAY`について、このソース自身が「`SFL1CTL`が(再)`WRITE`されたときに`SFL1FTR`の出力を生かすため」という趣旨のコメントを残している(=`OVERLAY`の無いレコードへの`WRITE`は、その手前の画面内容を消してしまう、という理解がこのソース自身の前提になっている)のと同じ理屈をあてはめると、`OVERLAY`の無い`SFL1FTR`へのこの2回目の`WRITE`は、画面全体を消してから`SFL1FTR`を書き直すはずで、直前に`write msgctl;`で出したはずのメッセージも一緒に消えてしまう可能性があります。だとすると、`%TARGET(*SELF)`と`SFLPGMQ`が同じ送り先を指すかどうかという上の疑問とは別に、**そもそもメッセージが次の`EXFMT`まで画面上に残らない**という、ソースの構造だけから読み取れる具体的な懸念がある、という見方が成り立ちます。`D0611AP`/`F0611AP`(ページ単位版)も、まったく同じ`write sfl1ftr; exfmt sfl1ctl;`の順序なので、同じ懸念があてはまります。この見方自体、実際に画面がどうなるかは対話操作でしか確認できないため(V3)、上の`%TARGET(*SELF)`の疑問とあわせて未検証のままです。

## 実演

**この実演で作る4つのオブジェクト(`D0611A`/`F0611A`・`D0611AP`/`F0611AP`)は、著者による実機コンパイル(V1、下の「実機メモ」参照)まで確認済みです。対話的な実行(`EXFMT`で実際に画面が出て、選択欄への入力・`ROLLUP`を受け付けるところ)は、この教材の検証ハーネス(非対話SSH)では確認できません。学習者自身の5250セッションで確認してください。**

1. SSHで接続し、`~/ibmi-kyozai`を最新にする(`git pull`)。

2. ソースを取り込む(1回の接続でまとめて行います)。

## 演習

1. **(読む)** `JUCHUM`のサンプル・データは8件です。`F0611AP`(`SFLPAG(3)`)では何ページ分の`loadNextPage()`呼び出しで全件読み込みが終わるか、実際に試す前に計算してください(答え: 3件・3件・2件の3回、うち最初の1回は最初の`EXFMT`より前です。画面が実際に何ページ分として見えるかは、上の「説明」で触れたとおり未確認です)。
2. **(穴埋め・修正)** `D0611AP`の`SFLPAG(3)`を`SFLPAG(5)`に変え、**あわせて`f0611ps.rpgle`の`dcl-c PAGESIZE 3;`も`5`に変えてください。** `SFLPAG`はDDS側の値(画面1ページに見せる件数)であるのに対し、`loadNextPage()`が実際に`JUCHUM`から読み込む件数を決めているのはRPG側の独立した定数`PAGESIZE`のほうです。この2つはたまたま同じ`3`という値を持っているだけで、`D0611AP`(DDS)だけを直して再コンパイルしても`F0611AP`(RPG)の`PAGESIZE`は`3`のままなので、`loadNextPage()`の読み込み件数は変わりません。両方を直したうえで`D0611AP`・`F0611AP`を再コンパイルし、`loadNextPage()`が読み込む件数が「5件・3件」の2回に変わることを確認してください。`SFLSIZ(4)`も、元のソースの`SFLPAG`+1という関係にならって`SFLSIZ(6)`に直すべきかどうか、自分で考えてから直してください。
3. **(独力で)** `F0611A`・`F0611AP`のどちらでも構わないので、`OPT`欄に不正な値を入れてメッセージを表示させたあと、`OPT`を空白に戻して`Enter`を押してください。ソースのどこにもメッセージを明示的に消す処理は無い(`WRITE MSGCTL`は`sendInvalidOpt`の中でしか呼ばれません)ため、メッセージが消えるかどうかを予想してから、実際に確認してください。
4. **(応用: 位置指定)** `JUCHUM`は`JUNO`をキーとした索引付き(keyed)ファイルです(`db/v1/juchum.pf`)。しかし`F0611AP`の`dcl-f juchum disk;`には`keyed`が付いておらず、常に格納順(このサンプル・データではたまたま`JUNO`の昇順と一致します)に先頭から読むだけです。**次を自分で試してください(この教材ではまだ実機コンパイルしておらず、模範解答ファイルもありません)。**
   - まず`dcl-f juchum disk keyed;`に変え、`loadNextPage`の最初の呼び出しより前に、固定のキー(例: `'J00004'`)で`setll`してから`loadNextPage()`を呼ぶよう変更してください(`SETLL`という名前自体は06-04の`%eof`の説明ですでに出てきていますが、実際に使うのはこの演習が初めてです)。1ページ目が`J00004`から始まることを確認してください。
   - **(発展)** 固定のキーではなく、画面に「開始注文番号」のような入力欄を追加し、入力し直すたびにその位置から表示をやり直せるようにしてみてください。ここでハマりやすい点を先に伝えておきます。`RRN1`・`eofReached`は一度セットされたら`WRITE`済みのサブファイル内容と一緒に残り続けるため、位置を変えるたびに「サブファイルを空にする」処理(`SFLCLR`。ただし`D0611AP`にはまだ無い、条件標識付きの新しいキーワードです)が要ります。06-10で学んだ`INDDS`の名前付き標識が、この条件標識を扱うヒントになるはずです。**ただし04-11では、DDSの条件標識のうち桁7に標識番号を直接置く形を使った出力フィールドの指定がこのハーネスの生成環境でコンパイルに失敗した実績(`CPD7410`/`CPD7606`/`CPD5238`)があり、後日の別の検証接続で桁8〜16(標識3組×3桁)という異なる候補を試した回でも、同じく`CPD5238`で失敗しています。`D0611A`/`D0611AP`自身もこれらの理由から条件標識を一切使わない設計になっています。** `SFLCLR`に条件標識を付ける際、同じ問題に当たる可能性があることを念頭に置いてください。うまくいくかどうかは、自分で実際にコンパイル・実行して確かめてください(うまくいかなかった場合も、どこで詰まったかを説明できれば十分な結果です)。

## 実機メモ

- **load-all版(`D0611A`/`F0611A`)は`part06-screens-compile`(確認日2026-09-26)で**V1**(コンパイル確認)まで到達しています。** `D0611A`(`CRTDSPF`)は接続1回目からHighest Severity 00でした。`F0611A`(`CRTBNDRPG`)は接続1回目、`%eof(sfl1)`にレコード様式名を渡していた実バグ(`RNF0391`)で失敗し、`%eof(d0611a)`のように表示装置ファイル名へ直す修正後、接続2回目でHighest Severity 00になりました(同じ接続の中で06-11bの`F0611BA`も`%found`側の同様のバグ`RNF0394`で失敗し、同じ直し方で2回目に成功しています。上の「説明」の該当節、`docs/probes.md`参照)。
- **ページ単位版(`D0611AP`/`F0611AP`、新規)は`part06-b6-batch`(確認日2026-09-27)で**V1**まで到達しています。** `%eof(d0611ap)`のように最初から表示装置ファイル名を渡す形で書かれているため、`CRTDSPF`・`CRTBNDRPG`とも1回の接続でHighest Severity 00になりました。
- **`EXFMT`/`WORKSTN`を含む対話実行そのものは、このハーネス(非対話SSH)では確認できません**(04-11以来の既知の制約と同じです)。したがって、load-allでの8件一覧・ページ単位での3件+3件+2件のページ送り・`OPT=5`での`F0604A`呼び出し・不正なオプションでの診断メッセージ表示——これらはすべて**V3**(学習者自身の5250セッションでの確認が必要)であり、実機では未確認のままです。
- **メッセージ・サブファイルへの`SND-MSG *DIAG %TARGET(*SELF)`+`SFLPGMQ`+`PGMQ='*'`という組み合わせは、コンパイル(V1)は確認済みですが、実際に画面上へメッセージが現れるかどうかは対話操作でしか確認できず(V3)、未検証(2026-09-28時点)のままです。** 一次資料(ILE RPG言語リファレンス)のSND-MSGの説明も、この具体的な組み合わせを直接の例としては示していません。さらに、`SFL1FTR`(`MORE`・`F3=Exit`のフッター)には`OVERLAY`が無く、`sendInvalidOpt`が`write msgctl;`した直後、メインラインが外側の`dow`ループの先頭に戻って`write sfl1ftr;`を再度実行する構造になっているため(上の「説明」参照)、そのタイミングで画面が消え、メッセージ自体が次の`EXFMT`まで残らない可能性があります(`D0611AP`/`F0611AP`も同じ構造です)。この点も対話操作でしか確認できず(V3)、未検証(2026-09-28時点)のままです。
- **`F0611AP`の`RRN1`(`SFILE`のRRNフィールド)は、`loadNextPage`が続きから読み込みを再開するための位置カウンターと兼用になっており、`READC`が選択行を読むたびに同じ`RRN1`へその行のRRNが書き込まれます(一次資料・ILE RPG言語リファレンスの`SFILE`キーワードの説明による)。** 行の選択と`ROLLUP`によるページ送りを同じセッションで両方行った場合に、この兼用がページ送りの継続にどう影響するかは、対話操作でしか確認できないため未検証(2026-09-28時点)のままです(上の「説明」参照)。
- 演習4(位置指定)のコードは、この教材ではまだ実機コンパイルしていません。模範解答ファイルも用意していません。未検証(2026-09-28時点)のままです。
