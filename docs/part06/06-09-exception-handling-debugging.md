## なぜ学ぶか

**04-06では、`TOKUIM` の暗黙オープンが失敗すると `RPG1216` という照会メッセージが出て、`*PSSR`(プログラム全体用のエラー処理サブルーチン)でも `MONMSG` でも捕まえられないまま非対話ジョブがハングする、という限界を見ました。** 04-12では、ゼロ除算(`RPG0102`)も同じ種類の照会メッセージになることを確認し、対策として「危険な演算を実行する前に `COMP` で弾く」という、事前チェック型の防御を学びました。

**このレッスンでは、同じゼロ除算を、正反対の考え方で扱います。** 危険な演算を事前に弾くのではなく、**実行させたうえで、失敗したらその場で捕まえる**という設計です。RPG IVの `monitor`/`on-error` は、`*PSSR` と同じ「エラーが起きたらどうするか」という発想の延長にありますが、決定的に違う点が1つあります——**`*PSSR` はプログラム全体に対して1つしか置けませんが、`monitor` はコードの好きなブロックを囲めます。** どこで、何を監視するかを、自分で選べるということです。

あわせて、`psds`(プログラム状態データ構造。実はRPG III/RPG400にも同じレイアウトの仕組みがあり、エラーが起きればプログラムのどこからでも読めました——RPG IVで変わったのは、読める場所ではなく「エラー処理そのものをブロック単位に絞れる」という点です)・`on-exit`(プロシージャ終了時の後始末)・`QMHSNDPM`(06-05〜06-08で `sendMsg`/`sendToJobLog` という名前で既に使ってきたAPIの、詳しい構文)を扱います。最後に、ILEのデバッグが対話操作でどう変わるかにも触れます(この部分は5250の対話セッションでの操作が前提のため、記述にとどめます)。

## 新出

- 中核概念:
  1. `monitor`/`on-error` は、RPG IIIの結果標識・`*PSSR` の後継だが、**`*PSSR` と違い、コードの好きなブロック単位で細かく囲める**。ただし「ブロックの中に書いた演算」しか監視できない点は `*PSSR`(プログラム全体という広いブロック)と同じ理屈であり、04-06で見た `RPG1216`(RPGサイクルが起動時に自動で行う暗黙オープンの失敗)のように、**どんなブロックの外で、しかもメインラインが実行される前に起きる**種類の失敗は、`monitor` でも `*PSSR` でもやはり捕まえられない。
  2. ILEのデバッグは、`CRTBNDRPG`/`CRTRPGMOD` の `DBGVIEW` パラメーターで、コンパイル済みのオブジェクトに**自由形式ソースそのもの**を表示するデバッグ・ビューを持たせられる(OPMでは `OPTION(*SRCDBG)`/`OPTION(*LSTDBG)` という別の指定で、対応できる言語もRPG・COBOL・CLに限られる)。
- 構文:
  - `monitor`/`on-error`
  - `psds`(プログラム状態データ構造。`*PROC`/`*STATUS`/`*ROUTINE` という予約語と、予約語を持たない位置指定サブフィールド)
  - `on-exit`(プロシージャ終了時に必ず実行される区画)
  - `QMHSNDPM`(Send Program Message API。`dcl-pr extpgm`・`qualified` なデータ構造・`likeds` の実例)
  - `DBGVIEW(*SOURCE)`
  - `STRDBG`(**V3**、記述のみ)
  - `STRSRVJOB`(**V3**、記述のみ)

## 説明

### `monitor`/`on-error` ―― ブロック単位のエラー処理

`src/qrpglesrc/f0609s.rpgle`(`F0609A`)の核心部分です。

```rpgle
dcl-s num    packed(3:0) inz(10);   // R0412A's NUM (Z-ADD10)
dcl-s zero   packed(3:0) inz(0);    // R0412A's ZERO (Z-ADD0) - deliberate
dcl-s answer packed(3:0);

monitor;
  answer = num / zero;

  // Only reached if the division above did NOT fail.
  msgText = 'F0609A: ' + %char(num) + ' / ' + %char(zero)
              + ' = ' + %char(answer) + ' (no error).';
  sendToJobLog(msgText);

on-error 102;
  msgText = 'F0609A: caught status ' + %char(pgmStatSts)
              + ' in ' + %trimr(pgmStatProc)
              + ' at line/stmt ' + %trimr(pgmStatLine)
              + ' - division by zero was caught, not pre-checked.';
  sendToJobLog(msgText);
endmon;
```

`num`(10)・`zero`(0)は、04-12の `R0412A` が使った `Z-ADD10`/`Z-ADD0` と同じ値です。**04-12は `COMP` で `ZERO` がゼロかどうかを先に確認し、ゼロなら `DIV` そのものを実行させませんでした。ここでは逆に、`DIV`(`answer = num / zero;`)を `monitor` ブロックの中でそのまま実行させ、失敗したら `on-error 102` で捕まえます。** `102` は、一次資料(ILE RPG言語リファレンス)の「Program Status Codes」表に載っている、`Divide by zero` を表すステータス・コードです。`monitor` ブロックの中身が最後まで正常に終われば `on-error` 側は実行されず、逆に例外が起きた時点で `monitor` ブロックの残りは打ち切られ、該当する `on-error` に飛びます。

**「ブロック単位」の具体的な意味**: 一次資料が示す公式な例では、ファイルの明示的な `OPEN` を `monitor` ブロックの中に置き、`on-error 1216;`(一次資料によれば、オープン/クローズ操作中に起きたエラーは常にステータス `1216` または `1217` になります)でオープンそのものの失敗を捕まえています。**つまり `monitor` は、自分がブロックの中に明示的に書いた演算であれば、`OPEN` を含めて何でも監視できます。** これは `*PSSR` には無かった柔軟さです——`*PSSR` はプログラム全体という1つの大きなブロックしか持てませんでした。

ただし、これは「`monitor` なら何でも捕まえられる」という意味ではありません。**04-06で見た `RPG1216` は、`TOKUIM` の暗黙オープン(F仕様書/`dcl-f` の宣言に基づき、RPGサイクルが起動時に自動で行うオープン)が失敗したものであり、これはメインラインのどんなコード(`monitor` ブロックを含む)が実行される前に起きます。** どんなブロックで囲もうと、まだ実行されていないコードは監視のしようがありません。`monitor` が `*PSSR` に対して勝っているのは「監視する範囲を、プログラム全体ではなく好きなブロックに絞れる」という点であって、「実行前に起きる失敗まで捕まえられる」という意味ではない、という点を混同しないでください。

**興味深い一致(この教材独自の推測、一次資料に明記されているわけではないので要確認)**: 04-06の `RPG1216`(OPMのメッセージID)と、上で触れたILE RPGのステータス・コード `1216`(オープン/クローズ・エラー)は、同じ番号です。どちらも「ファイルのオープンに失敗した」という同じ種類の現象を指しているためだと考えられますが、OPMのメッセージ体系とILEのステータス・コード体系は別物であり、この対応関係そのものは一次資料の記述として確認できたわけではありません。

### `psds` ―― プログラム状態データ構造

```rpgle
dcl-ds pgmStat psds;
  pgmStatProc *proc;
  pgmStatSts  *status;
  pgmStatLine char(8) pos(21);
  pgmStatRtn  *routine;   // declared for completeness, NOT reported
end-ds;
```

`psds` キーワードを付けた `dcl-ds` は、プログラムの実行状態を表す**プログラム状態データ構造**になります。`*proc`・`*status`・`*routine` は予約語で、**データ型を書く代わりに、この予約語自体をキーワードとして書きます**(サブフィールドの型・長さは、それぞれの予約語が自動的に決めます)。**発生した行/統計文番号(位置21〜28)には専用の予約語が無いため**、`char(8) pos(21)` のように、位置と型を明示して自分で取り出します。

**RPG III(RPG/400)にも、同じ考え方のプログラム状態データ構造がありました**(`*STATUS` は11〜15桁目、統計文番号は21〜28桁目、`*ROUTINE` は29〜36桁目——ほぼ同じレイアウトです)。**一次資料によれば、`STATUS` はエラーが起きるたびに更新され(エラー標識(56〜57桁目)を指定した演算で標識がオンになった場合でも、`*PSSR` が制御を受け取った場合でも)、プログラムのどこからでも読めました。** RPG IVで実際に変わったのは、`psds` 自体の読める範囲ではなく、**エラー処理の「受け皿」をブロック単位に絞れる**という点です——`*PSSR` はプログラム全体に対して1つしか置けませんでした。ただし `DIV` のようにエラー標識を指定する欄が無い演算(`DIV` の結果標識は結果の符号を示すだけです)では、エラーを自分で扱う手段はRPG IIIでは `*PSSR` か、04-12のような事前チェックしかなく、04-12の `R0412A` が `COMP` による事前チェックに頼ったのもこのためです。

**`pgmStatRtn`(`*routine`)は宣言されていますが、あえて使っていません。** 一次資料によれば、`*routine` は「通常のRPG IVサイクルを使っていないと有効ではない」と明記されており、プログラムをサイクルの外に連れ出すロジック(このプログラムのようにサブプロシージャの中でエラーが起きる場合)では、正しい値を返さない可能性があります。完全な形を示すためだけに宣言してあり、実際の報告には使っていません。

**実機で確認された、興味深い挙動**: 一次資料によれば、`*proc` は「`CRTRPGMOD` でコンパイルされたモジュールならモジュール名、`CRTBNDRPG` でコンパイルされたプログラムならプログラム名」を返します(**サブプロシージャの名前ではありません**)。実際に確認したところ、エラーはサブプロシージャ `runDivideDemo` の中で起きたにもかかわらず、`pgmStatProc` は `RUNDIVIDEDEMO` ではなく **`F0609A`**(`CRTBNDRPG` で作ったプログラムそのものの名前)を返しました(V2、下の「実機メモ」参照)。一次資料の説明どおりの結果です。

### `on-exit` ―― プロシージャ終了時に必ず実行される区画

```rpgle
dcl-s abnormalEnd ind;              // ON-EXIT's status indicator
...
  return;

on-exit abnormalEnd;
  if abnormalEnd;
    sendToJobLog('F0609A: runDivideDemo ended ABNORMALLY.');
  else;
    sendToJobLog('F0609A: runDivideDemo ended normally '
                   + '(MONITOR/ON-ERROR already handled any error).');
  endif;
end-proc;
```

`on-exit` は、そのプロシージャが**正常に終わっても、異常に終わっても、必ず1回だけ実行される**区画です。一次資料によれば、`on-exit` が実行されるのは「メイン部分の終わりに達したとき」「`return` に達したとき」「捕まえられなかった例外でプロシージャが終わったとき」「ジョブ/サブシステムの終了などでプロシージャがキャンセルされたとき」のいずれかです。Extended Factor 2 の標識(ここでは `abnormalEnd`)は、正常終了なら `*off`、異常終了・キャンセルなら `*on` になります。

**このプログラムでは、`monitor`/`on-error` が既にゼロ除算を捕まえているため、`runDivideDemo` は常に `return;` を経由して正常に終わり、`abnormalEnd` は常に `*off` です。** `abnormalEnd` が `*on` になるとしたら、それは `monitor`/`on-error` で捕まえていない**別の**未処理例外がこのプロシージャから漏れ出た場合だけです。

**`on-exit` にはいくつか制約があります。** 一次資料によれば、`on-exit` を持つプロシージャには `*PSSR` サブルーチンを置けません(「代わりに `monitor` グループを使うこと」と明記されています——`monitor`/`on-error` が `*PSSR` の後継である、という位置づけを裏付ける一文です)。**さらに、`on-exit` は cycle-main プロシージャ(メインライン)には書けません。** これが、`F0609A` の実際のロジック(`monitor`/`on-error`/`on-exit` の一式)がメインラインにではなく、`runDivideDemo` という**サブプロシージャ**に書かれている理由です。メインラインは `runDivideDemo();` を1回呼ぶだけの、単純な呼び出し役に徹しています。

### `QMHSNDPM` ―― ジョブ・ログへの直接送信

06-05〜06-08では、`sendMsg`/`sendToJobLog` という名前の手続きに文字列を渡すだけで、ジョブ・ログにメッセージが残ることだけを知っていれば十分でした。ここで、その内部で何が起きているかを詳しく見ます。

**なぜ `DSPLY` ではないのか**: 一次資料によれば、`DSPLY` はメッセージ・キューを指定しないと、バッチ・ジョブでは既定で `QSYSOPR`(システム・オペレーターのメッセージ・キュー)宛てになります。この教材のプログラムは非対話(バッチ/SSH)で実行することを前提にしているため、`DSPLY` をそのまま使うと、無関係な `QSYSOPR` にメッセージを送ってしまいます。そこで `QMHSNDPM`(Send Program Message API)を直接呼び、**自分のジョブのジョブ・ログにだけ**メッセージを残します。

```rpgle
dcl-ds qmhsndpmMsgFile qualified template;
  *n char(10) inz('QCPFMSG');
  *n char(10) inz('*LIBL');
end-ds;

dcl-ds qmhsndpmErrCode template;
  bytesProvided int(10) inz(0);
  bytesAvailable int(10);
  msgId char(7);
  *n char(1);
end-ds;

dcl-pr qmhsndpm extpgm;
  msgId          char(7) const;
  msgFile        likeds(qmhsndpmMsgFile) const;
  msgData        char(1000) const;
  dataLen        int(10) const;
  msgType        char(10) const;
  callStackEntry char(10) const;
  callStackCtr   int(10) const;
  msgKey         char(4) const;
  errorCode      likeds(qmhsndpmErrCode);
end-pr;
```

`QMHSNDPM` は9個の引数を取るシステムAPIです。この形は一次資料自身の実例(手続き名 `sendException` として載っている、`QMHSNDPM` を呼ぶ実例)をそのまま写したものです。

- **`qualified template`**: `qualified` は06-07で扱った「同じフィールド名を持つ複数のデータ構造を、名前がぶつからずに扱う」ためのキーワードです。`template` を付けると、そのデータ構造自体は変数として実体化されず、**型のひな型としてだけ**使われます(`likeds` で参照するための型定義、という位置づけです)。`*n` は無名のサブフィールドで、名前を付ける必要が無いときに使います。
- **`likeds(qmhsndpmMsgFile)`**: 06-07で扱った、あるデータ構造と**同じ型**の別のデータ構造(または、ここではプロトタイプのパラメーター)を宣言するキーワードです。`msgFile` パラメーターは `qmhsndpmMsgFile` という型のひな型と同じ形になります。
- **`bytesProvided int(10) inz(0)`**: `errorCode` パラメーターの先頭サブフィールドで、`0` を渡すと「エラーが起きたら例外メッセージで知らせてほしい(エラー・コード構造への書き込みではなく)」という意味になります。
- **`msgId('CPF9898')`**: `CPF9898` は、`QCPFMSG` メッセージ・ファイルに用意されている、「任意の差し替えテキストを送る」ための汎用の情報/エスケープ・メッセージです。一次資料の実例もこのIDを使っています。
- **`callStackEntry('*') : callStackCtr(0)`**: 呼び出し履歴の中で「これを呼んでいる手続き自身」を指す指定です。これにより、メッセージは**自分のジョブのジョブ・ログ**に残ります。

```rpgle
dcl-proc sendToJobLog;
  dcl-pi *n;
    msg char(200) const;
  end-pi;

  dcl-ds msgFile likeds(qmhsndpmMsgFile) inz(*likeds);
  dcl-ds errCode likeds(qmhsndpmErrCode) inz(*likeds);
  dcl-s  msgKey  char(4);

  qmhsndpm('CPF9898' : msgFile : msg : %len(%trimr(msg))
             : '*INFO' : '*' : 0 : msgKey : errCode);
end-proc;
```

**`msgType` について1点、正直に書いておきます。** 一次資料自身の実例は `msgType` に `'*ESCAPE'`(プログラムがそのまま終わる前提のエスケープ・メッセージ)を渡していますが、このプログラムは `'*INFO'`(情報メッセージ。エラーは既に処理済みで、プログラム自体は正常に続く)を渡しています。`'*INFO'` は広く使われている値ですが、一次資料の実例そのものが示している値ではないため、**一次資料で直接確認できたわけではない**部分として明記しておきます(実機での動作自体は下の「実機メモ」のとおり確認済みです。V2)。

**もう1点、技術的な制約として明記しておきます。** `SNDPGMMSG`(CLコマンド)は `QCMDEXC` 経由では、呼び出し元がRPGでもCLでも、どんな呼び出しの深さでも実行できません(`CPD0031`「Command SNDPGMMSG not allowed in this setting」。詳細は `docs/probes.md` を参照)。そのため、ジョブ・ログへの記録には `QMHSNDPM` を直接呼び出します。

### ILEのデバッグ: `DBGVIEW` と OPMとの違い(V3、記述のみ)

**この節は、対話的な5250セッションでの操作が前提のため、この教材の非対話の検証では確認していません。** 一次資料に基づく記述として読んでください。

`CRTBNDRPG`/`CRTRPGMOD` には `DBGVIEW` というパラメーターがあり、コンパイル済みのオブジェクトに、`STRDBG` が実際に表示するソースの形を持たせます。`DBGVIEW(*SOURCE)` を指定すると、`**FREE` の自由形式ソースそのものが、行番号付きでデバッガー画面に表示されます。

対してOPM(RPG III、`CRTRPGPGM`)では、ソース・レベルの対話デバッグを行うために `OPTION(*SRCDBG)`(または `*LSTDBG`)というコンパイル・オプションが必要で、一次資料によればOPM側でこれに対応する言語はRPG・COBOL・CLに限られます。04-12では `STRDBG` の基本操作(ブレークポイント・変数表示)だけを扱いましたが、**「デバッガーが実際に何を表示するか」は、ILEとOPMでコンパイル時の指定が違う**、というのがこの回で新しく押さえてほしい点です。

### `STRSRVJOB` ―― 動いている非対話ジョブに、後からデバッガーを差し込む(V3、記述のみ)

**この節も対話操作が前提であり、この教材の検証では確認していません。**

`STRSRVJOB` は、**自分が投入したのではない、既に動いている別のジョブ**(たとえばSSH経由で動いているバッチ・ジョブ)に対して、サービス操作(デバッグ・ダンプ・トレースなど)を後から差し込むためのコマンドです。一次資料によれば、`STRSRVJOB JOB(ジョブ番号/ユーザー/ジョブ名)` でそのジョブへのサービス操作を開始し、続けて `STRDBG` を実行すると、そのジョブを対話的にデバッグできるようになります(`ENDSRVJOB` で終了するまで有効です)。

**この教材の検証ハーネスは非対話のSSH接続で完結するため、「動いている最中の別ジョブに割り込む」という操作自体を試す機会がありません。** ILEを前提にしたこの部で初めて紹介する技法として、存在と用途だけを知っておいてください。実際の操作は、読者自身の5250セッション(2つの端末、または1つの端末から別ジョブを指定する形)で試してください。

## 実演

**この実演で作るオブジェクト(`F0609A`)は、著者による実機コンパイル・実行(V1/V2、下の「実機メモ」参照)まで確認済みです。** `WORKSTN` を使わない、04-09の `R0409A` や06-08の `F0608A` と同じ「1回 `CALL` すれば1回処理して終わり」のバッチ型プログラムです。

1. SSHで接続し、`~/ibmi-kyozai` を最新にします(`git pull`)。`exit` で5250に戻ります。
2. 5250のコマンド行で、`<自分のユーザー名>1/QRPGLESRC` にメンバーを用意します(`QRPGLESRC` 自体は06-01bで新規作成済みのはずです)。

   ```text
   ADDPFM FILE(<自分のユーザー名>1/QRPGLESRC) MBR(F0609A) SRCTYPE(RPGLE) TEXT('Exception handling: MONITOR/ON-ERROR/QMHSNDPM')
   ```

3. SSHでもう一度接続し、`src/qrpglesrc/f0609s.rpgle` を取り込みます。

   ```sh
   system "CPYFRMSTMF FROMSTMF('/home/<自分のユーザー名>/ibmi-kyozai/src/qrpglesrc/f0609s.rpgle') TOMBR('/QSYS.LIB/<自分のユーザー名>1.LIB/QRPGLESRC.FILE/F0609A.MBR') MBROPT(*REPLACE) STMFCCSID(1208)"
   ```

4. 5250に戻り、コンパイルします。

   ```text
   CRTBNDRPG PGM(<自分のユーザー名>1/F0609A) SRCFILE(<自分のユーザー名>1/QRPGLESRC) SRCMBR(F0609A)
   ```

   Highest Severity 00になることを確認してください。

5. 実行し、`DSPJOBLOG` で結果を確認します。

   ```text
   CALL PGM(<自分のユーザー名>1/F0609A)
   DSPJOBLOG
   ```

   次の3行が、この順番でジョブ・ログに現れることを確認してください(実際に確認された値は下の「実機メモ」のとおりです)。**2行目・3行目の末尾がピリオド2つ(`..`)になっているのは誤植ではありません**——`CPF9898` は渡された差し替えテキストの末尾に自動でピリオドを1つ追加するため、渡す文字列自体が既にピリオドで終わっていると、表示上は2つ並びます。

   ```text
   Attempt made to divide by zero for fixed point operation.
   F0609A: caught status 102 in F0609A at line/stmt 00023600 - division by zero was caught, not pre-checked..
   F0609A: runDivideDemo ended normally (MONITOR/ON-ERROR already handled any error)..
   ```

   **1行目は、`monitor` が捕まえた例外そのものがジョブ・ログに残った跡です。この行が出ていること自体は「プログラムが失敗した」ことを意味しません**——続く2行目・3行目が、`on-error` と `on-exit` によって、例外が正しく処理され、プログラムが異常終了せず正常に終わったことを示しています。

   **`line/stmt` の数値(`00023600`)は、あなたのメンバーでは同じ値になるとは限りません。** この8桁の値は、一次資料によれば「`OPTION(*SRCSTMT)` を指定した場合、ソースの行番号ではなく、ソースの並び番号(シーケンス番号)から導かれる統計文番号」です。`CPYFRMSTMF` で取り込んだ際にメンバーへ割り振られる並び番号は、ヘッダーのコメント量などによってずれることがあります。**大事なのは特定の数値そのものではなく、この番号を手がかりに、自分のメンバーの `answer = num / zero;` の行を実際に見つけられることです。**

## 同じ手順を別の対象で

**ここから先はV3(対話操作が前提で、この教材の非対話の検証では確認していない)です。5250のセッションを2つ用意できる場合に試してください。** **1つのPUB400アカウントで実際に2つの5250セッションを同時に開けるかどうか自体、このリポジトリーではまだ確認していません**(06-11bの演習5と同じ前提の不確実性です)。

04-09の `R0409A`(ZAHIK3)は、`ZAIKOM` を `CHAIN` した時点でそのレコードをロックし、`SHORT`(在庫不足)と判定されてもロックを保持したまま `*INLR` まで進みます。**この「判定が終わるまでロックを持ち続ける」性質を利用すると、2つの5250セッションで実際にロック競合を再現できます。**

1. セッションAで、`R0409A` を、`ZASU`(在庫)が読み込まれた直後、`COMP` の判定より前にブレークポイントを置いて `STRDBG` で実行を止めます(`STRDBG` のブレークポイント操作は04-12を参照)。これで、セッションAは `P00001` のレコードをロックしたまま止まります。**06-08の `F0608A` を使う場合、この位置は当てはまりません**——`F0608A` は最初の `CHAIN` をロックなしの `chain(n)` で行い(ウォームアップ設問2のとおり)、在庫充足を確認した後のもう一度の `CHAIN`(else節の中、ロック付き)を通るまでレコードはロックされないため、`F0608A` で試す場合は2回目の(ロック付きの)`CHAIN` の直後・2回目の `if` の判定より前にブレークポイントを置き直してください。
2. セッションBから、同じ `<自分のユーザー名>1/ZAIKOM` の商品コード `P00001` に対して同じプログラムを実行してみます。
3. `WRKOBJLCK OBJ(<自分のユーザー名>1/ZAIKOM) OBJTYPE(*FILE)` または `DSPRCDLCK`(該当するジョブに対して)で、セッションBがセッションAの持つロックを待たされている様子を観察します。
4. セッションAでブレークポイントを解除して実行を再開し、セッションBの `CALL` がその直後に完了することを確認します。**ただし、セッションAをブレークポイントで止めている時間がファイルの待ち時間の上限(`WAITRCD`)を超えていた場合、セッションBはこの時点で既に「レコード・ロック・エラー」(状況コード`1218`、演習4のヒント参照)で終わっている可能性があります(具体的な待ち時間の上限は、このリポジトリーでは未確認です)。その場合はセッションAを再開する前にセッションBを確認してください。**

**2セッション目が開けない場合の代替:** セッションAは`STRDBG`の入力待ちでコマンド行が使えないため、ロックを保持したまま同じジョブで別のコマンドを動かすには、システム要求(Sys Reqキー)で同じジョブに割り込むか、それが使えなければ`WRKOBJLCK`/`DSPRCDLCK`専用にもう1つ別のジョブ(別セッション、または別のサインオンによる対話ジョブ)を用意する必要があります(06-11bの演習5と同じやり方です)。そのうえで手順3の`WRKOBJLCK`/`DSPRCDLCK`だけを単独で試せば、セッションBによる競合の再現はできなくても、ロックが実在すること自体は確認できます。

**この2セッションでの再現方法そのものは、この教材のどの実機接続でも確認していません。** 検証ハーネス(SSH経由の非対話接続)は1回の接続・1つのジョブで完結する仕組みのため、2つの独立したジョブが同時に同じレコードを競合させる状況を作れません。これは06-11b(保守画面での排他制御)でも同じ考え方の演習として扱われます。**もし試す場合は、演習の最後に必ず `<自分のユーザー名>1/TXRESET` を実行し、`ZAIKOM` を初期状態に戻してください**(04-09・06-08と同じ理由です)。

## 演習

1. `zero` の初期値(`dcl-s zero packed(3:0) inz(0);`)を `inz(2);` に変えて再コンパイル・実行してください。今度は `monitor` ブロックの残りまで実行が進み、`DSPJOBLOG` に `F0609A: 10 / 2 = 5 (no error).` という行が出て、`on-error` 側はまったく実行されない**はずです**。実際にコンパイル・実行して確認してください。確認後は `inz(0);` に戻しておいてください。
2. `on-error 102;` を `on-error *all;` に変えて再コンパイル・実行してください。一次資料によれば `*all` は「他のどの `on-error`/`on-exception` ブロックにも捕まえられなかった例外」を最後に受け取る、汎用の受け皿です。このプログラムには `on-error` ブロックが1つしか無いため、ゼロ除算(ステータス102)は引き続き同じ `on-error` ブロックで捕まる**はずです**。実際に確認し、`102` という具体的な番号を書かなくても捕まえられることを確かめてください。確認後は `102` に戻しておいてください。

4. (発展・任意、ロックの本質)上の「同じ手順を別の対象で」を実際に試せた場合、あるいは試さなくても考えるだけでもかまいません——**なぜ `monitor`/`on-error` はレコード・ロックの競合そのものを「解決」できないのかを説明してください。** ヒント: ロック競合の一部(たとえば待ち時間の超過)は、状況コード`1218`という正真正銘の例外であり、`monitor`/`on-error 1218` でも(06-11bの `chain(e)` + `%error`/`%status(1218)` と機能的に同じ形で)捕まえられます。`monitor` が解決できないのは、その例外を捕まえる前提となる**「待たされている時間」そのもの**であり、待ち時間を無くしたり縮めたりする機能ではない、という点です。
5. **(発展・前提未確認のため保留中の任意課題)** 05-13(保守チケット3、`ZA0500` がバッチ中に応答なしで固まる)を、`*PSSR` ではなく `monitor`/`on-error` で解決できるか、同じ考え方で挑戦してみることもできます。**ただし、このコラムは今は試さないでください。** 理由は2つあります。第一に、`ZA0500` はRPG III(固定形式)のプログラムであり、`monitor`/`on-error` はRPG IVの構文なので、挑戦する前にまず06-01の `CVTRPGSRC` で `**FREE` へ変換する必要があります。第二に、もっと根本的な理由として——05-13自身の実機メモが明記しているとおり、チケット3の `*PSSR`/`QCMDEXC`/`CHGDTAARA` という機構自体は、計算仕様書段階のエラー(チケット1の `MINQTY` 不一致に由来する `RPG0907`)からは実際に発火することを実機で確認済みですが、**このチケットが本来報告している症状(`JUCHUD` の入力仕様書段階、`SUB JUSU AVAIL` より前で起きる10進数データ・エラー)を `*PSSR` が実際に捕まえられるかどうかは、05-13の実機メモでは未確認のまま記録されています**(次回接続での確認事項として05-13自身に記録されています)。この土台がまだ固まっていない状態で `monitor` への書き換えに挑戦しても、何と何を比べているのか分からなくなってしまいます。この入力段階の確認が済んでから挑戦してください。
