# 06-10 画面: INDDS と名前付き標識

> 所要時間: 60分 / 前提レッスン: 06-09 / 目標番号: 5 / 観測方法: 画面そのもの / 道具: 5250(コンパイル・実行、画面確認)、SSH(`CPYFRMSTMF` でのソース取り込み)/ 同時接続数: 5250×1(SSHでのソース取り込みは都度接続し直します。02-04・05-01・06-04と同じやり方です)/ 作る・変えるオブジェクト: `<USER>1/D0610A`(DSPF)・`<USER>1/F0610A`(RPG)/ DBVER: 1 / 依存するプローブ: なし / PTF 依存: なし / 容量の目安: わずか

## ゴール

- 表示装置ファイルの標識を、番号(`*IN03`のような書き方)ではなく、名前付きのデータ構造(`INDDS`)経由で扱える。
- DDS側の`INDARA`キーワードとRPG側の`INDDS`キーワードの役割分担(DDSは標識の番号を変えない、名前を付けるのはRPG側だけ)を説明できる。
- 06-04で作った番号標識版(`F0604A`)と、この課で作る名前付き標識版(`F0610A`)を読み比べ、同じ業務ロジックが標識の扱い方だけ違う形で書けることを確認できる。

## なぜ学ぶか

06-04の`F0604A`は、`*in03`という番号だけの標識で「`F3`が押されたか」を判定していました。画面が1つ、ファンクション・キーが1つならまだ読めますが、実際の保守画面(06-11bで扱う追加・変更・削除など)ではファンクション・キーも標識も増えていき、「`*IN12`って何のためだったか」をソースを遡って確認する手間が生まれます。RPG IVには、DDSのファイル全体の標識を**名前付きのデータ構造**として受け取る`INDDS`という仕組みがあり、`*IN03`の代わりに`f3Exit`のような意味の分かる名前で標識を扱えます。この課では、06-04の`D0604A`/`F0604A`を直接書き換えるのではなく、**同じ画面・同じロジックを持つ別バリエーション**(`D0610A`/`F0610A`)を新規に作り、両方を読み比べることで、`INDDS`が何を変え、何を変えないかを確認します。

## 新出

- RPG の `INDDS` キーワード(表示装置ファイルの標識を、番号ではなく名前付きデータ構造のフィールドとして扱う)
- DDS の `INDARA` キーワード(ファイル・レベルの宣言。専用の`INDARA`付きDSPFバリエーションを書く)

## 説明

### DDS側: `INDARA`キーワードを1行足すだけ

06-04の`D0604A`と、この課の`D0610A`を並べてみます。

`D0604A`(06-04、変更なし):

```text
     A                                      DSPSIZ(24 80 *DS3)
     A          R JUCFMT
     A                                      CF03(03)
```

`D0610A`(この課、新規):

```text
     A                                      DSPSIZ(24 80 *DS3)
     A                                      INDARA
     A          R JUCFMT
     A                                      CF03(03)
```

違いは`INDARA`という1行だけです。**`CF03(03)`は`D0610A`でも数字の`03`のままです。** DDSには「名前付き標識」という概念自体が無く、標識は常に番号で宣言します。`INDARA`は「この表示装置ファイルの標識を、RPG側で名前付きデータ構造として受け取れるようにする」というファイル・レベルの宣言で、`R`(レコード様式)の行より前に単独行で書きます。画面のレイアウト(`TOKCD`・`TOKNM`・`ORDNO1`〜`ORDDT4`など)は06-04からまったく変えていません。

### RPG側: `INDDS`キーワードと名前付き標識

`F0604A`(06-04、変更なし。抜粋):

```rpgle
dcl-f d0604a workstn;
dcl-f tokuim keyed;
dcl-f juchum;

dcl-s ordCount packed(3:0);

dow not *in03;
  exfmt jucfmt;

  if not *in03;
    ...
```

`F0610A`(この課、新規。抜粋):

```rpgle
dcl-f d0610a workstn indds(dspInds);
dcl-f tokuim keyed;
dcl-f juchum;

dcl-ds dspInds len(99);
  f3Exit ind pos(3);
end-ds;

dcl-s ordCount packed(3:0);

dow not f3Exit;
  exfmt jucfmt;

  if not f3Exit;
    ...
```

`dcl-f`に`indds(dspInds)`を付けると、`d0610a`ファイルの標識は`dspInds`という名前のデータ構造経由でやり取りされるようになります。`dspInds`は`len(99)`(標識データ構造の長さは常に99桁、という決まりです)の`dcl-ds`で、`f3Exit ind pos(3);`という1個のフィールドだけを持ちます。`pos(3)`は「DDS側の標識3番の値をここに割り当てる」という意味です。`*in03`と書いていた箇所はすべて`f3Exit`に置き換わり、それ以外(`TOKUIM`の`CHAIN`、`JUCHUM`の`CLOSE`+`OPEN`によるリワインド、`READ`のスキャン・ループ、4行の上限、`NOTFOUND`の扱い)は06-04とまったく同じロジックです。

### 一次資料の警告: `INDDS`を指定すると`*IN`配列は使えなくなる

ここが、この課で一番間違えやすい点です。一次資料(ILE RPG言語リファレンスの`INDDS`キーワードの説明)は、「`INDDS`キーワードを指定しない場合、`*IN`配列がそのファイルの標識のやり取りに使われる」と説明しています。これを逆に読むと、**`INDDS`を一度指定すると、そのファイルの標識は名前付きデータ構造経由に切り替わり、`*IN`配列側の同じ番号の要素はもう更新されなくなる**、ということになります。もし`F0610A`の中に`*in03`という書き方が(`f3Exit`に置き換え忘れて)1か所でも残っていたら、一次資料の説明どおりなら`*IN03`は`'0'`のまま変化しなくなり、`F3`を押してもループを抜けられなくなるはずです。**これはコンパイル・エラーにはならないはずです**——`*IN03`は文法上正しいフィールド参照なので、`CRTBNDRPG`はそのまま通ると考えられます(この組み合わせを実際にコンパイルして確かめた実機記録はまだありません)。実行してみて初めて、`F3`が効かないという形で気づく類の間違いだと考えられます。

## 実演

1. SSHで接続し、`~/ibmi-kyozai`を最新にします(`git pull`)。`D0610A`・`F0610A`はこのレッスンで新規に追加したソースなので、これより前のツリーのままだと、次の`CPYFRMSTMF`がソース・ファイルを見つけられず失敗します。

2. 06-04と同じ要領で、`D0610A`(DSPF)・`F0610A`(RPG)のソースを取り込みます(1回の接続でまとめて行います)。

   ```sh
   system "CPYFRMSTMF FROMSTMF('/home/<自分のユーザー名>/ibmi-kyozai/src/qddssrc/d0610s.dspf') TOMBR('/QSYS.LIB/<自分のユーザー名>1.LIB/QDDSSRC.FILE/D0610A.MBR') MBROPT(*REPLACE) STMFCCSID(1208)"
   system "CPYFRMSTMF FROMSTMF('/home/<自分のユーザー名>/ibmi-kyozai/src/qrpglesrc/f0610s.rpgle') TOMBR('/QSYS.LIB/<自分のユーザー名>1.LIB/QRPGLESRC.FILE/F0610A.MBR') MBROPT(*REPLACE) STMFCCSID(1208)"
   ```

3. 5250に戻り、`D0610A`を先にコンパイルします(`F0610A`が`dcl-f`で参照する外部記述ファイルなので、先に存在している必要があります)。続けて`F0610A`をコンパイルします。

   ```text
   CRTDSPF FILE(<自分のユーザー名>1/D0610A) SRCFILE(<自分のユーザー名>1/QDDSSRC) SRCMBR(D0610A)
   CRTBNDRPG PGM(<自分のユーザー名>1/F0610A) SRCFILE(<自分のユーザー名>1/QRPGLESRC) SRCMBR(F0610A)
   ```

   どちらも Highest Severity 00 になることを確認してください。

4. `CALL PGM(<自分のユーザー名>1/F0604A)`(06-04、番号標識版)と`CALL PGM(<自分のユーザー名>1/F0610A)`(この課、名前付き標識版)を、それぞれ実行して比べます(どちらもパラメーターは取りません)。画面の`Customer code:`欄に`C00001`と入力して`Enter`を押すと、両方とも同じ画面(`ACME TRADING CO`、`J00001`/`20260901`、`J00003`/`20260905`)が表示されるはずです。存在しない得意先コード`C99999`でも試し、両方とも`NOTFOUND`になることを確認してください。最後に`F3`を押し、両方とも同じように終了することを確認してください。

## 演習

`D0610A`/`F0610A`に、**`F12`キーで画面を初期状態に消去する**機能を追加してください(`F3`のような終了ではなく、得意先コード欄・名前欄・注文一覧をいったん空にして、次の検索に備える操作です)。

ヒント:

1. `D0610A`のレコード様式レベルに、`CF03(03)`の行と同じ書き方で`CF12(12)`を追加し、`CRTDSPF`で再コンパイルします。
2. `F0610A`の`dspInds`に、位置12を表す標識フィールド(例: `f12Clear ind pos(12);`)を追加します。
3. `exfmt`の後、`f12Clear`がONのときは`TOKUIM`/`JUCHUM`の検索処理を行わず、画面に表示している各フィールド(`TOKCD`・`TOKNM`・`ORDNO1`〜`ORDDT4`)を初期状態に戻してからループの先頭(次の`exfmt`)へ戻る、という分岐を追加します(`TOKCD`は`tokcd = *blanks;`のように他のフィールドと同じ書き方で代入してみてください。実際に画面表示が変わるかどうかは次段落の注記を参照)。既存の`f3Exit`判定と共存させる形(`F3`が優先)にしてください。

このコードは、この教材ではまだ実機コンパイルしていません(このレッスンの模範解答ファイルもまだ用意していません)。自分で実際にコンパイル・実行し、`F12`を押したときに画面が本当に初期状態へ戻るかどうかを確認してください。**`TOKCD`はDDS側で`I`(入力専用)指定なので、RPG側から代入しても実際に画面表示が変わるとは限りません**——`tokcd = *blanks;`は他のフィールドと同様に書いた上で、それでも画面上の`Customer code:`欄が実際に消えるかどうかを自分の目で確かめること自体がこの演習の狙いです(消えなかった場合も、それは「試して分かった」という正しい結果です)。

## 実機メモ

- 確認日: 2026-09-26。`part06-screens-compile`の1回目の接続で、`D0610A`(`CRTDSPF`)・`F0610A`(`CRTBNDRPG`)がともにHighest Severity 00でコンパイルできることを、接続結果の`run`セクションの生テキストを直接読んで確認した(V1)。同じ接続・同じバッチの中で`D0604A`/`F0604A`(06-04、比較対象)も同様に成功していることを確認済みで、このレッスンの実演で使う4オブジェクトはいずれもV1(コンパイル確認)まで到達している。同じバッチの残り2画面(`D0611A`/`F0611A`・`D0611BA`/`F0611BA`、06-11・06-11bの対象)は1回目の接続では別の実バグで失敗し、2回目の接続で修正・成功しているが、これは本レッスンの対象オブジェクトとは無関係。
- `INDDS`を指定すると、そのファイルの標識参照が`*IN`配列ではなく名前付きデータ構造経由に切り替わり、同じ番号への`*IN`配列参照はそれ以降ONにならなくなる、という説明は一次資料(ILE RPG言語リファレンスの`INDDS`キーワードの節)の記述に基づくものであり、この教材の検証ハーネスが実際に「`*IN03`を残したまま`INDDS`を指定したら`F3`が効かなくなる」ことを実機で再現して確かめたものではない。**未検証(2026-09-28時点)。**「`*in03`を残したままの`F0610A`は`CRTBNDRPG`が正常に通る(コンパイル・エラーにはならない)」という、説明中のコンパイルできる・できないの見立て自体も、実際にその組み合わせをコンパイルして確かめた実機記録はまだない。**未検証(2026-09-28時点)。**
- `EXFMT`を含む対話的な実行そのもの(`F3`での終了、`F0604A`/`F0610A`の切り替え比較、演習の`F12`消去)は、04-11以来の既知の制約どおり、このハーネスの非対話SSH経由では確認できない(`WORKSTN`プログラムを`CALL`すると、実デバイスが無いため応答なしになる)。実演・演習は、学習者自身の実際の5250セッションで確認してください。これは**V3**(対話操作でしか確認できない範囲)であり、**未検証(2026-09-28時点)**のままです。
