# 保守チケット 1: 在庫引当の結果が信用できない(まれにハングする)

## 起票者

営業部(受注担当)

## 症状

`JU0900C` を(`SBMJOB` ではなく)SSH 経由の非対話ジョブから直接 `CALL` で流すと、一部の実行で引当結果が明らかにおかしい(在庫が十分あるはずの注文が `SHORT` 判定になる、またはその逆)。

まれに、それ以上何も起きず応答なしのまま固まることもあり、ジョブ・ログを確認しないと原因が分からない。

ところが、`ZA0500` の `*ENTRY PLIST` と型を一致させた専用のテスト CL(テスト・ハーネス)経由で、同じ安全在庫しきい値を `CALL` で渡して試すと、毎回正常に動く。

## 調査・修正の進め方

1. **影響調査**(05-07 の手法): `DSPPGMREF`・`DSPDBR` を使い、`JU0900C` から `ZA0500` への呼び出し関係と、両者が使うオブジェクト(`JUCHUD`・`JUCHUM`・`ZAIKOM`)を確認する。
2. **原因の特定**: `JU0900C` の `CALL PGM(.../ZA0500) PARM(...)` と、`ZA0500` の `*ENTRY PLIST` を実際に見比べる。渡している値の**個数**だけでなく、**それぞれの長さ・小数点位置**が一致しているかを確認する。03-08 で学んだ、`CALL` が引数の型を厳密には検査しない場合がある、という点を思い出すこと。
3. **修正**: 型を一致させる。どちらの宣言を直すべきかを判断し、両方が同じ長さ・小数点位置になるようにする。
4. **回帰確認**: 修正後、テスト・ハーネス経由と `JU0900C` 経由の両方で同じ結果になることを確認する。TXCHECK(利用可能であれば)または手動での再検証を行う。
5. **移送と切り戻し**(05-12 の手順): 修正した版を本番役ライブラリーへ移送する手順と、問題が起きた場合に元の版へ切り戻す手順を、実際に一度たどっておく。

## ヒント

- `*LIBL` の罠(04-06 で確認したもの)は、このチケットの直接の原因ではない。`JU0900C`→`ZA0500` の呼び出しがライブラリー修飾されているかどうかも合わせて確認しておくとよい(別の不具合の芽になりうる)。
- 「個数は合っているのに型が違う」場合、コンパイルは通ってしまう。実行してみて初めて気づく類の不具合である。
