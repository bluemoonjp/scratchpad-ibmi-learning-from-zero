# 保守チケット 2: 在庫引当を受注日順に処理してほしい

## 起票者

営業部(受注担当)

## 症状

在庫が不足している商品について、実際には後から入力された(受注日 `JUDATE` が新しい)注文の方が先に引き当てられてしまい、電話で先に注文したはずの得意先が `SHORT` 判定になる、という業務からの問い合わせが来ている。

## 調査・修正の進め方

1. **影響調査**(05-07 の手法): `JU0900C` が `JUCHUD` をどう絞り込み・並び替えているか(`OPNQRYF` の `QRYSLT`・`KEYFLD`)を確認する。`DSPPGMREF`・`DSPDBR` で `ZA0500` が `JUCHUD`・`JUCHUM` をどう読んでいるか(1次・2次ファイル、マッチング・フィールド)も合わせて確認する。
2. **原因の特定**: 現在の読み取り順序が何を基準にしているか(受注番号順か、受注日順か)を突き止める。
3. **修正の検討**: `OPNQRYF` の並び替え基準を変更するだけで十分か、あるいは `ZA0500` 側のマッチング・レコード処理(1次・2次ファイルが同じ並び順であることを前提にしている)にも影響が及ぶかを検討する。**この検討には実機での確認が必要になる可能性が高い**(1次ファイルだけ並び順を変えると、2次ファイルとの整合が取れなくなることがある)。
4. **修正・回帰確認**: 検討した対策を実装し、受注日順に引当が行われることを、複数の受注データで確認する。
5. **移送と切り戻し**(05-12 の手順)。

## ヒント

- 「並び替えの基準を1箇所変えれば直る」とは限らない。マッチング・レコード処理(M1/MR)は、関係する複数のファイルの読み取り順序が揃っていることを前提にしている。
- 対策の実現可能性そのものが、このチケットの調査対象の一部である。
